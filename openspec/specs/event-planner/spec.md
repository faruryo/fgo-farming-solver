## Requirements

### Requirement: イベントデータの取り込み
システムは、ロト型イベントのロトボックス・交換所・イベント通貨の情報を Atlas Academy の `nice_event` から取得・コンパクト化して KV (`event_data_json`) に保存しなければならない (SHALL)。取得・整形は GitHub Actions 定期ワークフローで行い、Cloudflare Workers では KV を読むだけとする。保存は**全置換ではなく蓄積マージ**とし、過去に取り込んだロト型イベントは取り込み窓の外になっても KV から削除してはならない (SHALL NOT)。

#### Scenario: ロトボックスと箱コストの取得
- **WHEN** 取り込みワークフローが対象イベントを処理するとき
- **THEN** 各ロトの「1箱あたりの確定内容（アイテムと個数）」「1箱あたりのコスト（イベント通貨と個数）」「箱の最大数（`maxNum`）」「レアボックス判定（`isRare`）」が KV に保存される。

#### Scenario: 交換所の取得
- **WHEN** 取り込みワークフローが対象イベントを処理するとき
- **THEN** 交換所アイテムの「獲得物」「コスト（通貨・個数）」「在庫上限（`limitNum`）」が KV に保存される。

#### Scenario: 過去イベントの蓄積保持（マージ）
- **WHEN** 取り込みワークフローが実行され、既存 KV に過去のロト型イベントが存在するとき
- **THEN** 既存イベントは `id` をキーに温存され、今回フェッチしたイベントは同一 `id` を新データで上書き（upsert）、今回フェッチに含まれない過去イベントは削除されずに残る。

#### Scenario: 過去イベントのバックフィル
- **WHEN** 取り込み対象期間の下限を過去に遡って指定して取り込みを実行したとき
- **THEN** 指定期間内の過去ロト型イベントが `nice_event` から取得され、蓄積マージで KV に追加される。

#### Scenario: スキーマ不整合のスキップ
- **WHEN** あるイベントの `nice_event` がバリデーションに失敗したとき
- **THEN** そのイベントはスキップされ、他のイベントの取り込みと既存 KV データは影響を受けない。

#### Scenario: 上流障害時の既存データ保護
- **WHEN** 取り込み元のイベントカタログ (`basic_event.json`) が空、または既存 KV の取得に失敗したとき
- **THEN** KV への書き込みは行われず、既存の `event_data_json` がそのまま温存される（空データで上書きしない）。

#### Scenario: 変化が無いときの非書き込み
- **WHEN** マージ結果が既存 KV と同一（新規追加・更新が無い）のとき
- **THEN** KV への書き込みはスキップされ、既存データが温存される。

#### Scenario: 既存恒常データの不可侵
- **WHEN** イベントデータを取り込むとき
- **THEN** 恒常ドロップデータ (`all_drops_json`) と `getWars` の `eventId == 0` フィルタは変更されない。

### Requirement: 既存ロスターの不足素材からの箱数目標設定
システムは、ボックスイベントについて、**既存の永続ロスター**（`ChaldeaState` ＋所持数）から算出される不足素材に対し、必要箱数とその育成インパクト（確定報酬・交換所が不足素材をどれだけ充当するか）を提示しなければならない (SHALL)。本機能は永続ロスターを**読み取り専用**で利用し、ロスター・所持データを書き換えてはならない (SHALL NOT)。

#### Scenario: 既存ロスターの不足素材からの箱数提示
- **WHEN** ログイン済み／ロスター設定済みのユーザーがボックスイベントの計画ページを開いたとき
- **THEN** 既存 `ChaldeaState` ＋所持数から `get-materials`/`diff-materials` で不足素材を求め、ボックス確定報酬・交換所がそれをどれだけ充当するか（育成インパクト）と、満たすために必要な最小箱数・通貨・周回数・消費APが提示される。

#### Scenario: ロスターへの非書き込み
- **WHEN** イベント計画を算出・操作するとき
- **THEN** `ChaldeaState`・所持数・クラウド同期データは一切書き換えられない（read-only）。

#### Scenario: ロスター未設定時のフォールバック
- **WHEN** 未ログインまたはロスター未設定で計画ページを開いたとき
- **THEN** 育成インパクト表示は省略され、欲しい素材の直接指定（または目標箱数）による算出にフォールバックする。

### Requirement: ロト計画の算出
システムは、選択されたロト型イベントについて、ユーザー入力（目標箱数 または 欲しいアイテム数、所持イベント通貨、周回ノードと1周あたりのドロップ）から、必要イベント通貨・必要周回数・消費AP・確定報酬を算出しなければならない (SHALL)。

#### Scenario: 目標箱数からの必要通貨算出
- **WHEN** ユーザーが目標箱数 N を入力したとき
- **THEN** 必要イベント通貨 = `N × 1箱あたりコスト − 所持通貨`、確定獲得素材 = `N × 1箱内容` が算出される。

#### Scenario: 欲しいアイテム数からの必要箱数逆算
- **WHEN** ユーザーがロト/交換所で欲しいアイテムの目標個数を入力したとき
- **THEN** その個数を満たす最小の箱数（および交換所配分）と、それに必要なイベント通貨が算出される。
- **WHEN** 交換所アイテムが在庫上限 (`limitNum`) を超える要求のとき
- **THEN** 上限までで打ち切り、不足する旨を警告表示する。

#### Scenario: 周回層は既存ソルバで解く
- **WHEN** 必要イベント通貨（および直接欲しいイベント素材）が確定したとき
- **THEN** イベント通貨/素材を需要、周回ノードを変数とした `Drops` 互換データを合成して既存 `solve()` に渡し、最小AP/最小周回の周回計画を得る。
- **THEN** `solve()` 本体および恒常ソルバ (`/farming`) の挙動は変更されない。

#### Scenario: ドロップデータのフォールバックと明示
- **WHEN** 対象イベント周回ノードの Atlas ドロップデータが存在しないとき
- **THEN** ユーザーが「1周あたりの通貨/素材ドロップ」を手入力でき、その入力に基づいて周回数が算出される。
- **THEN** 算出結果には、使用したドロップ値のソース（Atlas / 手入力）と概算である旨が表示される。

#### Scenario: 確定報酬と周回ドロップの内訳分離
- **WHEN** 計画結果を表示するとき
- **THEN** 「ボックス確定報酬」と「周回ドロップ見込み」は内訳として分離表示され、需要充足判定は両者の合算で行われる。

#### Scenario: レアボックス報酬の扱い
- **WHEN** ボックスにレアボックス（`isRare`）の報酬が含まれるとき
- **THEN** レア報酬が**素材**の場合は確定報酬として充当計算に含める。
- **THEN** レア報酬が**サーヴァント／礼装／コマンドコード**の場合は「N箱で確定入手」として素材充当とは分離して表示する。

#### Scenario: 交換所の在庫上限での打ち切り
- **WHEN** 不足素材を交換所で充当する際に必要数が `limitNum` を超えるとき
- **THEN** 充当は `limitNum` までで打ち切り、超過分は警告のうえ残需要として周回計画（ソルバ）に回される。

### Requirement: ロト計画 UI
システムは、イベントの一覧（`/events`）と、イベントごとのイベントページ（`/events/[id]`）を提供しなければならない (SHALL)。一覧に載るイベントは「KV `event_data_json` に取り込まれたロト型イベント」と「イベント機能レジストリに登録されたイベント」の和集合とする。イベントページは、そのイベントで使える機能をセクションとして並べるハブとする。既存の恒常導線 (`/material` → `/farming`) は変更しない。一覧・イベントページは、URL 直打ち以外にアプリ内の常設導線（グローバルナビ等）から到達可能でなければならず (SHALL)、どのページもオーファン（到達不能）であってはならない (SHALL NOT)。画面上の名称は「イベント」「イベント一覧」とし、ロト型に限定した名称（「ボックスイベント」「ロトイベント一覧」）を一覧・ナビの見出しに用いてはならない (SHALL NOT)。

#### Scenario: イベント一覧
- **WHEN** ユーザーが `/events` を開いたとき
- **THEN** KV のロト型イベントとレジストリ登録イベントが、同一 ID の重複なく会期情報とともに「開催中・開催予定・終了済み」に分けて一覧表示される。
- **THEN** 各イベントには、そのイベントページで使える機能（例: 「ボックス計画」「料理作成」）がバッジで示される。

#### Scenario: KV に無いレジストリ登録イベント
- **WHEN** あるイベントが KV `event_data_json` に存在せず、イベント機能レジストリにのみ登録されているとき
- **THEN** 一覧にはレジストリの表示用メタ（名前・会期）で掲載され、イベントページも開ける。

#### Scenario: 一覧ページへの常設導線（オーファン禁止）
- **WHEN** ユーザーがアプリのどの画面からでもイベント機能を探すとき
- **THEN** グローバルナビゲーション（`components/common/nav.tsx`）に「イベント」の名称で `/events` 一覧への常設エントリが存在し、URL 直打ちなしで一覧ページへ到達できる。
- **AND** ダッシュボードからの個別イベント直行導線（`/events/[id]`）は一覧導線を代替せず、両者が併存する。

#### Scenario: ダッシュボードからのイベントページ導線
- **WHEN** ダッシュボードの開催中イベントカードのイベントが、ハブで機能提供可能な状態（KV `event_data_json` に取り込み済みのイベント ID 集合に含まれる、または静的レジストリに登録されたイベント）であるとき
- **THEN** そのカードに `/events/[id]` への導線が表示される。
- **WHEN** イベントが KV に未取り込みで、静的レジストリにも登録されていないとき（外部メタデータ上で `hasLottery` であっても）
- **THEN** 導線は表示されない（ハブ遷移後の `EventDataMissing` 露出を防止する）。

#### Scenario: 計画ページへの遷移
- **WHEN** ユーザーが一覧からイベントを選ぶ、またはダッシュボードの該当イベントから遷移したとき
- **THEN** そのイベントのイベントページ (`/events/[id]`) が開き、ヘッダー（名前・会期・開催状態）の下に、使える機能のセクションが表示される。

#### Scenario: 取り込みデータ未存在時の表示
- **WHEN** 対象イベントが KV にもイベント機能レジストリにも存在しないとき
- **THEN** イベントページはエラーにならず、データ未取得である旨のプレースホルダを表示する。

### Requirement: AP回復アイテムと聖晶石による消費AP内訳
システムは、計画の必要AP を、ユーザーの所持AP回復アイテム（りんご各種）と聖晶石に割り当てた内訳として提示しなければならない (SHALL)。AP の回復量はマスターレベル由来の最大AP に基づき、固定換算（旧 `金果実=40AP / 銀林檎=20AP`）を用いてはならない (SHALL NOT)。

#### Scenario: りんご所持数を反映した内訳
- **WHEN** ユーザーがマスターレベルと所持りんご各種の枚数を入力したとき
- **THEN** 必要AP に対して所持りんごを消費した内訳（種類ごとの消費数）と、賄いきれず残るAP を表示する。

#### Scenario: 不足分の聖晶石換算
- **WHEN** 所持りんごで必要AP を賄いきれないとき
- **THEN** 残りのAP を聖晶石（1個＝最大APの全回復）に換算した必要枚数を表示する。

#### Scenario: 所持りんご枚数の端末ローカル永続
- **WHEN** ユーザーが所持りんご枚数を入力したとき
- **THEN** 値は localStorage に永続するが `use-cloud-sync` の同期対象には含めない（端末ローカルのみ）。

### Requirement: 聖晶石必要枚数の課金額換算
システムは、必要な聖晶石枚数を、App Store の最大金額パックの単価で課金額（円）に換算して提示しなければならない (SHALL)。階段価格の最適化（分割購入・福袋・セール）は行わない。

#### Scenario: 最大パック単価での金額化
- **WHEN** 聖晶石の必要枚数が算出されたとき
- **THEN** App Store 最大パックの単価（現行 ¥10,000 / 168個）を一定単価として掛けた目安金額を表示する。

#### Scenario: 換算式のインフォメーション表示
- **WHEN** ユーザーが課金額表示の根拠を確認しようとしたとき
- **THEN** 「不足AP→聖晶石全回復換算→App Store最大パック単価で金額化、実最安は分割/セールで変動」という換算式の説明をインフォメーション（ツールチップ等）で確認できる。

### Requirement: 終了済みイベントのシミュレート
システムは、開催中イベントに加えて、終了済みイベントについても計画ページでのシミュレートを許可しなければならない (SHALL)。

#### Scenario: 終了済みイベントの選択
- **WHEN** ユーザーが一覧から終了済みのイベントを選んだとき
- **THEN** そのイベントの計画ページが開き、開催中と同一の入力・算出が行える。

#### Scenario: 会期外の明示
- **WHEN** 終了済みイベントの計画ページを開いたとき
- **THEN** 会期が終了している旨を明示する。

### Requirement: イベント機能レジストリ
システムは、イベント ID ごとにイベントページで使える機能（`features`）と必須の表示用メタ（`meta`: 名前・会期）を定義する静的レジストリを持たなければならない (SHALL)。レジストリ単独でイベントが成立するケースを担保するため、表示用メタ（`meta`）は必須プロパティとする (SHALL)。レジストリに載せる情報は、ゲーム内で公開済みのイベント情報に限らなければならない (SHALL)。同一イベントが KV にも存在するとき、表示用メタは KV の値を優先しなければならない (SHALL)。

#### Scenario: 料理作成イベントの登録
- **WHEN** イベント 80614（「カルデア南海大決戦！ ～マジムンアイランドに謎の巨人の影を見た～」）のイベントページを開いたとき
- **THEN** レジストリの登録に従って料理作成セクションが表示される。

#### Scenario: KV とレジストリの両方にあるイベント
- **WHEN** あるイベントが KV のロト型イベントであり、かつレジストリにも登録されているとき
- **THEN** 一覧・ヘッダーの名前と会期は KV の値で表示され、セクションはボックス計画とレジストリ登録機能の両方が表示される。

### Requirement: イベントページのセクション構成
システムは、イベントページにおいて、イベントが持つ機能ごとに独立したセクションを表示しなければならない (SHALL)。ボックス計画セクションは KV にロト型データがあるイベントでのみ、料理作成セクションはレジストリで料理作成が登録されたイベントでのみ表示しなければならない (SHALL)。各セクションの計算アルゴリズムは既存のロジック（ボックス計画、料理作成配分ソルバー等）をそのまま用い、同一の入力（素材必要数・所持数・設定値等）に対する算出結果が変わってはならない (SHALL NOT)。ただし、料理作成セクションは永続ロスター由来の need および実所持数（`STORAGE_KEYS.POSSESSION`）を入力とするため、共有 URL 等により `/material/result` とロスター内容が異なる場合は配分結果が異なり得る。ボックス計画セクションはドロップデータ（`/api/drops`）に依存せず独立して動作しなければならない (SHALL)。

#### Scenario: ボックス計画セクション
- **WHEN** KV にロト型データがあるイベントのイベントページを開いたとき
- **THEN** 既存のボックス計画（入力モード・箱数・通貨・周回・AP内訳・育成インパクト・交換所上限警告）がボックス計画セクションとして表示され、所持数キー `STORAGE_KEYS.ITEMS` に基づく既存挙動が維持される。

#### Scenario: 料理作成セクションの need は永続ロスター由来（read-only と旧設定移行維持）
- **WHEN** ロスター設定済みのユーザーが料理作成セクションを表示したとき
- **THEN** 料理作成アドバイザーは、永続ロスター（`ChaldeaState`）から求めた育成必要数と、実所持数（`STORAGE_KEYS.POSSESSION`）を受け取り、周回目的・ストック目標設定に従った実効不足として配分を計算する。
- **THEN** ロスター・所持数・周回目的・ストック目標設定は純粋な読み取り（read-only）として参照され、キー未存在時でも初期値の自動保存等による `ChaldeaState`・所持数・クラウド同期対象データの書き換え・汚染は発生しない (SHALL NOT)。
- **AND** `FARMING_PURPOSE` キーが未保存で旧キー（`QUEST_EFFICIENCY_SHORTAGE_ONLY`, `STOCK_ENABLED`）が残る端末では、自動書き込みを伴わずに旧設定（`all` / `reserve` / `training`）をメモリ上で復元する移行経路が維持される。明示的な切り替え操作時のみ保存が行われる。

#### Scenario: 周回目的が all のときの料理作成セクション
- **WHEN** ユーザーの周回目的が `all`（すべて）のとき
- **THEN** 料理配分計算のための有限目標は `training`（育成）としてフォールバック計算される。
- **AND** UI 上に「配布評価は今の育成を使用」（`common:farming-purpose-advisor-fallback`）の注記が表示される。

#### Scenario: 素材データ取得中・取得失敗・部分欠落時のセーフガード
- **WHEN** ロスター設定済みだが、サーヴァント必要素材（`getMaterialsForServantIds`）が取得中のとき、またはドロップデータが取得中（`drops.isLoading === true`）のとき
- **THEN** 配分計算は開始せず、ローディング状態を表示する。
- **WHEN** サーヴァント必要素材の取得に失敗したとき、一部サーヴァントの素材データが欠落したとき（部分欠落）、またはドロップ取得完了後（`drops.isLoading === false`）に正の need（need > 0）に関与するカタログ・ドロップ率・クエストデータの欠落が検知されたとき
- **THEN** 削減周回/APの過大評価・誤計算を防ぐため配分計算を行わず、データ不整合のエラーメッセージと再試行案内を表示する。

#### Scenario: ロスター未設定時の料理作成セクション
- **WHEN** ロスター未設定のユーザーが料理作成セクションを表示したとき
- **THEN** 配分計算は行わず、育成対象を設定すると料理配分を算出できる旨と、その設定画面への導線を表示する。

#### Scenario: 機能を持たないセクションは出さない
- **WHEN** イベントが KV のロト型データを持たないとき
- **THEN** ボックス計画セクションは表示されない。

### Requirement: ポイント報酬とミッションの取り込み
システムは、イベントデータの取り込みで KV (`event_data_json`) に保存するイベントについて、Atlas Academy の `nice_event` のポイント報酬（`rewards`）とミッション（`missions`）、イベントポイントの品目を、イベントごとの KV キー（`event_rewards:<イベント ID>`）に保存しなければならない (SHALL)。取り込むイベントの条件と、`event_data_json` の中身・取り込みの手順は変えない (SHALL)。イベントごとのキーは、イベントページが表示するイベントのキーだけを読み、イベント一覧・ダッシュボード・通知は読まない (SHALL)。

ポイント報酬は、必要な累計ポイントの昇順に、累計ポイントと報酬を保存しなければならない (SHALL)。ミッションは、表示順に、ミッション ID・種類・表示名・報酬と、達成の条件（`missionProgressType` が `clear` のもの）の要点を保存しなければならない (SHALL)。条件の要点は、条件の種類・対象 ID・必要数と、条件の詳細があればその種類と対象 ID とする (SHALL)。報酬は、既存のイベントデータと同じく品目 ID（`itemId`）・種類（`objType`）・個数で持ち、アイテムには交換所と同じ方法で名前とアイコンを付けなければならない (SHALL)。

システムは、イベントの周回クエストのドロップに含まれる、種類が `eventPoint` の品目の ID を、そのイベントのポイントの品目として保存しなければならない (SHALL)。該当が複数あるときは1周あたりの見込みの合計が最も大きいもの（同じなら ID の小さいもの）とし、無いときは保存しない (SHALL)。

あるイベントのポイント報酬またはミッションが Atlas の応答に無い、または整形に失敗したときは、そのイベントのキーを書いてはならず (SHALL NOT)、KV に前の値があればそれが残るようにしなければならない (SHALL)。Atlas の応答にあって空の配列のときは、空として書く (SHALL)。ポイント報酬とミッションの処理の失敗で、`event_data_json` の取り込みと KV への保存を止めてはならない (SHALL NOT)。`event_data_json` に変化が無い日も、ポイント報酬とミッションは書かなければならない (SHALL)。

#### Scenario: ポイント報酬のあるイベント
- **WHEN** 取り込み対象のイベントの `rewards` に、累計1,000ポイントで赤銅の果実1個などの報酬が180件ある
- **THEN** そのイベントのキーに、累計ポイントの昇順で180件のポイント報酬が、品目 ID・種類・個数と、アイテムなら名前とアイコンつきで保存される

#### Scenario: ミッションのあるイベント
- **WHEN** 取り込み対象のイベント（例: 80632）の `missions` に100件のミッションがある
- **THEN** そのイベントのキーに、表示順で100件のミッションが、種類・表示名・報酬・達成の条件の要点（条件の詳細の対象クエスト ID を含む）つきで保存される

#### Scenario: イベントポイントの品目
- **WHEN** イベントの周回クエストのドロップに、種類が `eventPoint` の品目（例: パンプキン収穫ポイント）がある
- **THEN** その品目の ID がイベントのポイントの品目として保存される

#### Scenario: イベント一覧は読まない
- **WHEN** イベント一覧（`/events`）やダッシュボードを開く
- **THEN** イベントごとのキーは読まれず、`event_data_json` の読み込みの量は変わらない

#### Scenario: 整形に失敗しても前の値を残す
- **WHEN** 前日までの取り込みでミッションが保存されたイベントで、今日の取り込みのミッションの整形が失敗する
- **THEN** そのイベントのキーは書かれず前日の値のまま残り、`event_data_json` はこれまでどおり保存される

#### Scenario: event_data_json に変化が無い日
- **WHEN** その日の取り込みで `event_data_json` に変化が無い
- **THEN** `event_data_json` は書かれず、取り込み対象のイベントのポイント報酬とミッションのキーは書かれる

#### Scenario: 値が無いイベント
- **WHEN** キーが無いイベント（取り込み前の過去のイベントなど）のイベントページを開く
- **THEN** ポイント報酬とミッションは無しとして扱われ、イベントページはこれまでどおり表示される
