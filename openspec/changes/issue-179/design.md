# Design

## Context

### Atlas の交換所に並ぶサーヴァント扱いの交換（確認済み、2026-10-28 に JP の API で取得）

`/nice/JP/event/{id}` の `shop` の各エントリーは `purchaseType` を持つ。今の取り込み（`compactShop`）は `purchaseType` が `item` で `payType` が `eventItem` のものだけを取る。

| イベント | `item` | `servant` | ほか |
|---|---|---|---|
| 80632（復刻版:盈月剣風帖、ロトの無い交換所） | 42 | 12 | なし |
| 80506（ポホヨラのクリスマス・イブ、ボックスガチャ） | 48 | 12 | `commandCode` 3 |

直近に終わった 50 件のイベントでは、`item` 169・`eventSvtJoin` 130・`servant` 34・`costumeRelease` 9・`setItem` 2 だった（対価はすべて `eventItem`）。

`servant` のエントリーの `targetIds` は、アイテムの番号ではなくサーヴァント（svt）の番号である。中身は次のとおり。

- 種火: 叡智の業火・猛火・大火。`type` は `combineMaterial`、在庫上限は 100〜200
- フォウくん: 英霊結晶・星／太陽／流星／日輪のフォウくん。`type` は `statusUp`、在庫上限は 1〜40
- 礼装: `type` は `servantEquip`
- 宝具強化専用のサーヴァント（80506 のアビゲイル〔サンタ〕）: `type` は `svtMaterialTd`

`gifts` は空で、`setNum` は 1 だった。エントリー自体に `name`（交換所の見出し）はあるが、アイコンもレア度も無い。

**礼装は1枚限りではない。** 80632 の「月より団子」は、3種の通貨にそれぞれ在庫上限 2・1・1 の別の行で並ぶ。1行の在庫上限は `limitNum` で表され、アイテムの交換と同じに扱える。

### 名前・レア度・アイコンの取得元（確認済み）

- `export/JP/basic_svt.json`（約 2.4MB、4483 件）は、`id`・`name`・`rarity`・`type`・`face`（アイコンの完全な URL）を、種火・フォウくん・礼装・サーヴァントのすべてについて持つ。`basic_equip.json` は礼装だけで、種火とフォウくんを含まない
- アイコンの URL は番号から一律には作れない。`9770500` の `face` は `f_97705000.png` だが、`2800801`（宝具強化専用）は `f_28008000.png` になる。`face` をそのまま使う
- 取り込みのスクリプト（`scripts/refresh-event-data.ts`）は今 `nice_item.json`・`basic_event.json`・イベント・war・クエストを取得しており、svt の一覧は取っていない。GitHub Actions の定期ワークフロー（`.github/workflows/refresh-event-data.yml`）はスクリプトを呼ぶだけで、ワークフローを変えずに取得を足せる

### 番号の衝突（確認済み）

`nice_item.json` と `basic_svt.json` の両方にある番号は `9305420` の1件だけだった（礼装「完璧なお正月」と、同じ番号のイベントアイテム）。今の画面と計算は、品目の番号（`itemId`）をアイテムの番号として次の場所で突き合わせている。サーヴァント扱いの品目をそのまま `itemId` に入れると、衝突する番号でアイテムの所持数・必要数・必要／不要の選択を拾う。

- `lib/event-shop-summary.ts` の `shopItemStatus`: 育成計画の必要数（`totalNeed`）と、育成計画で扱う素材の集合（`planItemIds`）
- `components/events/EventShopList.tsx` の `useWantedItems`: 必要／不要の保存（`STORAGE_KEYS.EVENTS_SHOP_WANTED_ITEMS`。キーは番号の文字列、値は `true`）
- `app/events/[id]/page.tsx`: ドロップ表からの AP 換算値（`prices.get(String(itemId))`）
- `lib/event-plan.ts`（ボックス計画）: 素材の需要（`demand.get(shopItem.itemId)`）と名前の対応表

交換回数・全部交換・必要量・周回の内訳は、品目の配列の位置と対価の通貨で計算しており、`itemId` に依らない。

### 取り込みの判定への影響

`decideEventImport` は、ロトの無いイベントで交換所の最初の品目の対価をイベントの通貨にする。サーヴァント扱いの品目が Atlas の順で先に並ぶと、既に取り込んだイベントの通貨が変わりうる。また、アイテムの交換が無くサーヴァント扱いの交換だけがある交換所のイベントは、今は「ロトも交換所も無い」として飛ばされ、この変更の後は取り込まれる。

## Goals / Non-Goals

**Goals:**

- `purchaseType` が `servant` で対価がイベントアイテムの交換を取り込み、名前・レア度・アイコンを付けて交換所に並べる
- 交換回数・全部交換・必要量・周回の内訳・AP 予算に入れる
- 計画の対象外として必要／不要を選べるようにし、アイテムの品目と取り違えない

**Non-Goals:**

- コマンドコード・霊衣開放権・`eventSvtJoin`・`setItem` の交換（issue の範囲外）
- 礼装の所持の管理や、種火で上がるレベルの計算など、サーヴァント扱いの品目を育成計画に入れること
- ボックス計画（`EventPlannerClient`）の画面にサーヴァント扱いの品目を出すこと。ボックス計画は素材の需要から交換を選ぶので、サーヴァント扱いの品目は需要に現れず、選ばれない（衝突する番号でも拾わないようにだけする）

## Decisions

### D1. 品目の種類を任意のフィールドで持つ

`EventShopItem` に任意のフィールド `kind?: 'svt'` を足し、サーヴァント扱いの品目にだけ `'svt'` を入れる。無いときはアイテムの品目として読む。`itemId` には svt の番号を入れる。レア度は任意のフィールド `rarity?: number` で持つ。

- 代案: `itemId` を負の数や大きな数にずらす。番号の意味が変わり、画面で番号を出す箇所（名前が無いときの `#itemId`）と Atlas へのリンクがずれるので採らない
- 代案: 別の配列 `svtShop` に分ける。交換回数・全部交換・必要量・効率順の並びがすべて配列の位置で動いており、2つの配列をまたぐ並びと回数の結び付けを作り直すことになるので採らない

古い KV データには `kind` が無く、すべてアイテムの品目として今までどおり動く。KV の形の変更は後方互換の追加だけになる。

### D2. 名前・レア度・アイコンは `basic_svt.json` から1回で引く

取り込みのスクリプトで、交換所に `servant` のエントリーがあるイベントを処理する前に `basic_svt.json` を1回取得し、`id` → `{ name, rarity, face }` の対応表を作って `compactShop` に渡す。イベントごとに `/basic/JP/svt/{id}` を引くより通信が少なく、1回の取得で済む。

取得に失敗したとき、または対応表に番号が無いときは、名前を Atlas のエントリーの `name`（交換所の見出し）にし、アイコンとレア度を付けずに保存する。そのイベントの取り込みは止めない。`basic_svt.json` の取得の失敗で、アイテムの交換とロトの取り込みまで止めないため。

### D3. 取り込む交換の条件

`purchaseType` が `item` または `servant` で、`payType` が `eventItem` のものを取る。`servant` は `targetIds` の各番号を1品目にする（アイテムの交換と同じ）。

### D4. イベントの通貨は、アイテムの品目があればその最初の品目から取る

`decideEventImport` の通貨は、`kind` の無い（アイテムの）品目のうち最初のものの対価から取り、アイテムの品目が無いときだけサーヴァント扱いの品目の最初のものから取る。既に取り込んだイベントの通貨を、この変更で変えないため。サーヴァント扱いの交換だけの交換所のイベントは取り込む（交換所として並べられるので、飛ばす理由が無い）。

### D5. 突き合わせは `kind` を見てから行う

- `shopItemStatus`: `kind` が `'svt'` の品目は、育成計画の必要数と素材の集合を見ずに「計画の対象外」にする。育成計画で扱う素材の一覧を読み込めないときも、計画の対象外と判定できる。育成計画が未設定・読み込み中・失敗のときに状態を出さない規則は、アイテムの品目と同じ
- 必要／不要の保存: キーを、アイテムの品目は今までどおり番号の文字列、サーヴァント扱いの品目は `svt:<番号>` にする。今の保存の形（キー → `true`）とキーの意味を変えないので、保存済みの選択はそのまま使える。保存のキーは今と同じ `events/shopWantedItems` のままとする
- AP 換算値: `kind` が `'svt'` の品目には引かず、効率と順位を出さない（AP 換算値の無い品目として前に並ぶ）
- ボックス計画（`lib/event-plan.ts`）: 素材の需要との突き合わせと名前の対応表で、`kind` が `'svt'` の品目を除く
- 交換所で埋まらない不足の要約: 計画の対象外なので、今の規則のまま数えない

### D6. 表示

品目の名前は `name`、アイコンは `icon`（`face` の URL）で、アイテムの品目と同じ行の形で出す。1回の個数・在庫上限・対価・回数の列も同じとする。レア度は名前の横に出さず、データとして保存するだけにする（今の行の形にレア度の表示が無く、礼装と種火の見分けは名前とアイコンで付くため）。

### D7. 既存のイベントへの反映

取り込みのワークフローは、取り込み窓の中のイベントを取り直して蓄積マージで上書きする。窓の外の過去のイベントは取り直さないので、マージ後に「Refresh event_data KV cache」を `backfill_since` を指定して手動で実行し、過去のイベントの交換所にもサーヴァント扱いの品目を入れる。本番の KV への書き込みになるので、この変更の作業者は行わず、実装 PR の本文の「人がやること」に書く。

## Risks / Trade-offs

- `basic_svt.json` は約 2.4MB で、取り込みのたびに1回取得する。GitHub Actions のジョブで動くので Workers の CPU 上限には当たらない → 許容する
- 礼装の在庫上限は通貨ごとの行で分かれるので、全部交換では礼装を最大の枚数（80632 なら4枚）まで交換する。礼装を1枚だけ欲しい利用者は回数を手で減らす → 交換所の在庫どおりの挙動で、ほかの品目と同じ
- 種火の在庫上限は 100〜200 と大きく、全部交換の必要量と周回数が今より大きくなる → 交換所に実際にある品目なので正しい値になる。種火を交換しない利用者は回数を 0 にするか、不足素材のみの操作で「不要」のままにする
- 取り込みの順で通貨を決める規則（D4）は、サーヴァント扱いの交換だけのイベントでは Atlas の並び順に依る → 今のアイテムの品目と同じ依り方
