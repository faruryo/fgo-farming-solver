# Design

## Context

動機は proposal.md の Why を参照。

- 絆アップ礼装の一覧は `lib/material-catalog.ts` の `distillBondUpCraftEssences` が `nice_equip.json` から蒸留し、`bondUpCraftEssences: { id, collectionNo, name, rarity, cost, face, target, rate, add }[]` としてカタログに載る。`bondUpFunctionEffect` は `svals` の `EventId` と `Individuality` だけを見て除外しており、関数の `functvals`・`overWriteTvalsList` を見ていない。#183 の実測は「`Individuality` が0でない効果はイベント限定のものにしかなかった」としたが、特性の条件は `svals` ではなく関数側にあった
- 提案は `lib/bond/craft-essence-advice.ts` の `adviseBondCraftEssences` が決める。同じ対象・増加率・固定・コストの礼装を1つの種類にまとめ、種類ごとの枚数だけを探索し、全員に同じ増加率を掛ける(`servantCount * (boosted + partyAdd) + selfAdd`)。UI は `components/bond/craft-essence-advisor.tsx`
- カタログのサーヴァント(`MaterialCatalogServant`)は特性を持たない。更新ジョブは `lib/material-catalog-updater.ts` の `servantValidatorFor` / `equipValidatorFor` で、蒸留項目が欠けた既存カタログのときに検証子なしで取り直す

### 実測(2026-11-02、propose の時点で実行)

`https://api.atlasacademy.io/export/JP/nice_equip.json`(約21MB)と `nice_servant.json`(約69MB、Last-Modified 2026-11-01)を取得して読んだ。

- 効く相手の条件は関数の2か所にある
  - `functvals`: 特性の配列。要素のどれか1つを持つ相手に効く(異星の神は `[304 悪, 203 星]` で「〔星の力〕または〔悪〕」)
  - `overWriteTvalsList`: 特性の配列の配列。内側の配列のすべてを持つ相手に効き、外側はどれか1つ。`functvals` より優先する(幸せな花嫁へは `[[300 秩序, 2 女性]]`、カルデアの者は `[[301 混沌, 2858 七騎士], [2801200]]`。2801200 はソロモン(サーヴァント ID 2801200)だけが持つ特性)。`script.overwriteTvals` に同じ値が入るが読まない
- イベント限定を除く59件をこの規則で読むと、読めない条件は0件。効果・コスト・条件の組は次のとおり

  | コスト | 対象 | 増加率 | 固定 | 条件 | 件数 | 例 |
  |---|---|---|---|---|---|---|
  | 5 | パーティ全体 | 0 | 50 | 全員 | 9 | 英霊肖像 |
  | 5 | 自身 | 0 | 50 | 全員 | 1 | 英霊肖像:ダレイオス三世 |
  | 9 | パーティ全体 | 20 | 0 | 全員 | 21 | 英霊極点 |
  | 9 | パーティ全体 | 100 | 0 | 〔Fate/stay nightのサーヴァント〕(2883) | 7 | 英霊逢魔 |
  | 12 | パーティ全体 | 25 | 0 | 全員 | 3 | 狼のはなし |
  | 12 | パーティ全体 | 50 | 0 | 全員 | 5 | カルデア・ティータイム(サポート時150) |
  | 12 | パーティ全体 | 100 | 0 | 全員 | 1 | カルデア・ランチタイム |
  | 12 | パーティ全体 | 200 | 0 | 礼装ごとに異なる | 12 | 手稿の翼〔キャスター 104〕、流転の剣聖〔セイバー 100〕、シークレット・ミッション〔ライダー 103〕、ガン・ディーラー〔アサシン 105〕、記憶の大図書館〔中立 302〕、カルデア・モーニング〔今を生きる人類 2654〕、至誠の一針〔霊衣を持つ者 2780〕、ＮＦＦから愛をこめて〔ケモノ科 2821〕、レポートチェック〔秩序かつ善〕、幸せな花嫁へ〔秩序かつ女性〕、カルデアの者〔混沌かつ七騎士、またはソロモン〕、異星の神〔悪、または星〕 |

- カルデア・ティータイムのサポート時の値は、関数の `followerVals`(`svals` と同じ形)にある。最大解放で `RateCount: 150`(未解放は30)。issue は「データの数値に無い」としていたが、礼装ごとに持つ方針はそのまま使え、手入力の表は要らない。`followerVals` を持つ非イベントの礼装はこれだけ
- `svals` のキーは非イベントの礼装では `Individuality`(すべて0)・`RateCount`・`AddCount` だけ。`ApplySupportSvt` と `Target` はイベント限定の礼装にしか現れない。`funcquestTvals` はすべて空
- サーヴァント(`type` が `normal` / `heroine`、475件)の `traits` は `{ id, name }[]` で、1件あたり平均17個。ID だけを JSON にすると全体で約47KB
- 霊基再臨・霊衣で特性が上書きされる(`ascensionAdd.individuality` が空でない)サーヴァントは102件。そのうち上の条件に使われる特性が基本の `traits` と変わるのは、〔ケモノ科〕15件、〔善〕6件、〔今を生きる人類〕・〔中立〕・〔悪〕各3件、〔混沌〕・〔女性〕各2件、〔秩序〕1件(重複を含む延べ35件)

## Goals / Non-Goals

**Goals:**
- 礼装の条件の判定は、カタログに載せた特性 ID の照合だけで済ませ、ブラウザで Atlas の JSON を読まない
- 提案の探索は今の「種類ごとの枚数」の形を保ち、条件は種類を分ける鍵に入れて表す

**Non-Goals:**
- 霊基・霊衣ごとの特性の選択(基本の特性で判定する)
- サポート時の増加率を使う提案(#186)
- 特性の名前の表示(提案の画面に条件を出す必要はまだない)

## Decisions

### 1. カタログの項目

- サーヴァントに `traits?: number[]` を足す。`nice_servant` の `traits` の ID を、1要素以上・正の整数・重複なしのときだけ入れる。基本の特性だけを使う
- 絆アップ礼装に `appliesTo?: number[][]` を足す。`[]` は全員に効く。`[[104]]` はキャスター、`[[304], [203]]` は悪または星、`[[300, 2]]` は秩序かつ女性。蒸留が書く値は常にあり、項目がないのは項目を足す前のカタログだけ。型は古いカタログを読む consumer のために任意だが、書き込む候補の検証では必須にする(spec の「持たなければならない」)
- 絆アップ礼装に `supportRate?: number` を足す。最大解放の段の関数の `followerVals` の最後の要素の `RateCount` が `svals` の `RateCount` と違うときだけ入れる。対象が `party` のときだけ読む
- どれも任意項目の追加なのでキーとスキーマバージョンは変えない(`cost` と `bondUpCraftEssences` を足したときと同じ)。`materialCatalogFingerprint` はサーヴァントと礼装のオブジェクト全体を含むので、変えなくても新しい項目の差分で書き込まれる

却下: `appliesTo` を「全員」と「条件」の判別共用体にする。`[]` で全員を表せば照合が `groups.length === 0 || groups.some(g => g.every(t => traits.has(t)))` の1行で済む。
却下: 条件に使われる特性だけをサーヴァントに持たせる。約47KB で上限の5MB に対して小さく、礼装が増えたときにサーヴァント側の蒸留をやり直さずに済む。

### 2. 蒸留の規則(#183 の規則への追加と変更)

- 条件は、関数の `overWriteTvalsList` が空でなければその各配列の ID を組に、空なら `functvals` の各 ID を1つずつの組にする。どちらも空なら `[]`(全員)
- 読めない効果として捨てる(この効果しかない礼装は一覧に入れない):
  - `svals` の `Individuality` が0でない(今までどおり)
  - `svals` に `Individuality`・`RateCount`・`AddCount`・`EventId` 以外のキーがある
  - `funcquestTvals` が空でない
  - 組に空のものがある、または正の整数でない ID がある(Atlas は負の ID を「持たない」に使う)
- 同じ礼装に複数の関数が残るとき、対象と条件がすべて同じなら今までどおり値を足す。対象か条件が混ざる礼装は今のデータにないため、一覧に入れずに捨てる(`shortcut` として実装にコメントを残す。今の対象が混ざる場合の扱いと同じ)

### 3. 提案の探索

`adviseBondCraftEssences` に選んだサーヴァントの `traits` を渡す。`appliesTo` のない礼装は呼び出し側(UI)で候補から外し、残りが0件なら「礼装のデータを読み込めない」を出す。

- 各礼装について、選んだサーヴァントのうち条件に合う相手の集合(ビットマスク。`traits` のないサーヴァントは `appliesTo` が `[]` の礼装だけに合う)を求め、空なら捨てる
- 種類の鍵を `target|rate|add|cost|mask` にする。言い換えの候補は同じ種類の残りの礼装なので、spec の「効く相手も同じ」がそのまま満たされる
- 評価はサーヴァントごとに、`mask` が自分を含む `party` の種類の増加率と固定を足して `floor(base * (1000 + rate) / 1000) + add` とする。`self` の種類は、`mask` に含まれるサーヴァントにだけ付けられ、付けた相手に `add` が入る
- 比較は今の「合計 → コスト → 枚数」の後に、組み合わせの礼装の図鑑番号を小さい順に並べた列の辞書順を足す。効く相手で種類を分けると、〔キャスター〕20%+〔セイバー〕20% と全員10%+〔キャスター〕20% のような同点が普通に起き、探索の順で表示が変わるため。各種類の中では図鑑番号の小さい礼装から使うので、列は種類ごとの枚数から決まる
- 自身に効く種類は、`mask` の人数を超えて付けない。複数の自身に効く種類が同じ相手を取り合う場合の割り当ての判定はしない(`shortcut`: 自身に効く礼装は条件なしのダレイオス1件だけ。条件付きの自身に効く礼装が増えたら割り当ての判定を足す、と実装にコメントを残す)
- 枝刈りは今と同じ(枚数は種類の礼装数・残りの枠・残りのコストで抑える)。種類は実データで最大20程度、枠は5なので、組の数は多くても十数万で、ブラウザで問題にならない
- 割り当て(どの礼装をどのサーヴァントに付けるか)は合計に影響しない `party` の礼装について今までどおり表示の安定のための順で付け、`self` の礼装は `mask` に含まれるサーヴァントへ先に付ける

却下: 種類をまとめずに礼装1枚ずつを探索する。59枚から最大5枚の組は500万を超え、同じ効果の入れ替えを重複して数える。
却下: 条件の文字列(`appliesTo` の JSON)を種類の鍵にする。〔キャスター〕と〔中立〕が選んだ相手に対して同じ効き方をするとき、言い換えに並ばず、どちらを入れても同じ合計の組を重複して探索する。

### 4. 取り直し

`servantValidatorFor` は既存カタログのサーヴァントが誰も `traits` を持たないときも `{}` を返す。`equipValidatorFor` は既存の `bondUpCraftEssences` がどれも `appliesTo` を持たないときも `{}` を返す。ローカル開発用の `lib/material-catalog-local.ts` は蒸留関数を共有しているので、同じ項目が入る。

## Risks / Trade-offs

- [霊基・霊衣で特性が変わる35件では、基本の特性と実際の編成がずれる] → 基本の特性で判定すると spec に書いた。霊基を入力させるのは絆トラッカーの入力を増やすので今回はしない。ずれが問題になれば、どの霊基でも条件に合う相手だけに数える方式へ変えられる(データは `ascensionAdd.individuality` にある)
- [デプロイ直後、更新ジョブが走るまでは `appliesTo` のない古いカタログが配信される] → UI は `appliesTo` のない礼装を候補にしないので、誤った提案は出ずに「読み込めない」になる。更新ジョブが取り直すと直る
- [Atlas が条件の表し方を変える] → 読めない形は捨てるので誤った提案は出ない。件数の20%超の減少は既存の検証で拒否され、前のカタログが残る
- [`traits` の追加でカタログが約50KB 増える] → 上限の5MB に対して小さい

## Migration Plan

1. 実装 PR をマージしてデプロイする
2. 次の Material Catalog の更新ジョブが、`traits` と `appliesTo` のない既存カタログを見て `nice_servant.json` と `nice_equip.json` を検証子なしで取り直し、書き込む
3. 戻すときは実装を revert する。追加した項目は古い consumer に無視されるので、KV の値は戻さなくてよい
