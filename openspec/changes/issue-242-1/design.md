# Design

## Context

動機は proposal.md の Why を参照。

今の交換所（`components/events/EventShopList.tsx`）の［必要｜不要］は次のとおり（2026-11-06 にコードを読んで確かめた）。

- 保存値は端末の `events/shopWantedItems` の1つで、イベントをまたいで共通。形は `Record<string, boolean>`。キーはアイテムの品目では Atlas の番号（`String(itemId)`）、サーヴァント扱いの品目では `svt:<番号>`（`shopWantedKey`）
- 値の入り方は品目で違う。既定で交換する品目（伝承結晶 6999・カルデアの夢火 1000、`DEFAULT_WANTED_ITEM_IDS`）は `true` と `false` の両方を保存し、保存が無ければ「必要」。それ以外の品目は「必要」のときだけ `true` を保存し、「不要」にするとキーを消す（保存が無ければ「不要」）
- 切り替えは、育成計画が使えるときに「計画の対象外」の品目と既定で交換する品目の行にだけ出る。交換回数を変えず、「不足素材のみ」（`allocateShortfallOnly`）でだけ使う。「必要」の計画の対象外の品目と既定で交換する品目は在庫上限まで、在庫上限の無いものは 0 にして「回数を入れてください」と示す
- 「全部交換」（`selectAllCurrenciesUpToLimit`）は選択を見ず、在庫上限のある品目をすべて上限にする
- 交換回数はイベントごとに端末の `events/shopInputs/<イベント>` に保存し、クラウド同期しない（`event-shop-saved-inputs`）。通貨ごとの必要量は `computeShopCurrencyNeeds(shop, counts, owned)` で出し、周回の内訳・合計・AP 予算・ボーナス礼装の比較はその必要量から出す。今は選択が回数の計算に効く経路は無い
- アイテム一覧（`/items`、`components/items/index.tsx`）は、ドロップのデータの品目を大分類・分類ごとのカードに並べ、行は短縮 ID のリンク（`/items/<短縮 ID>`）だけ。行のデータは Atlas の番号（`atlasId`）も持つ
- クラウド同期の対象は `CLOUD_SYNC_KEYS`（22キー）。`events/shopWantedItems` は入っていない。キーを足すと、縮小保存の抑止（`findMissingKeys`、欠けたキーが 2 以上で保存を止める）の数える対象にも入る
- 交換所の品目名は今はリンクでもボタンでもない。`components/ui/popover.tsx` があり、ほかの画面（クエストの効率など）で使っている

## Goals / Non-Goals

**Goals:**

- issue の「決まったこと」1〜4 を仕様にする
- 「いらない」の品目の回数を、合計・通貨の必要量・周回数のどこにも入れない
- issue の「仕様で決めること」4点と、仕様を書く中で見つけた1点に、推奨と案を付けて判断点にする

**Non-Goals:**

- 周回ソルバーの目標、育成計算機、クエストの効率など、交換所とアイテム一覧のほかの画面に設定を効かせること（判断点4）
- 交換回数の保存の形とキー、クラウド同期しないことを変えること
- ロトのあるイベントの箱計画と、品目がすべてサーヴァント扱いの交換所の一覧（周回計算の無い一覧）に「欲しい／いらない」を出すこと

## Decisions

### 判断点

各判断点に、違いが出る操作を1行で書く。案ごとの 375px の画面のモックは、PR のオーナー向けの説明に載せる。

#### 1. 今の［必要｜不要］の保存値の引き継ぎ（issue の「仕様で決めること」1）

操作: 前の交換所で伝承結晶を［不要］、呼符を［必要］にしていた人が、更新後に交換所を開く。

推奨: **A. 同じ保存値を新しい意味で読む**。`true` は「欲しい」、`false` は「いらない」、保存の無い品目は「欲しい」とする。

| 案 | 伝承結晶（前に不要） | 呼符（前に必要） | 前に何も選ばなかった計画の対象外の品目 | 前の版に戻したとき |
|---|---|---|---|---|
| **A. 同じ保存値を新しい意味で読む（推奨）** | いらない（畳まれる） | 欲しい | 欲しい | 前の版も同じ値を同じ意味で読める |
| B. 新しい保存先にして何も引き継がない | 欲しい（入力欄が出る） | 欲しい | 欲しい | 前の版は前の選択のまま |
| C. 新しい保存先に、明示した選択だけを1回写す | いらない | 欲しい | 欲しい | 前の版は前の選択のまま（その後の変更は前の版に届かない） |

根拠: 前の値で利用者がはっきり選んだのは、既定で交換する品目の `false`（不要）と、ほかの品目の `true`（必要）だけで、どちらも新しい2値にそのまま対応する。計画の対象外の品目の「不要」は保存が無いだけなので、どの案でも「何も設定していない」と区別できず「欲しい」になる（前も入力欄は出ていたので、見た目は変わらない）。A は保存先を増やさず、判断点3で同期に加えるキーも1つで済む。前の版の読み方（`true` だけを必要とし、既定で交換する品目は `false` を不要とする）とも食い違わないので、戻しても選択は壊れない。B は、伝承結晶と夢火を［不要］にしていた人の選択を捨て、その2品目が入力欄つきで戻ってくる。C は A と同じ結果を、保存先を2つにして得るので、写した後に前の版へ戻すと、新しい版での変更が前の版に届かない。A で取りこぼすのは、前の版での「不要」の初期値（計画の対象外の品目）を「いらない」として引き継げないことで、これはどの案でも取りこぼす。

#### 2. 回数を入れた後で「いらない」にしたときの回数（issue の「仕様で決めること」2）

操作: 交換所で呼符に 3 を入れる → 品目名をタップして「いらない」 → 畳んだ「いらない品目」から「欲しい」に戻す。

推奨: **A. 保存した回数は残し、「いらない」の間は計算に入れない**。「欲しい」に戻すと 3 が入力欄と計算に戻る。「全部交換」と「不足素材のみ」も「いらない」の品目の回数を変えない。

| 案 | 「いらない」にした直後の合計 | 「欲しい」に戻したとき | ほかのイベントの保存した回数 | アイテム一覧で変えたとき |
|---|---|---|---|---|
| **A. 残して計算から除く（推奨）** | 呼符の 3 は入らない | 3 が戻る | 残り、計算から除く | 同じ規則で済む |
| B. 今開いているイベントの回数を 0 にする | 0 なので入らない | 0 | 残る。除く規則が別に要る | 開いているイベントが無いので消せず、除く規則だけが効く |
| C. すべてのイベントの保存した回数を 0 にする | 0 なので入らない | 0 | 0 にする | 端末のすべてのイベントの保存値を書き換える |

根拠: 設定はイベントをまたいで共通なので、1つのイベントで「いらない」にすると、回数を入れていたほかのイベントの行も畳まれる。B で開いているイベントの回数を消しても、ほかのイベントの見えない回数は残るので、「いらない」の回数を計算に入れない規則はどの案でも要る。A はその規則1つで済み、押し間違えて「いらない」にしても戻せば回数が戻る。B は、規則が2つになり、アイテム一覧で変えたときだけ回数が残るので、どこで変えたかで結果が変わる。C は、1回の操作で見ていないイベントの保存値まで書き換え、戻しても回数が戻らない。A で取りこぼすのは、「いらない」の品目の回数が保存値に残り続けることで、画面には出ず、計算にも入らない。

#### 3. 設定をクラウド同期に含めるか（issue の「仕様で決めること」3）

操作: PC のアイテム一覧で聖杯を「いらない」にする → スマホで交換所を開く。

推奨: **A. 設定を同期に含め、交換回数は今までどおり同期しない**。

| 案 | スマホの聖杯 | 同期の変更 | 縮小保存の抑止 |
|---|---|---|---|
| **A. 設定だけ同期する（推奨）** | いらない（畳まれる） | 同期のキーに1つ足す | 足したキーが欠けた端末からの保存で、欠けたキーの数に1つ入る |
| B. 同期しない（端末だけ） | 欲しい（PC と食い違う） | 無い | 変わらない |
| C. 設定と交換回数の両方を同期する | いらない。回数も PC と同じ | 設定のキーと、イベントごとの回数のキー（イベントの数だけ増える）を足し、`event-shop-saved-inputs` の「同期しない」を外す | イベントの数だけ欠けうるキーが増える |

根拠: issue は設定を「どの画面でも同じ設定が効く」アプリ全体の好みとしており、同じ利用者の別の端末で食い違うと、その目的に反する。今の同期の対象にも、ドロップ率の表示や効率の設定など、利用者の好みの設定が入っている。設定は品目の番号を鍵にした小さな1つの値で、イベントの数で増えない。B は、端末ごとに同じ品目を選び直すことになり、アイテム一覧で決めた設定がスマホの交換所に届かない。C は、イベントごとの入力を端末だけにした今の仕様を変える別の判断で、この issue の範囲を超える。A で取りこぼすのは2つある。1つは、回数が端末ごとのままなので、別の端末では「欲しい」の品目の回数を入れ直すことだ（今と同じ）。もう1つは、更新の前に2台の端末でそれぞれ選んでいた値が、同期のときに1台分にまとまることだ。この値は今まで同期していないので、端末に残る前の選択は「未同期の変更」として記録されていない。片方の端末（PC）が更新後に設定を変えて保存すると、もう片方の端末（スマホ）は未同期の変更が無いので自動ロードでクラウドの値を受け取り、同期はキーの値を丸ごと置き換えるので、スマホだけで［不要］にしていた伝承結晶の選択が消えて「欲しい」に戻る。品目ごとに統合する同期は、今の同期のどのキーにも無い仕組みで、守れるのは前の版で明示した選択（多くは伝承結晶と夢火の2品目）だけなので、この change では足さず、消えた選択は利用者が設定し直す。

#### 4. 交換所とアイテム一覧のほかの画面に効かせるか（issue の「仕様で決めること」4）

操作: アイテム一覧で凶骨を「いらない」にする → 周回ソルバー（/farming）の目標を開く。

推奨: **A. この change では交換所とアイテム一覧だけに効かせ、ほかの画面は別の issue にする**。

| 案 | 周回ソルバーの凶骨 | この change で決めること | 完了条件との対応 |
|---|---|---|---|
| **A. 交換所とアイテム一覧だけ（推奨）** | 今のまま | 交換所とアイテム一覧の振る舞いだけ | issue の完了条件と同じ範囲 |
| B. 周回ソルバーの目標でも「いらない」の品目を目標から外す | 目標の一覧に出ない、または外れた印が付く | 育成計画で不足がある素材を「いらない」にしたときに目標をどうするか | 完了条件に無い画面のスクリーンショットと検証が増える |
| C. 育成計算機・クエストの効率まで、素材を扱うすべての画面に効かせる | 外れる | 画面ごとに「いらない」の意味（表示から外すのか、計算から外すのか） | 同上で、さらに広い |

根拠: 交換所の「いらない」は「この品目を交換しない」で意味が1つに決まるが、周回ソルバーや育成計算機では、育成計画で足りない素材を「いらない」にしたときに、目標から外すのか、表示だけ外すのかが決まっておらず、画面ごとに別の判断が要る。issue の完了条件も交換所とアイテム一覧だけを挙げている。A は、設定の値と保存（判断点1・3）をこの change で決めておき、ほかの画面は意味を決めてから同じ設定を読む形で足せる。B と C は、その意味の判断を、この change の中で根拠の無いまま決めることになる。A で取りこぼすのは、issue の冒頭の「どの画面でも同じ設定が効く」のうち、交換所とアイテム一覧のほかの画面の分で、それは別の issue で扱う。

#### 5. 「不足素材のみ」で「欲しい」の計画の対象外の品目に入れる回数（仕様を書く中で見つけた点）

操作: 「欲しい」の呼符（計画の対象外・在庫上限 10）に手で 5 を入れる → ［不足素材のみ］を押す。

推奨: **A. 0 にする**。「不足素材のみ」は、育成計画の不足のある素材の品目にだけ回数を入れ、計画の対象外の品目・足りている素材・使わない素材は 0 にする。

| 案 | 呼符の回数 | 何も設定していない計画の対象外の品目（聖杯・コイン・礼装など） | 押した後の結果が決まるもの |
|---|---|---|---|
| **A. 0 にする（推奨）** | 0 | 0 | 育成計画と所持数と設定だけ |
| B. 在庫上限まで入れる（今の「必要」と同じ） | 10 | すべて在庫上限 | 同上 |
| C. 回数を変えない | 5 のまま | 押す前の回数のまま | 押す前の回数にもよる |

根拠: issue の決まったこと1で、何も設定していない品目は「欲しい」になり、伝承結晶と夢火を在庫上限まで入れる動きもやめる。今の「必要」の計画の対象外の品目を在庫上限にする規則（B）をそのまま使うと、何も設定していない聖杯・コイン・礼装までがすべて在庫上限になり、「不足素材のみ」が「全部交換」とほぼ同じ結果になる。A は、ボタンの名前どおり不足の分だけを入れ、今の「すべての品目の回数を置き換える」性質（押した結果が押す前の回数によらない）を保つ。C は、手で入れた呼符の 5 を残せるが、先に「全部交換」を押してから「不足素材のみ」を押すと、計画の対象外の品目が在庫上限のまま残り、不足の分だけにならない。A で取りこぼすのは、手で入れた計画の対象外の品目の回数が「不足素材のみ」で 0 に戻ることで、利用者は「不足素材のみ」を先に押してから手で入れる。

### 決めたこと

#### 設定の値と初期値（issue の決まったこと1）

「欲しい」と「いらない」の2つだけにし、「自動」は置かない。何も設定していない品目は「欲しい」とする。伝承結晶と夢火を「不足素材のみ」で在庫上限まで入れる扱い（既定で交換する品目）はやめ、伝承結晶はほかの素材と同じく不足の分だけ、夢火はほかの計画の対象外の品目と同じく 0 にする（判断点5）。育成計画で扱う素材の一覧を読めないときに、伝承結晶を「使わない」、夢火を「計画の対象外」と表示する番号による判定は、ラベルのために残す。

#### イベントをまたいで共通（issue の決まったこと2）

設定はイベントごとに分けない。アイテムの品目はアイテムの番号ごと、サーヴァント扱いの品目は獲得物ごとに持ち、今の保存値のキーの分け方（`svt:` の付いたキー）をそのまま使う。

#### 交換所の操作（issue の決まったこと3）

- 行に切り替えを常には出さない。品目名をタップしたときだけポップアップを出す。ポップアップは今の設定を示し、選ぶとすぐに変えて閉じる
- 「いらない」の行は一覧から外し、一覧の最後に「▸ いらない品目 N 件」として畳む。開いたときの名前のタップは、品目名と同じポップアップを出す（操作を1種類にするため）。畳んだ部分は開くたびに閉じた状態から始め、開閉を保存しない
- ポップアップと畳みは、育成計画が未設定・読み込み中・失敗のときも使える。設定は育成計画に依らない品目の好みなので、育成計画の状態で操作を消さない
- 「全部交換」と「不足素材のみ」は「欲しい」の品目にだけ回数を入れ、「いらない」の品目の回数を変えない（判断点2の A と同じ規則）
- 複数の通貨で交換できる品目をまとめた行は、品目が同じなので1つの設定で行ごと畳む
- 品目がすべてサーヴァント扱いの交換所の一覧は周回計算が無いので、ポップアップも畳みも出さない

#### アイテム一覧（issue の決まったこと4）

アイテムの番号の分かるすべての行に、「欲しい／いらない」の切り替えを常に出す。切り替えは品目の詳細へのリンクと別の操作にする。行は短縮 ID で並んでいるが、設定は行の Atlas の番号で引く（交換所の品目の番号と同じ系統）。

#### 効率順の順位と見出し

「いらない」の行は1つの一覧から外すので、効率順の順位と「効率順」「AP 換算なし」の見出しは「欲しい」の行だけで付ける（`event-shop-efficiency` の「効率順の1つの一覧」を MODIFIED にした）。順位を「いらない」の行も含めて付けると、一覧に順位の欠番が出る。「欲しい」に戻した行は、その規則で決まる位置（効率のある行は効率の順、無い行は交換所の順）に並ぶ。

#### 計算から除く範囲

「いらない」の品目の回数は、通貨ごとの選んだ交換の合計・必要量・周回の内訳・合計の周回数と AP・AP 予算・ボーナス礼装の比較に入れない。通貨ごとの「全交換の合計」（在庫上限のある品目をすべて交換するのに要る数）は、利用者の選んだ交換ではなく交換所全体の大きさを示す値なので、「いらない」の品目も含めたままにする。

#### 交換所で埋まらない不足

「いらない」の品目には回数が入らないので、品目がすべて「いらない」の素材は埋まらない素材として要約に数える。「交換所では N 個足りない」は、その素材の「欲しい」の品目のうち最後の行に出し、「欲しい」の品目が無ければ出さない（畳んだ部分は名前だけを出すため）。

#### spec の書き方

`event-shop-single-list` の「交換所の品目を1つの一覧で並べる」と `event-shop-servant-exchange` の「品目がすべてサーヴァント扱いの交換所の一覧」は、切り替えと消える要件の名前を挙げていて、archive の後に新しい要件と食い違うので MODIFIED で直した。`event-shop-saved-inputs` の「保存値を読むまで初期値を見せない」も、対象の「品目の『要る』」を新しい設定に合わせた。`event-shop-roster-need` の「品目ごとの要る・要らない」「不足素材のみ」と、`event-shop-servant-exchange` の「サーヴァント扱いの品目の必要／不要」は、シナリオを外す必要があり、MODIFIED ではシナリオを外せない（`openspec validate` が既存のシナリオの欠けを誤りにする）ので、REMOVED と新しい名前の ADDED に分けた。

## Risks / Trade-offs

- [伝承結晶と夢火を「不足素材のみ」で在庫上限まで入れていた利用者は、更新後に同じボタンで上限まで入らなくなる] → 決まったこと1のとおりオーナーと決めた変更。PR 本文とリリースの説明に書く
