## Context

現行は `EventCraftRecipe.targetItem` に `yieldCount: 1` を載せ、Stage 1 の `craft_*` はその1素材だけを `item_*` / `cap_*` に足す。`cap_*` は不足数以上の主産物作成を禁止している。フリクエ側はもともと期待ドロップの連続 LP である。検証テーブルは proposal 参照。

## Goals / Non-Goals

**Goals:**
- 1皿の期待獲得をレアリティ帯の固定係数で MILP に載せる。
- ついで素材の充足を `cap_主産物` が阻害しない。
- 既存の Stage 1a/1b / Stage 2a/2b の分割は維持する。

**Non-Goals:**
- レシピごとの実測テーブルやユーザー編集可能な確率。
- 外れを見込んだ保守的（分位）最適化。
- QP・種火を育成ソルバーの目的に入れること。
- 交換所での食材変換。

## Decisions

### 1. 期待値テーブルはデータ層で導出する

銅・銀・金それぞれ対象素材は4種。枠は銅: 4+QP、銀: 4+種火、金: 4+種火+QP。

- `FEATURED = 0.4`
- `other = (1 - FEATURED) / (slots - 1)` → 銅銀 0.15、金 0.12
- QP/種火スロットは yield 0

代替: レシピごとに手書き yield。12皿×4素材で重複し、均等ルールの変更が散らばる。帯ごとに対象 ID を束ねて係数を計算する。

### 2. Stage 1 から `cap_*` を外す

`item_*` の下限（不足充足）だけ残す。整数ソルバーが余分な皿を積みうるが、Stage 1b の総食材最小化がゼロ効果の皿を落とす。主産物キャップを残すと、期待高が足りていてもついで銅が足りないケースでアンダギーを止められる。

### 3. Stage 2 の `V_base` は期待バスケット

`sum_i yield_{j,i} * isolatedCost(i)`。ドロップデータのない i は 0。主産物だけの旧 `yieldCount * isolatedCost(featured)` より、銀のついで3種を使い切りが正しく評価する。`computeSingleItemBaseValues` のキャッシュキーは `id` / featured `shortId` / `yieldCount` だけでなく、期待 yield マップ（shortId ソート済み）を含める。テストの `recipes` 差し替えでついで係数だけ変えた連続呼び出しが古い `V_base` を使わないこと。

### 4. UI

カード主表示は従来どおり期待高の料理名。作成数の近くに「期待: 凶骨 0.40 / 他銅 0.15×3」相当の短い内訳（i18n）を足す。確率の全表は出さない。

配分全体の期待収集は純関数で `sum_j totalCount_j * yield_{j,i}`（i は育成素材のみ）。結果の上か料理リストの直前に「この配分での期待獲得」としてアイコン＋名前＋個数（小数1桁可）を出す。不足枠と余剰枠は足し合わせる（おすすめどおり作った合計）。種火・QPは出さない。

### 5. テスト

純関数で (a) 銅料理1皿が他銅3種にも 0.15 を足す (b) 主産物不足0でも他銅不足があれば作成されうる (c) 旧 `yieldCount=1` のフィクスチャを期待値係数に更新する (d) 1レシピ除外の削減帰属が `fullNeed` から他レシピを引いて再計算される (e) 過産時に帰属が元の不足を超えない。

### 6. カード削減 `unitSaved` は期待バスケット除外

`calculateAllocatedDeficitSavings` は主産物だけを戻すとついで削減が落ちる。クランプ済み `postCraftNeed` に当該レシピの期待 yield を足し戻すのも不可。小数 yield と `cap_*` 撤去では整数皿が不足を超える過産が起き、need 1 に対し 0.40×3 皿だとクランプ後 0 に 1.20 を足して帰属が膨らむ。除外時の need は `fullNeed` から当該以外の全レシピの期待獲得を引いた値（下限 0）とする。

## Risks / Trade-offs

- **[期待値と実運の差]** → フリクエと同じ期待値主義。UI で「期待値」と分かる文言にする。
- **[javascript-lp-solver と小数 yield]** → 係数 0.4 / 0.15 / 0.12 は既存ドロップ率と同型。必要なら整数スケール（100倍）は実装時に判断。
- **[帰属表示 `unitSaved`]** → 除外 need は `fullNeed` から他レシピを引く。クランプ後への足し戻しは過産で過大になる。

## Migration Plan

フロントのみ。デプロイ後は食材入力が同じでも推奨皿数が変わる。ロールバックはレシピ yield を 1 に戻す。

## Open Questions

なし。検証ルール（40% / 残り均等）は探索で確定済み。
