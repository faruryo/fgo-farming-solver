# Design

## Context

`hooks/use-local-storage.ts` の `useLocalStorage` は、サーバーの描画とクライアントの最初の描画を揃えるため `useState(initialState)` で描き、マウント後の `useEffect` で保存値を読んで `setState` する。読み終えたかを表す `isInitialized` は内部にあるが、返り値は `[state, setState]` の2つだけで、呼び出し側は読む前かどうかを知れない。/events/[id] は `force-dynamic` のサーバー描画なので、読み込み直すと、サーバーが描いた初期値の HTML が hydration と effect の終わりまで見える。

交換所の画面（`components/events/EventShopList.tsx` の `EventShopList`）では、同じコンポーネントの中で3つの保存値を読む。交換所の入力（`useShopSavedInputs`）、所持数、品目の「要る」（どちらも `useShopRosterPlan` の中）。育成計画は `hooks/use-roster-need.ts` の `useRosterNeed` を通して読み、その結果の状態は今 `empty` / `loading`（素材の取得中） / `error` / `ready` の4つ。読む前は保存値が空なので `empty` になり、「育成対象を設定すると…」の案内が出る。AP 予算の欄（`ApBudgetInputs`）と内訳（`ShopApBudget`）は子コンポーネントで、`useApBudgetProfile` を通して、マスターレベルと黄金の果実を別のインスタンスで読む。

`useRosterNeed` はロト計画（`EventPlannerClient`）と料理作成（`EventCraftSection`）も使う。ロト計画は `hasRoster = status !== 'empty'` で育成計画のボタンと未設定の説明を出し分け、入力モードの初期値を最初の描画の `hasRoster` で決める（`useState(hasRoster ? 'roster' : 'boxes')`）。event-planner の spec には未 archive の change `issue-127-bug-events` の delta があるので、この change では event-planner の要件を書き換えず、ロト計画の振る舞いも変えない。

issue の求めで、交換所以外で `useLocalStorage` を使う画面のうち、同じ症状が見えるものを数えた。数え方は、呼び出し元を全件読み、保存値から出す表示がサーバー描画と最初の描画に初期値で出て、別の理由の待ち（`mounted` の旗、取得中のスケルトン、閉じたダイアログ、透明から始まるアニメーション）に隠れていないものを「見える」とした。コードの読み取りによる判定で、ブラウザでは測っていない。

| ルート | 初期値で見えるもの |
|---|---|
| /todo | タスクの一覧が「タスクがありません」、自動生成と通知のスイッチが既定 |
| /farming（/farming/manual も同じ画面） | 個数の欄が空で「最低1つ入力」の警告、クエストが全部選ばれた状態 |
| /items/[id] | ドロップ率の表示の切り替えが既定 |
| /material/class-score | 全クラスが未設定、集計が 0 |
| /material/class-score/[className] | 全マスが未選択、集計が 0 |
| /events/[id] のロト計画・料理作成 | 育成計画の未設定の説明、AP 予算の既定値 |
| /（ダッシュボード） | 期限間近のタスクのカードが後から現れる（値の入れ替わりではない） |

交換所を除いて 7 ルート（値が入れ替わるのは / を除く 6）。/material、/material/result、/quests、/quests/[id]、/bond は別の理由の待ちに隠れて見えない。/material/[className] などで、取得の後に初めて描かれる部品が初期値で1回描かれる箇所は、見えるかを決められなかった。

ロト計画の入力モードは、最初の描画の時点で育成計画が常に `empty` なので、育成計画のある人でも「箱数」で始まる。これはちらつきではなく、既定の選択が保存値を見ないまま決まる別の不具合で、この change では扱わない（ロト計画の振る舞いを変えないため）。

## Goals / Non-Goals

**Goals:**
- 交換所の画面で、保存値から出す表示を、読み終えるまで読み込み中の表示にする（specs の「保存値を読むまで初期値を見せない」）
- 読み終えたかを、保存値を読む共通の仕組みから呼び出し側が知れるようにし、ほかの画面が後から同じ直し方を使えるようにする

**Non-Goals:**
- 交換所以外の 7 ルートのちらつき（上の表）
- ロト計画の入力モードの初期値の不具合
- サーバー描画をやめる、保存値をサーバーへ送る、など描画の仕組みの変更
- 保存のキー・保存値の形・計算の変更

## Decisions

### 判断点

#### 1. 読み込み中に何を見せるか

推奨: **A. 保存値から出す部分を、まとめて読み込み中の表示（スケルトン）に置き換える。**

| 案 | 0 を見せない確かさ | 見た目 | 変える量 |
|---|---|---|---|
| A. 交換所の周回計算と品目の表を、読み終えるまでまとめてスケルトンにする（推奨） | 1か所で止めるので、保存値から出す数の出し漏れが無い | 読み込みの間は品目名や在庫上限も見えず、読み終えた時に高さが変わる | 小さい |
| B. 欄を空欄にして操作できなくし、必要量・周回の内訳・合計などの数を「—」にする | 保存値から出す数が、まとめ・行ごとの計画・通貨ごとの必要量・ボーナス礼装の比較・AP 予算に散っていて、1つでも漏れると 0 が残る | 品目名と在庫上限は先に見え、高さも変わらない | 大きい（表示の箇所ごとに分岐） |
| C. サーバー描画をやめ、読み終えるまで何も描かない | A と同じ | 読み込みの間は空白で、読み込み中だと分からない | 小さい |

A は、issue が困っている「0 が見える」を、表示の箇所を1つずつ直さずに確実に消せる。代わりに、読み込みの間（hydration の終わりまで）は品目の一覧も読めず、読み終えた時にスケルトンから表に高さが変わる。B は一覧を先に読めるが、交換所の数の出し所は多く、どれかで 0 が残ると同じ不具合が戻る。C は A と同じだけ隠すうえ、読み込み中だと分からない。

#### 2. 読み終えたかを呼び出し側へどう渡すか

推奨: **A. `useLocalStorage` の返り値の3つ目に、読み終えたか（真偽値）を足す。**

| 案 | 既存の呼び出し側への影響 | 子のコンポーネントの扱い | リロードの 0 |
|---|---|---|---|
| A. 返り値の3つ目に読み終えたかを足す（推奨） | 今の呼び出し側（26ファイル）はすべて2つの要素の分割代入なので、変えなくてよい | 値を読むインスタンスごとに、自分の印を見る | 消える |
| B. 保存値を描画の中で同期に読む（外部の値を購読する React の仕組み） | 読み方の作り直しで、他タブの同期と補正の書き戻しを全部見直す | 後からマウントする部品は最初から保存値で描ける | サーバーは保存値を知らないので、hydration の間は消えない。結局 A と同じ印が要る |
| C. 画面ごとにマウント済みの旗を持つ（/material などが既にしている形） | 変えない | 旗は同じコンポーネントの中の値にしか効かず、子が自分で読む値は、子が現れた最初の描画で初期値になる | 親の中だけ消える |

A は、保存値と読み終えた印を同じ effect で立てるので、印が立った描画では値も保存値になっている。B は後からマウントする部品の1回の描画も消せるが、リロードの症状は消せず、使い所の多い hook を作り直すことになる。C は交換所の AP 予算のように、子が自分で読む値に効かない。

#### 3. この change で直す範囲

推奨: **A. 交換所の画面（周回計算・品目の「要る」・育成計画から出す状態・AP 予算）。**

| 案 | 交換所で 0 や既定値が残るか | ほかの画面 | 確かめる量 |
|---|---|---|---|
| A. 交換所の画面で保存値から出す表示すべて（推奨） | 残らない | 共通の部品（育成計画、AP 予算の欄）を通して、同じページのロト計画と料理作成の一部も直る | /events/[id] の交換所 |
| B. 交換所の周回計算の欄と数だけ（issue の例そのまま） | 「要る」のチェック、育成計画の未設定の案内、AP 予算の既定値が残る | 変わらない | 交換所の周回計算 |
| C. 上の表の 7 ルートもまとめて直す | 残らない | すべて直る | 7 ルートそれぞれで読み込み中の見せ方を決めて確かめる |

A は、利用者が交換所を読み込み直したときに見える初期値をすべて消す。B は issue の例は直るが、同じ画面のほかの欄で同じ症状が残る。C は画面ごとに見せ方の判断が要り（/farming の警告、/todo の空の一覧など）、1つの PR で決めて確かめる量が大きいので、判断点2の印ができてから画面ごとに扱う方がよい。

### 決めたこと

1. **`useLocalStorage` は、保存値の読み込みと同じ effect で印を立てる。** 保存値の `setState` と印の `setState` は同じ effect の中なので、同じ描画で反映される。`useInitial` のときは保存値を読まないので、マウント後に印だけ立てる。印は読み終えたキーについて立てるので、キーが変わった描画では、新しいキーの保存値を読むまで立たない。印は返り値の3つ目で、既存の呼び出し側は変えない。
2. **育成計画は「まだ読んでいない」状態を足す。** `useRosterNeed` が、育成計画の保存値を読み終えるまで、新しい状態 `unread` を返す。既存の `loading`（素材の取得中）を流用しないのは、ロト計画が `status !== 'empty'` を「育成計画あり」と読み、入力モードの初期値もそれで決めるため。`loading` を返すと、育成計画の無い人にも育成計画のボタンが一瞬出て、入力モードが「育成計画」で固定される。ロト計画は `unread` を `empty` と同じに扱い、今の振る舞いを保つ。料理作成は `unread` を `loading` と同じ「読み込み中」に扱う（育成計画の未設定の案内が一瞬出るのも直る。読み終えた後の表示は今と同じ）。
3. **交換所は1つの印でまとめて止める。** `EventShopList` は、交換所の入力・所持数・「要る」の印がすべて立ち、育成計画が `unread` でなくなるまで、返す要素のうち育成計画の素材の読み込み（`rosterPlan.loader`）を除くすべて（周回の合計のまとめ、全部交換などの操作と育成計画の状態の行、通貨ごとの品目の表、ボーナス礼装の比較、1周の獲得量の表、周回の内訳、AP 予算）の代わりにスケルトンを出す。表の一部だけを止めると、「周回の合計: 不要」やボーナス礼装の比較の 0 のように、保存値から出す別の表示に初期値が残るため。どれも同じコンポーネントの hook なので、1つの印にまとめられる。読み込み中は欄を描かないので、利用者は欄を変えられず、保存値が入力で上書きされることもない（specs の「読み込み中は入力で保存値を上書きしない」）。サーヴァント扱いの品目だけの一覧（`EventShopCatalog`）は保存値を読まないので止めない。
4. **AP 予算は、値を読む部品が自分の印を見る。** `useApBudgetProfile` が、マスターレベルと黄金の果実の両方を読み終えたかを返す。`ApBudgetInputs` と交換所の `ShopApBudget` は、印が立つまで欄と内訳の代わりにスケルトンを出す。親の印だけで止めると、子が現れた最初の描画で初期値が1回描かれるため。`ApBudgetInputs` はロト計画も使うので、ロト計画の AP 予算の欄も同じく直る。ロト計画の内訳（`EventPlanResultCard` が親から受け取る値）は変えない。
5. **読み込み中の表示は、既存の `components/ui/skeleton.tsx` の `Skeleton` を使う。** 文言は足さない（翻訳の辞書は変えない）。読み上げのために、スケルトンを囲む要素に `aria-busy` を付ける。

## Risks / Trade-offs

- [読み込みの間（hydration の終わりまで）、交換所の品目の一覧が読めない] → 判断点1 のとおり、0 を確実に消す方を取る。読み込みは hydration 直後の effect で終わる
- [スケルトンから表に変わるときに高さが変わり、下の内容がずれる] → スケルトンに表のおおよその高さを持たせ、ずれを小さくする
- [`RosterNeed` に状態を足すと、状態を全部扱う箇所で漏れうる] → 今の呼び出し側は `status !== 'empty'` の比較や if の連鎖で状態を見ているので、状態を足しても型検査では落ちない。料理作成の `resolveBlockedView` と交換所の育成計画の行は、状態ごとの分岐を網羅の検査（扱いの無い状態で型エラーになる形）に書き換え、ロト計画の `unread` の扱いはテストで固める（tasks 2.2）
- [ほかの 7 ルートは今のまま] → Context の表で残る場所を示す。印を使えば同じ直し方ができる

## Migration Plan

保存のキーと保存値の形は変えないので、移すものは無い。戻すときはコードを戻すだけでよい。
