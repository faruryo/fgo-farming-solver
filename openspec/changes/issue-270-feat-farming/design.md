# Design

## Context

動機は proposal.md の Why を参照。設計を決める今の状態は次のとおり。

- 育成計算機は周回目的に応じた 1 つの目標だけを周回計算の API へ送る。「新規サーヴァントに備える」のときは在庫基準まで含めた目標を送るが、それがストック込みの目標であることは API に伝わらない
- API 側には、ストック込みの目標を別の引数で受け取ると 2 目標を解いて 2 件 1 組で保存し、2 件目にだけ印を付ける経路が残っている。この引数を送る画面は 2026-10-17 以降ない
- 印は保存する計算結果の中の値で、履歴の取得はそこから読む。データベースに印の列はない
- 印を読む側は既にある。結果ページと履歴の一覧の「ストック込み」の札、計算履歴ページとダッシュボードのグラフ（結果ページもダッシュボードと同じグラフを出す）の「通常 / ストック込み」の切り替え。切り替えは両方の種別があるときだけ出て、線と達成予想は選んだ種別の計算だけで描く
- 過去に 2 件 1 組で保存された計算がデータベースに残っている。これを 1 つのカードにまとめる表示、組での削除、組での公開設定の切り替えは今も動いている

## Goals / Non-Goals

**Goals:**

- 「新規サーヴァントに備える」で解いた計算に印が付き、今ある札とグラフの切り替えがそのまま効く
- 仕様と API から、戻さないと決めた 2 目標の保存を外す

**Non-Goals:**

- 2 目標の同時計算に戻すこと
- 札やグラフの見た目を作り直すこと
- 過去に保存された計算を書き換えること（判断点 1）
- 過去の 2 件 1 組の計算の表示・削除・公開設定の連動を消すこと

## Decisions

### 判断点

#### 判断点 1: この変更より前に「備える」で解いて印なしで保存された計算を、付け直すか

推奨: **付け直さない**（案 A）。

| 案 | 過去の線の崩れ | 本番のデータに触るか | 足すコード | 取り違えの危険 |
|---|---|---|---|---|
| A. 付け直さない（推奨） | 残る。気になる計算は履歴から削除すれば線から消える（今ある機能） | 触らない | なし | なし |
| B. 結果ページに、持ち主が「ストック込みとして扱う」を切り替える操作を足す | 持ち主が 1 件ずつ直せる | 持ち主の操作でその計算だけ書き換わる | 切り替えの API と画面、テスト | 低い（本人が見て決める） |
| C. 本番のデータベースをまとめて書き換えて印を付ける | 一度に直る | 触る（人が本番に対して実行する） | 書き換えの手順 | 高い。保存された計算には周回目的が残っておらず、目標の個数から「備える」で解いたかを推し量るしかない |

- 根拠: 過去の計算には、どの周回目的で解いたかが記録されていない。C は推し量りで本番のデータを書き換えるので、必要分の計算を誤ってストック込みにする失敗がありうる。A はその失敗を避けられ、本番のデータを読まずに済む。「備える」が入ったのは 2026-10-17 で、印なしで保存された期間は 1 か月ほどに限られる。グラフは新しい計算が増えるほど古い点の影響が薄れ、期間を「1ヶ月」「3ヶ月」に絞れば古い点は外れる
- A で取りこぼすもの: 過去の「備える」の計算は「通常」の線に残り、その期間の線の山と達成予想のずれは自動では直らない。直したい持ち主は、その計算を履歴から削除する（結果ページの URL は削除後も開ける）
- B は A の後からでも足せる。過去の点を残したまま系列だけ直したい要望が出たら、別の issue で B を足す

### 決めたこと

- **印を付ける条件は「育成計算機が『新規サーヴァントに備える』で送ったこと」だけにする**。在庫基準が必要数を上回らず、送る目標が「今の育成」と同じになる場合も印を付ける。目標の中身で印を決めると、在庫が増減するたびに同じ目的の計算が 2 つの系列を行き来し、どちらの線も途切れるため。オーナーの決定（「`reserve` で解いた計算に印を付ける」）にもそのまま合う
- **API の引数は真偽 1 つにする**。周回目的そのもの（3 種）は渡さない。保存した計算を読む側が見分けるのは今も「ストック込みかどうか」だけで、「素材全体の効率を見る」は「今の育成」の目標で解くので、目的を渡しても読む側の扱いは変わらない
- **印は API に来た引数をそのまま信じる**。印が変えるのは、送った本人の計算の札とグラフの系列だけで、他人のデータにも公開範囲にも効かないので、サーバーで目標の中身と突き合わせない
- **ストック込みの目標を別の引数で渡す経路は API から消す**。残すと、仕様から外した 2 件 1 組の保存が API を直接呼べば今後も作れてしまう。古い形の要求が来たら、その引数を無視して通常の目標で 1 件を保存する（エラーにしない。送る画面は既にない）
- **手入力の周回計算には印を付けない**。手入力は周回目的の影響を受けない（solver の「手入力ソルバーは影響を受けない」）ので、個数がどちらの目的のものかをシステムは知らない
- **グラフの系列の分け方は、今ある「通常 / ストック込み」の切り替えをそのまま使う**。2 本の線を 1 つのグラフに重ねない。在庫基準込みの合計 AP は必要分より桁が大きくなりやすく、重ねると必要分の線が底に張り付いて推移が読めなくなる。達成予想日も系列ごとに 1 つなので、切り替えのほうが読み違えない。切り替えの「通常」の表記も変えない（「通常」には手入力の計算も入るので「必要分」とは言い切れない）
- **データベースの列は足さない**。印は今までどおり保存する計算結果の中に入れ、履歴の取得が読む。マイグレーションも本番への作業もない
- **過去の 2 件 1 組の計算の表示・削除・公開設定の連動は残す**。データベースに残っている組を壊さないため。仕様から外すのは「これから 2 件 1 組を保存する」要件だけ
- **「計算結果の公開・非公開設定」の要件にある「2目標ペア保存時の公開設定連動」の筋書きは、この変更では消さない**。openspec は要件の一部の筋書きだけを落とす差分を受け付けず（`openspec validate --strict` が「MODIFIED は今ある筋書きを省けない」で落ちることを 2026-11-15 に確かめた）、消すには要件ごと外して別名で足し直すしかない。2 件 1 組を保存する経路が API から無くなるので、この筋書きの条件（2 目標を保存するとき）は起きなくなり、残っていても動きとは食い違わない

## Risks / Trade-offs

- [開いたままの古い画面が、引数なしで「備える」の計算を送る] → その計算は今までどおり印なしで保存される。再読み込みすれば直る。数は限られ、判断点 1 の A と同じ扱い（気になれば削除）で足りる
- [API を直接呼べば、誰でも自分の計算に印を付けられる] → 変わるのは本人の履歴の表示だけ。公開範囲・他人のデータ・進捗の保存には効かない
- [印が付き始めると、ダッシュボードのグラフの初期表示が「ストック込み」側になることがある] → 既にある動き（初期表示は最新の計算の種別）で、切り替えが同じ場所に出る。「備える」を選んでいる人には、選んだ目的の推移が最初に出るほうが合う
- [在庫基準が効かない状態で「備える」で解くと、必要分と同じ目標でも「ストック込み」に入る] → 決めたことの 1 つ目のとおり、目的で分けるほうを採る

## Migration Plan

- デプロイだけで有効になる。データベースの変更も本番への手作業もない
- 戻すときは、この変更を revert する。revert の前に印付きで保存された計算は「ストック込み」の札と系列のまま残る（意味は正しいので直さなくてよい）
