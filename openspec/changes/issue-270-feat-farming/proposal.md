# Proposal

## Why

周回目的「新規サーヴァントに備える」で育成計算機から周回計算へ送ると、在庫基準まで含めた目標が 1 つだけ送られるが、保存される計算には「ストック込み」の印が付かない（#263 の調査、PR #269）。そのため結果ページに「ストック込み」の札が出ず、計算履歴のグラフでは在庫基準込みの AP が「通常」の線に混ざって、推移の線と達成予想日が崩れる。

一方 `farming-history` と `solver` の仕様には、2026-10-17 の farming-purpose-modes で外した「必要分とストック込みの 2 目標を同時に計算して 2 件で保存する」要件が残っていて、今の動き（選んだ 1 つの目標で計算する）と食い違っている。オーナーの決定（2026-11-15、#270）は「目標は 1 つのまま、備える目的で解いた計算に印を付け、履歴のグラフでは別の系列にする。2 目標の同時計算には戻さない」。

## What Changes

- 周回計算の API に、ストック込みの計算であることを渡す引数を足す。育成計算機は「新規サーヴァントに備える」で送るときにこの引数を付け、保存される計算に「ストック込み」の印が記録される
- 印の付いた計算は、今ある仕組みのまま、結果ページと履歴の一覧に「ストック込み」の札が出て、履歴のグラフ（計算履歴ページ・ダッシュボード・結果ページ）では「通常 / ストック込み」の切り替えの「ストック込み」側の系列に入る。札とグラフの切り替えは既にあるので作り直さない
- **BREAKING**: 周回計算の API から、2 目標を同時に計算して 2 件で保存する経路（ストック込みの目標を別の引数で渡す経路）を外す。この引数を送っている画面は 2026-10-17 以降ない
- `farming-history` の仕様から「2 目標の連結保存」の要件を外す。過去に 2 件 1 組で保存された計算の表示・削除・公開設定の連動は今のまま残す
- `solver` の仕様から「2 目標結果の進捗アンカー」の要件を外す
- 過去に印なしで保存された「備える」の計算は付け直さない（design の判断点 1）

## Capabilities

### New Capabilities

なし

### Modified Capabilities

- `farming-history`: ストック込みの印を、育成計算機が「新規サーヴァントに備える」で送った計算に付ける条件を足す。2 目標の連結保存の要件を外す
- `solver`: 2 目標結果の進捗アンカーの要件を外す

## Impact

- コード: `app/api/solve/route.ts`（引数の追加、2 目標の経路の削除）、`lib/farming/build-solve-params.ts`（備える目的のときに引数を付ける）、それぞれのテスト。`components/material/result.tsx` は `buildSolveParams` の返す引数をそのまま送るだけなので触らない
- データベース: 列は足さない。印は今までどおり保存する計算結果の中に入り、履歴の取得がそこから読む。マイグレーションなし
- 画面: 札とグラフの切り替えは今あるものをそのまま使う。新しい画面部品はない
- 過去の計算: 変えない。この変更より前に「備える」で解いた計算は「通常」の系列に残る
- 対象件数: 数えていない。この変更は「どの計算をストック込みの系列に入れるか」の判定を変えるが、対象になるのはこの変更の後に保存される計算だけで、過去の計算は 1 件も動かない。過去に印なしで保存された「備える」の計算が何件あるかは本番の D1 にしかなく、本番の D1 は読まない方針（#270 の起動時の指示）なので取れなかった。影響は例だけで説明する: 「備える」で解いた計算（例: 在庫基準込みで合計 AP 12,000）は、今は「通常」の線に入って必要分の計算（例: 合計 AP 3,000）の間に山を作るが、変更後に解いたものは「ストック込み」の系列に入り、「通常」の線には入らない
