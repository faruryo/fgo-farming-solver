# Design

## Context

この change は、#134 の実装 PR #168 がマージされた後の main に乗る。#168 の後の交換所の周回計算（`components/events/EventShopList.tsx`）は、通貨ごとのカード（交換回数・所持数・必要量）、全部交換の操作、周回の内訳（`planShopCurrencies` の結果）、AP 予算、ボーナスを含まない旨の注記（`event-shop-plan-bonus-note`）を持つ。

ドロップの統計は、`scripts/refresh-event-data.ts` が Atlas の `/nice/<region>/quest/<id>/<phase>` の `drops` から作る。1つのドロップの素の1周の期待値は `dropCount / runs × num` で、4桁に丸めて `perRun` に入る。issue #130 の調査（2026-10-19 のコメント）で、`num` はボーナス前の枠の数で、ボーナスはドロップ1回ごとに +N で効くと確かめた。ボーナス込みの1周の獲得量は `perRun + (dropCount / runs) × N` になる。今の KV は `dropCount / runs` を持っていない。1つのクエストに同じ品目のドロップが複数（枠の数の違うもの）あることがあり、それぞれに足す。

イベントポイントの品目は、#161 が `event_rewards:<id>` の `pointItemId` に保存している。`lib/get-events.ts` の `getEventRewards` で読めるが、イベントページはまだ読んでいない。

## Goals / Non-Goals

**Goals:**
- 手で入れたボーナスから、クエストごとのボーナス込みの1周の獲得量を出し、交換所の周回計算に反映する
- ボーナスがすべて0のときは、今の計算と完全に同じ結果にする

**Non-Goals:**
- Atlas の礼装（`eventDropUp` / `eventPointUp`）とサーヴァントの `extraPassive` からの自動取り込み、礼装の所持の入力（オーナーの判断で後回し）
- 箱のあるイベントの箱計画（`manualDropPerRun`）への反映。オーナーの判断に無いので変えない
- ポイントの累計からポイント報酬の到達を出すこと（epic #129 の D1）
- ボーナスの値の保存

## Decisions

### 1. 取り込みで1周あたりのドロップ回数を保存する

`EventFarmingNode` のドロップに任意の項目（1周あたりのドロップ回数、`dropCount / runs` を4桁に丸めた値）を足し、`scripts/refresh-event-data.ts` で書く。任意にするのは、取り込み直す前の KV とモックのデータを読めるようにするため。`perRun` の式と丸めは変えない。

採らなかった案: `num` を保存して `perRun / num` で回数を戻す。丸めた `perRun` から割り戻すと誤差が出る。

### 2. ボーナスはソルバーに渡す前のドロップ率に足す

`lib/event-plan.ts` に、イベントとボーナス（品目 ID → N）から、ドロップごとの1周の獲得量を `perRun + 回数 × N` に置き換えたイベントを返す純粋関数を置く。`planShopCurrencies` と、#165 の区切りの基準（`currencyApThresholds`）の呼び出し側で、この関数を通したイベント（とその `farmingNodes`）を渡し、`buildEventDrops`・`runEventSolver`・`planShopCurrencies`・`currencyApThresholds` の中は変えない。オーナーの判断は #162・#165・#168 への反映なので、周回の内訳・AP 予算（#168 は周回の合計 AP から出る）と、#165 の効率の区切りの基準を、同じボーナス込みの値でそろえる。区切りだけ素の値のままだと、同じ画面に通貨1個の AP が2つ並ぶ。回数を持たないドロップは `perRun` のまま返し、ボーナスを反映できなかった品目の ID を一緒に返す。ボーナスが空か全部0なら、入ったイベントをそのまま返す（同じ結果になることを保証する）。

採らなかった案: `buildEventDrops` にボーナスの引数を足す。箱計画と共用の関数の形が変わり、箱計画の結果を変えないことの確認が増える。

### 3. ポイントの品目はページで読んで渡す

`app/events/[id]/page.tsx` で、ロトの無い交換所イベントのときだけ `getEventRewards(eventId)` を読み、`pointItemId` を `EventShopList` に渡す。無ければポイントの欄と列を出さない。ポイントは交換所の必要量に入らないので、周回計算には効かず、1周の獲得量の表にだけ出る。

### 4. 画面

- ボーナスの入力: 交換所のセクションの上部（全部交換の操作の近く）に「ボーナス（1ドロップあたり +N）」のカードを置き、通貨（通貨名か ID の見出しと同じ表記）とポイントの品目ごとに数の欄を並べる。375px では2列で折り返す
- 1周の獲得量: 周回の内訳の上に、クエストごとの行、列が通貨とポイントの表を置く。値は通貨もポイントも小数1桁。通貨もポイントも落ちないクエストの行は出さない。ボーナスを入れた品目の列は、素の値との差（例: `+10.0`）を小さく添える。列が多いときは表の中だけ横に流し、ページに横スクロールを出さない
- 注記: ボーナスがすべて0なら今の注記のまま。1つでも入れたら「入れたボーナス（1ドロップあたり +N）を含む見込みです」に変える。回数が無くて反映できない品目があれば、その品目名を挙げて「データの更新前のため、ボーナスを反映できません」と出す
- 入力は `useState` で持つ（#162 の交換回数と同じ）

## Risks / Trade-offs

- [本番の KV が回数を持たないイベントが残る] → 定期の取り込みが取り込み直すのは、開催中か終了後 30 日以内のイベントだけで、それより古いイベントは KV の前の値が残る（`scripts/refresh-event-data.ts` の対象イベントと蓄積マージ）。古いイベントは、`BACKFILL_SINCE` を付けた取り込みを人が回すまで回数を持たず、反映できないことを表示して素の値で計算する。手で KV を書き換えない
- [#168 がマージされる前に実装に入ると、乗る画面が無い] → 実装（ops-graph）は #168 のマージ後に main から始める
- [ボーナスの値を毎回入れ直す手間] → 保存はしない（Non-Goals）。要望が出たら別の issue で扱う
