# Proposal

## Why

ロトの無い交換所イベントの周回計算（#162・#165・#134）は、ドロップ増加礼装のボーナス（「1ドロップにつき +N」。ドロップ数を増やすのは礼装だけで、サーヴァントのボーナスでは増えない）を含まない素のドロップ統計で解くので、ボーナス礼装を編成して周回する利用者には、実際より多い周回数と AP が出る（issue #130、epic #129）。1周あたりに通貨とイベントポイントがいくつ手に入るかも、画面に出ていない。

## What Changes

- ロトの無い交換所イベントの交換所のセクションに、短い見出しと「何を入れると何が変わるか」の説明の1行を添えて、通貨ごとと、イベントポイントの品目の「1ドロップにつき +N」の入力を足す。値は利用者が手で入れる（オーナーの判断。Atlas からの自動取り込みと礼装の所持の入力は作らない）
- クエストごとに、ボーナス込みの1周あたりの通貨とイベントポイントの獲得量を出す。1周の獲得量は「素の1周の期待値 + 1周あたりのドロップ回数 × N」
- 入れたボーナスを、交換所の周回計算（周回の内訳の周回数・合計 AP・通貨ごとの見込み獲得量・AP 予算）に反映する。#165 の効率が良い区切りは #176 で無くなったので対象にしない
- イベントデータの取り込みで、各ドロップの1周あたりのドロップ回数も保存する。取り込み直す前のデータ（回数が無い）では、ボーナスを反映できないことを示し、素の値で計算する
- ボーナスがすべて0のときは、今の周回計算と同じ結果を出す

## Capabilities

### New Capabilities
- `event-drop-bonus`: ロトの無い交換所イベントで、利用者が入れた「1ドロップにつき +N」のボーナスから、1周あたりの通貨とイベントポイントの獲得量を出し、交換所の周回計算に反映する

### Modified Capabilities
（なし。交換所の周回計算の既存の要件（`event-planner` の #128 の要件、#134 の `event-shop-ap-budget`）は書き換えず、ボーナスを入れたときの振る舞いを新しい capability に足す。`event-planner` は未 archive の change `issue-127-bug-events` が持つ capability で、その change が archive されるまで同じ capability に delta を足さない。既存の要件「ドロップの統計にイベントのボーナス（礼装・サーヴァント）が含まれないことを示す」は文言にサーヴァントを含むが、示す中身（統計はボーナスを含まない）は保ったまま注記の文言だけを礼装に直すので、要件とは食い違わない。要件の文の「サーヴァント」を直すのは issue-127 の archive の後に回す。また `event-shop-ap-budget` は #134 の要件のまま変えない）

## Impact

- 前提: #134 の実装 PR #168 がマージ済みであること。画面は #168 の後の `components/events/EventShopList.tsx` の上に乗る
- `scripts/refresh-event-data.ts`（各ドロップの1周あたりのドロップ回数を保存する）と `lib/master-data/types.ts`（ドロップの型に任意の項目を足す）
- `lib/event-plan.ts`（ボーナス込みの1周の獲得量をソルバーの入力に使う）
- `components/events/EventShopList.tsx` と `app/events/[id]/page.tsx`（ボーナスの入力、1周の獲得量の表、ポイントの品目の受け渡し）
- `locales` の events の文言
- 本番の KV の値は、定期の取り込みが取り込み直す開催中か終了後 30 日以内のイベントから新しい項目を持つ。それより古いイベントは、`BACKFILL_SINCE` を付けた取り込みを人が回すまで持たない。手で書き換えない
