# Design

## Context

動機は proposal.md の Why を参照。

この change の「絆アップ礼装」は、獲得絆を増やす効果(Atlas の関数の種類 `servantFriendshipUp`)を持つ概念礼装を指す。絆Lv10の報酬で得るサーヴァント専用の礼装(絆礼装)とは別物で、提案の対象にしない。

- 絆トラッカー(`/bond`)は Material Catalog(`material_catalog_v1`)からサーヴァントの一覧と `bondGrowth` を読み、fgodrop のクエストの基本絆ポイントで周回クエストの候補を作る(`lib/bond/quest-candidates.ts`)。礼装のデータとサーヴァントのコストはまだどこにもない
- Material Catalog は GitHub Actions の更新ジョブ(`scripts/run-updater.ts` → `lib/material-catalog-phase.ts` → `lib/material-catalog-updater.ts`)が Atlas の巨大な JSON を条件付き GET で取り、蒸留して KV に書く。Worker では巨大な JSON を parse しない
- マスターレベルは `useMasterLevel`(localStorage `masterLevel`、クラウド同期済み)にあり、最大AP は `lib/master-profile/max-ap.ts` の静的な変化点テーブルから引く

## Goals / Non-Goals

**Goals:**
- 提案は小さな純関数で決め、UI は結果を描くだけにする
- 礼装のデータはカタログに載せ、ブラウザで22MB の JSON を読まない

**Non-Goals:**
- 所持礼装の入力と凸状態の入力(オーナーの判断で今は扱わない)
- 提案の結果を残り周回数・到達見込みの見積もりへ反映すること。見積もりは今までどおりリザルト画面の値を使う
- 選択の保存とクラウド同期
- イベント限定の絆アップ礼装、イベントのボーナス、フレンドのサポートの礼装、編成ボーナス(絆Lv15到達者などによるもの)

## Decisions

### 1. 礼装データは Material Catalog に足す

カタログの更新ジョブに `nice_equip.json` を、検証子を持つ条件付き取得の取得元(今は `sources.niceServant` と `sources.niceItem` の2つ)の3つ目として足し、`sources.niceEquip` に検証子を持つ。イベント一覧(`eventUrl`)の取得は検証子を持たないので数えない。蒸留の結果は `bondUpCraftEssences: { id, collectionNo, name, rarity, cost, face, target: 'party' | 'self', rate, add }[]` としてカタログに載せる。サーヴァントには `cost?` を足す。どちらも任意項目の追加なのでキーとスキーマバージョンは変えない(`bondGrowth` を足したときと同じ扱い)。

- 却下: ブラウザから Atlas の `nice_equip.json` を直接取る。22MB あり、絆トラッカーを開くたびに読ませられない
- 却下: 別の KV キーに分ける。consumer(`/bond`)は既にカタログを読んでおり、更新の単位を増やす理由がない

`materialCatalogFingerprint` に `bondUpCraftEssences` を含める。含めないと、`nice_equip.json` だけが変わった回が「蒸留結果が同一」とみなされて書き込まれず、新しい礼装が載らないうえに `sources.niceEquip` の検証子も保存されず、毎回22MB を取り直すことになる。空の一覧は検証で拒否する(空を保存すると、取り直しの規則も UI の「読み込めない」表示も働かない)。

取り直しは `servantValidatorFor` と同じ形で、既存カタログのサーヴァントが誰も `cost` を持たないときは `nice_servant.json` を、`bondUpCraftEssences` がないときは `nice_equip.json` を検証子なしで取る。`nice_equip.json` だけが変わった回は、サーヴァントと素材とアイテムを既存カタログから引き継ぐ。`buildMaterialCatalog` はサーヴァントの項目を明示して組み直すので、`cost` も `bondGrowth` と同じく写す。

ローカル開発用の `lib/material-catalog-local.ts`(KV がない `pnpm dev` の経路)も `nice_equip` を取って `bondUpCraftEssences` と `sources.niceEquip` を組む。

蒸留の規則:
- `servantFriendshipUp` の関数を持つスキルのうち、`condLimitCount` が最大の段のスキルだけを読む(最大解放の値)
- `svals` は最後の要素(スキルLvの最大)を読む。現状どの礼装も1要素
- `EventId` を持つ関数と `Individuality` が0でない関数は捨てる。残る関数がない礼装は一覧に入れない
- 対象は `ptFull` を `party`、`self` を `self` とし、それ以外の対象の関数は捨てる
- `self` の関数の `RateCount` は捨て、`AddCount` だけを読む。自身に効く増加率は今のデータ(イベント限定を除く)になく、提案の式でも扱わない(`shortcut` として実装にコメントを残す)
- 同じ礼装に複数の関数が残るときは、対象ごとに `RateCount` と `AddCount` を足す。対象が混ざる礼装は今のデータにないため、混ざったら一覧に入れずに捨てる(`shortcut` として実装にコメントを残す)

### 2. 編成コストの上限は静的テーブル

`lib/master-profile/max-ap.ts` と同じ形で、上の変化点テーブルを `lib/master-profile/max-cost.ts` に持ち、`maxCostForLevel(level)` を出す。マスターレベルの上限が上がったときは最大AP と一緒に更新する。

- 却下: `NiceUserLevel.json` を実行時に取る。最大AP が既に静的テーブルで、同じ値の出どころを2つにしない

### 3. 提案は「何を何枚入れるか」の小さなナップサック

パーティ全体に効く効果は誰に付けても同じなので、各礼装の価値は付ける相手によらない。

- パーティ全体の増加率 `r`: 選んだ各サーヴァントの獲得絆を `floor(base × (1 + R/1000))` で増やす(R は編成全体の増加率の合計)。切り捨てがあるため、増加率の価値は合計してから評価する
- パーティ全体の固定 `a`: 全員に `a`
- 自身の固定 `a`: 付けた1体に `a`

探索は、礼装を「(対象, 増加率, 固定, コスト)」の効果の種類にまとめ(今のデータで8種類、各種類の枚数の上限は件数)、選ぶ枚数の合計がサーヴァントの数以下、コストの合計が「上限 − サーヴァントのコストの合計」以下となる各種類の枚数の組を全部たどる。サーヴァント最大5体・8種類なので組の数は千程度で、評価は R の合計と固定の合計からそのまま出せる。最良の組は「合計の獲得絆が大きい → 使うコストが小さい → 礼装の枚数が少ない」の順で1つに決める。

決まった枚数を、各種類の中で図鑑番号の小さい順の礼装に割り当て、サーヴァントには選んだ順に「自身に効く礼装 → コストの大きい礼装」の順で付ける(結果は同じなので表示の安定のための規則)。同じ種類の残りの礼装を言い換えの候補として返す。

- 却下: 礼装ごとの0-1ナップサック(DP)。効果の種類にまとめれば全探索で足り、同じ効果の礼装の扱い(言い換え)も同時に決まる
- 却下: 同じ礼装を何枚でも入れられるとする。所持を扱わないため、毎回いちばん倍率の高い礼装を全員に付ける答えに固定される(issue の材料コメントの未決事項)

### 4. 1周の獲得絆の元は基本絆ポイント

リザルト画面から入れた値は礼装のボーナスを含みうるので、提案では使わない。周回クエストの基本絆ポイント(fgodrop の `bondPoints`)を全員に同じく使う。

### 5. 画面

`components/bond/index.tsx` の Tabs に「礼装の提案」タブを足し、新しいコンポーネント(`components/bond/craft-essence-advisor.tsx`)に入力(サーヴァントの選択、クエスト、マスターレベル)と結果を描く。クエストの共通の候補は、選んだサーヴァントごとの `bondQuestCandidates` の結果の共通部分を、先頭のサーヴァントの並び順で取る。選んだサーヴァントが0体のときは共通部分を取らず(空集合の共通部分を「全クエスト」としない)、選ぶよう示す。文言は既存の ja/en の翻訳ファイルに足す。

## Risks / Trade-offs

- [ゲーム内の獲得絆の計算は、絆の増加率・固定値の足し方と切り捨ての順が公開されていない] → 提案の数値は推定として示す(spec の式で決める)。組み合わせの順位は増加率と固定値の大小で決まるため、細部の丸めが違っても提案が変わることはまれ
- [同じ礼装を2枚入れたときの効果の重ね掛けを確かめていない] → 同じ礼装は1枚までとしたので結果に影響しない
- [`nice_equip.json` の取得が失敗すると、カタログ全体の更新が止まる] → 既存の取得元と同じ last-known-good の扱い。サーヴァントの更新も止まるが、既存のカタログは配信され続ける
- [Atlas がスキルや `svals` の形を変える] → 蒸留の検証(件数の20%超の減少、値の範囲)で拒否し、既存のカタログを保持する

## Migration Plan

1. 実装をマージすると、次の定期更新でカタログに `cost` と `bondUpCraftEssences` が入る(取り直しの規則で、取得元が未変更でも入る)
2. それまでは提案に「礼装のデータを読み込めない」と出る。入力と見積もりは影響を受けない
3. 戻すときは実装を revert する。カタログに残った任意項目は古い consumer に無視される
