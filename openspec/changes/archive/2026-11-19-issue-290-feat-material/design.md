## Context

所持の切り替えは今、カード下端の `.c-owned-btn`（所持なら「✓ 所持」、未所持なら「未所持」）だけで行っている。Lv・宝具Lv の小窓（`ServantLevelDialog`）は一覧に1つだけあり、所持済みカードの Lv 表示を押すと開く（未所持のカードには Lv 表示が無いので開けない）。小窓は閉じたあと、開いた Lv 表示のボタンへフォーカスを戻す。PR #296（#292）が小窓の Lv・宝具Lv の欄を替えている最中で、まだマージされていない。

## Goals / Non-Goals

**Goals:**
- 所持済みのカードから所持を切り替えるボタンを外し、カード1枚あたりの要素を減らす
- 所持→未所持の操作を小窓のボタン列に移す

**Non-Goals:**
- 小窓の Lv・宝具Lv の欄の作り（#292 / PR #296 の範囲）
- 所持の目印の追加、確認の小窓、「元に戻す」
- 所持の値の形・保存・同期の変更

## Decisions

### 決めたこと

- 「未所持に戻す」は小窓の下のボタン列（今の「キャンセル」「保存」の並び）に置く。オーナーの決定 1-A。欄には触らないので PR #296 との重なりはボタン列だけになる
- カードに所持の目印を足さない。オーナーの決定 2-A
- 確認を挟まず、押したらすぐ未所持にして小窓を閉じる。Lv・宝具Lv と育成計画の値は消さない。オーナーの決定 3-A。今のカードのボタンと同じく所持の印だけを反転させる
- 「未所持に戻す」は「保存」とも「キャンセル」（輪郭だけ）とも区別できるよう、背景も輪郭も無いボタン（ghost）にしてボタン列の左端に離して置く。押し間違えても「未所持」ボタンで戻せ、値は失われないので、破壊的な操作の赤は使わない
- 小窓から所持の印を変えるため、小窓に「未所持に戻す」の通知を渡し、一覧側で該当サーヴァントの所持の印を反転させる。所持の印は今もカード側の `setState` で書いているので、一覧側から同じ保存先を書き換える経路を足す

### 判断点

#### 1. 未所持に戻したあとのフォーカスをどこへ置くか

小窓は閉じたときに、開いた Lv 表示のボタンへフォーカスを戻す。未所持になると Lv 表示のボタンはカードから消えるので、戻し先が無くなる。

| 案 | キーボード・読み上げで続けて操作できるか | 実装の量 |
|---|---|---|
| **A（推奨）** そのカードの「未所持」ボタンへ移す | できる（押せば所持に戻せる位置にいる） | 一覧側で戻し先を切り替える数行 |
| B そのカード全体（`#svt-<id>`）へ移す | 位置は保てるが、カードはフォーカスできる要素ではないので `tabindex` を足す必要がある | 474 枚に属性が増える |
| C 何もしない（ブラウザ任せで `body` へ） | できない。一覧の先頭からたどり直しになる | 0 |

絞り込み（「未所持を隠す」など。#293 で端末に保存される）で未所持のカードが一覧から外れるときは、A の戻り先が無いので、一覧の絞り込みの選択欄へ移す。

推奨は A。避けられる失敗: フォーカスが文書の先頭に飛び、キーボードの利用者が今どこにいるかを失うこと。取りこぼすもの: 「未所持」ボタンが描かれる前に移そうとすると空振りするので、閉じ終わり（`onOpenChangeComplete`）で移す必要がある。小窓の `finalFocus` は今、開いた Lv 表示のボタンを返すが、未所持に戻した場合はそのボタンが消えるので、`finalFocus` は何も返さず（フォーカスを戻さず）、閉じ終わりの処理だけが戻し先を決める。2か所が順に上書きし合わないようにするため。

#### 2. 小窓で書き換えかけた Lv・宝具Lv を「未所持に戻す」で保存するか

| 案 | 利用者の予想との合い方 | 失うもの |
|---|---|---|
| **A（推奨）** 保存しない（「キャンセル」と同じく捨てる） | 「未所持に戻す」は所持の操作で、値の保存ボタンではない | 書きかけの値 |
| B 保存してから未所持にする | 「保存」を押していないのに値が変わる | なし |
| C 書きかけがあれば「未所持に戻す」を押せなくする | 押せない理由が分かりにくい | 操作の手数 |

推奨は A。避けられる失敗: 押していない「保存」が働き、範囲外や書きかけの値が残ること。取りこぼすもの: 書きかけの値を入れ直す手間（未所持では Lv を使わないので影響は小さい）。

#### 3. スマホ幅でアペンドスキル5つ目の枠が右端で切れる既知の崩れ（#282 の確認で発見）をあわせて直すか

| 案 | この PR の範囲 | 崩れが残る期間 |
|---|---|---|
| **A（推奨）** 別の issue に切り出す | 所持ボタンの件だけ | 別 issue の対応まで |
| B この change で直す | アペンドスキルの並びの CSS まで広がる | なし |
| C 直さずに記録だけ残す | 所持ボタンの件だけ | 決まらない |

推奨は A。避けられる失敗: 原因の違う崩れを混ぜて、所持ボタンの変更の見た目の確かめが崩れの直しに引きずられること。取りこぼすもの: 同じカードを2回触ることになる。ボタンを外してカードが低くなっても、横幅の崩れは変わらない見込み。

## Risks / Trade-offs

- [PR #296 と `servant-level-dialog.tsx` で競合する] → 欄に触らずボタン列だけを変える。先にマージされた側に合わせて、後の側がボタン列の数行を取り込む
- [所持から未所持にする入口が小窓だけになり、見つけにくくなる] → 所持→未所持はめったに使わない操作で、オーナーが小窓に移すと決めた。Lv 表示は所持済みのカードに常に出ている
- [カードが低くなり、`#svt-<id>` へ飛んだときの位置がずれる] → 実装の後に 1280px と 375px で飛び先の位置を確かめる

## Migration Plan

保存するデータの形は変えないので、移行は無い。戻すときは PR を revert する。
