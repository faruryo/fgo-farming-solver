## ADDED Requirements

### Requirement: サーヴァントの特性の蒸留

システムはサーヴァントの特性(クラス・属性・性別・その他の特性)を、Atlas Academy の特性 ID の一覧として任意項目で蒸留しなければならない (SHALL)。特性は、基本の特性と、霊基再臨の段階(第1再臨・第2再臨・第3再臨・最終再臨)ごとの特性を蒸留しなければならない (SHALL)。段階ごとの特性は `nice_servant.json` の `ascensionAdd.individuality.ascension` から読み、第1再臨は再臨0、第2再臨は再臨1と2のどちらでも持つ特性、第3再臨は再臨3、最終再臨は再臨4の値とし、値が空の再臨は基本の特性とする。霊衣の特性(`ascensionAdd.individuality.costume`)は蒸留してはならない (SHALL NOT)。段階ごとの特性は、どれかの段階の特性が基本の特性と異なるサーヴァントにだけ含めなければならない (SHALL)。特性の一覧は1要素以上で各要素が正の整数であり、重複を含まない場合に限り含めなければならず (SHALL)、条件を満たさないサーヴァントは特性を省いて蒸留し(段階ごとの特性に条件を満たさない段階があるときは段階ごとの特性だけを省く)、それを理由に候補カタログ全体を拒否してはならない (SHALL NOT)。特性の追加は既存の consumer と互換であり、キーとスキーマバージョンを変えてはならない (SHALL NOT)。

#### Scenario: 正常な特性
- **WHEN** `nice_servant.json` のサーヴァントが基本の特性として〔女性〕〔セイバー〕〔秩序〕〔善〕などの特性を持ち、霊基再臨で特性が変わらない
- **THEN** 蒸留後のそのサーヴァントに、それらの特性 ID の一覧が含まれ、段階ごとの特性は含まれない

#### Scenario: 霊基再臨で特性が変わる
- **WHEN** サーヴァントの `ascensionAdd.individuality.ascension` で、再臨3と4にだけ〔ケモノ科〕を加えた特性があり、再臨0〜2は空である
- **THEN** 蒸留後のそのサーヴァントに、第1再臨・第2再臨は基本の特性、第3再臨・最終再臨は〔ケモノ科〕を含む特性として、4つの段階の特性が含まれる

#### Scenario: 霊衣の特性は蒸留しない
- **WHEN** サーヴァントの `ascensionAdd.individuality.costume` にだけ基本の特性と異なる特性がある
- **THEN** 蒸留後のそのサーヴァントに、霊衣の特性も段階ごとの特性も含まれない

#### Scenario: 不正な特性
- **WHEN** あるサーヴァントの特性が欠落している、空である、または正の整数でない ID を含む
- **THEN** そのサーヴァントは特性なしで蒸留され、他の検証を通過すれば候補カタログは保存される

## MODIFIED Requirements

### Requirement: バージョン付き Material Catalog の生成

システムは、Atlas Academy の JP サーヴァント・育成素材・アイテム・概念礼装データから、育成素材計算機と絆トラッカーに必要な項目だけを含む `schemaVersion: 1` の Material Catalog を生成し、`MASTER_DATA` namespace の単一キー `material_catalog_v1` に保存しなければならない (SHALL)。カタログは `updatedAt`、取得元の ETag / Last-Modified、サーヴァント一覧、サーヴァント別素材、表示用アイテム一覧、絆アップ礼装の一覧を含み、すべて同一の更新単位として扱わなければならない (SHALL)。

#### Scenario: 正常な入力から単一スナップショットを生成する

- **WHEN** Atlas Academy のサーヴァントデータ、アイテムデータ、概念礼装データが正常に取得され、検証を通過したとき
- **THEN** `servants`、`materials`、`items`、絆アップ礼装の一覧、`schemaVersion`、`updatedAt`、取得元検証子を含むカタログが 1 つの KV 値として保存される。
- **THEN** 利用者は異なる更新世代のサーヴァント情報・素材・アイテム情報・絆アップ礼装を組み合わせて受け取らない。

#### Scenario: 表示に不要なアセットを除外する

- **WHEN** Atlas Academy の `nice_servant.json` からサーヴァント表示情報を蒸留するとき
- **THEN** 各サーヴァントには `id`、`name`、`className`、`collectionNo`、`rarity` と、カードで使用する代表顔画像 URL だけが含まれ、有効な絆Lv別の累積必要ポイントを持つサーヴァントにはそれに加えて `bondGrowth` が、有効な編成コストを持つサーヴァントには `cost` が、有効な特性を持つサーヴァントには特性の一覧(霊基再臨の段階で特性が変わるサーヴァントには段階ごとの特性も)が含まれる。
- **THEN** `charaGraph`、衣装別画像一式、その他の未使用 `extraAssets` は Material Catalog に含まれない。

#### Scenario: アイテム情報を用途に限定する

- **WHEN** 育成素材計算機用のアイテム情報を蒸留するとき
- **THEN** 素材増減・不足表示に必要な `id`、`name`、`icon` だけが Material Catalog に含まれる。

### Requirement: 蒸留項目が欠けた既存カタログからの取り直し

システムは、既存カタログのサーヴァントがいずれも `bondGrowth` を持たない場合、いずれも `cost` を持たない場合、またはいずれも特性を持たない場合、`nice_servant.json` を条件なしで取得して蒸留し直さなければならない (SHALL)。取得元が未変更でも、`bondGrowth`、`cost`、または特性を持たないサーヴァント一覧を再利用し続けてはならない (SHALL NOT)。既存カタログが絆アップ礼装の一覧を持たない場合、または一覧のいずれの礼装も効く相手の条件を持たない場合は、`nice_equip.json` を条件なしで取得しなければならない (SHALL)。

#### Scenario: 項目追加後の最初の更新
- **WHEN** 既存の `material_catalog_v1` のサーヴァントがいずれも `bondGrowth` を持たず、`nice_servant.json` は前回から変化していない
- **THEN** updater は検証子を付けずに `nice_servant.json` を取得し、`bondGrowth` を含む候補カタログを構築する

#### Scenario: コストの追加後の最初の更新
- **WHEN** 既存の `material_catalog_v1` のサーヴァントがいずれも `cost` を持たず、`nice_servant.json` は前回から変化していない
- **THEN** updater は検証子を付けずに `nice_servant.json` を取得し、`cost` を含む候補カタログを構築する

#### Scenario: 特性の追加後の最初の更新
- **WHEN** 既存の `material_catalog_v1` のサーヴァントがいずれも特性を持たず、`nice_servant.json` は前回から変化していない
- **THEN** updater は検証子を付けずに `nice_servant.json` を取得し、特性を含む候補カタログを構築する

#### Scenario: 絆アップ礼装の一覧の追加後の最初の更新
- **WHEN** 既存の `material_catalog_v1` が絆アップ礼装の一覧を持たない
- **THEN** updater は検証子を付けずに `nice_equip.json` を取得し、絆アップ礼装の一覧を含む候補カタログを構築する

#### Scenario: 効く相手の条件の追加後の最初の更新
- **WHEN** 既存の `material_catalog_v1` の絆アップ礼装がいずれも効く相手の条件を持たず、`nice_equip.json` は前回から変化していない
- **THEN** updater は検証子を付けずに `nice_equip.json` を取得し、効く相手の条件を含む絆アップ礼装の一覧で候補カタログを構築する

### Requirement: 絆アップ礼装の一覧の蒸留

システムは Atlas Academy の JP 概念礼装データ(`nice_equip.json`)から、獲得絆を増やす効果を持つ概念礼装を絆アップ礼装の一覧として蒸留し、Material Catalog に含めなければならない (SHALL)。一覧の各礼装は、ID、図鑑番号、名前、レアリティ、コスト、表示用の顔画像 URL、効果の対象(パーティ全体か装備したサーヴァント自身か)、最大解放時の獲得絆の増加率(千分率)と固定の増加量、効く相手の条件を持たなければならない (SHALL)。

効く相手の条件は、全員に効くか、特性 ID の組の「または」(いずれかの組のすべての特性を持つサーヴァントに効く)として持たなければならない (SHALL)。1つの特性だけの組を並べたものは「いずれかの特性を持つ」、複数の特性を持つ1つの組は「すべての特性を持つ」を表す。条件付きの礼装は、画面に出す効く相手の表記として、最大解放の段のスキルの効果文(`detail`)の最初の〔から最後の〕までの文字列(例:〔キャスター〕、〔星の力を持つサーヴァント〕または〔悪〕)も持たなければならない (SHALL)。効果文に〔〕のない条件付きの礼装は、条件を読めない礼装として扱う。パーティ全体に効く礼装のうち、サポートで付けたときの増加率が自分で付けたときと異なるものは、最大解放時のサポート時の増加率(千分率)も持たなければならない (SHALL)。

特定のイベントの間だけ効く効果は蒸留してはならない (SHALL NOT)。効く相手の条件を特性の組の「または」として読めない効果も蒸留してはならない (SHALL NOT)。獲得絆を増やす効果がそれしかない礼装は一覧に含めてはならない (SHALL NOT)。残った効果の間で効く相手の条件が異なる礼装は、1つの条件で表せないため一覧に含めてはならない (SHALL NOT)。最大解放で効果が変わる礼装は最大解放時の値を、変わらない礼装はその値を使わなければならない (SHALL)。

`nice_equip.json` は保存済みの ETag / Last-Modified を使って条件付き GET で取得し、`304 Not Modified` のときは parse せず、既存の検証済みカタログの絆アップ礼装の一覧を再利用しなければならない (SHALL)。絆アップ礼装の一覧の追加と、効く相手の条件・サポート時の増加率の追加は既存の consumer と互換であり、キーとスキーマバージョンを変えてはならない (SHALL NOT)。

書き込む前に、絆アップ礼装の ID の一意性、名前と顔画像 URL が空でないこと、コストが正の整数であること、増加率と増加量が有限の0以上の値でいずれかが正であること、効く相手の条件が全員に効くか1つ以上の空でない組からなり各特性 ID が正の整数であること、条件付きの礼装は空でない効く相手の表記を持つこと、サポート時の増加率を持つときは有限の0以上の値であることを検証し、満たさない候補カタログを拒否して既存の `material_catalog_v1` を保持しなければならない (SHALL)。絆アップ礼装の一覧が空の候補と、既存の正常なカタログに対して絆アップ礼装の件数が20%超減少する候補を受理してはならない (SHALL NOT)。絆アップ礼装の一覧だけが変わった候補も、他の蒸留結果の変化と同じく書き込まなければならない (SHALL)。

#### Scenario: パーティ全体の増加率を持つ礼装
- **WHEN** `nice_equip.json` の礼装が、パーティ全体の獲得絆を未解放で2%、最大解放で10%増やす効果を持ち、効く相手の条件を持たない
- **THEN** 蒸留後の一覧にその礼装が対象パーティ全体、増加率100、固定の増加量0、全員に効くものとして含まれる

#### Scenario: 自身の固定値を持つ礼装
- **WHEN** 礼装が、装備したサーヴァント自身の獲得絆を50増やす効果だけを持ち、最大解放で効果が変わらない
- **THEN** 蒸留後の一覧にその礼装が対象自身、増加率0、固定の増加量50、全員に効くものとして含まれる

#### Scenario: クラスに効く礼装
- **WHEN** 礼装が、パーティのうち〔キャスター〕の獲得絆を最大解放で20%増やす効果を持つ(例: 手稿の翼)
- **THEN** 蒸留後の一覧にその礼装が増加率200、〔キャスター〕の特性1つの組だけを効く相手の条件として含まれる
- **THEN** その礼装の効く相手の表記は、効果文「クエストクリア時に得られる〔キャスター〕クラスの絆を20%増やす[最大解放]」から取った「〔キャスター〕」になる

#### Scenario: いずれかの特性に効く礼装
- **WHEN** 礼装が、〔星の力を持つサーヴァント〕または〔悪〕の獲得絆を増やす効果を持つ(例: 異星の神)
- **THEN** 蒸留後の一覧にその礼装が、〔星〕の組と〔悪〕の組の「または」を効く相手の条件として含まれ、効く相手の表記は「〔星の力を持つサーヴァント〕または〔悪〕」になる

#### Scenario: すべての特性を持つ相手に効く礼装
- **WHEN** 礼装が、〔秩序〕かつ〔女性〕の獲得絆を増やす効果を持つ(例: 幸せな花嫁へ)
- **THEN** 蒸留後の一覧にその礼装が、〔秩序〕と〔女性〕の2つからなる1つの組を効く相手の条件として含まれる

#### Scenario: サポート時の値が異なる礼装
- **WHEN** 礼装が、パーティ全体の獲得絆を最大解放で5%、サポートで付けたときは15%増やす効果を持つ(例: カルデア・ティータイム)
- **THEN** 蒸留後の一覧にその礼装が増加率50、サポート時の増加率150として含まれる

#### Scenario: イベント限定の効果を除く
- **WHEN** 礼装の獲得絆を増やす効果が、特定のイベントの間だけ効くものしかない
- **THEN** その礼装は絆アップ礼装の一覧に含まれない

#### Scenario: 条件を読めない効果を除く
- **WHEN** 礼装の獲得絆を増やす効果が、特性の組の「または」として読めない条件を持つものしかない
- **THEN** その礼装は絆アップ礼装の一覧に含まれない

#### Scenario: 効く相手の表記がない条件付きの礼装を除く
- **WHEN** 条件付きの礼装の最大解放の段の効果文に〔〕がない
- **THEN** その礼装は絆アップ礼装の一覧に含まれない

#### Scenario: 効果ごとに条件が異なる礼装を除く
- **WHEN** 礼装が獲得絆を増やす効果を2つ持ち、一方は全員に、もう一方は〔キャスター〕にだけ効く
- **THEN** その礼装は絆アップ礼装の一覧に含まれない

#### Scenario: 概念礼装データが未変更
- **WHEN** `nice_equip.json` の条件付き GET が `304 Not Modified` を返し、既存カタログが効く相手の条件を持つ絆アップ礼装の一覧を持つ
- **THEN** updater は `nice_equip.json` を parse せず、既存の絆アップ礼装の一覧を候補カタログに引き継ぐ

#### Scenario: 概念礼装データだけが変わった
- **WHEN** `nice_servant.json` と `nice_item.json` が `304 Not Modified`、`nice_equip.json` が `200 OK` を返し、蒸留した絆アップ礼装の一覧が既存カタログと異なる
- **THEN** updater は絆アップ礼装の一覧と `nice_equip.json` の検証子を更新した候補カタログを `material_catalog_v1` に書き込む

#### Scenario: 空の絆アップ礼装の一覧を拒否する
- **WHEN** 蒸留した絆アップ礼装の一覧が0件になる
- **THEN** updater は KV への書き込みを行わず、既存の `material_catalog_v1` を保持する

#### Scenario: 不正な絆アップ礼装を拒否する
- **WHEN** 候補カタログの絆アップ礼装に、コストが0の礼装、増加率と増加量がともに0の礼装、または空の組や正の整数でない特性 ID を含む条件を持つ礼装が含まれる
- **THEN** updater は KV への書き込みを行わず、既存の `material_catalog_v1` を保持する
