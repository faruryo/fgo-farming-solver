## Purpose

ロトの無い交換所イベントで、利用者が手で入れたドロップ増加礼装の「1ドロップにつき +N」のボーナスから、1周あたりの通貨とイベントポイントの獲得量を出し、交換所の周回計算の周回数と AP をボーナス込みにする。

## ADDED Requirements

### Requirement: ボーナスの入力
システムは、ロトの無い交換所イベントの交換所の周回計算に、交換所の通貨ごとと、イベントポイントの品目（そのイベントにあるとき）の「1ドロップにつき +N」を入れる欄を設けなければならない (SHALL)。値は 0 以上の整数とし、初期値は 0 とする (SHALL)。負の数・小数・数でない値は 0 以上の整数に直さなければならない (SHALL)。入れた値は画面を開いている間だけ持ち、保存してはならない (SHALL NOT)。礼装の所持を入れる欄を設けてはならない (SHALL NOT)。欄の近くには、短い見出し（「ドロップ増加礼装」）と、何を入れると何が変わるか（例:「編成した礼装の 1ドロップにつき +N を入れると、1周の獲得量と周回数がボーナス込みになります」）を1行で示さなければならない (SHALL)。ボーナスをサーヴァントの効果として示してはならない (SHALL NOT)。

#### Scenario: 通貨とポイントの欄
- **WHEN** 交換所の通貨が3種類あり、イベントポイントの品目があるイベントを開いたとき
- **THEN** 3種類の通貨とイベントポイントの品目のそれぞれに、初期値 0 のボーナスの欄が表示される

#### Scenario: 見出しと説明
- **WHEN** 利用者が交換所の周回計算を開いたとき
- **THEN** ボーナスの欄の近くに「ドロップ増加礼装」の見出しと、入れると1周の獲得量と周回数が変わることを示す1行が表示される

#### Scenario: ポイントの品目が無いイベント
- **WHEN** イベントポイントの品目が無いイベントを開いたとき
- **THEN** ボーナスの欄は交換所の通貨の分だけ表示される

#### Scenario: 不正な値
- **WHEN** 利用者がボーナスの欄に -3 や 2.5 を入れたとき
- **THEN** 値はそれぞれ 0 と 2 として扱われる

### Requirement: ボーナス込みの1周の獲得量
システムは、ドロップの統計があるクエストごとに、交換所の通貨とイベントポイントの品目の1周あたりの獲得量を、ボーナス込みで小数1桁に丸めて表示しなければならない (SHALL)。ボーナス込みの1周の獲得量は「素の1周の期待値 + 1周あたりのドロップ回数 × その品目のボーナス」でなければならない (SHALL)。ボーナスはドロップ1回ごとに足し、1周の合計に1回だけ足してはならない (SHALL NOT)。どの通貨もイベントポイントも落ちないクエストは表に出さない。

#### Scenario: 1周に複数回落ちる通貨
- **WHEN** あるクエストで、ある通貨の素の1周の期待値が 15.0、1周あたりのドロップ回数が 5.0 で、利用者がその通貨のボーナスに 2 を入れたとき
- **THEN** そのクエストのその通貨の1周の獲得量は 25.0 と表示される

#### Scenario: イベントポイント
- **WHEN** あるクエストで、イベントポイントの素の1周の期待値が 600、1周あたりのドロップ回数が 3.0 で、利用者がポイントのボーナスに 100 を入れたとき
- **THEN** そのクエストのイベントポイントの1周の獲得量は 900.0 と表示される

#### Scenario: ボーナスが0のとき
- **WHEN** すべてのボーナスが 0 のとき
- **THEN** 各クエストの1周の獲得量は素の1周の期待値と同じである

#### Scenario: 通貨もポイントも落ちないクエスト
- **WHEN** あるクエストのドロップに、交換所の通貨もイベントポイントの品目も無いとき
- **THEN** そのクエストは1周の獲得量の表に出ない

### Requirement: 交換所の周回計算への反映
システムは、交換所の周回計算（周回の内訳のクエストごとの周回数、合計の周回数と AP、通貨ごとの見込み獲得量、AP 予算）を、ボーナス込みの1周の獲得量で求めなければならない (SHALL)。すべてのボーナスが 0 のときは、ボーナスの機能が無いときと同じ結果を出さなければならない (SHALL)。周回の内訳の近くの注記は、ドロップの統計がイベントのボーナスを含まない値であることを示したうえで、ボーナスを1つでも入れたときは、入れたドロップ増加礼装のボーナス（1ドロップにつき +N）を足して計算していることを示さなければならない (SHALL)。

#### Scenario: ボーナスで周回数が減る
- **WHEN** ある通貨の必要量が 300 で、その通貨を落とすクエストが1つだけ（素の1周の期待値 10.0、1周あたりのドロップ回数 5.0）あり、利用者がその通貨のボーナスに 2 を入れたとき
- **THEN** 1周の獲得量は 20.0 として解かれ、周回の内訳の周回数は 15 周、見込み獲得量は 300 以上になる

#### Scenario: ボーナスが0のとき
- **WHEN** すべてのボーナスが 0 のとき
- **THEN** 周回の内訳・合計・見込み獲得量・AP 予算は、ボーナスの機能が無いときと同じである

### Requirement: ドロップ回数が無いデータ
システムは、イベントデータの取り込みで、各ドロップの1周あたりのドロップ回数を保存しなければならない (SHALL)。1周あたりのドロップ回数を持たないドロップ（取り込み直す前のデータ）にはボーナスを足してはならず (SHALL NOT)、素の1周の期待値で計算しなければならない (SHALL)。ボーナスが入っていて、その品目にドロップ回数を持たないドロップが1つでもあるときは、ボーナスを反映できない品目があることを表示しなければならない (SHALL)。

#### Scenario: 取り込み直す前のデータ
- **WHEN** ドロップがどれも1周あたりのドロップ回数を持たないイベントで、利用者がある通貨のボーナスに 2 を入れたとき
- **THEN** その通貨の1周の獲得量と周回の内訳は素の値のまま出て、その通貨にボーナスを反映できないことが表示される

#### Scenario: 取り込みの値
- **WHEN** Atlas のクエストのドロップで、ある通貨の runs が 100、dropCount が 500、num が 3 のとき
- **THEN** 取り込んだそのドロップの素の1周の期待値は 15、1周あたりのドロップ回数は 5 である
