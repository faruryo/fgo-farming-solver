## Context

**今の保存の形**

- 育成計算機の保存値（localStorage の `material`、型は `hooks/create-chaldea-state.ts` の `ChaldeaState`）は、サーヴァントの ID ごとに「未所持かどうか」の印（`disabled`。`true` が未所持）と、再臨・スキル・アペンドスキルの今の値と目標の値を持つ。カードの「✓ 所持 / 未所持」の切り替え（`components/material/servant-card.tsx` の `toggleOwned`）はこの印だけを反転する
- Lv・宝具Lv を入れる場所は無い
- `material` はクラウド同期の対象（`lib/constants/storage-keys.ts` の `CLOUD_SYNC_KEYS`）で、同期の縮小ガード（`lib/cloud-sync/shrink-guard.ts`）は `material` と `posession` の中身を数えている

**今のクラウド同期の作り**（main のコードを読んで確かめた。決定2 の前提）

- 保存内容は、同期するキー（`CLOUD_SYNC_KEYS` の 23 個）ごとの localStorage の文字列をそのまま並べた表と、保存した時刻・端末の ID の組。`/api/cloud` はこの本文を中身を見ずに KV に置き、同じ本文を日ごとのスナップショット（D1）にも書く。サーバーの側にキーの一覧は無い
- 保存（`hooks/use-cloud-sync.ts` の `handleSave`）は、自分の版が知っているキーだけを集めて、クラウドの保存内容をまるごと置き換える。キーごと・サーヴァントごとの合成はしない
- 取り込み（同じファイルの `applyData`）は、クラウドの保存内容のうち自分の版が知っているキーだけを localStorage に書き、キーごとに通知を出して表示中の画面を更新する。クラウドの保存内容に無いキーは、端末から消さない
- 新旧は端末ごとの記録（最後に編集した時刻と最後に同期した時刻）で決める（`lib/cloud-sync/decision.ts`）。クラウドのほうが新しく、端末に未同期の編集が無ければ自動で取り込む。未同期の編集があれば競合として利用者に選ばせる。一度も同期していない端末に編集があり、クラウドにもデータがあれば、食い違いの画面（`components/cloud/divergence-dialog.tsx`）を出す
- 縮小ガード（`lib/cloud-sync/shrink-guard.ts`）は、保存しようとする内容とクラウドの今の内容を、所持のサーヴァントの数・所持している素材の種類の数・消えたキーの数（2 個以上）の3つで比べ、大きく減る保存を止めて確かめの画面（`components/cloud/shrink-guard-dialog.tsx`）を出す。サーヴァントと素材は「10 以上減って、半分以下になる」で止まる
- 食い違いの画面と同期の管理画面（`/cloud`）の見比べは、端末とクラウドの規模（所持のサーヴァントの数、スキルの合計、素材の数。`components/cloud/parts/stats-logic.ts`）を並べる。縮小で止まっているときの同期の管理画面は、キーごとの項目の数も並べる（`lib/cloud-sync/storage-diff.ts`。同期するキーの一覧から作る）
- 同期するキーへの書き込みは、キーを指定した通知が出れば、未同期の編集として記録され、自動同期が有効なら 5 秒後に保存される。`useLocalStorage`（`hooks/use-local-storage.ts`）は書き込みのたびにこの通知を出すが、既定では、開いたときにまだ無いキーへ初期値を書き、その書き込みでは通知を出さない。`lazyWrite` を付けた hook は、返した setter が呼ばれるまで書かず、まだ無いキーへの最初の書き込みでも通知を出す（品目の欲しい・いらないの設定の `hooks/use-item-want-setting.ts` がこの形）
- 縮小ガードが比べるクラウドの内容は、この端末が最後に取得したもの（開いたとき、タブに戻ったとき、自分の保存の直後に取得する）。保存の直前には取り直さない

**実測（2026-11-14、この6枚と Atlas の公開データで測った）**

2回に分けて測った。1回目ははじめの2枚（まるごと写った 42 枚のカード）で比べ方を選び、2回目は6枚（まるごと写った 120 枚のカード）で、選んだ比べ方と読み方を「決めたこと」の手順のとおりに通した（段を探す範囲だけは、隠れた段と切れた段の差も見るために、見出しの下から顔の正方形が画像に収まるいちばん下まで広げた）。下の表は、どちらの回の値かを書いてある。

1回目の測り方: repo の外に置いた使い捨てのスクリプトで、main にある `lib/shop-screenshot-import/icon-match.ts` の関数（`integralImage`・`cropCells`・`downscaleIcon`・`iconPixelDiff`・`rawPixelDiff`）をそのまま呼び、Atlas の `nice_servant`（JP）から取った顔のアイコンと、まるごと写った 42 枚のカード（2枚 × 3段 × 7列）の顔の部分を比べた。文字認識は、アプリが使っている部品（`ppu-paddle-ocr/web`、`lib/possession-import/ocr-engine.ts` と同じ既定の設定）をヘッドレスの Chromium で動かして測った。当たったサーヴァントが正しいかは、切り抜きと当たったアイコンを並べて目で確かめた。

2回目の測り方: 同じ `icon-match.ts` の関数と `lib/possession-import/ocr-engine.ts` の `recognizeWithBoxes` を1つにまとめてヘッドレスの Chromium で動かし、画像とアイコンの画素は canvas で読んだ。見出しは画像をまるごと読んで探し、段は顔の照合で探し、カードは 27 通りの切り出しで照合し、文字の帯は 2 倍、画面の上の表示は等倍で読んだ。正しいかは、1回目と同じく切り抜きと当たったアイコンを並べた一覧と、元の画像の文字を目で見て確かめた。切り出しと一時ファイルは確かめのあとに消した。

## Goals / Non-Goals

**Goals:**

- 実物の6枚で測った値で、読み取り（画面の見分け、格子、顔の照合、文字）を決める
- 測れていない点を1か所に並べ、そこは「読めなかった画像」か「要確認」に倒す
- Lv と宝具Lv は下がらないことと画面の作り（並び、上限、所持数）を使って読み取りの結果を検査し、引っかかった行を「要確認」に回す（issue のオーナーのコメント、2026-11-14）
- 既存の `ChaldeaState` の形と、育成計画の値を変えない
- スマホで取り込んだ Lv・宝具Lv を、同じアカウントの PC の育成計算機のカードで見られるようにする（決定2）。同期の方式（保存内容をまるごと入れ替える、新旧と競合の決め方）は変えない

**Non-Goals:**

- スキルLv・アペンドスキルLv・フォウの取り込み（オーナーの指定で範囲の外）
- レイドの編成計算・ダメージ計算（別 issue）
- Lv・宝具Lv を取り込みを通さずに手で直す画面と、Lv・宝具Lv での並べ替え・絞り込み・専用の一覧のページ。見る場所は育成計算機のカードの表示だけにする（下の「一覧での表示」）。使う側（編成計算）を作る issue で出す
- Lv・宝具Lv を端末の間でサーヴァントごとに合成すること（下の「クラウド同期」）
- 取り込みで「所持」を「未所持」に戻すこと（写っていないサーヴァントは変えない）
- 「サーヴァント強化」の選択画面のほかの画面（マイルームの霊基一覧など）と、7 列でない表示の読み取り

## Decisions

### 判断点

残る判断点は無い。前の版の判断点（1・2・5・8・9・10）は、オーナーが 2026-11-14 に全部決めた（1=A、2=B、5=A、8=A、9=A、10=A）。番号は前の版から引き継ぎ、下の「決めたこと」に「決定1」「決定2」…として同じ番号で書いた。3・4・6・7 は前の版までに取り下げてある（3: スキルLv は範囲の外、4: 同じサーヴァントを複数持つ場合は一番強い 1 騎、6: 格子は顔の照合で探す、7: 実物が届いた）。

決定2（クラウド同期）に合わせてこの版で決めた細かい点（保存値の載せ方、端末の間の新旧、縮小ガード、古い版のアプリ、一覧での表示）は、案が分かれるものも推奨を1つ選び、「決めたこと」の「クラウド同期」「一覧での表示」に採らなかった案と理由とともに書いた。オーナーの指定（判断点を増やさない）による。

### 決めたこと

#### 決定1: 「所持」は育成計算機の既存の所持の印に書く（オーナーの決定、案A）

入れたサーヴァントの既存の所持の印（`material` の中）を「所持」にする。Lv・宝具Lv は新しい保存先に置く。

確かめの画面のいちばん上の行:

```text
│ 12枚を読みました　当てた 243 騎 / 要確認 5 行　新しく所持になる 31 騎 │
│ （確定すると、育成計算機の 31 騎のカードが「✓ 所持」になり、必要な素材の合計に入る）
```

| 採らなかった案 | 中身 | 採らなかった理由 |
|---|---|---|
| B | 所持も新しい保存先だけに持ち、既存の所持の印は変えない | 育成計算機の「所持」と取り込んだ所持が別物になり、利用者がどちらを見ればよいか分からなくなる |
| C | `ChaldeaState` のサーヴァントごとの値に Lv・宝具Lv の欄を足す | 既存の保存値の補い方（`hooks/use-chaldea-state-merger.ts`）が新しい欄を知らず、欄が落ちるか、型の変更が育成計算機の全体に広がる |

根拠: issue は「取り込んだサーヴァントを所持にし」と書いており、このアプリで「所持」を表すのは既存の印だけ。印の反転は今のカードの操作と同じ書き込みなので、育成計画の今の値と目標の値には触れない。新しく「所持」になったサーヴァントは育成計算の対象に入り、必要な素材の合計が増える（カードを手で「所持」にしたときと同じ動き）。確かめの画面に「新しく所持になる N 騎」を出して、確定の前に見えるようにする。

#### 決定2: Lv・宝具Lv をクラウドに同期する（オーナーの決定、案B）

オーナーの言葉: 「基本スマホから入力するけど PC からみたい」。スマホで取り込んだ Lv・宝具Lv が、同じアカウントの PC に同期で届き、PC の育成計算機のカードで見える。載せ方は下の「クラウド同期」、PC で見る場所は下の「一覧での表示」。

| 採らなかった案 | 中身 | 採らなかった理由 |
|---|---|---|
| A | 端末だけに保存する（交換所の入力と同じ扱い） | PC で見るには PC でも画像を選んで取り込み直すことになり、オーナーの使い方（入力はスマホ、見るのは PC）に合わない |
| C | `material` の中に入れて同期に乗せる | 決定1 の案C と同じ。`ChaldeaState` の形は変えない |

#### 決定5: 顔のアイコンの照合用のデータは更新ジョブで作って1回で配る（オーナーの決定、案A）

マスターデータの更新ジョブが顔のアイコンを 16×16 に縮めたデータを作って `MASTER_DATA` の KV に置き、API のルートから1回で配る。画像を選んだあとの進み具合は「照合用のデータを読み込んでいます…」「画像を読み取っています 3 / 12」の順に出す。

| 採らなかった案 | 中身 | 採らなかった理由 |
|---|---|---|
| B | 交換所の取り込みと同じく、画像を選んだあとに端末が Atlas から全部取る | 初回に 2,065 枚・約 68MB（iPhone の通信とメモリ）。取得の失敗が照合の失敗になる |
| C | カードのクラスのアイコンと星でサーヴァントの候補を絞ってから、その候補だけ端末が取る | クラスと星を読む照合が別に要り、その読み違いが顔の照合の前に入る。絞っても1クラスで数百枚になる |

根拠: 縮めた画素は 1 枚 1,024 バイトで、2,065 枚で約 2.1MB。配る形（JSON、下の「照合用のデータ」）では約 2.8MB（圧縮前）になり、KV の1つの値に入る。顔のアイコンは 128×128 の PNG なので、8×8 の升目の平均で 16×16 になり、実測で使った `downscaleIcon` と同じ計算になる。生成物を repo に置かないのは、サーヴァントが増えるたびにバイナリの差分が git に溜まるため。取りこぼすもの: 更新ジョブに段が1つ増える。本番では、マージのあとに更新ジョブが1回走るまで使えない。新しいサーヴァントは、次に更新ジョブが走るまで当たらない（「要確認」になり、手で選べる）。

#### 決定8: 入力は「サーヴァント強化」の選択画面だけ。「宝具Lv.順」を主に案内し「Lv.順」も受け付ける（オーナーの決定、案A）

画像を選ぶ段の案内:

```text
│ ゲームの「サーヴァント強化」でサーヴァントを選ぶ画面を、並びを          │
│ 「宝具Lv.順」にして、上から下まで少しずつ重ねて撮ってください。          │
│ 宝具Lv と Lv の両方を読み取ります。                                     │
│ 「Lv.順」の画像も読めますが、その画像からは Lv だけを取り込みます。       │
│                                        [ 画像を選ぶ（複数可） ]          │
```

| 採らなかった案 | 中身 | 採らなかった理由 |
|---|---|---|
| B | 「宝具Lv.順」の画像だけを受け付ける | Lv.順で撮った画像は撮り直しになる。並びを見分ける読み取りが1つ増える |
| C | マイルームの霊基一覧も受け付ける | 霊基一覧の実物の画像が無く、見出しも違うので、目印と寸法を別に測ることになり、実装が遅れる |

根拠: 実物で、宝具Lv.順の画面はカードの上に宝具Lv、下に Lv が同時に出て、Lv.順の画面は上に Lv だけが出ると確かめた。値の種類は文字の形（下の「値の読み取り」）で決まるので、並びを見分ける読み取りを足さずに両方の画像を受け付けられる。Lv.順の画像だけを選んだ利用者は、宝具Lv が入らない（確かめの画面の「宝具Lv —」で分かる）。issue の題は「霊基一覧」だが、オーナーが実物として渡したのは強化の選択画面で、所持しているサーヴァントが全部並ぶ点は同じ。

#### 決定9: 再臨の段階ごと・霊衣の顔のアイコンを全部候補にし、同じサーヴァントに束ねる（オーナーの決定、案A）

再臨の段階ごと（4 枚）と霊衣の顔のアイコンを全部候補に入れ、同じサーヴァントの ID に束ねる。決め方はサーヴァントどうしの比で、どの段階・霊衣に当たったかは保存しない。

| 採らなかった案 | 中身 | 採らなかった理由 |
|---|---|---|
| B | 最終の段階の顔のアイコンだけを候補にする（478 枚、配る形で約 0.7MB） | 霊衣・途中の段階のカードが全部「要確認」になり、数百騎では数十行を手で選ぶことになる（実測で 120 枚のうち 16 枚、約 13% が最終の段階でない絵だった） |
| C | 案A に加えて、当たった段階・霊衣も保存する | 画面の絵はゲームの表示の設定で選べるもので、育成の進み（再臨の段階）を表さない。育成計画の再臨の値と紛らわしい値が増え、使う側が無い |

根拠: 実測で、全部の段階と霊衣を候補にしても、当たったアイコンとの差（120 枚で 7.4 以下）と別のサーヴァントとの差（20.1 以上）は分かれた。候補が増えても取り違えは出ていない。同じサーヴァントを複数持つ 5 騎では、育てていない個体が第1段階、育てた個体が最終の段階や霊衣の絵で出ていて、段階をまたいで同じ ID に束ねないと「一番強い 1 騎」を選べない。取りこぼすもの: 照合用のデータが 4 倍強（配る形で約 2.8MB）になる。

#### 決定10: 並びの項目と向きは、画像ごとに画面右上の表示を読む（オーナーの決定、案A）

並び順の検査（下の「読み取り結果の検査」）は、画像の並びの項目（宝具Lv.順か Lv.順か）と向き（降順か昇順か）を知らないと行えない。画像ごとに、画面右上の並びの項目と向きの表示を切り出して読む。どちらかを読めなかった画像は並び順の検査に入れず、その枚数を知らせる。選ぶ段に並びを選ぶ欄は置かない。

```text
│ 確かめの画面: 27枚を読みました　当てた 540 騎 / 要確認 6 行                       │
│               並びを読めなかった画像: 1枚（この画像は並び順の検査をしていません）   │
```

| 採らなかった案 | 中身 | 採らなかった理由 |
|---|---|---|
| B | 選ぶ段で、利用者が項目と向きを選ぶ | 選んだ画像の全部に同じ並びを当てるので、宝具Lv.順と Lv.順の画像を一緒に選ぶ使い方（決定8）に合わない。選び間違えると、並び順に合わない読みが大量に出る |
| C | 項目はカードの上の文字の種類、向きはつないだ並びの先頭と末尾の値の大小で決める | 検査する値そのもので検査の前提を決めることになる。先頭か末尾の1枚を読み違えると向きを取り違え、ほとんどの行が「要確認」になる |

根拠: 実測で、切り出して読めば並びの項目も「降順」も6枚とも確からしさ 0.96 以上で読めた（Context の「画面の上の表示」）。画像をまるごと読んだ結果には「降順」が出なかったので、切り出して読む。画面の表示は撮った時点の並びそのものなので、利用者の記憶（案B）や読んだ値（案C）より確かで、画像ごとに並びが違っても扱える。読めなかったときに検査を止めるだけで値は今までどおり読むので、測れていない「昇順」や別の端末で外しても、間違った値が入るほうには倒れない。取りこぼすもの: 文字の読みが画像1枚につき2つ増える（実測で1つ約 60〜200 ミリ秒）。

**読み取りの流れ**（画像1枚ごと）

0. 照合用のデータを読み込めていなければ、画像を1枚も読まずに、読み込めなかったことを知らせて終わる（段の位置を顔の照合で探すので、データが無いとカードを取り出せない）
1. 画像を canvas に描き、枠つきの文字認識を1回かけて、見出し「強化するサーヴァントを選択してください」の枠を探す
2. 見出しの枠から長さの単位と格子の横の位置を決め、顔の照合で段の位置を探す（下の「画面の見分けと格子」）
3. 段ごとに7枚のカードの顔を照合する（下の「顔の照合」）
4. カードごとに上と下の文字の帯を切り出し、拡大して文字認識にかけ、値を読む（下の「値の読み取り」）
5. 画面の上の表示（所持数、並びの項目、並びの向き）を切り出して読む（下の「画面の上の表示」）
6. 確かめの画面に出すカードの切り抜き（小さな画像）だけを残し、画像の canvas と画素の配列は次の画像に進む前に手放す

すべての画像を読んだあとに、画像をつなぎ、読みを検査し、サーヴァントごとにまとめる（下の「画像のつなぎ」「読み取り結果の検査」「まとめ」）。

交換所の取り込み（`lib/shop-screenshot-import/analyze.ts`）は canvas を最後まで持っているが、この取り込みは数十枚になるので持たない。issue の「iPhone で多数の画像を一度に読むときのメモリ」への答えはこれで、iPhone の実機では測れていない（下の「測れていない点」）。

**画面の見分けと格子**

- 見出し「強化するサーヴァントを選択してください」が読めた画像だけを読む。読めなければ「読めなかった画像」として知らせ、何も取り出さない。実測で、この見出しは6枚とも同じ枠に確からしさ 1.00 で読めた。見出しの見分けは、1つの枠の文字から空白と記号を除いたものが「強化するサーヴァントを選択」を含むかで行う（列の位置を枠の左端から測るので、文の頭から読めた枠だけを使う。ほかの選択画面の見出しや、2つの枠に分かれて読めた見出しは当たらず、「読めなかった画像」になる）
- 長さの単位は見出しの枠の高さ。顔の一辺、列の間隔、いちばん左の列の位置、文字の帯の位置は、Context の「画面の寸法」の倍数で持つ。倍数は1つの場所の定数に置く。列は7つ
- 段の位置は文字では決めない（画像をまるごと読む文字認識では、カードの文字が枠にならなかった）。次の順で探す
  1. 上の文字の帯が格子の上の端（Context の「画面の寸法」）より下に来るいちばん上の位置から、下の文字の帯の下端が画像に収まるいちばん下の位置まで、顔の正方形を縦に顔の一辺の 2%（実測の 4 画素）ずつずらす。位置ごとに、7つの列の決めた位置の切り出し（列ごとに1つ。位置や一辺は振らない）を全候補と比べ、7つの列のうちいちばん小さい差をその位置の差とする（最後の段はカードが1枚だけのことがあるので、1つの列が当たれば段とする）
  2. 差が上限（下の「顔の照合」の 10）以下の位置を拾う。拾った位置どうしが段の間隔の半分より近ければ同じ段として、差がいちばん小さい位置だけを残す。実測で、上限以下になるのは段ごとに続いた 1〜5 つの位置だけだった
  3. 残した位置を段とし、段ごとに7つの列を照合する（下の「顔の照合」の 27 通りの切り出しで、ずらした刻みのずれを吸収する）
- 下の文字の帯の下端が画像の下の端からはみ出す段（途中で切れた段）は読まない。続けて撮った次の画像にまるごと写る。顔の正方形だけが収まる位置を試さないのは、実測で、4 画素だけ切れた段の 7 枚のうち 3 枚だけが当たり、残りが「要確認」のカードになったため
- 上の文字の帯が格子の上の端より上に来る段（上の端で見出しやボタンの帯に隠れた段）は読まない。こういう段は下の Lv の文字だけが見えて、宝具Lv の文字が見えない。実測の3枚では、顔の半分以上が隠れていて差が 30.5 以上になり、位置を試しても段にならなかった。位置で決めるのは、顔が少しだけ隠れた段（比べる升目は隠れず、上の文字だけが隠れる）を、宝具Lv の無いカードとして読まないため
- 段が1つも見つからない画像は「読めなかった画像」として知らせる（7 列でない表示、照合用のデータに無いカードだけの画像を含む）
- 時間は、実測から、画像をまるごと読むのに約 1 秒、段を探すのに 2.2〜4.0 秒、カードの照合に 1 枚約 70 ミリ秒（21 枚で約 1.5 秒）、文字の帯に 1 つ約 0.1 秒（42 個で約 4〜5 秒）、画面の上の表示に約 0.3 秒で、画像1枚あたり約 10 秒の見込み（Node とデスクトップの Chromium の値）

**顔の照合**

- 比べ方は、切り出しを 16×16 に縮め（`cropCells`）、明るさをそろえずに RGB の差の絶対値の平均を取る（`rawPixelDiff`）。明るさをそろえる `iconPixelDiff` は使わない（実測で 4 / 42 しか当たらなかった）
- 比べる升目は、16×16 のうち上から 4〜11 番目の段（8 段）で、左から 4〜16 番目の列（13 列）の 104 升。上の文字とクラスのアイコン、左の鍵と星のバッジ、下の星・Lv の文字・帯・「PARTY」・「+50%」が重なる升目を除いたもの。除く升目は、照合用のデータを読み込んだあとに候補の側で透明にしておく（`rawPixelDiff` は不透明な升目だけを比べるので、関数を足さずに済む）
- 探す幅は、段と列で決めた位置のまわりで、位置と一辺を ±5% の中で 5% 刻みに振る 27 通り。全候補と比べる。実測で、広く探す2段の探し方と 42 枚とも同じ結果になった
- 候補は、育成計算機の一覧にいるサーヴァント（保存値に所持の印を書ける ID）のアイコンだけにする。照合用のデータにあっても一覧にいない ID は候補にしない
- 決め方は、アイコンどうしではなくサーヴァントどうしで比べる。サーヴァントごとに一番近いアイコンの差を取り、一番近いサーヴァントの差が上限 10 を超えれば「要確認」（どのサーヴァントにも近くない）、超えなければ、一番近いサーヴァントの差 ÷ 次に近い別のサーヴァントの差が 0.5 以下なら決め、超えれば「要確認」（顔の差が小さい）にする。実測は、まるごと写った 120 枚が差 7.4 以下・比 0.24 以下、別のサーヴァントが差 20.1 以上、空いた位置が差 30.2 以上。上限と比のしきい値は1つの場所の定数に置く
- 段の中で、差が上限を超え、文字の帯からも値（「数字/数字」の形）が1つも読めなかった位置は、カードが無い位置（一覧の最後の段の空き）として捨てる。値が読めた位置は「要確認」のカードにする。値でない文字が読めただけの位置は捨てる（実測で、空いた位置の背景が「X」と読めた）

**値の読み取り**

- カードごとに、上の帯と下の帯（Context の「画面の寸法」）を切り出し、2 倍に拡大して文字認識にかける。実測で、2 倍で「数字/数字」が全部読め、3 倍にしても変わらず、時間は倍になった
- 帯の文字から「数字/数字」の形を探し、まわりの文字（「Lv」「宝具」など）は使わない。実測で、まわりの文字は崩れることがあり、数字は崩れなかった
- 値の種類は右の数字（上限）で決める。上限が 5 で、同じ帯の文字に「宝」か「具」があれば宝具Lv、上限が 20〜120 なら Lv。左の数字（今の値）を値にする。ゲームの Lv の上限は、再臨していない星1の 20 がいちばん小さく（星5 は 50、星4 は 40）、宝具Lv の上限 5 と重ならない。実測で、宝具Lv の帯は 99 個とも「宝具」が読めていた。「宝」「具」を求めるのは、宝具Lv.順と Lv.順のほかの並びで、カードに「数字/5」の形の別の値が出たときに、宝具Lv として黙って入れないため
- 上限が 5 なのに「宝」も「具」も無い、上限が 5 でも 20〜120 でもない、今の値が上限より大きい、今の値が範囲（Lv は 1〜120、宝具Lv は 1〜5）に無い読みは、その種類の値を決めない（値が範囲に無い）。Lv の上限が、上限になりうる数（20 から 90 までの 5 刻みと、92 から 120 までの 2 刻み。Context の「Lv の上限の取りうる値」）でない読みも同じ扱いにする（「83/87」など）。そのカードの読みは、下の「読み取り結果の検査」で通らなかった読みになる
- 1つの帯に「数字/数字」の形が2つ以上あるときは、確からしさのいちばん高いものを使う
- 帯から値が読めなかった種類は「無い」とする。Lv.順の画像では、下の帯に文字が無いので宝具Lv が「無い」になり、Lv だけが入る（決定8）
- どの種類も読めなかったカードは、サーヴァントだけを当てたカードになる

**画面の上の表示**

- 見出しの枠から、Context の「画面の寸法」の倍数で、所持数・並びの項目・並びの向きの3つの矩形を決め、それぞれ等倍で文字認識にかける（画像をまるごと読んだ結果は使わない。実測で「降順」が出ず、所持数が崩れた）。倍数はほかの寸法と同じ場所の定数に置く
- 並びの項目: 読めた文字から空白と記号を除き、「順」を含んで「宝」か「具」を含めば宝具Lv.順、「Lv順」（大文字と小文字は区別しない）に一致すれば Lv.順とする。どちらでもなければ（ほかの並び、読み違い）、項目は読めなかったものとする
- 並びの向き: 読めた文字が「降順」を含めば降順、「昇順」を含めば昇順。どちらでもなければ読めなかったものとする
- 並びの項目の値は、宝具Lv.順なら宝具Lv の今の値、Lv.順なら Lv の今の値（実測で、Lv.順の画面は上限ではなく今の値で並んでいた）
- 項目か向きを読めなかった画像は「並びを読めなかった画像」とし、並び順の検査と枚数の検査に入れない。カードの値は今までどおり読んで、まとめに入れる。確かめの画面に枚数を出す（決定10）
- 所持数: 矩形の文字から「数字/数字」の形を探し、左の数字を所持数とする。読めなければ「無い」とする

**画像のつなぎ**（並びの項目と向きが同じ画像の集まりごとに）

- 画像ごとの段を、上から順の並びとして持つ。2つの段は、カードのある位置が同じで、両方で当たった位置のサーヴァントがすべて同じで、両方で当たった位置が1つ以上あれば、同じ段とする（値の読みは比べない。片方で「要確認」になった位置は問わない）
- 2枚の画像は、片方の段の並びをもう片方に対して縦にずらしたとき、重なる段（1段以上）がすべて同じ段になるずらし方があれば、つながるとする。ずらし方が2つ以上あれば、つないだ並びで並び順に合わないカード（下の「読み取り結果の検査」）がいちばん少ないものを使い、それも同じなら重なる段がいちばん多いものを使う
- つながる画像をつないで、段の1本の並び（つながり）にする。重なった段のカードは1枚のカードとして数え、画像ごとの読みをそのカードの読みとして全部持つ
- つながりが2つ以上あるとき（間に重なりが無い）は、先頭のカードの並びの項目の値、同じなら末尾のカードの値で順に並べて（降順の画面なら大きいほうを先、昇順なら小さいほうを先。それも同じなら選んだ順）、1本の並びにする。値を持たないカードは飛ばして、値を持ついちばん近いカードで比べる
- つなぎは並び順の検査と枚数の検査のためだけに使う。取り込む値は下の「まとめ」で読みの組から決めるので、つなぎを取り違えても、読んでいない値が入ることは無い。ただし、取り違えで並び順に合わないとされた読みは取り込む値の候補から外れるので、合っている読みが外れて「要確認」が増えることと、同じサーヴァントを複数持つ場合に弱い個体の値が入ること（Risks）はありうる

**読み取り結果の検査**（オーナーのコメントの検査。Lv と宝具Lv は下がらない）

読みごと（1枚の画像の1枚のカード）に次を見る。1つでも引っかかった読みを「通らなかった読み」とする。

| 検査 | 引っかかる読み | 理由の表示 |
|---|---|---|
| 値の範囲 | 上の「値の読み取り」で値が範囲に無かった読み（今の値が上限を超える、宝具Lv が 1〜5 でない、Lv の上限が上限になりうる数でない、など） | 値が範囲に無い |
| レア度 | 当てたサーヴァントのレア度（育成計算機の一覧が持つ値）で上限になりうる数（Context の表と、再臨の段階ごとの上限）に、読んだ Lv の上限が無い読み。星5 のサーヴァントに「85/85」など。顔が「要確認」のカードでは見ない | Lv の上限がレア度に合わない |
| 並び順 | 1本の並びの中で、並び順に合わない読み（下） | 並び順に合わない |

並び順に合わない読みの決め方:

- 1本の並びのカードのうち、並びの項目の値を持つもの（値の範囲とレア度の検査を通った読みがあり、その値が1つに決まるもの）を、読んだ順（上の段から、段の中は左から）に並べる
- 降順の画面なら値が増えない並び、昇順なら値が減らない並びになるように、いちばん少ない枚数のカードを外す。外し方が2通り以上あれば、どれかの外し方で外れるカードをすべて外す。外れたカードの読みが、並び順に合わない読み（「5・5・3・5・5」なら 3 のカード、「3・5」だけならどちらとも決まらないので両方。「5・3」は降順に合っているので外さない）
- 重なった段で1枚のカードに値の違う読みが2つ以上あるときは、そのカードを上の並びに入れず、読みごとに、前後の外れなかったカードの値の間に無ければ並び順に合わない読みとする

推定できる値（「要確認」の行に候補として添える）:

- 並び順か値の範囲で通らなかった読みの、並びの項目の値について、同じ1本の並びで前後のいちばん近い外れなかったカードの値を見る。前後が同じ値なら、その値を推定した値とする。違えば、値は決めずに、前後の値の範囲（「90〜100 のはず」）を添える。前か後ろが無い（並びの端）ときは、ある側の値を範囲の端として添える
- 並びの項目でない種類の値（宝具Lv.順の画像の Lv）と、並びを読めなかった画像の値は、前後から推定しない

前に取り込んだ保存値との比較は、読みごとではなく、取り込む 1 騎を決めたあとに行う（下の「まとめ」）。

**枚数の検査**

- 並びの項目と向きが同じ画像の集まりごとに、つないだあとのカードの数（当てたカードと「要確認」のカード。捨てた空きの位置と、切れた段は数えない）を数え、いちばん多い集まりの数を「読めたカードの数」とする
- 所持数は、読めた画像の所持数がすべて同じなら、その数。1枚も読めないか、画像の間で違えば、枚数の検査をしない
- 読めたカードの数が所持数より少なければ、確かめの画面に「所持サーヴァント N のうち K 枚を読みました。撮り漏れがないか確かめてください」と知らせる。確定は止めない。多いか同じなら何も出さない
- 所持数がサーヴァントでないもの（種火など）を数えているか、フィルターで絞った表示で所持数が変わるかは、実物で確かめていない（下の「測れていない点」）。確かめるまでは、知らせるだけにして確定を止めない。実装のあとの実地の確かめ（tasks.md の 5.3）で実物と比べ、合うと分かってから厳しくするかを決める

**まとめ**（選んだすべての画像をまたいで。同じサーヴァントを複数持つ場合はオーナーが決めた: 一番強い 1 騎だけを取り込む）

- カードごとの読みは、Lv と宝具Lv の組（どちらも無くてよい）。当てたサーヴァントごとに集める
- 通らなかった読み（上の「読み取り結果の検査」）は、取り込む値の候補から外す
- どちらの値も無い読み（サーヴァントだけを当てたカード）は、同じサーヴァントにほかの読みがあれば捨てる。無ければ、値の無い1つの行にする
- 残った読みのうち、一番強い組を取り込む値にする。比べる順は、宝具Lv が高いほう、同じなら Lv が高いほう。無い値は、どの値よりも低いものとして比べる。ほかの組は捨て、「要確認」にも候補にもしない。続けて撮った画像の重なり（同じ組）、別の個体、片方の画像での読み違いを見分けずに、この1つの決まりで扱う
- 通った読みが1つも無く、通らなかった読みだけがあるサーヴァントは、行を捨てずに「要確認」にする。通らなかった読みのうち一番強い組（通らなかった種類の値は無いものとして比べる）を行の元にし、通った種類の値は入れたまま、通らなかった種類の欄を空にして、理由と、候補（読んだ値が 1〜120・1〜5 の範囲にあればその値、推定した値があればその値）を添える
- 取り込む 1 騎の値が決まった行は、前に取り込んだ保存値と比べる。Lv か宝具Lv が保存値より低ければ、その行を「要確認」（前に取り込んだ値より低い）にし、低かった種類の欄を空にして、読んだ値と保存値を候補にする。読みに無い種類と、保存値の無い種類は比べない。捨てた個体の読みは比べない
- 行はサーヴァントごとに1つにする

**照合用のデータ**

- 対象は Atlas の `nice_servant` のプレイアブルなサーヴァント（種類が `normal` と `heroine`）の、再臨の段階ごとと霊衣の顔のアイコン（決定9）
- 更新ジョブ（`scripts/run-updater.ts`）に段を足す。前回のデータにあるアイコン（アイコンの URL で見分ける）は取り直さず、増えたものだけを取得して縮める。取得できなかったアイコンは飛ばして記録し、次の実行で取り直す（実行は失敗にしない。実測でも 1 枚が 404 を返した）。`nice_servant` は育成の素材の一覧の段（`runMaterialCatalogPhase`）も条件付きで取っているが、変わっていないと中身が返らず、その段の結果は顔を1枚しか持たないので、顔の段では使えない。顔の段は自分で `nice_servant` を取る。照合用のデータがまだ無いときと、前回取得できなかったアイコンが記録に残っているときは無条件で取り、それ以外は顔の段が自分で持つ目印（前回の応答の ETag など）で条件付きにして、変わっていなければ何もせずに終わる。この段がまるごと失敗したとき（`nice_servant` を取れない、KV に書けない）は、ほかの段と同じく実行を失敗として終わらせるが、ほかの段（ドロップ、ダッシュボード、サーヴァントの一覧、育成の素材の一覧）は止めず、前回のデータは残す
- データの形は JSON で、アイコンごとにサーヴァントの ID・アイコンの URL・16×16 の RGBA を base64 にした文字列を持つ。1枚が約 1.4KB、2,065 枚で約 2.8MB（圧縮前）になる。配るときは圧縮がかかる。比べる升目だけに削らないのは、升目の選び方を端末の側の定数だけで変えられるようにするため
- PNG は新しい依存を足さず、Node の zlib で読む。128×128・8bit RGBA・非インターレースでない画像は飛ばして記録する
- 配る API のルートを1つ足す（`/api/material-catalog` と同じく KV を読んで返す）。端末は画像を選んだあとに1回だけ取得する
- ローカルの dev server には KV の値が無い。新しいルートは、ファイルを読める環境（`/api/material-catalog` がローカルの読み込みに切り替えるのと同じ判定）で KV に値が無ければ、git に入れないローカルのファイルを読む。このファイルの書き出しは新しく作る（今の `DRY_RUN=1` は KV への書き込みを飛ばすだけで、ファイルは書かない）。顔の段を `DRY_RUN=1` で走らせたときに書き出す。tasks.md の 5.2・5.3 の前に呼び出し側がこれを1回走らせる
- 本番の KV に初めてデータが入るのは、マージのあとに更新ジョブが走ったとき。それまでは照合用のデータを読み込めない扱い（画像を読まずに、読み込めなかったことを知らせる）になる

**保存**

- 所持: 入れたサーヴァントのうち未所持のものだけ、`material` の所持の印を「所持」にする。同じサーヴァントのほかの値と、すべてのサーヴァントに共通の目標（`all`）には触れない。書き込みは、保存値の読み込みと競合しないよう、前の値を受け取って返す形で行う
- Lv・宝具Lv: 新しい localStorage のキー（`servantLevels`）を `lib/constants/storage-keys.ts` に1つ足し、`ChaldeaState` と同じサーヴァントの ID をキーにして、Lv（`lv`）と宝具Lv（`npLv`）を持つ（どちらも無くてよい）。値は `{"100100": {"lv": 90, "npLv": 2}}` の形の JSON。読むときは、Lv は 1〜120、宝具Lv は 1〜5 の整数だけを通し、それ以外の値はその欄が無いものとする。全体が表でなければ空として読む
- 読み取りで値が無かった種類は、保存されている値を残す（Lv.順の画像だけを取り込み直しても宝具Lv が消えない）
- 読み書きの hook は `hooks/` に1つだけ作り、確かめの画面の確定と一覧の表示の両方がそれを使う。`hooks/use-item-want-setting.ts` と同じく、`useLocalStorage` に `lazyWrite` を付け、`onGet` は表かどうかだけを見る `recordOrEmpty` にする（`repairOnGet` は付けない）。hook は保存値の生の表を持ち、上の読み方（範囲の外の値を無いものとする）は、表示と取り込みに使う値を作るときにだけ当てる。こうする理由は2つ。(1) 開いただけの端末に空の保存値を作らないため。取り込みの無い端末が空の保存値を持つと、その端末の保存がクラウドに空の値を載せ、取り込んだ端末がそれを取り込んで Lv・宝具Lv を全部失う（キーが無ければ、取り込みは端末の値を消さない）。(2) hook が読み方を通したあとの値を持つと、書き戻すときに知らない欄が落ちるため
- 書くときは、取り込む行のサーヴァントの `lv` と `npLv` だけを置き換える。保存値にある、この版が知らないサーヴァントの ID の項目と、項目の中のこの版が知らない欄は、そのまま残す（あとの版が欄を足しても、この版の取り込みと同期で消えないようにするため）

**クラウド同期**（決定2。同期の方式は変えず、同期するキーを1つ足す）

- 載せ方: `servantLevels` を `CLOUD_SYNC_KEYS` のいちばん後ろに足す。保存内容では、ほかのキーと同じく、キーの名前に localStorage の文字列がそのまま入る。既存のキーの中身と、保存内容の包み（キーごとの表と、時刻・端末の ID）は変えない。`/api/cloud` とスナップショットは本文を中身を見ずに置くので、サーバーの側は変えない
- 変更の記録: 確かめの画面の確定は、`material` を育成計算機の画面の今の書き込みの経路で、`servantLevels` を上の「保存」の hook で書く（どちらも前の値を受け取って返す形）。`servantLevels` の hook は `lazyWrite` なので、初めての取り込みの書き込みでも通知が出る。これで未同期の編集として記録され、自動同期が有効なら 5 秒後に1回の保存でクラウドに載る。自動同期が無効の端末では、今までどおり同期の管理画面から手で保存する
- 届いたときの表示: 取り込みはキーごとに通知を出すので、`servantLevels` を `useLocalStorage` で読んでいるカードの表示は、開き直さなくても変わる

端末の間の扱い（既存の決まりをそのまま当てる。Lv・宝具Lv だけの特別な扱いは作らない）:

| 場面 | 動き |
|---|---|
| スマホで取り込み、PC には未同期の編集が無い | スマホの保存のあと、PC でページを開くかタブに戻ると、自動で取り込まれてカードに出る（PC の自動同期が有効か、PC が初めての同期のとき。無効なら同期の管理画面から読み込む） |
| 別の端末のほうが新しく、この端末に未同期の編集が無い | クラウドの `servantLevels` で、この端末のものをまるごと置き換える |
| 別の端末のほうが新しく、この端末に未同期の編集がある | 競合として利用者に選ばせる。クラウドを選べば Lv・宝具Lv もクラウドのもの、この端末を選べばこの端末のものが、ほかのキーと一緒にまるごと残る |
| 片方の端末にだけ取り込みがあり、取り込みの無い端末が、クラウドに Lv・宝具Lv があると知ったうえで（最後に取得したクラウドの内容に入っている）上書きしようとする | 縮小ガードの新しい指標（下）で止めて確かめる |
| 取り込みの無い端末が、別の端末の取り込みを知らないまま保存する（PC のタブを開いたままにして、スマホの保存のあとに取得し直していない） | 縮小ガードは最後に取得した内容と比べるので止まらず、ほかのキーと同じく、あとの保存が残ってクラウドから Lv・宝具Lv が消える。取り込みの無い端末は保存値のキーを持たない（上の「保存」の hook）ので、取り込んだ端末がこの保存内容を取り込んでも、その端末の Lv・宝具Lv は消えず、その端末の次の保存でクラウドに戻る（Risks） |
| 2つの端末で別々に取り込んだ | 既存の決まりのとおり（あとから保存する端末がクラウドのほうが新しいと知っていれば競合になって利用者が選び、知らないまま保存すればあとの保存が残る）。どちらでも、片方の端末の Lv・宝具Lv がまるごと残る。サーヴァントごとに高いほうを取ることはしない |
| 一度も同期していない端末で取り込み、クラウドにもデータがある | 既存の食い違いの画面が出る。Lv・宝具Lv の数を両方に出す（下） |

サーヴァントごとに合成しない理由: 同期は保存内容をまるごと入れ替える方式で、所持の印（`material`）もまるごと入れ替わる。Lv・宝具Lv だけを合成すると、所持の印は片方の端末のもの、Lv は両方を混ぜたもの、という組み合わせになる。合成は同期の新旧の決め方に手を入れる変更で、この issue の範囲（入力はスマホ、見るのは PC）には要らない。負けた側の値は、スクリーンショットを取り込み直せば戻る。

縮小ガード（`lib/cloud-sync/shrink-guard.ts` の `measurePayload`・`isDestructiveShrink`）:

- 指標を1つ足す。「Lv か宝具Lv の値を持つサーヴァントの数」（`servantLevels` の項目のうち、Lv が 1〜120 の整数か、宝具Lv が 1〜5 の整数であるものの数。保存値を読む関数と同じ見方）。クラウドの数から 10 以上減り、半分以下になる保存を止める（しきい値は既存の `SHRINK_MIN_DELTA`・`SHRINK_RATIO` をそのまま使う）
- 足す理由: 取り込みの無い端末（`servantLevels` のキーが無い）がクラウドを上書きすると、消えるキーは 1 個なので、既存の3つの指標では止まらない（消えたキーは 2 個以上で止まる。所持の印は両方の端末にあって減らない）。数百騎ぶんの Lv・宝具Lv が黙って消える
- キーが無い・空のときは 0 と数える。保存しようとする内容の `servantLevels` が JSON として読めないときは、`material`・`posession` と同じく測れないものとして保存を中止する。クラウドの側が読めないときは、既存の決まりどおり数の比べをやめて、消えたキーだけで決める
- 確かめの画面（`components/cloud/shrink-guard-dialog.tsx`）と、保存が止まっている間の同期の管理画面（`components/cloud/index.tsx` の `summarizeScale`）の「保存しようとした内容」と「クラウド」の要約に、Lv・宝具Lv の数を足す。止まった理由がこの指標だけのとき、ほかの数は両方で同じなので、この数が無いと理由が見えない

食い違いの画面と見比べ:

- 規模（`components/cloud/parts/stats-logic.ts` の `Stats`）に同じ数え方の Lv・宝具Lv の数を足し、食い違いの画面の要約（`components/cloud/divergence-dialog.tsx`）と、同期の管理画面の見比べ（`components/cloud/parts/comparison-view.tsx`）に1行ずつ出す。片方の端末にだけ取り込みがあるときに、どちらを残すと Lv・宝具Lv が消えるかが、選ぶ前に分かる
- キーごとの項目の数（縮小で止まっているときの同期の管理画面）は、同期するキーの一覧から作られるので、キーを足すだけで `servantLevels` の行が出る

古い版のアプリ（`servantLevels` を同期するキーに持たない版。デプロイをまたいで開いたままのタブなど）:

| 場面 | 動き |
|---|---|
| 古い版が、Lv・宝具Lv を含む保存内容を取り込む | 自分の知っているキーだけを書くので、`servantLevels` を読まずに飛ばす。ほかのキーは今までどおり取り込まれ、失敗しない。既存のキーの中身と包みを変えないのは、これを保つため |
| 古い版が保存する | 自分の知っているキーだけでクラウドをまるごと置き換えるので、クラウドの保存内容から `servantLevels` が消える。配り終えたコードの動きなので、この変更では止められない |
| そのあと、新しい版の端末が取り込む | 取り込みは、クラウドに無いキーを端末から消さない。Lv・宝具Lv を持っていた端末（取り込んだスマホ、一度届いた PC）では値が残り、カードの表示も変わらない。その端末が次に保存したときに、クラウドに戻る |
| そのあと、まだ Lv・宝具Lv が届いていない端末が取り込む | Lv・宝具Lv は空のまま。持っている端末が次に保存するまで届かない（Risks） |

新しい版の端末が、クラウドに `servantLevels` が無いのを見つけてすぐ保存し直すことはしない。取り込みの直後に保存を足すと、古い版のタブと新しい版の端末が互いの保存を上書きし合う動きを作りうるうえ、既存のキー（クラススコアや絆の記録を足したとき）と違う扱いになる。古い版が残るのはデプロイをまたいで開いたままのタブだけで、開き直せば新しい版になる。

**一覧での表示**（PC で見る場所。決定2）

- 育成計算機のカード（`components/material/servant-card.tsx`）の名前の下、クラスの表示の並びに、保存されている値を「Lv 90・宝具 2」の形で出す。表示だけで、押しても何も起きない

**確かめの画面と入口**

- 選ぶ段に、撮る画面と並びの案内を出す（決定8 の案内の文面）
- 行が数百になるので、「要確認」を上にまとめ、当てた行は畳んで件数を出す

- 利用者が手で入れる Lv は 1〜120、宝具Lv は 1〜5 の整数だけを受け付ける。範囲に無い値が入っている行は取り込みに入れられない
- 所持の印を書くときは、育成計算機の画面が使っている、保存値を補ったあとの状態（一覧にいる全サーヴァントの ID を持つ）を前の値として受け取る。保存値に ID がまだ無いサーヴァントが飛ばされないようにするため
- 「要確認」の行は取り込みに入れる印を外した状態で出し、検査に通らなかった値・保存値より低かった値の欄は空にして候補を並べる（候補は押すと欄に入る。範囲だけが分かるときは、欄の横に範囲を出す）。利用者がその行のサーヴァントと空の欄をすべて決めた時点で、印を自動で付ける（付いた印は利用者が外せる）。決まっていない間は印を付けられない
- 続けて撮った画像の片方でだけ「要確認」になったカードを、利用者が既に当てた行のあるサーヴァントに決めると、同じサーヴァントの行が2つになる。まとめ直さず、重なりとして知らせて、片方を外してもらう（重なりは取り込みに入れる行だけで数える）
- サーヴァントを選ぶ欄は名前で絞り込める

### 測れていない点

実物は 1 台の端末で撮った 6 枚（一覧のいちばん上の2枚、途中の3枚、最後の1枚）。前の版で測れていなかった点のうち、途中まで送った画像、一覧の最後の段、宝具Lv が 5 でないカード（「1/5」）、再臨していないカード、同じサーヴァントの複数所持は、この 6 枚で測れた（Context）。次の点はまだ測れていないので、読み取りは「読めなかった画像」か「要確認」に倒れる作りにし、実装のあとの実地の確かめ（tasks.md の 5.3）で見られるものは見る。食い違えば実装を止めて報告する。

## Risks / Trade-offs

- [似た顔のサーヴァント（同じ人物の別クラスなど）を取り違える] → サーヴァントどうしの差の比で決め、小さければ「要確認」。当てた行にも切り抜きと当てたアイコンを並べて出す。実測の 120 枚では比が 0.24 以下で、取り違えは無かった
- [実測の 120 枚より多い種類の絵で、差の上限 10 と比 0.5 が合わない] → 定数を1つの場所に置き、実地の確かめ（tasks.md の 5.3）で別のサーヴァントに当たった行が 1 つでもあれば報告して止める
- [段を探す照合と、カード 1 枚につき 2 回の文字認識で、数十枚の画像に時間がかかる] → 進み具合を出す。実測からの見込みは、デスクトップで画像 1 枚あたり約 10 秒、27 枚で約 4〜5 分。iPhone ではこれより遅い
- [同じサーヴァントを複数持っていて、一番強い個体の読みが検査に通らず、弱い個体の読みだけが通る] → 弱い個体の値が「要確認」にならずに入りうる。前に取り込んだ値があれば、それより低い値として「要確認」になる。初めての取り込みでは止まらない。オーナーの決定（通らない読みは候補から外し、ほかの個体は「要確認」にしない）のとおりで、当てた行の切り抜きと値を見て直せる
- [宝具Lv.順の画像の読みの Lv だけが検査に通らず、同じサーヴァントの Lv.順の画像の読みが通る] → 読みは組で扱うので、宝具Lv.順の読みが組ごと候補から外れ、Lv だけの組が取り込まれる。正しく読めていた宝具Lv は入らない（間違った値は入らない。確かめの画面の「宝具Lv —」で分かり、保存されている宝具Lv は残る）
- [並びの表示を読み違える、または同じサーヴァントのカードが2段以上続いて重なりを取り違える] → 並び順に合わない読みが増えて「要確認」が増えるか、枚数の知らせが出る。取り込む値は読みの組から決めるので、読んでいない値が入ることは無い。合っている読みが候補から外れるので、同じサーヴァントを複数持つ場合は、上の項と同じく弱い個体の値が入りうる
- [所持数がカードの数と合わない数え方だった] → 撮り漏れの知らせが毎回出る。知らせるだけで確定は止めず、実地の確かめ（tasks.md の 5.3）で比べる
- [新しく「所持」になったサーヴァントで育成計算の必要な素材が増える] → 確かめの画面に新しく所持になる数を出す（決定1）
- [古い版のアプリ（デプロイをまたいで開いたままのタブ）が保存して、クラウドから Lv・宝具Lv が消える] → 持っている端末の値は消えず、その端末の次の保存で戻る。まだ届いていない端末（初めて開く PC など）には、それまで届かない。スマホで何か編集するか、同期の管理画面から手で保存すれば戻る（上の「クラウド同期」の古い版の表）
- [取り込みの無い端末が、別の端末の取り込みを知らないまま保存する（開いたままの PC のタブ）] → クラウドから Lv・宝具Lv が消える。取り込んだ端末の値は消えず、その端末の次の保存で戻るが、それまで PC には届かない。同期の方式（最後に取得した内容と比べる、まるごと入れ替える）から来る動きで、ほかの同期する値と同じ。この変更では、開いただけの端末が空の保存値を作らないようにして、取り込んだ端末の値まで消えることだけを防ぐ
- [2つの端末で別々に取り込み、競合で片方を選ぶ] → 選ばなかった側の Lv・宝具Lv は消える（ほかの同期する値と同じ）。食い違いの画面と見比べに Lv・宝具Lv の数を出して、選ぶ前に分かるようにする。消えた値は取り込み直せば戻る
- [この端末の Lv・宝具Lv の保存値が JSON として読めない形に壊れる] → 縮小ガードが測れないものとして保存を中止する（`material` が壊れたときと同じ）。取り込み直すと、読めない保存値は空として読まれて書き直されるので戻る
- [照合用のデータが本番に入る前に画面が出る] → 読み込めないときは画像を読まずに知らせる。更新ジョブの初回の実行を「人がやること」に書く

## Migration Plan

- 既存の保存値は読み替えない。新しいキーが無い端末は、Lv・宝具Lv が空の状態から始まる
- クラウドの保存内容も読み替えない。同期するキーが1つ増えるだけで、新しいキーの無い保存内容（今ある全部）は、Lv・宝具Lv が空のものとして扱う。縮小ガードの新しい指標は、クラウドの数が 0 なので、今ある保存内容では止まらない
- 戻すときは入口とカードの表示を外し、同期するキーの一覧から新しいキーを外す。新しいキーは端末とクラウドに残っても、ほかの機能は読まない（消えたキーの判定は、今の一覧にあるキーだけを見るので、外したキーでは止まらない）。取り込みで立てた所持の印は残る（手で「未所持」に戻せる）
