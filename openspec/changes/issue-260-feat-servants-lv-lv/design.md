# Design

## Context

動機は proposal.md の Why を参照。

**今の保存の形**

- 育成計算機の保存値（localStorage の `material`、型は `hooks/create-chaldea-state.ts` の `ChaldeaState`）は、サーヴァントの ID ごとに「未所持かどうか」の印（`disabled`。`true` が未所持）と、再臨・スキル・アペンドスキルの今の値と目標の値を持つ。カードの「✓ 所持 / 未所持」の切り替え（`components/material/servant-card.tsx` の `toggleOwned`）はこの印だけを反転する
- Lv・宝具Lv を入れる場所は無い
- `material` はクラウド同期の対象（`lib/constants/storage-keys.ts` の `CLOUD_SYNC_KEYS`）で、同期の縮小ガード（`lib/cloud-sync/shrink-guard.ts`）は `material` と `posession` の中身を数えている

**使い回せる部品**

- 枠つきの文字認識: `lib/possession-import/ocr-engine.ts` の `recognizeWithBoxes`（文字・確からしさ・画像の上の枠を返す。初めて使うときに読み込む）
- アイコンの照合: `lib/shop-screenshot-import/icon-match.ts`（切り出しを升目の平均で 16×16 に縮める、Atlas のアイコンの不透明な升目で明るさをそろえて RGB の差を取る、位置と一辺を粗く探してから細かく探し直す、一番近い差 ÷ 次に近い差で決める）
- 確かめの画面の作り: `components/events/ShopScreenshotImport.tsx`（切り抜きと理由、照合の並べ表示、要確認の行で候補を選ぶ欄、取り込みに入れる印）

**顔のアイコンの実測（2026-11-14、Atlas の公開データ `nice_servant` の JP）**

| 数えたもの | 値 |
|---|---|
| プレイアブルなサーヴァント | 478 騎 |
| 再臨の段階ごとの顔のアイコン | 1,912 枚（全員が 4 枚ずつ） |
| 霊衣の顔のアイコン | 154 枚 |
| 合計 | 2,066 枚 |
| 1枚の形式と大きさ（1枚を取得して確かめた） | PNG・128×128・8bit RGBA・非インターレース・約 30KB |

2,066 枚を端末が1枚ずつ取ると約 62MB になる。16×16 の RGBA に縮めると 1枚 1,024 バイトで、全部で約 2.1MB（圧縮前）になる。交換所の取り込みは候補の通貨が数個だったので、画像を選んだあとに端末が Atlas から取っていた。

**参考画像で分かったこと**

実物の代わりに、ネットで見つけた古い画像2枚を見た（repo には入れない）。

| | 参考画像1 | 参考画像2 |
|---|---|---|
| 画面 | 中国版のスキル強化のサーヴァント選択画面（960×540） | 2020年の日本版の霊基変還の一覧（1136×640） |
| 写っている列 | 横に6枚 | 横に7枚 |
| カードの上の文字 | 「Lv. 80/80」の形 | 入手した日付 |
| カードのほかの表示 | 左上にクラスのアイコン、左に鍵、顔の中央に「強化可能」にあたる文字、右下にスキルLv「9/9/9」の形、下に星 | 左上にクラスのアイコン、左に鍵、顔の中央に「ロック中」、下に星、上に「NEW!」、カードの下に「Servant」などの種類 |
| サーヴァントでないカード | 無い | ある（種火、仮加入のサーヴァント） |
| 宝具Lv | 写っていない | 写っていない |

ここから言えるのは次の4つ。

1. カードは等しい間隔の格子に並ぶ。列の数は画面や密度で変わる（6 と 7）
2. カードごとに同じ形の文字が、カードの中の同じ位置に出る。何が出るかは並び順で変わる
3. 顔の上に、クラスのアイコン・鍵・文字・星が重なる。重なる所は画面で違う
4. 2枚とも古く解像度が低い。今の版の霊基一覧の画面、宝具Lv の出方、iPhone の解像度での読み取りの精度は分からない

## Goals / Non-Goals

**Goals:**

- 参考画像で決められる骨格（格子の検出、カードの中の位置関係の持ち方、照合の流れ、確かめの画面、保存先の形）を決める
- 実物を見ないと決められない点を1か所に並べ、数値を推測で決めない
- 既存の `ChaldeaState` の形と、育成計画の値を変えない

**Non-Goals:**

- レイドの編成計算・ダメージ計算（別 issue）
- サーヴァント詳細画面からのスキルLv・アペンドスキルLv・フォウの取り込み（次の issue）
- 取り込んだ Lv・宝具Lv を一覧で見る画面と、取り込みを通さずに手で直す画面。保存されている値は、取り込みの確かめの画面の「今の値」で見る。使う側（編成計算）を作る issue で出す
- 取り込みで「所持」を「未所持」に戻すこと（写っていないサーヴァントは変えない）

## Decisions

### 判断点

#### 判断点1: 「所持」をどこに書くか

推奨は案A。

| 案 | 中身 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|---|
| **A（採る）** | 入れたサーヴァントの既存の所持の印（`material` の中）を「所持」にする。Lv・宝具Lv は新しい保存先に置く | 所持が2か所に分かれて食い違うこと。`ChaldeaState` の型を変えて既存の読み書きを壊すこと | 新しく「所持」になったサーヴァントが育成計算の対象に入り、必要な素材の合計が増える（カードを手で「所持」にしたときと同じ動き） |
| B | 所持も新しい保存先だけに持ち、既存の所持の印は変えない | 育成計算の必要な素材が取り込みで変わること | 育成計算機の「所持」と取り込んだ所持が別物になり、利用者がどちらを見ればよいか分からなくなる |
| C | `ChaldeaState` のサーヴァントごとの値に Lv・宝具Lv の欄を足す | 保存先が1つで済むこと | 既存の保存値の補い方（`hooks/use-chaldea-state-merger.ts`）と同期の縮小ガードが新しい欄を知らず、欄が落ちるか、型の変更が育成計算機の全体に広がる |

根拠: issue は「取り込んだサーヴァントを所持にし」と書いており、このアプリで「所持」を表すのは既存の印だけ。印の反転は今のカードの操作と同じ書き込みなので、育成計画の今の値と目標の値には触れない。必要な素材が増える点は、確かめの画面に「新しく所持になる N 騎」を出して確定の前に見えるようにする。

#### 判断点2: Lv・宝具Lv の保存先をクラウド同期するか

推奨は案A。

| 案 | 中身 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|---|
| **A（採る）** | 端末だけに保存する（交換所の入力と同じ扱い） | 同期の縮小ガードとマージが新しい保存先を知らないまま載せて、別の端末の古い値で上書きされること | 別の端末では取り込み直しが要る（所持の印は `material` に入るので同期される） |
| B | 同期の対象に足す | 端末ごとの取り込み直し | 縮小ガード・食い違いの画面・保存の検証に新しい保存先の扱いを足す変更が要り、同期の仕様の変更になる |
| C | `material` の中に入れて同期に乗せる | 同期の変更 | 判断点1 の案C と同じ |

根拠: Lv・宝具Lv はスクリーンショットからいつでも取り直せる値で、使う側（編成計算）がまだ無い。同期に載せるのは、使う側ができて端末をまたぐ必要が見えてからでも遅くない。

#### 判断点3: スキルLv の取り込みを範囲に入れるか

推奨は案A。

どの画面で何が読めるか（参考画像と issue から。今の版では実物で確かめる）:

| 画面 | Lv | 宝具Lv | スキルLv |
|---|---|---|---|
| 霊基一覧（Lv の並び） | 読める見込み | 読めない見込み | 読めない |
| 霊基一覧（宝具Lv の並び） | 分からない | 読める見込み | 読めない |
| スキル強化のサーヴァント選択画面（参考画像1） | 読める | 読めない | 読める（「9/9/9」の形） |

案B の確かめの画面（スキル強化の選択画面も受け付け、スキルLv の列が増える）:

| 案 | 中身 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|---|
| **A（採る）** | この変更では Lv・宝具Lv だけ。スキルLv は読まない | 実物で確かめる画面が2種類に増えて、霊基一覧の取り込みが遅れること。スキル強化の画面では顔の中央に文字が重なり（参考画像1）、照合が別の調整になること | 編成計算にスキルLv が要るなら、次の issue まで手で入れるか、既定の値を使うことになる |
| B | スキル強化の選択画面も受け付け、スキルLv（3つ）を読んで、Lv・宝具Lv と同じ新しい保存先に置く。育成計画の値には書かない | スキルLv を別の画面（サーヴァント詳細、1騎ずつ）で取る手間 | 確かめる画面と読み取りの形が増える。スキルLv が育成計画の「今の値」と新しい保存先の2か所に分かれる |

根拠: issue はスキルLv を次の issue にしている。読み取りは「カードの文字から読めた種類の値だけを取る」作り（下の「決めたこと」の値の読み取り）なので、あとで種類を足すときに作り直しにならない。案A で取りこぼすのは時期だけで、案B は実物での確かめを増やす。

#### 判断点4: 同じサーヴァントを複数持つ場合

推奨は案A。

| 案 | 中身 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|---|
| **A（採る）** | サーヴァントごとに1つの行にまとめる。同じ種類の値が食い違えば、大きいほうを初めの値にして「要確認」にし、読んだ値から選べるようにする | 育てていない2騎目の値（Lv 1 など）が黙って入ること。保存の形が「サーヴァントごとに1つ」で済むこと | 2騎目を別に記録できない |
| B | 黙って大きいほうを取る | 「要確認」が増えること | 読み違い（90 を 9 と読むなど）と重複を見分けられず、間違った値が確かめなしで入りうる |
| C | 同じサーヴァントを複数の行として保存する | 2騎目の記録 | 保存の形と確かめの画面が複雑になる。Lv の画像と宝具Lv の画像を別に撮ると、どの Lv がどの宝具Lv と同じ1騎かを決められない |

根拠: Lv と宝具Lv を別の画像から取る（下の「決めたこと」）と、画像をまたいで同じ1騎を追えるのはサーヴァントの ID だけになる。続けて撮った画像の重なりは同じ値になるので「要確認」にならず、食い違うのは本当に複数持っているときと読み違いのときだけ。

#### 判断点5: 顔のアイコンの照合用のデータをどう配るか

推奨は案A。

| 案 | 中身 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|---|
| **A（採る）** | マスターデータの更新ジョブが顔のアイコンを 16×16 に縮めたデータを作って `MASTER_DATA` の KV に置き、API のルートから1回で配る | 端末が 2,066 枚・約 62MB を取ること（iPhone の通信とメモリ） | 更新ジョブに段が1つ増える。新しいサーヴァントは、次に更新ジョブが走るまで当たらない（「要確認」になり、手で選べる） |
| B | 交換所の取り込みと同じく、画像を選んだあとに端末が Atlas から全部取る | 更新ジョブの変更 | 初回に約 62MB。取得の失敗が照合の失敗になる |
| C | カードのクラスのアイコンと星でサーヴァントの候補を絞ってから、その候補だけ端末が取る | 取る枚数 | クラスと星を読む照合が別に要り、その読み違いが顔の照合の前に入る。絞っても1クラスで数百枚になる |

根拠: 実測で 2,066 枚ある。縮めたデータは約 2.1MB（圧縮前）で、KV の1つの値に入る。顔のアイコンは 128×128・8bit RGBA・非インターレースの PNG なので、8×8 の升目の平均で 16×16 になり、交換所の取り込みで Atlas のアイコンを縮めるのと同じ計算になる。生成物を repo に置かないのは、サーヴァントが増えるたびにバイナリの差分が git に溜まるため。

#### 判断点6: カードの格子をどう見つけるか

推奨は案A。

| 案 | 中身 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|---|
| **A（採る）** | カードごとに同じ形で出る文字（Lv など）の枠を目印にして、枠の並びから列と段の間隔を求め、格子を組む。文字が読めなかったカードの位置は間隔から補う | 文字認識が1回で済み、目印にした文字からそのまま値が読める。交換所の取り込みの「文字の枠を目印にして、その大きさを長さの単位にする」と同じ流儀で、解像度が変わっても同じ規則が使える | カードに文字が出ない並び順の画像では格子を組めない。目印にできる文字の形は実物で確かめる |
| B | 画素からカードの枠の繰り返しを探す | 文字に頼らないこと | 背景・「NEW!」・選択の光で壊れやすく、新しい検出を一から作って実物で調整することになる |
| C | 格子を組まず、顔のアイコンを画像の全体から探す | 格子の検出 | 2,066 枚 × 画像の全体の位置で、端末では終わらない |

根拠: 参考画像は2枚とも、カードごとに同じ形の文字（Lv、日付）が同じ位置に出ている。目印を「Lv の文字」に決め打ちせず「カードごとに繰り返す同じ形の文字」にしておけば、宝具Lv の並びの画像でも同じ組み方が使える。

#### 判断点7: 実物が届く前にどこまで進めるか

推奨は案A。

| 案 | 中身 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|---|
| **A（採る）** | この仕様で骨格と判断点を決める。実物が届いたら、下の「実物で確かめてから決める点」を実測で埋める仕様の変更を出し、そのあと1回で実装する | 見ていない画面の数値で実装して作り直すこと（#220 は実物を見ずに書いた行の読み取りを作り直した） | 実物が届くまで実装が始まらない |
| B | 参考画像から測った仮の数値で全部実装し、実物で食い違えば直す | 実装の開始を待つこと | 参考画像は版も国も解像度も違い、宝具Lv は写っていない。読み取りの部分は高い確率で作り直しになる |
| C | 画面に依らない部分（保存、照合用のデータ、確かめの画面）だけ先に実装し、読み取りは別の変更にする | 待ち時間の一部 | 読み取りが無いと入口を出せず、使えない画面と保存先だけが先に入る。確かめの画面に出す行の形は読み取りの結果で決まるので、先に作ると合わせ直しになる |

根拠: 実物のスクリーンショットはオーナーが撮れば届くもので、待ちは短い。仮の数値で作ると、#220 と同じ作り直しをレイドの開催中にやることになる。

### 決めたこと

**読み取りの流れ**（画像1枚ごと）

1. 画像を canvas に描き、枠つきの文字認識を1回かける
2. カードごとに繰り返す同じ形の文字の枠を目印にして、列と段の間隔を求め、カードの格子を組む（判断点6）。目印の枠の高さを長さの単位にし、カードの中の位置（顔の部分、値の文字が出る範囲）はその倍数で持つ。倍数は1つの場所の定数に置く
3. 文字の枠を、中心が入るカードに振り分け、カードごとに値を読む
4. カードごとに顔の部分を切り出し、照合用のデータと比べる
5. 確かめの画面に出すカードの切り抜き（小さな画像）だけを残し、画像の canvas と画素の配列は次の画像に進む前に手放す

交換所の取り込み（`lib/shop-screenshot-import/analyze.ts`）は canvas を最後まで持っているが、霊基一覧は数十枚になるので持たない。issue の「iPhone で多数の画像を一度に読むときのメモリ」への答えはこれで、足りるかは実物で確かめる。

**値の読み取り**

カードに振り分けた文字を、種類ごとの形（Lv の形、宝具Lv の形）に当てて読む。位置ではなく文字の形で種類を決めるので、並び順でカードの文字が変わっても、読めた種類だけが入る。どの種類も読めなければ、サーヴァントだけを当てたカードになる。種類を足す（スキルLv など）ときは形を1つ足す。Lv の形は参考画像1 では「Lv. 80/80」（今の Lv / 上限）で、今の版の形と宝具Lv の形は実物で確かめる。

**顔の照合**

- 比べ方（16×16 への縮小、明るさをそろえた RGB の差）は `icon-match.ts` のものを使う
- 候補が 2,066 枚あるので、交換所の探し方（位置と一辺を広く振る）をそのまま全候補にかけない。格子から決めた位置のまわりの少ない切り出しで全候補との差を取り、近い順の上位だけを、位置と一辺を振る探し方にかける
- 決め方は、アイコンどうしではなくサーヴァントどうしで比べる。サーヴァントごとに一番近いアイコンの差を取り、一番近いサーヴァントの差 ÷ 次に近い別のサーヴァントの差がしきい値以下なら決め、超えれば「要確認」にする。同じサーヴァントの段階どうしは似ているので、アイコンどうしで比べると当たっているカードが「要確認」になる
- 顔の上に重なる表示（クラスのアイコン、鍵、文字、星）の升目は比べに使わない。どの升目を除くかは実物で確かめる
- 上位に残す数、切り出しを振る幅、しきい値は実物で確かめる。1つの場所の定数に置く
- 霊衣・再臨の段階でアイコンが変わるサーヴァント（issue の「決まっていないこと」）は、段階ごとと霊衣のアイコンを全部候補に入れて、同じサーヴァントの ID に結び付けることで扱う

**照合用のデータ**

- 対象は Atlas の `nice_servant` のプレイアブルなサーヴァント（種類が `normal` と `heroine`）の、再臨の段階ごとと霊衣の顔のアイコン
- 更新ジョブ（`scripts/run-updater.ts`）に段を足す。前回のデータにあるアイコン（アイコンの URL で見分ける）は取り直さず、増えたものだけを取得して縮める。取得できなかったアイコンは飛ばして記録し、次の実行で取り直す。この段の失敗でほかの段（ドロップ、ダッシュボード、サーヴァントの一覧）を止めない
- PNG は 128×128・8bit RGBA・非インターレースと確かめてあるので、新しい依存を足さず、Node の zlib で読む。形式が違う画像は飛ばして記録する
- 配る API のルートを1つ足す（`/api/material-catalog` と同じく KV を読んで返す）。端末は画像を選んだあとに1回だけ取得する
- 本番の KV に初めてデータが入るのは、マージのあとに更新ジョブが走ったとき。それまでは照合用のデータを読み込めない扱い（すべて「要確認」）になる

**保存**

- 所持: 入れたサーヴァントのうち未所持のものだけ、`material` の所持の印を「所持」にする。同じサーヴァントのほかの値と、すべてのサーヴァントに共通の目標（`all`）には触れない。書き込みは、保存値の読み込みと競合しないよう、前の値を受け取って返す形で行う
- Lv・宝具Lv: 新しい localStorage のキーを `lib/constants/storage-keys.ts` に1つ足し、`ChaldeaState` と同じサーヴァントの ID をキーにして、Lv と宝具Lv（どちらも無くてよい）を持つ。読むときは、Lv は 1〜120、宝具Lv は 1〜5 の整数だけを通し、それ以外の値はその欄が無いものとする。全体が表でなければ空として読む
- 読み取りで値が無かった種類は、保存されている値を残す（Lv の画像だけを取り込み直しても宝具Lv が消えない）

**確かめの画面と入口**

- 入口は `components/material/index.tsx` の一覧の上（所持の数を出している並び）に置く。選ぶ・読み取る・確かめるの3段のダイアログにし、選ぶ段と進み具合は `components/common/possession-import/PossessionImportDialog.tsx`、確かめる段は `components/events/ShopScreenshotImport.tsx` と同じ作りにする。どちらのファイルの挙動も変えない
- 行が数百になるので、「要確認」を上にまとめ、当てた行は畳んで件数を出す
- 「要確認」の理由: 顔の差が小さい、値が範囲に無い、同じサーヴァントで値が食い違う、照合用のデータを読み込めない
- サーヴァントを選ぶ欄は名前で絞り込める
- サーヴァントでないカード（参考画像2 の種火など）は、どのサーヴァントにも近くないので「要確認」になる。利用者は取り込みに入れないまま確定できる

### 実物で確かめてから決める点

オーナーの実物の霊基一覧のスクリーンショットが届いてから決める。ここに挙げた値は、この仕様では決めていない。

| 点 | 今分かっていること | 実物で見ること |
|---|---|---|
| 今の版の霊基一覧のカードの作り | 参考画像は中国版のスキル強化の画面と 2020 年の霊基変還で、霊基一覧そのものではない | カードに出る文字と重なる表示、顔の部分の位置 |
| Lv の文字の形と出る位置 | 参考画像1 は「Lv. 80/80」がカードの上に出る | 今の版の形（上限が付くか、聖杯転臨の表示）、どの並び順で出るか |
| 宝具Lv の文字の形と出る位置 | 参考画像に写っていない | どの並び順で出るか、Lv と同じ画像に出るか、文字か数字だけか |
| 格子の目印にできる文字 | 参考画像は2枚ともカードごとに同じ形の文字が出る | 目印の枠の高さを単位にしたときの、列と段の間隔・顔の部分の位置の倍数 |
| 一覧の密度（左下のボタンで3段階） | Chaldea の説明では中の密度が認識しやすい | どの密度で読めるか。利用者に密度を指定してもらうか |
| 顔の照合の精度 | 交換所の通貨（候補が数個）では比が 0.11〜0.22 で決まった | 候補 2,066 枚で比がどう分かれるか、しきい値、上位に残す数、比べに使わない升目 |
| iPhone の解像度での文字認識 | 参考画像は 960×540 と 1136×640 | カードの小さな文字が読める確からしさ、読み違いの出方 |
| 多数の画像でのメモリと時間 | 画像を1枚ずつ手放す作りにする | iPhone で数十枚を続けて読めるか、1枚あたりの時間 |
| サーヴァントでないカード・特別な表示 | 参考画像2 には種火や仮加入のサーヴァントが混ざる | 霊基一覧に混ざるもの（マシュの形態、編成中・お気に入りの印など） |

## Risks / Trade-offs

- [顔の上に重なる表示が多く、16×16 では別のサーヴァントと見分けられない] → 重なる升目を比べから除く。それでも分かれなければ「要確認」になり、利用者が選ぶ。「要確認」が多すぎて使えないかは実物で確かめ、だめなら升目の数や比べ方を見直す仕様の変更を出す
- [似た顔のサーヴァント（同じ人物の別クラスなど）を取り違える] → サーヴァントどうしの差の比で決め、小さければ「要確認」。当てた行にも切り抜きと当てたアイコンを並べて出す
- [新しく「所持」になったサーヴァントで育成計算の必要な素材が増える] → 確かめの画面に新しく所持になる数を出す（判断点1）
- [照合用のデータが本番に入る前に画面が出る] → 読み込めないときは全部「要確認」にして知らせる。更新ジョブの初回の実行を「人がやること」に書く
- [実物が届く前に実装へ進むと、読み取りの数値が無い] → tasks.md の 3 の節は「実物で確かめてから決める点」が埋まるまで実装できないと明記する（判断点7）

## Migration Plan

- 既存の保存値は読み替えない。新しいキーが無い端末は、Lv・宝具Lv が空の状態から始まる
- 戻すときは入口を外す。新しいキーは残っても、ほかの機能は読まない。取り込みで立てた所持の印は残る（手で「未所持」に戻せる）
