# Design

## Context

動機は proposal.md の Why を参照。

**今の保存の形**

- 育成計算機の保存値（localStorage の `material`、型は `hooks/create-chaldea-state.ts` の `ChaldeaState`）は、サーヴァントの ID ごとに「未所持かどうか」の印（`disabled`。`true` が未所持）と、再臨・スキル・アペンドスキルの今の値と目標の値を持つ。カードの「✓ 所持 / 未所持」の切り替え（`components/material/servant-card.tsx` の `toggleOwned`）はこの印だけを反転する
- Lv・宝具Lv を入れる場所は無い
- `material` はクラウド同期の対象（`lib/constants/storage-keys.ts` の `CLOUD_SYNC_KEYS`）で、同期の縮小ガード（`lib/cloud-sync/shrink-guard.ts`）は `material` と `posession` の中身を数えている

**一次資料: オーナーの実物のスクリーンショット2枚（2026-11-14）**

ゲームの「サーヴァント強化」のサーヴァント選択画面を、iPhone（2796×1290）で撮ったもの。並びを「宝具Lv.順」にした1枚と「Lv.順」にした1枚。個人の画面なので repo には入れず、この文書には測った数値だけを書く。前の版の仕様が頼った古い参考画像（中国版のスキル強化の画面、2020年の霊基変還の一覧）は、設計の根拠から外した。

| 見たもの | 宝具Lv.順の画面 | Lv.順の画面 |
|---|---|---|
| カードの上の文字 | 「宝具Lv.5/5」の形 | 「Lv. 120/120」の形（今の Lv / 上限） |
| カードの下の文字 | 「Lv. 80/80」の形 | 無い（星と聖杯の印が出る） |
| 1枚の画像で読める値 | 宝具Lv と Lv の両方 | Lv だけ |

| 格子の外 | 右に「所持枠」の表、上に所持数、左にボタンの列 | 同じ |

**実測（2026-11-14、この2枚と Atlas の公開データで測った）**

測り方: repo の外に置いた使い捨てのスクリプトで、main にある `lib/shop-screenshot-import/icon-match.ts` の関数（`integralImage`・`cropCells`・`downscaleIcon`・`iconPixelDiff`・`rawPixelDiff`）をそのまま呼び、Atlas の `nice_servant`（JP）から取った顔のアイコンと、まるごと写った 42 枚のカード（2枚 × 3段 × 7列）の顔の部分を比べた。文字認識は、アプリが使っている部品（`ppu-paddle-ocr/web`、`lib/possession-import/ocr-engine.ts` と同じ既定の設定）をヘッドレスの Chromium で動かして測った。当たったサーヴァントが正しいかは、切り抜きと当たったアイコンを並べて目で確かめた。

顔のアイコンの数:

| 数えたもの | 値 |
|---|---|
| プレイアブルなサーヴァント（種類が `normal` と `heroine`） | 478 騎 |
| 再臨の段階ごとの顔のアイコン | 1,912 枚（全員が 4 枚ずつ） |
| 霊衣の顔のアイコン | 154 枚 |
| 取得できた数 | 2,065 枚（霊衣の 1 枚は URL が 404 を返した） |
| 1枚の形式と大きさ | PNG・128×128・RGBA・約 30KB（2,065 枚で約 68MB） |

顔の照合（候補は 2,065 枚、決め方はサーヴァントどうしの比。42 枚のカード）:

| 比べ方 | 正しく一番近くなった数 | 一番近い差 | 次に近い別のサーヴァントの差 | 比（一番近い ÷ 次） |
|---|---|---|---|---|
| `iconPixelDiff`（明るさをそろえる）・全部の升目 | 4 / 42 | 11.7〜17.3 | 15.5〜20.1 | 0.70〜1.00 |
| `rawPixelDiff`（明るさをそろえない）・全部の升目 | 42 / 42 | 13.9〜25.2 | 28.7〜45.7 | 0.33〜0.72 |
| `rawPixelDiff`・重なる升目を除く（下の「比べる升目」） | 42 / 42 | 1.5〜6.2 | 18.7〜36.3 | 0.07〜0.22 |

- 明るさをそろえる比べ方は、暗いアイコン（画面のほとんどが黒いもの）がどのカードにも一番近くなり、使えない。候補が数個だった交換所の通貨では起きなかった
- 重なる升目を除くと、当たったアイコンとの差は 6.2 以下、別のサーヴァントとの差は 18.7 以上に分かれた。「PARTY」と「+50%」が重なったカード（11 枚）も同じ範囲に入った
- 当たったアイコンの内訳は、最終の段階（第4段階）が 37 枚、霊衣が 4 枚、第1段階が 1 枚。最終の段階だけを候補にすると、5 枚（約 1 割）が当たらない
- 下の端で切れた4段目の 14 枚は、顔の正方形が画像からはみ出す。はみ出さない小さな切り出しで比べると、一番近い差は 11.7〜34.4、比は 0.55〜1.00 で、まるごと写ったカード（6.2 以下）と分かれた
- 探す幅: カードの位置を決めてから、位置と一辺を ±5% の中で 5% 刻みに振る 27 通りの切り出しを全候補と比べるだけで、42 枚とも同じ結果になった（一番近い差 6.0 以下、次の差 19.4 以上、比 0.21 以下）。Node で 1 枚あたり約 70 ミリ秒。当たった切り出しの一辺は 196〜203 画素だった

段の位置（縦にずらしながら、2つの列で全候補との一番近い差を取った。4 画素刻み）:

- 段のある位置（顔の上端が 346・602・854 画素）でだけ差が 2〜5 に落ち、16 画素以上ずれた位置では 25 以上だった。段の位置は顔の照合そのもので見つけられる

文字認識:

| 読み方 | 宝具Lv（宝具Lv.順） | 下の Lv（宝具Lv.順） | 上の Lv（Lv.順） |
|---|---|---|---|
| 画像をまるごと1回で読む | 0 / 21 | 0 / 21 | 「数字/数字」が正しく読めたのは 4 / 21 |
| カードごとに文字の帯を切り出し、2 倍に拡大して読む | 28 / 28（切れた4段目も上の帯は写っている） | 21 / 21 | 28 / 28 |

- まるごと読む方法では、カードの上の文字はほとんど枠にならない。見出し「強化するサーヴァントを選択してください」は2枚とも確からしさ 1.00 で同じ枠（左 568・上 48・幅 869・高さ 57 画素）に読めた
- 帯を読む方法では、「数字/数字」の部分は全部正しく読めた（確からしさ 0.91〜1.00）。まわりの文字は「Lv:120/120」「Ly.100/100」「4Lv.100/100」「宝具LV.5/5」のように崩れることがあり、確からしさの低い余計な枠（「2」など、0.19〜0.38）が付くこともあった
- 帯1つは 2 倍で約 65〜85 ミリ秒（3 倍では約 110〜170 ミリ秒で、読めた数は同じ）。まるごと読むのは 1 回 0.7〜0.8 秒（デスクトップの Chromium）

| 列の間隔 | 238.8 | 4.19 |

**使い回す部品**

- `lib/shop-screenshot-import/icon-match.ts` の `integralImage`・`cropCells`（切り出しを升目の平均で 16×16 に縮める）、`downscaleIcon`（Atlas のアイコンを縮める）、`rawPixelDiff`（不透明な升目だけで RGB の差を取る）、`coarseRects`（位置と一辺を振る）。このファイルは変えない。`iconPixelDiff`・`decideCurrency`・`matchIconInImage` は通貨向け（明るさをそろえる、通貨の ID で決める）なので使わない
- `lib/possession-import/ocr-engine.ts` の `recognizeWithBoxes`（枠つきの文字認識）。変えない
- 確かめの画面の作り: `components/events/ShopScreenshotImport.tsx`（切り抜きと理由、要確認の行で候補を選ぶ欄、取り込みに入れる印）

## Goals / Non-Goals

**Goals:**

- 実物の2枚で測った値で、読み取り（画面の見分け、格子、顔の照合、文字）を決める
- 測れていない点を1か所に並べ、そこは「読めなかった画像」か「要確認」に倒す
- 既存の `ChaldeaState` の形と、育成計画の値を変えない

**Non-Goals:**

- スキルLv・アペンドスキルLv・フォウの取り込み（オーナーの指定で範囲の外）
- レイドの編成計算・ダメージ計算（別 issue）
- 取り込んだ Lv・宝具Lv を一覧で見る画面と、取り込みを通さずに手で直す画面。保存されている値は、取り込みの確かめの画面の「今の値」で見る。使う側（編成計算）を作る issue で出す
- 取り込みで「所持」を「未所持」に戻すこと（写っていないサーヴァントは変えない）
- 「サーヴァント強化」の選択画面のほかの画面（マイルームの霊基一覧など）と、7 列でない表示の読み取り

## Decisions

### 判断点

前の版から番号を引き継ぐ。変えたのは次のとおり。

- 判断点3（スキルLv を範囲に入れるか）は取り下げた。オーナーが範囲の外と決めたので Non-Goals に書いた
- 判断点6（カードの格子をどう見つけるか）は取り下げた。実測で、カードの文字の枠を目印にする案が成り立たないと分かり、選ぶ余地が無くなったので「決めたこと」の「画面の見分けと格子」に書いた
- 判断点7（実物が届く前にどこまで進めるか）は取り下げた。実物が届いた
- 判断点8（入力に使う画面）と判断点9（再臨の段階・霊衣で絵が変わる点）を足した
- 判断点4 は、宝具Lv.順の画面では1枚のカードから Lv と宝具Lv が一緒に読めることに合わせて、案を書き直した
- 判断点5 は、数を実測の値（取得できた 2,065 枚）に直した

#### 判断点1: 「所持」をどこに書くか

推奨は案A。

確かめの画面のいちばん上の行（案で変わる所）:

```text
案A │ 12枚を読みました　当てた 243 騎 / 要確認 5 行　新しく所持になる 31 騎 │
    │ （確定すると、育成計算機の 31 騎のカードが「✓ 所持」になり、必要な素材の合計に入る）
案B │ 12枚を読みました　当てた 243 騎 / 要確認 5 行                        │
    │ （確定しても育成計算機のカードは「未所持」のまま。取り込んだ所持は編成計算だけが読む）
案C │ 案A と同じ見た目。保存先だけが違う（`material` の中に Lv・宝具Lv の欄が増える）
```

| 案 | 中身 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|---|
| **A（採る）** | 入れたサーヴァントの既存の所持の印（`material` の中）を「所持」にする。Lv・宝具Lv は新しい保存先に置く | 所持が2か所に分かれて食い違うこと。`ChaldeaState` の型を変えて既存の読み書きを壊すこと | 新しく「所持」になったサーヴァントが育成計算の対象に入り、必要な素材の合計が増える（カードを手で「所持」にしたときと同じ動き） |
| B | 所持も新しい保存先だけに持ち、既存の所持の印は変えない | 育成計算の必要な素材が取り込みで変わること | 育成計算機の「所持」と取り込んだ所持が別物になり、利用者がどちらを見ればよいか分からなくなる |
| C | `ChaldeaState` のサーヴァントごとの値に Lv・宝具Lv の欄を足す | 保存先が1つで済むこと | 既存の保存値の補い方（`hooks/use-chaldea-state-merger.ts`）と同期の縮小ガードが新しい欄を知らず、欄が落ちるか、型の変更が育成計算機の全体に広がる |

根拠: issue は「取り込んだサーヴァントを所持にし」と書いており、このアプリで「所持」を表すのは既存の印だけ。印の反転は今のカードの操作と同じ書き込みなので、育成計画の今の値と目標の値には触れない。必要な素材が増える点は、確かめの画面に「新しく所持になる N 騎」を出して確定の前に見えるようにする。

#### 判断点2: Lv・宝具Lv の保存先をクラウド同期するか

推奨は案A。

別の端末で取り込みの入口を開いたときの見え方（案で変わる所）:

```text
案A │ [顔] エミヤ   Lv — → 80   宝具Lv — → 5   ☑   │（別の端末では今の値が空。撮り直して取り込む）
案B │ [顔] エミヤ   Lv 80 → 80  宝具Lv 5 → 5   ☑   │（同期された値が今の値に出る）
案C │ 案B と同じ見た目。値は `material` の中にある
```

| 案 | 中身 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|---|
| **A（採る）** | 端末だけに保存する（交換所の入力と同じ扱い） | 同期の縮小ガードとマージが新しい保存先を知らないまま載せて、別の端末の古い値で上書きされること | 別の端末では取り込み直しが要る（所持の印は `material` に入るので同期される） |
| B | 同期の対象に足す | 端末ごとの取り込み直し | 縮小ガード・食い違いの画面・保存の検証に新しい保存先の扱いを足す変更が要り、同期の仕様の変更になる |
| C | `material` の中に入れて同期に乗せる | 同期の変更 | 判断点1 の案C と同じ |

根拠: Lv・宝具Lv はスクリーンショットからいつでも取り直せる値で、使う側（編成計算）がまだ無い。同期に載せるのは、使う側ができて端末をまたぐ必要が見えてからでも遅くない。

#### 判断点4: 同じサーヴァントを複数持つ場合

推奨は案A。

同じサーヴァントのカードが2枚（Lv 90・宝具Lv 5 と Lv 1・宝具Lv 1）写ったときの確かめの画面:

```text
案A │ ▼ 要確認（1）                                                        │
    │ [切り抜き][切り抜き] 同じサーヴァントのカードが2枚あります              │
    │    [顔] アルトリア   ( Lv 90・宝具Lv 5 )  ( Lv 1・宝具Lv 1 )   ☐ 取り込む │
    │    （どちらかを選ぶと印が付く。選ぶまで入らない）                       │
案B │ ▶ 当てた行（243）                                                     │
    │ [切り抜き][顔] アルトリア   Lv — → 90   宝具Lv — → 5   ☑               │
    │    （Lv の高いカードを黙って採る。もう1枚は出ない）                     │
案C │ ▶ 当てた行（244）                                                     │
    │ [切り抜き][顔] アルトリア (1)   Lv — → 90   宝具Lv — → 5   ☑           │
    │ [切り抜き][顔] アルトリア (2)   Lv — → 1    宝具Lv — → 1   ☑           │
```

| 案 | 中身 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|---|
| **A（採る）** | サーヴァントごとに1つの行にまとめる。カードごとの読み（Lv と宝具Lv の組）が食い違えば「要確認」にし、値は決めずに、読んだ組を Lv の高い順（同じなら宝具Lv の高い順）の候補として出す。利用者が選ぶまで入れない（交換所の取り込みの食い違いの行と同じ） | 育てていない2枚目の値（Lv 1 など）や読み違いが黙って入ること。保存の形が「サーヴァントごとに1つ」で済むこと | 2枚目を別に記録できない。複数持つサーヴァントの数だけ、選ぶ操作が要る |
| B | 黙って Lv の高い組を採る | 選ぶ操作 | 読み違いと重複を見分けられず、間違った値が確かめなしで入りうる。数百行の当てた行に埋もれて、採られなかったカードがあったことに気づけない |
| C | 同じサーヴァントを複数の行として保存する | 2枚目の記録 | 保存の形が「サーヴァントごとに複数」になり、続けて撮った画像の重なり（同じカードが2回写る）と本当の2枚目（同じ値で2枚持つ）を見分けられない。編成計算が同じサーヴァントの2枚目を使う場面は少ない |

根拠: 続けて撮った画像の重なりは同じ組になるので「要確認」にならず、食い違うのは本当に複数持っているときと読み違いのときだけ。Lv.順の画面で読んだ Lv だけのカードは、同じ Lv の組があればその組と同じカードとして扱う（下の「決めたこと」の「まとめ」）。

#### 判断点5: 顔のアイコンの照合用のデータをどう配るか

推奨は案A。

画像を選んだあとの進み具合の表示（案で変わる所）:

```text
案A │ 照合用のデータを読み込んでいます…（1回の取得）                 │
    │ 画像を読み取っています 3 / 12                                  │
案B │ 顔のアイコンを取得しています 812 / 2,065（初回は約 68MB）       │
    │ 画像を読み取っています 3 / 12                                  │
案C │ 画像を読み取っています 3 / 12（カードごとにクラスを見分けてから、│
    │ そのクラスの顔のアイコンを取得）                                │
```

| 案 | 中身 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|---|
| **A（採る）** | マスターデータの更新ジョブが顔のアイコンを 16×16 に縮めたデータを作って `MASTER_DATA` の KV に置き、API のルートから1回で配る | 端末が 2,065 枚・約 68MB を取ること（iPhone の通信とメモリ） | 更新ジョブに段が1つ増える。本番では、マージのあとに更新ジョブが1回走るまで使えない。新しいサーヴァントは、次に更新ジョブが走るまで当たらない（「要確認」になり、手で選べる） |
| B | 交換所の取り込みと同じく、画像を選んだあとに端末が Atlas から全部取る | 更新ジョブの変更。マージしてすぐ使えること | 初回に約 68MB。取得の失敗が照合の失敗になる |
| C | カードのクラスのアイコンと星でサーヴァントの候補を絞ってから、その候補だけ端末が取る | 取る枚数 | クラスと星を読む照合が別に要り、その読み違いが顔の照合の前に入る。絞っても1クラスで数百枚になる |

根拠: 縮めたデータは 1 枚 1,024 バイトで、2,065 枚で約 2.1MB（圧縮前）になり、KV の1つの値に入る。顔のアイコンは 128×128 の PNG なので、8×8 の升目の平均で 16×16 になり、実測で使った `downscaleIcon` と同じ計算になる。生成物を repo に置かないのは、サーヴァントが増えるたびにバイナリの差分が git に溜まるため。

#### 判断点8: 入力に使う画面

推奨は案A。

画像を選ぶ段の案内（案で変わる所）:

```text
案A │ ゲームの「サーヴァント強化」でサーヴァントを選ぶ画面を、並びを          │
    │ 「宝具Lv.順」にして、上から下まで少しずつ重ねて撮ってください。          │
    │ 宝具Lv と Lv の両方を読み取ります。                                     │
    │ 「Lv.順」の画像も読めますが、その画像からは Lv だけを取り込みます。       │
    │                                        [ 画像を選ぶ（複数可） ]          │
案B │ …並びを「宝具Lv.順」にして撮ってください。                               │
    │ （ほかの並びの画像は「読めなかった画像」として知らせ、何も取り込まない）   │
案C │ 「サーヴァント強化」の選択画面か、マイルームの「霊基一覧」を撮ってください。│
```

| 案 | 中身 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|---|
| **A（採る）** | 「サーヴァント強化」の選択画面だけを受け付ける。「宝具Lv.順」を主に案内し、「Lv.順」の画像も受け付けて Lv だけを読む | 1種類の画面を1回撮るだけで両方の値がそろうこと。Lv.順で撮ってしまった画像が無駄にならないこと | Lv.順の画像だけを選んだ利用者は、宝具Lv が入らない（確かめの画面の「宝具Lv —」で分かる） |
| B | 「宝具Lv.順」の画像だけを受け付ける | 宝具Lv の無い半端な取り込み | Lv.順で撮った画像は撮り直しになる。並びを見分ける読み取りが1つ増える |
| C | マイルームの霊基一覧も受け付ける | issue の題のとおりの画面を使えること | 霊基一覧の実物の画像が無く、見出しも違うので、目印と寸法を別に測ることになり、実装が遅れる |

根拠: 実物で、宝具Lv.順の画面はカードの上に宝具Lv、下に Lv が同時に出て、Lv.順の画面は上に Lv だけが出ると確かめた。値の種類は文字の形（下の「決めたこと」の「値の読み取り」）で決まるので、案A は並びを見分ける読み取りを足さずに両方の画像を受け付けられる。issue の題は「霊基一覧」だが、オーナーが実物として渡したのは強化の選択画面で、所持しているサーヴァントが全部並ぶ点は同じ。

#### 判断点9: 再臨の段階・霊衣で絵が変わるサーヴァントの照合

推奨は案A。

霊衣を表示にしているサーヴァントのカードの確かめの画面:

```text
案A │ ▶ 当てた行                                                              │
    │ [切り抜き][顔（霊衣）] 斎藤一   Lv — → 80   宝具Lv — → 5   ☑             │
案B │ ▼ 要確認                                                                │
    │ [切り抜き] どのサーヴァントにも近くない                                   │
    │    サーヴァント [ 選ぶ ▾ ]   Lv [ 80 ]   宝具Lv [ 5 ]   ☐ 取り込む        │
案C │ ▶ 当てた行                                                              │
    │ [切り抜き][顔（霊衣）] 斎藤一（霊衣）  Lv — → 80   宝具Lv — → 5   ☑       │
    │    （当たった段階・霊衣も保存する）                                       │
```

| 案 | 中身 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|---|
| **A（採る）** | 再臨の段階ごと（4 枚）と霊衣の顔のアイコンを全部候補に入れ、同じサーヴァントの ID に束ねる。決め方はサーヴァントどうしの比で、どの段階・霊衣に当たったかは保存しない | 霊衣や途中の段階を表示にしているカードが「要確認」になること（実測で 42 枚のうち 5 枚、約 1 割が最終の段階でない絵だった）。同じサーヴァントの段階どうしが似ていて「要確認」になること | 照合用のデータが 4 倍強（約 2.1MB）になる |
| B | 最終の段階の顔のアイコンだけを候補にする（478 枚、約 0.5MB） | データの大きさと照合の時間 | 霊衣・途中の段階のカードが全部「要確認」になり、数百騎では数十行を手で選ぶことになる |
| C | 案A に加えて、当たった段階・霊衣も保存する | あとで絵を再現したくなったときの取り直し | 画面の絵はゲームの表示の設定で選べるもので、育成の進み（再臨の段階）を表さない。育成計画の再臨の値と紛らわしい値が増え、使う側が無い |

根拠: 実測で、全部の段階と霊衣を候補にしても、当たったアイコンとの差（6.2 以下）と別のサーヴァントとの差（18.7 以上）は分かれた。候補が増えても取り違えは出ていない。

### 決めたこと

**読み取りの流れ**（画像1枚ごと）

1. 画像を canvas に描き、枠つきの文字認識を1回かけて、見出し「強化するサーヴァントを選択してください」の枠を探す
2. 見出しの枠から長さの単位と格子の横の位置を決め、顔の照合で段の位置を探す（下の「画面の見分けと格子」）
3. 段ごとに7枚のカードの顔を照合する（下の「顔の照合」）
4. カードごとに上と下の文字の帯を切り出し、拡大して文字認識にかけ、値を読む（下の「値の読み取り」）
5. 確かめの画面に出すカードの切り抜き（小さな画像）だけを残し、画像の canvas と画素の配列は次の画像に進む前に手放す

交換所の取り込み（`lib/shop-screenshot-import/analyze.ts`）は canvas を最後まで持っているが、この取り込みは数十枚になるので持たない。issue の「iPhone で多数の画像を一度に読むときのメモリ」への答えはこれで、iPhone の実機では測れていない（下の「測れていない点」）。

**画面の見分けと格子**

- 見出し「強化するサーヴァントを選択してください」が読めた画像だけを読む。読めなければ「読めなかった画像」として知らせ、何も取り出さない。実測で、この見出しは2枚とも同じ枠に確からしさ 1.00 で読めた。見出しの見分けは、文字認識の崩れに備えて、空白と記号を除いた文字が「サーヴァントを選択」を含むかで行う
- 長さの単位は見出しの枠の高さ。顔の一辺、列の間隔、いちばん左の列の位置、文字の帯の位置は、Context の「画面の寸法」の倍数で持つ。倍数は1つの場所の定数に置く。列は7つ
- 段の位置は文字では決めない（画像をまるごと読む文字認識では、カードの文字が枠にならなかった）。見出しの下から画像の下の端まで、顔の正方形を縦に少しずつずらしながら、7つの列で全候補との一番近い差を取り、差が上限（下の「顔の照合」）以下に落ちる位置を段とする。実測で、段の位置では差が 2〜5、16 画素以上ずれた位置では 25 以上だった。ずらす刻みは顔の一辺の 2%（実測の 4 画素）
- 顔の正方形が画像の下の端からはみ出す段（途中で切れた段）は読まない。続けて撮った次の画像にまるごと写る。上の端で見出しやボタンの下に隠れた段は、差が上限以下に落ちないので段にならない
- 段が1つも見つからない画像は「読めなかった画像」として知らせる（7 列でない表示、照合用のデータに無いカードだけの画像を含む）

**顔の照合**

- 比べ方は、切り出しを 16×16 に縮め（`cropCells`）、明るさをそろえずに RGB の差の絶対値の平均を取る（`rawPixelDiff`）。明るさをそろえる `iconPixelDiff` は使わない（実測で 4 / 42 しか当たらなかった）
- 比べる升目は、16×16 のうち上から 4〜11 番目の段（8 段）で、左から 4〜16 番目の列（13 列）の 104 升。上の文字とクラスのアイコン、左の鍵と星のバッジ、下の星・Lv の文字・帯・「PARTY」・「+50%」が重なる升目を除いたもの。除く升目は、照合用のデータを読み込んだあとに候補の側で透明にしておく（`rawPixelDiff` は不透明な升目だけを比べるので、関数を足さずに済む）
- 探す幅は、段と列で決めた位置のまわりで、位置と一辺を ±5% の中で 5% 刻みに振る 27 通り。全候補と比べる。実測で、広く探す2段の探し方と 42 枚とも同じ結果になった
- 候補は、育成計算機の一覧にいるサーヴァント（保存値に所持の印を書ける ID）のアイコンだけにする。照合用のデータにあっても一覧にいない ID は候補にしない
- 決め方は、アイコンどうしではなくサーヴァントどうしで比べる。サーヴァントごとに一番近いアイコンの差を取り、一番近いサーヴァントの差が上限 10 を超えれば「要確認」（どのサーヴァントにも近くない）、超えなければ、一番近いサーヴァントの差 ÷ 次に近い別のサーヴァントの差が 0.5 以下なら決め、超えれば「要確認」（顔の差が小さい）にする。実測は、当たったカードが差 6.2 以下・比 0.22 以下、切れたカードと別のサーヴァントが差 11.7 以上。上限と比のしきい値は1つの場所の定数に置く
- 段の中で、差が上限を超え、文字の帯からも値が1つも読めなかった位置は、カードが無い位置（一覧の最後の段の空き）として捨てる。値が読めた位置は「要確認」のカードにする

**値の読み取り**

- カードごとに、上の帯と下の帯（Context の「画面の寸法」）を切り出し、2 倍に拡大して文字認識にかける。実測で、2 倍で「数字/数字」が全部読め、3 倍にしても変わらず、時間は倍になった
- 帯の文字から「数字/数字」の形を探し、まわりの文字（「Lv」「宝具」など）は使わない。実測で、まわりの文字は崩れることがあり、数字は崩れなかった
- 値の種類は右の数字（上限）で決める。上限が 5 なら宝具Lv、上限が 60〜120 なら Lv。左の数字（今の値）を値にする。ゲームの Lv の上限は 60 より小さくならないので、宝具Lv と取り違えない
- 今の値が上限より大きい、上限が 5 でも 60〜120 でもない、今の値が範囲（Lv は 1〜120、宝具Lv は 1〜5）に無い読みは、その種類の値を決めずにカードを「要確認」（値が範囲に無い）にする
- 1つの帯に「数字/数字」の形が2つ以上あるときは、確からしさのいちばん高いものを使う
- 帯から値が読めなかった種類は「無い」とする。Lv.順の画像では、下の帯に文字が無いので宝具Lv が「無い」になり、Lv だけが入る（判断点8）
- どの種類も読めなかったカードは、サーヴァントだけを当てたカードになる

**まとめ**（選んだすべての画像をまたいで、判断点4）

- カードごとの読みは、Lv と宝具Lv の組（どちらも無くてよい）。サーヴァントごとに集める
- 同じ組は1つにまとめる（続けて撮った画像の重なり）
- 片方の値しか無い読み（Lv.順の画像の Lv だけ）は、その値が同じで、もう片方の値を持つ組があれば、その組にまとめる。そういう組が2つ以上あれば、どれにもまとめずに残す
- まとめたあとに組が1つなら、その値の行にする。2つ以上残れば「要確認」（同じサーヴァントで値が食い違う）にして、値を決めずに、組を Lv の高い順（同じなら宝具Lv の高い順、値の無いものは後ろ）の候補として持つ

**照合用のデータ**

- 対象は Atlas の `nice_servant` のプレイアブルなサーヴァント（種類が `normal` と `heroine`）の、再臨の段階ごとと霊衣の顔のアイコン（判断点9）
- 更新ジョブ（`scripts/run-updater.ts`）に段を足す。前回のデータにあるアイコン（アイコンの URL で見分ける）は取り直さず、増えたものだけを取得して縮める。取得できなかったアイコンは飛ばして記録し、次の実行で取り直す（実行は失敗にしない。実測でも 1 枚が 404 を返した）。`nice_servant` は育成の素材の一覧の段（`runMaterialCatalogPhase`）も条件付きで取っているが、変わっていないと中身が返らず、その段の結果は顔を1枚しか持たないので、顔の段では使えない。顔の段は自分で `nice_servant` を取る。照合用のデータがまだ無いときと、前回取得できなかったアイコンが記録に残っているときは無条件で取り、それ以外は顔の段が自分で持つ目印（前回の応答の ETag など）で条件付きにして、変わっていなければ何もせずに終わる。この段がまるごと失敗したとき（`nice_servant` を取れない、KV に書けない）は、ほかの段と同じく実行を失敗として終わらせるが、ほかの段（ドロップ、ダッシュボード、サーヴァントの一覧、育成の素材の一覧）は止めず、前回のデータは残す
- データの形は JSON で、アイコンごとにサーヴァントの ID・アイコンの URL・16×16 の RGBA を base64 にした文字列を持つ。1枚が約 1.4KB、2,065 枚で約 2.8MB（圧縮前）になる。配るときは圧縮がかかる。比べる升目だけに削らないのは、升目の選び方を端末の側の定数だけで変えられるようにするため
- PNG は新しい依存を足さず、Node の zlib で読む。128×128・8bit RGBA・非インターレースでない画像は飛ばして記録する
- 配る API のルートを1つ足す（`/api/material-catalog` と同じく KV を読んで返す）。端末は画像を選んだあとに1回だけ取得する
- ローカルの dev server には KV の値が無い。新しいルートは、ファイルを読める環境（`/api/material-catalog` がローカルの読み込みに切り替えるのと同じ判定）で KV に値が無ければ、git に入れないローカルのファイルを読む。このファイルの書き出しは新しく作る（今の `DRY_RUN=1` は KV への書き込みを飛ばすだけで、ファイルは書かない）。顔の段を `DRY_RUN=1` で走らせたときに書き出す。tasks.md の 5.2・5.3 の前に呼び出し側がこれを1回走らせる
- 本番の KV に初めてデータが入るのは、マージのあとに更新ジョブが走ったとき。それまでは照合用のデータを読み込めない扱い（すべて「要確認」）になる

**保存**

- 所持: 入れたサーヴァントのうち未所持のものだけ、`material` の所持の印を「所持」にする。同じサーヴァントのほかの値と、すべてのサーヴァントに共通の目標（`all`）には触れない。書き込みは、保存値の読み込みと競合しないよう、前の値を受け取って返す形で行う
- Lv・宝具Lv: 新しい localStorage のキーを `lib/constants/storage-keys.ts` に1つ足し、`ChaldeaState` と同じサーヴァントの ID をキーにして、Lv と宝具Lv（どちらも無くてよい）を持つ。読むときは、Lv は 1〜120、宝具Lv は 1〜5 の整数だけを通し、それ以外の値はその欄が無いものとする。全体が表でなければ空として読む
- 読み取りで値が無かった種類は、保存されている値を残す（Lv.順の画像だけを取り込み直しても宝具Lv が消えない）

**確かめの画面と入口**

- 入口は `components/material/index.tsx` の一覧の上（所持の数を出している並び）に置く。選ぶ・読み取る・確かめるの3段のダイアログにし、選ぶ段と進み具合は `components/common/possession-import/PossessionImportDialog.tsx`、確かめる段は `components/events/ShopScreenshotImport.tsx` と同じ作りにする。どちらのファイルの挙動も変えない
- 選ぶ段に、撮る画面と並びの案内を出す（判断点8 の案A の文面）
- 行が数百になるので、「要確認」を上にまとめ、当てた行は畳んで件数を出す

  ```text
  ┌ スクリーンショットから取り込む ───────────────────────────────┐
  │ 27枚を読みました　当てた 540 騎 / 要確認 6 行　新しく所持になる 31 騎 │
  │ 読めなかった画像: 1枚（IMG_0412.png）                           │
  │                                                              │
  │ ▼ 要確認（6）                                                 │
  │ [カードの切り抜き] 顔の差が小さい                              │
  │    サーヴァント [ 選ぶ ▾ ]   Lv [ 90 ]   宝具Lv [ 2 ]   ☐ 取り込む │
  │ [切り抜き][切り抜き] 同じサーヴァントのカードが2枚あります       │
  │    [顔] アルトリア  ( Lv 90・宝具Lv 5 ) ( Lv 1・宝具Lv 1 )  ☐ 取り込む │
  │                                                              │
  │ ▶ 当てた行（540）                                             │
  │ [切り抜き][顔] マシュ       Lv 80 → 90    宝具Lv 1 → 2   ☑     │
  │ [切り抜き][顔] エミヤ       Lv — → 80     宝具Lv — → 5   ☑     │
  │                                        [ 閉じる ] [ 確定する ] │
  └──────────────────────────────────────────────────────────────┘
  ```

- 「要確認」の理由: 顔の差が小さい、どのサーヴァントにも近くない、値が範囲に無い、同じサーヴァントで値が食い違う、照合用のデータを読み込めない
- 「要確認」の行は取り込みに入れる印を外した状態で出し、食い違った値・範囲に無かった値の欄は空にして候補を並べる。利用者がその行のサーヴァントと空の欄をすべて決めた時点で、印を自動で付ける（付いた印は利用者が外せる）。決まっていない間は印を付けられない
- 続けて撮った画像の片方でだけ「要確認」になったカードを、利用者が既に当てた行のあるサーヴァントに決めると、同じサーヴァントの行が2つになる。まとめ直さず、重なりとして知らせて、片方を外してもらう（重なりは取り込みに入れる行だけで数える）
- サーヴァントを選ぶ欄は名前で絞り込める

### 測れていない点

実物は 1 台の端末の、一覧のいちばん上で撮った 2 枚だけ。次の点は測れていないので、読み取りは「読めなかった画像」か「要確認」に倒れる作りにし、実装のあとの実地の確かめ（tasks.md の 5.3）で見る。食い違えば実装を止めて報告する。

| 点 | 今分かっていること | 倒し方 |
|---|---|---|
| 一覧を途中まで送った画像（上の段が見出しの下に隠れる） | 2枚とも一覧のいちばん上 | 段は顔の照合で探すので、縦の位置は問わない作り。隠れた段は差が上限を超えて段にならない |
| 一覧の最後の段（7枚に満たない） | 写っていない | 差が上限を超え、文字も読めない位置は捨てる |
| ほかの端末・縦横比（iPad など） | iPhone の 2796×1290 だけ | 長さは見出しの枠の倍数で持ち、位置は ±5% 振る。合わなければ段が見つからず「読めなかった画像」になる |
| 7 列でない表示（左下のボタンで切り替える表示） | 7 列だけ | 読まない。案内に 7 列の表示で撮るよう書く |
| サーヴァントでないカード・照合用のデータに無い新しいサーヴァント | 写っていない。切れたカードは差 11.7 以上だった | 差が上限 10 を超えて「要確認」になる |
| iPhone の実機での時間とメモリ | デスクトップの Chromium で、文字の帯1つ約 65〜85 ミリ秒、照合はカード1枚約 70 ミリ秒（Node） | 画像を1枚ずつ手放す。進み具合を出す |
| 宝具Lv が 5 でないカード、Lv が上限でないカード | 宝具Lv は「5/5」だけ、Lv は「116/118」が1枚 | 上限の数字で種類を決めるので、今の値が違っても同じ規則で読める |

## Risks / Trade-offs

- [似た顔のサーヴァント（同じ人物の別クラスなど）を取り違える] → サーヴァントどうしの差の比で決め、小さければ「要確認」。当てた行にも切り抜きと当てたアイコンを並べて出す。実測の 42 枚では比が 0.22 以下で、取り違えは無かった
- [実測の 42 枚より多い種類の絵で、差の上限 10 と比 0.5 が合わない] → 定数を1つの場所に置き、実地の確かめ（tasks.md の 5.3）で別のサーヴァントに当たった行が 1 つでもあれば報告して止める
- [文字認識がカード 1 枚につき 2 回走り、数十枚の画像で時間がかかる] → 進み具合を出す。実測の速さなら、画像 1 枚（カード 21 枚）でデスクトップは数秒
- [新しく「所持」になったサーヴァントで育成計算の必要な素材が増える] → 確かめの画面に新しく所持になる数を出す（判断点1）
- [照合用のデータが本番に入る前に画面が出る] → 読み込めないときは全部「要確認」にして知らせる。更新ジョブの初回の実行を「人がやること」に書く

## Migration Plan

- 既存の保存値は読み替えない。新しいキーが無い端末は、Lv・宝具Lv が空の状態から始まる
- 戻すときは入口を外す。新しいキーは残っても、ほかの機能は読まない。取り込みで立てた所持の印は残る（手で「未所持」に戻せる）
