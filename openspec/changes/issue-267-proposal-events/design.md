## Context

動機は proposal.md の Why。今の構成は次のとおり。

- `components/events/EventHubClient.tsx` が、機能ごとのセクション（`<h2>` の見出しつき）を縦に並べる。ボックスのあるイベントではボックス計画（`EventPlannerClient`）だけを出し、交換所の計算（`EventShopList`）はロトの無い交換所イベント（`isShopOnlyEvent`）でだけ出す。`app/events/[id]/page.tsx` も、交換所の AP 換算値とイベントポイントの品目をロトの無い交換所イベントでだけ読む
- `EventPlannerClient` は `lib/event-plan.ts` の `allocateShop` で、不足素材（「育成ロスター」）と欲しい素材（「欲しい素材指定」）を交換所の品目に割り当て、交換の対価の合計を箱を開ける通貨の必要量に足す。品目の対価の通貨（`costItemId`）は見ない。`mocks/events.json` のボックスのあるイベント5件のうち4件は、交換所の対価がすべて箱の通貨と別の通貨で、この足し方では周回数が誤る
- 不足の元は `hooks/use-roster-need.ts` の `useRosterNeed`（サーヴァントの育成だけ）。育成計算機は `lib/class-score/calculate-total.ts` でクラススコアの必要分を足しているが、イベントページは足していない。料理作成だけが `useStockTarget` で周回目的に追従し、交換所（`useShopRosterPlan`）とボックス計画は「今の育成」固定
- `components/ui/tabs.tsx`（base-ui の Tabs）は `/bond` と `/farming` の結果で使われている。どちらも開いたタブを覚えない
- 交換所の一覧の上は #259 で「スクショから読み取る」の主ボタンと「⋯」メニューに整理したばかり

## Goals / Non-Goals

**Goals:**
- ボックスと交換所を別のタブにし、ボックスのあるイベントでも交換所の計算を通貨ごとに正しく出す
- イベントページの3つの欄（ボックス・交換所・クラフト）で、同じ求め方の不足（クラススコア込み、周回目的に追従）を使う
- あとから「ポイント」のタブを足せる形にする

**Non-Goals:**
- 周回ポイントのシミュレータ（#137）
- ボックスと交換所をまとめた1つの周回計画
- 交換所の一覧の上の操作の並び（#259）を変えること
- ボックスのあるイベントの、ボーナス礼装の ☆ と通貨の対応の取り込み
- ボックス計画の入力の保存（今までどおり保存しない）

## Decisions

### 判断点

#### 判断点1: タブが1つしか無いイベントで、タブの列を出すか

ロトの無い交換所イベント（直近では大半のイベント）や、ボックスだけのイベントでは、出すタブが1つになる。

| 案 | 画面 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|---|
| **A（推奨）: 出さない。今の見出しのセクションのまま** | 交換所イベントの画面は今と同じ | 押しても何も変わらないタブの列で、1画面の縦の幅を使わない（オーナーは1画面に詰め込まないことを好む） | 「ポイント」のタブを足した時点で、交換所イベントの画面にタブの列が新しく現れる |
| B: 1つでも出す | 交換所イベントでも「交換所」のタブが1つ出る | 「ポイント」のタブを足したときに画面の形が変わらない | 選ぶもののないタブの列が常に1行増える |
| C: 機能が無いタブも、押せない灰色で出す | 「ボックス（無し）」「交換所」が並ぶ | どのイベントでも同じ位置に同じタブがある | 無い機能を毎回見せることになり、タブの数だけ横幅を使う（375px で文言が詰まる） |

推奨は A。今の交換所イベントの画面を変えずに済み、タブの列はタブを選ぶ意味があるときだけ出る。

#### 判断点2: 両方あるイベントで、開いたときにどのタブが開き、どう覚えるか

| 案 | 一覧から開く | 交換所に切り替えて再読み込み | 避けられる失敗 | 取りこぼすもの |
|---|---|---|---|---|
| **A（推奨）: 並びの最初（ボックス）を開く。切り替えたタブは URL のクエリに残す** | ボックス | 交換所 | 開いたときの画面がいつも同じで迷わない。再読み込みや URL の共有で同じタブになる。端末に新しい保存値を足さない（クラウド同期の対象を増やさない） | 交換所ばかり使う人は、一覧から開くたびに交換所へ切り替える |
| B: このイベントで最後に開いたタブを端末に覚える | 前回のタブ | 交換所 | 毎日交換所を使う人が切り替えずに済む | 開くたびに画面が変わりうる。イベントごとの保存値が増え、終わったイベントの値が残る |
| C: いつもボックス。URL にも残さない | ボックス | ボックス | 作りが最も小さい | 再読み込みで開いていたタブが戻る。交換所のタブを URL で人に見せられない |

推奨は A。クエリの名前は `tab`、値は `box`・`shop`・`craft`（後の `points`）とし、切り替えは `history.replaceState` で行って履歴を増やさない（戻るでタブを1つずつ戻らない）。ダッシュボードとイベント一覧の導線はクエリを付けない。

### 決めたこと

#### タブの名前・並び・作り方

タブは「ボックス」「交換所」「クラフト」の順。名前はオーナーの言葉（「ボックスと交換所と」）に合わせて短くする。タブは `features`（`box`・`shop`・`craft`）から並びの表で作り、表に1行足せばタブが増える形にする（#137 の「ポイント」は `points` の行を足す）。タブの列を出すときは、タブの中の `<h2>` を出さず、今の説明の1行（交換所の「交換したい数を入れると、要る周回数と AP が出ます」など）だけを残す。ヘッダー（名前・会期・開催状態・箱数・通貨）はタブの上に今のまま置く。

レジストリで料理作成の登録がある `80614` は KV では交換所イベントでもあるので、「交換所」「クラフト」の2つのタブになる。

#### 既存の欄の置き場所

| タブ | 置く欄 |
|---|---|
| ボックス | 入力モード、目標箱数、所持通貨と開けた箱数、ドロップ増加礼装（箱を開ける通貨の +N）、AP 予算、手入力ドロップ、育成インパクト、周回計画の結果。周回目的の表示は入力モードの欄に置く（「育成ロスター」のときに意味を持つため） |
| 交換所 | `EventShopList` をそのまま（一覧の上の主ボタンと「⋯」メニュー、品目の一覧、通貨ごとの所持数と必要量、ドロップ増加礼装・ボーナス礼装、AP 予算、周回の内訳）。周回目的の表示は不足の要約の行に置く。品目がすべてサーヴァント扱いのときは品目の一覧（`EventShopCatalog`） |
| 料理作成 | `EventCraftSection` をそのまま（周回目的の表示は今の位置） |

AP 予算（マスターレベル・黄金の果実）は端末の同じ保存値を読むので、ボックスと交換所のタブのどちらで入れても両方に効く（`event-shop-ap-budget` の今の規則のまま）。

#### ボックス計画から交換所の配分を外す

`EventPlannerClient` から `allocateShop` の呼び出しを外す。「育成ロスター」では、不足から箱の確定報酬を引いた残りを、そのまま周回ドロップの需要としてソルバーに渡す。「欲しい素材指定」では、選べる素材を箱の内容だけにし（`collectSelectableItems` から交換所の品目を外す）、`reverseCalcBoxes` は箱の確定報酬だけで最小箱数を探す。`computeRosterImpact` の充当は箱の確定報酬だけにする。`EventPlanResultCard` の「交換所」の行と、在庫上限の警告を消す。`allocateShop`・`ShopAllocationResult` は使う所が無くなれば消す。

#### 各タブの計算は互いに使わない

交換所タブはボックス計画の入力（目標箱数・所持通貨）を使わず、ボックス計画も交換所タブの交換回数を使わない。オーナーの「しっかり分ける」に合わせ、両方の結果を合算する1つの周回計画は作らない。`80586` のように交換所の対価が箱の通貨と同じイベントでは、2つのタブの周回数を利用者が足すことになる（Risks）。

#### 交換所タブのデータ

`app/events/[id]/page.tsx` は、交換所の品目がサーヴァント扱いだけでない交換所があれば、ロトの有無によらず AP 換算値とイベントポイントの品目を読む。ボックスのあるイベントは取り込みで ☆ と通貨の対応（`bonusRarities`）を持たないので、交換所タブのボーナスは通貨ごとの +N の手入力になる（`event-drop-bonus` の「☆ と対応しない通貨」の規則のまま）。取り込み直しても対応を持たないので、「データの更新前のため礼装の枚数を比べられません」は出さない（`event-drop-bonus` の「ボーナス礼装の枚数の入力」を MODIFIED にする）。交換所タブの入力は `event-shop-saved-inputs` のとおりイベントごとに保存する。ボックスのあるイベントは今まで保存値が無いので、初めて開いたときは 0 から始まる。

#### タブを切り替えても入力を残す

タブの中身は、初めて開いたときに描き、その後はタブを切り替えても描いたまま隠す（base-ui の `keepMounted` 相当）。ボックス計画の入力は画面の状態だけで保存しないので、切り替えで中身を外すと入力が消えるため。最初から全部を描かないのは、交換所の一覧（`EventShopList`）が重く、ボックスだけを見る人の表示を遅くしないため。

#### 不足の求め方を1か所にする

`useRosterNeed` の `totalNeed` に、クラススコアの目標の必要分（`sumClassScoreMaterials`）を足す。クラススコアの保存値は書き込まずに読み、育成計画と同じく `useLocalStorage` の読み終わりを待って、読み終えるまでは `unread` にする（`readClassScoreState` を描画の中で同期に読むと hydration が食い違い、effect で後から読むと、クラススコアの目標だけの利用者に一瞬「育成対象を設定」が出て `event-shop-saved-inputs` の「育成計画と AP 予算も初期値を見せない」に反するため）。育成計算機の `calculateTotalRequiredMaterials` と同じ合算（`mergeMaterials`）を使い、合計を食い違わせない。サーヴァントの育成対象が無くてもクラススコアの目標があれば `ready` にする（素材カタログが要らないので読み込みを待たない）。ボックス計画の `computeShortfall`・`computeRosterImpact` は、`chaldeaState` と `materialsForServants` から求め直さず、この `totalNeed` から下の周回目的で求めた実効不足を受け取る形に変える（`totalNeed` と所持数だけを渡すと「今の育成」の不足にしかならず、ボックス計画が「新規サーヴァントに備える」に追従しないため）。

周回目的は `useStockTarget` を読み、`lib/quest-efficiency.ts` の `computeFiniteTarget`（「新規サーヴァントに備える」では必要数と在庫基準の大きい方）で実効必要数を出す。所持数を入れていない素材を対象外にする規則は、料理作成の `buildNeedByApiItemId`・`positiveNeedAtlasIds` と同じにする。在庫基準はカテゴリとレアリティで決まるので、ボックスと交換所のタブでも素材の分類が要る。ページで料理作成と同じ `getItems` を、ボックスか交換所があるときにも読む。「素材全体の効率を見る」は料理作成と同じく「今の育成」で求め、注記は短く「不足は今の育成で計算」とする。

ラベルは、「今の育成を進める」では今の文言（「育成にあと N 個」「育成計画の不足 N 素材のうち…」）を変えない。「新規サーヴァントに備える」では在庫基準の分は育成の不足ではないので「あと N 個」「不足 N 素材のうち…」にし、所持数を入れていない素材は「所持数が未入力」と表示する。

#### 交換所の各 capability の範囲の読み替え

交換所の各 capability は、要件の本文で対象を「ロトの無い交換所イベントの交換所」と書いている。中身は変えずに対象だけを「イベントページの交換所タブ」へ広げるため、その句を含む要件だけを MODIFIED にし、句だけを置き換えた（`event-shop-ap-budget`・`event-shop-efficiency`・`event-shop-remaining-import`・`event-shop-saved-inputs`・`event-shop-single-list`・`event-drop-bonus`・`event-shop-servant-exchange`・`item-want-setting`）。`event-shop-servant-exchange` の「品目がすべてサーヴァント扱いの交換所の一覧」は表示の要件で、交換所の他の要件より優先すると定めているので、対象を交換所タブに広げる。取り込みの要件（`event-drop-bonus` の ☆ と通貨の対応の取り込み、`event-shop-servant-exchange` のサーヴァント扱いの交換の取り込み）は取り込みの範囲の話なので変えない。各 spec の Purpose の「ロトの無い交換所イベント」は delta では変えられないので、archive のときに直す。`event-planner` の要件「ロトの無い交換所イベントの周回計画」は、`item-want-setting`・`event-shop-servant-exchange` が名前で参照しているので名前を変えず、本文で交換所タブ全体に当てる。

## Risks / Trade-offs

- [`80586` のように交換所の対価が箱の通貨と同じイベントでは、ボックスと交換所の周回数を利用者が自分で足す] → 今の簡易な配分はこのイベントでだけ正しかったが、4件では誤っていた。合算は「ポイント」のタブと合わせて後で考える（範囲外）
- [ボックス計画の「育成ロスター」と「欲しい素材指定」の結果が、交換所の分だけ変わる（必要箱数・周回数が増えうる）] → 交換所での充当は交換所タブの「足りない分だけ」で見られる。オーナーの決定どおり
- [クラススコアの必要分で、イベントページの不足が増える] → 育成計算機の合計と揃うので意図どおり
- [交換所タブを描いたまま隠すので、両方開いたあとはメモリを使う] → 1ページ内の2つのタブで、交換所の一覧はロトの無い交換所イベントと同じ大きさ
- [ボックスのあるイベントの交換所タブで、☆ ごとのボーナス礼装の比較が出ない] → 通貨ごとの +N の手入力で計算はできる。取り込みの拡張は範囲外

## Migration Plan

保存値の形は変えない。ボックスのあるイベントの交換所タブは、`event-shop-saved-inputs` の今のキーでイベントごとに保存を始める。戻すときはコードを戻せばよく、残った交換所タブの保存値は読まれないだけで害はない。
