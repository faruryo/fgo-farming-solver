## ADDED Requirements

### Requirement: イベントページのタブの指定と切り替え
システムは、イベントページのタブの列を出すとき、ページを開いた時点では、URL でタブが指定されていなければ、並びの最初のタブを開かなければならない (SHALL)。利用者がタブを切り替えたら、開いているタブを URL のクエリに残し、ページを読み込み直したときと、その URL を開いたときに、同じタブを開かなければならない (SHALL)。タブの切り替えでブラウザの履歴を増やしてはならない (SHALL NOT)。URL で指定されたタブがそのイベントに無いときは、エラーにせず並びの最初のタブを開かなければならない (SHALL)。開いていたタブを端末に保存してはならない (SHALL NOT)。ダッシュボードとイベント一覧からイベントページへの導線は、タブを指定しない URL のままとする (SHALL)。

システムは、タブを切り替えても、画面を開いている間は、それぞれのタブで利用者が入れた値（ボックス計画の目標箱数・所持通貨・入力モード、交換所タブの交換回数など）を消してはならない (SHALL NOT)。

#### Scenario: 何も指定せずに開く
- **WHEN** 利用者が、ダッシュボードから 80549 のイベントページを開いたとき
- **THEN** 「ボックス」のタブが開いている

#### Scenario: 切り替えたタブを読み込み直す
- **WHEN** 利用者が 80549 のイベントページで「交換所」のタブに切り替えてから、ページを読み込み直したとき
- **THEN** 「交換所」のタブが開いていて、ブラウザで戻るとイベントページの前に見ていたページへ戻る

#### Scenario: 無いタブを指定した URL
- **WHEN** 利用者が、料理作成の登録の無いイベントのページを、料理作成のタブを指定した URL で開いたとき
- **THEN** エラーにならず、並びの最初のタブが開いている

#### Scenario: 切り替えても入力が残る
- **WHEN** 利用者が 80549 の「ボックス」のタブで目標箱数に 10 を入れ、「交換所」のタブに切り替えてから「ボックス」のタブに戻ったとき
- **THEN** 目標箱数は 10 のままである

### Requirement: イベントページの不足の求め方
システムは、イベントページで育成計画の不足を使うすべての欄（ボックス計画の「育成ロスター」の入力モードと育成インパクト、交換所タブの品目の要る・要らないと要約と「足りない分だけ」、料理作成）で、次の同じ求め方の必要数と不足を使わなければならない (SHALL)。

- 必要数は、育成計画のページで設定したサーヴァントの育成対象の必要数と、クラススコアの目標の必要数の合計とし、育成計算機（`/material`）が出す合計と同じでなければならない (SHALL)
- 所持数は実所持数（所持数のページで保存した値）とする
- ヘッダーの周回目的が「今の育成を進める」のときは、不足を「必要数 − 所持数（0 未満は 0）」とする
- 「新規サーヴァントに備える」のときは、所持数を入れた素材について、必要数とカテゴリ・レアリティ別の在庫基準の大きい方から所持数を引いた値（0 未満は 0）を不足とし、所持数を入れていない素材は不足に数えない（料理作成・配布アドバイザーと同じ実効不足）
- 「素材全体の効率を見る」のときは「今の育成を進める」と同じに求め、不足が今の育成で求めたものであることを不足の近くに示す

サーヴァントの育成対象とクラススコアの目標のどちらかがあれば、育成計画が設定済みとして扱わなければならない (SHALL)。どちらも無いときは育成計画が未設定として扱う。システムは、ボックス計画の「育成ロスター」の入力モードの欄と交換所タブの不足の要約の近くに、現在の周回目的を表示し、ハンバーガーメニューと同じモード選択 UI を開けなければならない (SHALL)。周回目的を変えたときは、開いているタブの不足をページを開き直さずに求め直さなければならない (SHALL)。育成計画・クラススコアの目標・所持数・周回目的は読むだけとし、イベントページから書き換えてはならない (SHALL NOT)。

#### Scenario: クラススコアの必要分を足す
- **WHEN** サーヴァントの育成で素材 S が 10 個、クラススコアの目標で素材 S が 5 個要り、素材 S の所持数が 8 で、周回目的が「今の育成を進める」のとき
- **THEN** 交換所タブの素材 S の品目に「育成にあと 7 個」と表示され、ボックス計画の「育成ロスター」の不足でも素材 S の不足は 7 個として計算される

#### Scenario: クラススコアの目標だけがある
- **WHEN** 育成対象のサーヴァントが1人もいないが、クラススコアの目標があるとき
- **THEN** ボックス計画の入力モードに「育成ロスター」が出て、交換所タブの「足りない分だけ」の操作を押せる

#### Scenario: 新規サーヴァントに備える
- **WHEN** 周回目的が「新規サーヴァントに備える」で、素材 S の必要数が 3、在庫基準が 20、所持数が 12 のとき
- **THEN** 素材 S の不足は 8 として、交換所タブの表示・要約・「足りない分だけ」とボックス計画の不足に使われる

#### Scenario: 備えるときに所持数を入れていない素材
- **WHEN** 周回目的が「新規サーヴァントに備える」で、素材 S の所持数を入れていないとき
- **THEN** 素材 S は不足に数えられず、交換所タブの「足りない分だけ」の操作で素材 S の品目の回数は 0 になる

#### Scenario: 素材全体の効率を見る
- **WHEN** 周回目的が「素材全体の効率を見る」のとき
- **THEN** 不足は「今の育成を進める」と同じ値で、交換所タブの要約とボックス計画の不足の近くに、今の育成で計算していることが表示される

#### Scenario: 周回目的を変えても交換回数は変わらない
- **WHEN** 利用者が交換所タブで「足りない分だけ」の操作をしたあと、周回目的を「今の育成を進める」から「新規サーヴァントに備える」に変えたとき
- **THEN** 品目のラベルと要約は新しい周回目的で求め直され、入れ終えた交換回数は変わらない

## MODIFIED Requirements

### Requirement: 既存ロスターの不足素材からの箱数目標設定
システムは、ボックスイベントについて、本 capability の「イベントページの不足の求め方」に従う不足素材に対し、必要箱数とその育成インパクト（箱の確定報酬が不足素材をどれだけ充当するか）を提示しなければならない (SHALL)。本機能は永続ロスターを**読み取り専用**で利用し、ロスター・所持データを書き換えてはならない (SHALL NOT)。交換所の品目は育成インパクトの充当に含めてはならない (SHALL NOT)（交換所の計算は交換所タブで行う）。

#### Scenario: 既存ロスターの不足素材からの箱数提示
- **WHEN** ログイン済み／ロスター設定済みのユーザーがボックスイベントの計画ページを開いたとき
- **THEN** 「イベントページの不足の求め方」で不足素材を求め、ボックス確定報酬がそれをどれだけ充当するか（育成インパクト）と、満たすために必要な最小箱数・通貨・周回数・消費APが提示される。

#### Scenario: ロスターへの非書き込み
- **WHEN** イベント計画を算出・操作するとき
- **THEN** `ChaldeaState`・所持数・クラウド同期データは一切書き換えられない（read-only）。

#### Scenario: ロスター未設定時のフォールバック
- **WHEN** 未ログイン、またはサーヴァントの育成対象もクラススコアの目標も未設定で計画ページを開いたとき
- **THEN** 育成インパクト表示は省略され、欲しい素材の直接指定（または目標箱数）による算出にフォールバックする。

### Requirement: ロト計画の算出
システムは、選択されたロト型イベントについて、ユーザー入力（目標箱数 または 欲しいアイテム数、所持イベント通貨、周回ノードと1周あたりのドロップ）から、必要イベント通貨・必要周回数・消費AP・確定報酬を算出しなければならない (SHALL)。ボックス計画は交換所の品目を計算に含めてはならず (SHALL NOT)、交換の対価をイベント通貨の必要量に足してはならない (SHALL NOT)。

#### Scenario: 目標箱数からの必要通貨算出
- **WHEN** ユーザーが目標箱数 N を入力したとき
- **THEN** 必要イベント通貨 = `N × 1箱あたりコスト − 所持通貨`、確定獲得素材 = `N × 1箱内容` が算出される。

#### Scenario: 欲しいアイテム数からの必要箱数逆算
- **WHEN** ユーザーがロトで欲しいアイテムの目標個数を入力したとき
- **THEN** その個数を満たす最小の箱数と、それに必要なイベント通貨が算出される。箱の確定報酬で満たせない分は周回ドロップの需要として周回計画に回される。
- **AND** 欲しいアイテムとして選べるのは箱の内容の素材だけで、交換所の品目は選べない。

#### Scenario: 周回層は既存ソルバで解く
- **WHEN** 必要イベント通貨（および直接欲しいイベント素材）が確定したとき
- **THEN** イベント通貨/素材を需要、周回ノードを変数とした `Drops` 互換データを合成して既存 `solve()` に渡し、最小AP/最小周回の周回計画を得る。
- **THEN** `solve()` 本体および恒常ソルバ (`/farming`) の挙動は変更されない。

#### Scenario: ドロップデータのフォールバックと明示
- **WHEN** 対象イベント周回ノードの Atlas ドロップデータが存在しないとき
- **THEN** ユーザーが「1周あたりの通貨/素材ドロップ」を手入力でき、その入力に基づいて周回数が算出される。
- **THEN** 算出結果には、使用したドロップ値のソース（Atlas / 手入力）と概算である旨が表示される。

#### Scenario: 確定報酬と周回ドロップの内訳分離
- **WHEN** 計画結果を表示するとき
- **THEN** 「ボックス確定報酬」と「周回ドロップ見込み」は内訳として分離表示され、需要充足判定は両者の合算で行われる。

#### Scenario: レアボックス報酬の扱い
- **WHEN** ボックスにレアボックス（`isRare`）の報酬が含まれるとき
- **THEN** レア報酬が**素材**の場合は確定報酬として充当計算に含める。
- **THEN** レア報酬が**サーヴァント／礼装／コマンドコード**の場合は「N箱で確定入手」として素材充当とは分離して表示する。

#### Scenario: 交換所の在庫上限での打ち切り
- **WHEN** 不足素材や欲しい素材のうち、交換所に在庫上限のある品目のある素材を、ボックス計画で扱うとき
- **THEN** ボックス計画は交換所の品目で充当せず、在庫上限での打ち切りと警告を出さない。在庫上限での打ち切りは交換所タブの計算だけで扱われる。

#### Scenario: 交換所は箱の計算に入れない
- **WHEN** 交換所の品目の対価が箱を開ける通貨と違うイベント（例: `80549`）で、ボックス計画の目標箱数を入れたとき
- **THEN** 必要イベント通貨は箱の分だけで算出され、結果に交換所の行と交換所の在庫上限の警告は表示されない

### Requirement: ロト計画 UI
システムは、イベントの一覧（`/events`）と、イベントごとのイベントページ（`/events/[id]`）を提供しなければならない (SHALL)。一覧に載るイベントは「KV `event_data_json` に取り込まれたイベント（ロト型イベントと、ロトの無い交換所イベント）」と「イベント機能レジストリに登録されたイベント」の和集合とする。イベントページは、そのイベントで使える機能をセクションとして並べるハブとする。既存の恒常導線 (`/material` → `/farming`) は変更しない。一覧・イベントページは、URL 直打ち以外にアプリ内の常設導線（グローバルナビ等）から到達可能でなければならず (SHALL)、どのページもオーファン（到達不能）であってはならない (SHALL NOT)。画面上の名称は「イベント」「イベント一覧」とし、ロト型に限定した名称（「ボックスイベント」「ロトイベント一覧」）を一覧・ナビの見出しに用いてはならない (SHALL NOT)。

#### Scenario: イベント一覧
- **WHEN** ユーザーが `/events` を開いたとき
- **THEN** KV のイベント（ロトの無い交換所イベントを含む）とレジストリ登録イベントが、同一 ID の重複なく会期情報とともに「開催中・開催予定・終了済み」に分けて一覧表示される。
- **THEN** 各イベントには、そのイベントページで使える機能（「ボックス計画」「交換所」「料理作成」）がバッジで示される。

#### Scenario: KV に無いレジストリ登録イベント
- **WHEN** あるイベントが KV `event_data_json` に存在せず、イベント機能レジストリにのみ登録されているとき
- **THEN** 一覧にはレジストリの表示用メタ（名前・会期）で掲載され、イベントページも開ける。

#### Scenario: 一覧ページへの常設導線（オーファン禁止）
- **WHEN** ユーザーがアプリのどの画面からでもイベント機能を探すとき
- **THEN** グローバルナビゲーション（`components/common/nav.tsx`）に「イベント」の名称で `/events` 一覧への常設エントリが存在し、URL 直打ちなしで一覧ページへ到達できる。
- **AND** ダッシュボードからの個別イベント直行導線（`/events/[id]`）は一覧導線を代替せず、両者が併存する。

#### Scenario: ダッシュボードからのイベントページ導線
- **WHEN** ダッシュボードの開催中イベントカードのイベントが、ハブで機能提供可能な状態（KV `event_data_json` に取り込み済みのイベント ID 集合に含まれる、または静的レジストリに登録されたイベント）であるとき
- **THEN** そのカードに `/events/[id]` への導線が表示される。
- **WHEN** イベントが KV に未取り込みで、静的レジストリにも登録されていないとき（外部メタデータ上で `hasLottery` であっても）
- **THEN** 導線は表示されない（ハブ遷移後の `EventDataMissing` 露出を防止する）。

#### Scenario: 計画ページへの遷移
- **WHEN** ユーザーが一覧からイベントを選ぶ、またはダッシュボードの該当イベントから遷移したとき
- **THEN** そのイベントのイベントページ (`/events/[id]`) が開き、ヘッダー（名前・会期・開催状態）の下に、使える機能が本 capability の「イベントページのセクション構成」に従って表示される。

#### Scenario: 取り込みデータ未存在時の表示
- **WHEN** 対象イベントが KV にもイベント機能レジストリにも存在しないとき
- **THEN** イベントページはエラーにならず、データ未取得である旨のプレースホルダを表示する。

#### Scenario: ロトの無い交換所イベントの掲載
- **WHEN** ロトが無く交換所のあるイベント（例: `80632`）が KV に取り込まれているとき
- **THEN** ダッシュボードの開催中イベントのカードに `/events/[id]` への導線が出て、`/events` 一覧にも交換所のバッジ付きで出る。

### Requirement: イベント機能レジストリ
システムは、イベント ID ごとにイベントページで使える機能（`features`）と必須の表示用メタ（`meta`: 名前・会期）を定義する静的レジストリを持たなければならない (SHALL)。レジストリ単独でイベントが成立するケースを担保するため、表示用メタ（`meta`）は必須プロパティとする (SHALL)。レジストリに載せる情報は、ゲーム内で公開済みのイベント情報に限らなければならない (SHALL)。同一イベントが KV にも存在するとき、表示用メタは KV の値を優先しなければならない (SHALL)。

#### Scenario: 料理作成イベントの登録
- **WHEN** イベント 80614（「カルデア南海大決戦！ ～マジムンアイランドに謎の巨人の影を見た～」）のイベントページを開いたとき
- **THEN** レジストリの登録に従って料理作成セクションが表示される。

#### Scenario: KV とレジストリの両方にあるイベント
- **WHEN** あるイベントが KV のロト型イベントであり、かつレジストリにも登録されているとき
- **THEN** 一覧・ヘッダーの名前と会期は KV の値で表示され、ボックス計画とレジストリ登録機能の両方がタブとして表示される。

### Requirement: イベントページのセクション構成
システムは、イベントページにおいて、イベントが持つ機能ごとに独立したタブを、ヘッダーの下に表示しなければならない (SHALL)。タブは「ボックス」「交換所」「料理作成」とし、この順に並べる (SHALL)。「ボックス」のタブは KV のイベントのロトが1件以上あるイベントでのみ、「交換所」のタブは KV のイベントの交換所が1件以上あるイベントでのみ、「料理作成」のタブはレジストリで料理作成が登録されたイベントでのみ表示しなければならない (SHALL)。ロトの有無によらず、交換所のあるイベントでは「交換所」のタブを表示しなければならない (SHALL)。KV に交換所のデータが無いイベントで、「交換所」のタブを出してはならない (SHALL NOT)。表示するタブが1つだけのイベントでは、タブの列を出さず、その機能を今の見出し（ボックスは「ロト計画」、交換所は「交換所の周回計算」または「交換所の品目」、料理作成は「料理作成」）のセクションとして表示しなければならない (SHALL)。タブの列を出すときは、タブの中に同じ名前の見出しを重ねて出してはならない (SHALL NOT)。

「ボックス」のタブの中身はボックス計画とし、交換所の品目を扱ってはならない (SHALL NOT)。「交換所」のタブの中身は、本 capability の「ロトの無い交換所イベントの周回計画」と、交換所の各 capability（`event-shop-single-list`・`event-shop-servant-exchange` など）に従う。品目がすべてサーヴァント扱いの交換所では品目の一覧だけとし、それ以外では周回計算とする。交換所の周回計算は、ロトのあるイベントでもロトの無い交換所イベントと同じ画面・同じ計算とする (SHALL)。「料理作成」のタブの中身は料理作成セクションとする。各タブの計算アルゴリズムは既存のロジック（ボックス計画、交換所の周回計算、料理作成配分ソルバー等）を用い、同一の入力（素材必要数・所持数・設定値等）に対する算出結果が変わってはならない (SHALL NOT)。ただし、ボックス計画から交換所の配分を外したことによる差と、本 capability の「イベントページの不足の求め方」による素材必要数の変化を除く。料理作成セクションは永続ロスター由来の need および実所持数（`STORAGE_KEYS.POSSESSION`）を入力とするため、共有 URL 等により `/material/result` とロスター内容が異なる場合は配分結果が異なり得る。ボックス計画はドロップデータ（`/api/drops`）に依存せず独立して動作しなければならない (SHALL)。

#### Scenario: ボックス計画セクション
- **WHEN** KV にロト型データがあるイベントのイベントページを開いたとき
- **THEN** 既存のボックス計画（入力モード・箱数・通貨・周回・AP内訳・育成インパクト）が「ボックス」のタブ（タブが1つだけなら「ロト計画」のセクション）として表示され、育成ロスターの不足数は「イベントページの不足の求め方」に従って算出される。
- **AND** ボックス計画の中に交換所の配分・交換所の行・交換所の在庫上限の警告は表示されない。

#### Scenario: 料理作成セクションの need は永続ロスター由来（read-only と旧設定移行維持）
- **WHEN** ロスター設定済みのユーザーが料理作成セクションを表示したとき
- **THEN** 料理作成アドバイザーは、「イベントページの不足の求め方」の必要数（サーヴァントの育成とクラススコアの目標の合計）と、実所持数（`STORAGE_KEYS.POSSESSION`）を受け取り、周回目的・ストック目標設定に従った実効不足として配分を計算する。
- **THEN** ロスター・クラススコアの目標・所持数・周回目的・ストック目標設定は純粋な読み取り（read-only）として参照され、キー未存在時でも初期値の自動保存等による `ChaldeaState`・所持数・クラウド同期対象データの書き換え・汚染は発生しない (SHALL NOT)。
- **AND** `FARMING_PURPOSE` キーが未保存で旧キー（`QUEST_EFFICIENCY_SHORTAGE_ONLY`, `STOCK_ENABLED`）が残る端末では、自動書き込みを伴わずに旧設定（`all` / `reserve` / `training`）をメモリ上で復元する移行経路が維持される。明示的な切り替え操作時のみ保存が行われる。

#### Scenario: 周回目的が all のときの料理作成セクション
- **WHEN** ユーザーの周回目的が `all`（すべて）のとき
- **THEN** 料理配分計算のための有限目標は `training`（育成）としてフォールバック計算される。
- **AND** UI 上に「配布評価は今の育成を使用」（`common:farming-purpose-advisor-fallback`）の注記が表示される。

#### Scenario: 素材データ取得中・取得失敗・部分欠落時のセーフガード
- **WHEN** ロスター設定済みだが、サーヴァント必要素材（素材カタログ `/api/material-catalog`）が取得中のとき、またはドロップデータが取得中（`drops.isLoading === true`）のとき
- **THEN** 配分計算は開始せず、ローディング状態を表示する。
- **WHEN** サーヴァント必要素材の取得に失敗したとき、一部サーヴァントの素材データが欠落したとき（部分欠落）、またはドロップ取得完了後（`drops.isLoading === false`）に正の need（need > 0）に関与するカタログ・ドロップ率・クエストデータの欠落が検知されたとき
- **THEN** 削減周回/APの過大評価・誤計算を防ぐため配分計算を行わず、データ不整合のエラーメッセージと再試行案内を表示する。

#### Scenario: ロスター未設定時の料理作成セクション
- **WHEN** サーヴァントの育成対象もクラススコアの目標も未設定のユーザーが料理作成セクションを表示したとき
- **THEN** 配分計算は行わず、育成対象を設定すると料理配分を算出できる旨と、その設定画面への導線を表示する。

#### Scenario: 機能を持たないセクションは出さない
- **WHEN** イベントが KV のロト型データを持たないとき
- **THEN** 「ボックス」のタブとボックス計画のセクションは表示されない。

#### Scenario: ロトの無い交換所イベントのページ
- **WHEN** ユーザーが、ロトが無く交換所のあるイベント（例: `80632`）で、料理作成の登録の無いイベントのイベントページを開いたとき
- **THEN** タブの列は表示されず、ボックス計画も表示されず、交換所のセクション（「交換所の周回計算」の見出しの交換所の周回計算）が表示される。
- **AND** 品目は通貨ごとに分かれず1つの一覧に並び、その下の通貨ごとのカードに通貨名と全交換に要る合計が出る。

#### Scenario: ロトのあるイベントの表示は変わらない
- **WHEN** ユーザーが、ロトのあるイベントのイベントページを開いたとき
- **THEN** ボックス計画の入力と結果は、交換所の配分・交換所の行・交換所の在庫上限の警告が無くなることを除いて今までどおり表示される。

#### Scenario: ロトと交換所の両方があるイベント
- **WHEN** ユーザーが、ロトと交換所の両方があるイベント（例: `80549`）のイベントページを開いたとき
- **THEN** ヘッダーの下に「ボックス」「交換所」のタブがこの順に表示され、「交換所」のタブには、ロトの無い交換所イベントと同じ交換所の周回計算（一覧の上の操作、通貨ごとの所持数と必要量、周回の内訳）が表示される。
- **AND** 「交換所」のタブの必要量は、品目ごとの対価の通貨ごとに求められ、箱を開ける通貨の必要量に足されない。

#### Scenario: 交換所と料理作成があるイベント
- **WHEN** ユーザーが、ロトが無く交換所があり、レジストリで料理作成が登録されたイベント（例: `80614`）のイベントページを開いたとき
- **THEN** 「交換所」「料理作成」のタブがこの順に表示される。

#### Scenario: 通貨名を持たない古いデータ
- **WHEN** 交換所のエントリーに通貨の表示名が保存されていないとき
- **THEN** 交換所のタブ（またはセクション）は通貨の見出しに通貨の ID を含む表示（「名前不明のアイテム（ID …）」）を出し、エラーにならない。

### Requirement: ロトの無い交換所イベントの周回計画
システムは、イベントページの交換所タブ（ロトの無い交換所イベントでは交換所のセクション。以下同じ）で、交換所の品目ごとに交換する回数を選べなければならない (SHALL)。ロトのあるイベントの交換所タブも、この要件に従わなければならない (SHALL)。回数の初期値は0とし、在庫上限のある品目は上限を超えて選べてはならない (SHALL NOT)。在庫上限のある品目をすべて上限まで選ぶ操作を、交換所の上部ですべての通貨にまとめて提供しなければならない (SHALL)。通貨ごとの「上限まで選ぶ」の操作は、上部の操作と役目が重なるため設けない（#168 のプレビューへのオーナーの指摘による判断）。在庫上限の無い品目は、利用者が回数を入れたときだけ数える (SHALL)。

システムは、通貨ごとに所持数を入れられなければならず (SHALL)、通貨ごとの必要量を「選んだ交換の対価の合計 − 所持数（0未満は0）」として表示しなければならない (SHALL)。必要量が1以上の通貨があり、イベントの周回クエストにドロップの統計があるとき、システムは通貨ごとの必要量をすべて満たす AP 最小の周回の内訳を、既存のソルバーで1回に求めて表示しなければならない (SHALL)。1周で複数の通貨が落ちるクエストは、それぞれの通貨の必要量に同時に効くものとして扱わなければならない (SHALL)。表示は、クエストごとの周回数、合計の周回数と AP、必要量が1以上の通貨ごとの見込み獲得量とする (SHALL)。必要量が1以上の通貨のうち、どの周回クエストのドロップの統計にも現れないものがあるときは、その通貨名と、周回では集められないことを示さなければならず (SHALL)、その通貨を満たしたかのような周回の内訳として示してはならない (SHALL NOT)。ドロップの統計にイベントのボーナス（礼装・サーヴァント）が含まれないことを、周回の内訳の近くに示さなければならない (SHALL)。

周回クエストにドロップの統計が無いときは、周回の内訳を出さず、ドロップの統計が無いため周回を出せないことを示さなければならない (SHALL)。選んだ交換が無い、または所持数で足りるときは、周回は不要であることを示さなければならない (SHALL)。交換所タブの計算は、同じページのボックス計画の入力（目標箱数・所持通貨など）を使ってはならず (SHALL NOT)、ボックス計画の算出結果を変えてはならない (SHALL NOT)。交換所の一覧の既存の表示（通貨ごとの全交換の合計、上限なしの表示、通貨名が無いときの ID の見出し）は保たなければならない (SHALL)。

#### Scenario: 1種類の通貨の交換を選ぶ
- **WHEN** 80632 で、武蔵うどんを対価にする品目を合計1,200個分選び、武蔵うどんの所持数を200と入れる
- **THEN** 武蔵うどんの必要量は1,000と表示され、武蔵うどんを1,000個集める AP 最小の周回の内訳（クエストごとの周回数、合計の周回数と AP）が表示される

#### Scenario: 複数の通貨を同時に集める
- **WHEN** 3種類の通貨それぞれに必要量があり、3種類が同時に落ちる周回クエストがある
- **THEN** 3種類の必要量をすべて満たす周回の内訳が1つ表示され、通貨ごとの見込み獲得量はそれぞれの必要量以上になる

#### Scenario: 上限まで選ぶ
- **WHEN** 交換所の上部で「全部交換」を押す
- **THEN** すべての通貨で在庫上限のある品目が上限の回数で選ばれ、在庫上限の無い品目は0のままになる。通貨ごとのカードには上限まで選ぶ操作が無い

#### Scenario: ドロップの統計が無い
- **WHEN** 交換所はあるが、周回クエストのドロップの統計がまだ無いイベントで交換を選ぶ
- **THEN** 通貨ごとの必要量は表示され、周回の内訳の代わりに、ドロップの統計が無いため周回を出せないことが表示される

#### Scenario: 周回では落ちない通貨がある
- **WHEN** 必要量のある通貨のうち1種類が、どの周回クエストのドロップの統計にも現れない
- **THEN** その通貨名と、周回では集められないことが表示され、ほかの通貨の周回の内訳はその通貨を除いた必要量で表示される。必要量のある通貨がすべてそうなら、周回の内訳は出さない

#### Scenario: 所持数で足りる
- **WHEN** 選んだ交換の対価の合計が、どの通貨も所持数以下である
- **THEN** 周回は不要であることが表示される

#### Scenario: ボックスのあるイベントの交換所タブ
- **WHEN** 80549 の交換所タブで、ある通貨を対価にする品目を選び、ボックスのタブで目標箱数を変えたとき
- **THEN** 交換所タブの必要量と周回の内訳は目標箱数によらず同じで、ボックスのタブの必要イベント通貨は交換所タブで選んだ交換によらず同じである
