# Design

## Context

### 交換所から育成計画と所持数を使えるか（確認済み）

ロトの無い交換所イベントでは、`app/events/[id]/page.tsx`（サーバー）が KV のイベントを読み、`components/events/EventHubClient.tsx`（`'use client'`）が `EventShopList` を出す。育成計画と所持数は、どちらもブラウザの localStorage にあり、クライアントの部品から読める。サーバーや D1 を新しく読む必要は無い。

- 育成計画: `hooks/use-roster-need.ts` の `useRosterNeed()`。`STORAGE_KEYS.MATERIAL` の育成対象から `getMaterialsForServantIds` で素材を取り、`computeTotalNeed` で素材ごとの総必要数（atlasId → 個数）を返す。状態は `empty`（育成対象なし）・`loading`・`error`（一部の取得に失敗）・`ready` の4つ。localStorage には書かない
- 所持数: `useLocalStorage(STORAGE_KEYS.POSSESSION, {}, { lazyWrite: true })`。所持数のページ（`PossessionModal` など）が保存する実所持数で、atlasId の文字列 → 個数（`number | undefined`）。`STORAGE_KEYS.ITEMS` は周回目標で、キーも drops の `item.id` と体系が違う。箱計画（`EventPlannerClient`）は既存の挙動を保つために `ITEMS` を読んでいるが（`openspec/specs/event-planner/spec.md`）、`EventCraftSection` は `POSSESSION` を読んでおり（event-hub-page の design で実所持数と周回目標を分けると決めた）、この change はそちらに合わせる
- 箱計画（`EventPlannerClient` の roster モード）は、`useRosterNeed` と `ITEMS` から `computeShortfall`（必要数 − 所持数、0 以下は除く）を出している。`EventCraftSection` も `useRosterNeed` を使い、`empty` のときに「育成対象を設定する」（`/material`）のリンクを出している
- 交換所の品目の `itemId` は atlasId で、`computeShortfall` のキーと同じ ID 体系（`computeRosterImpact` が `shopItem.itemId` で突き合わせている）

`useRosterNeed` は、hook を呼ぶ部品ごとに `getMaterialsForServantIds` で素材を取得する（`lib/get-materials.ts` にキャッシュは無い）。交換所だけのイベントでは `EventPlannerClient` は出ないが、`isShopOnlyEvent` は craft との組み合わせを除外しないので、shop と craft が両方あるイベントでは `EventShopList` と `EventCraftSection` が二重に取得する。今のレジストリ（`data/event-features.ts`）に該当するイベントは無いので、この change では取得を共有せず、許容する。

### 育成計画で扱う素材と、扱わない品目をどう見分けるか（確認済み）

育成計画の総必要数（`computeTotalNeed`）に現れうるのは、サーヴァントの霊基再臨・スキル・アペンドスキルの素材（`ascensionMaterials`・`skillMaterials`・`appendSkillMaterials`）と QP（atlasId 1）だけである。必要数が 0 の品目について「育成計画で扱う素材だが今は使わない」（A）と「このサイトが育成計画で扱っていない品目」（B）を見分けるには、全サーヴァントの3種の素材に現れる atlasId の集合が要る。

Atlas の `nice_servant.json` と `nice_item.json`（JP、2026-10-26 取得）で、2つの候補の集合を比べた。

| 候補 | 件数 | 合わない点 |
|---|---|---|
| `lib/get-items.ts` の `getItems` が使う種類（`qp`・`skillLvUp`・`tdLvUp`） | 123 | 育成計画に出ない22件を含む（聖杯・聖杯の雫、星光の砂・トーチ・星冠の結晶、遡行の羅針盤、夢火、コード・オープナー／リムーバー）。逆に、霊基再臨に使う種類 `eventItem` の特殊な素材52件（黄金髑髏・蘭奢待など）を含まない |
| 全サーヴァントの3種の素材の和集合 | 152 | 育成計画に出うる素材と一致する（種類は `skillLvUp` 86・`tdLvUp` 14・`eventItem` 52） |

`getItems` の種類で見分けると、交換所に聖杯やコード・リムーバーが並んだときに「使わない」（A）になり、オーナーの意図（サイトが対応していないだけで要るかもしれない品目は B にする）に反する。和集合を使う。伝承結晶（6999、`skillLvUp`）はスキルの素材なので和集合に入り A になる。

実データでの分かれ方（イベント 80627 の交換所のうち `purchaseType` が `item` の品目）: 秘石・魔石・輝石・ピース・モニュメント・強化素材・伝承結晶は A、コード・リムーバー（5003）・巡霊の葉（48、`revivalItem`）・他のイベントアイテム（首輪ドーナッツ・三日月パイ、`eventItem`）は B、QP は対象外になる。種火・フォウくん（英霊結晶）・ピース・オブ・メモリー（礼装）は `purchaseType` が `servant`、霊衣開放権は `costumeRelease` で、取り込み（`compactShop` は `purchaseType` が `item` のものだけを取る）の時点で交換所のデータに入らず、今の交換所の画面にも並ばない。並べるかはこの change の範囲外とし、並べたときはその ID が和集合に入らないので B になる。呼符（4001、`gachaTicket`）・サーヴァントコイン（`svtCoin`）も和集合に入らず B になる。

和集合は、素材カタログ（KV の `material_catalog_v1`、`/api/material-catalog` が返す）の `materials` から `lib/material-catalog.ts` の `materialCatalogItemIds` で出せる。素材カタログは全サーヴァントの素材を持ち、`hooks/use-material-catalog.ts` の `useMaterialCatalog()` がクライアントで取得している（育成計画のページと絆のページが使う。応答は `Cache-Control: public, max-age=300`、上限 5MB）。

### 今の交換所の画面（#168・#177 の後）

- 上部: 周回の合計の1行、「全部交換」の操作（#177 で「効率の良いところまで交換」と区切りの線は消えた）
- 通貨ごとのカード: 品目の行（順位・品目・1回の個数・在庫上限・1回の対価・回数・効率）、所持数（通貨）、必要量
- 周回の内訳、AP 予算

## Goals / Non-Goals

**Goals:**
- 品目の行に、育成計画から見た要る・要らないを出し、計画の対象外の品目は利用者が要る・要らないを選べるようにする
- 不足素材のみを交換回数に入れる操作と、そのときに交換所で埋まらない不足の要約を出す

**Non-Goals:**
- 周回で直接落ちる素材（イベントの周回クエストのドロップ）で不足が埋まる分。周回の内訳はイベント通貨を集める周回で、素材のドロップを不足に充てると、要る分の計算と周回の計算が互いに依存する。まず交換所だけで埋まる分を出し、ドロップで埋まる分は別 issue にする（オーナー判断 2026-10-26）
- 通貨（イベントアイテム）の所持数を、所持数のページの値から自動で入れること。今の通貨の所持数の入力のまま
- 交換回数と、計画の対象外の品目の要る・要らないの保存（決定 7）
- 箱計画（ロトのあるイベント）の roster モードの変更
- 聖杯・夢火・コード・オープナーなど、計画の対象外の品目を育成計画に取り込むこと
- `purchaseType` が `item` でない交換（種火・フォウくん・礼装・霊衣開放権）を交換所のデータと画面に入れること

## Decisions

### 1. 不足は `computeShortfall` と同じ定義で、`EventShopList` で求める

`EventShopList` で `useRosterNeed()` と所持数（`STORAGE_KEYS.POSSESSION`、`lazyWrite: true`）を読む。`ready` のときだけ、`computeShortfall` と同じ「総必要数 − 所持数（0 未満は 0）」を求める。`useRosterNeed` が返す `totalNeed` をそのまま使い、所持数を引くだけの純粋関数を `lib/event-shop-summary.ts` に置く。`computeShortfall` を呼ぶと総必要数を作り直すため、使わない。所持数の正規化は `EventPlannerClient` と同じく `Number(v) || 0` とする。

QP（atlasId 1）は `computeTotalNeed` が総必要数に足しているが、交換所の QP の品目で育成計画の QP を埋める使い方は想定せず、桁も他の素材と合わないので、対象から外す（オーナー判断 2026-10-26）。QP の品目にはラベルを出さず、不足素材のみでは 0 回にし、要約に数えない。

### 2. 品目の状態は、育成計画で扱う素材の集合で A と B に分ける

`EventShopList` で `useMaterialCatalog()` を呼び、`materialCatalogItemIds(catalog.materials)` で育成計画で扱う素材の集合を作る（`useMemo`）。品目の状態は次の順に決める純粋関数を `lib/event-shop-summary.ts` に置く。

1. QP（atlasId 1）: 状態なし
2. 総必要数が 1 以上: 不足が 0 なら「足りている（交換不要）」、1 以上なら「あと N 個」。素材カタログの集合に入っているかを見ない（総必要数は全サーヴァントの素材から出るので、集合に入っているはず。素材カタログが新しいサーヴァントに追いついていないときも、必要数を優先する）
3. 総必要数が 0 で、集合に入る: 「使わない」（A）
4. 総必要数が 0 で、集合に入らない: 「計画の対象外」（B）

素材カタログを読み込み中か、読み込みに失敗したときは、3・4 を見分けられない。このときは 1・2 だけを出し、必要数 0 の品目にはラベルも切り替えも出さず、「計画の対象外の品目を見分けられない」の1行を出す（失敗のときは `useMaterialCatalog` の `reload` で再読み込みできるようにする）。不足素材のみの操作は、2 の品目だけで使える。

採らなかった案:
- `getItems` の種類（`qp`・`skillLvUp`・`tdLvUp`）で見分ける。Context の比較のとおり、聖杯などが A になり、霊基再臨の特殊な素材が B になる
- サーバー（`page.tsx`）で素材カタログを読んで集合を渡す。素材カタログは最大 5MB で、Workers の無料プランの CPU 時間（10ms）で JSON を parse すると打ち切られうる（`refresh-event-data.yml` の冒頭の方針と同じ理由）。集合の ID だけを返す API を足しても、同じ parse が要る
- KV の交換所のデータに品目の種類を足す。取り込みと KV の形を変えるうえ、種類だけでは霊基再臨の特殊な素材（`eventItem`）とイベントの通貨（同じ `eventItem`）を見分けられない

### 3. 不足素材のみの回数は新しい純粋関数で出し、`allocateShop` は使わない

`lib/event-shop-summary.ts` に、交換所・不足（atlasId → 個数）・「要る」を選んだ計画の対象外の品目（交換所の配列の添字の集合）から、品目ごとの交換回数（`ShopExchangeCounts`、キーは交換所の配列の添字）と、素材ごとに交換所で埋まらない残りと、在庫上限が無くて回数を入れられなかった「要る」の品目を返す純粋関数を置く。

- 不足のある素材: 交換所の元の順に品目を見て、まだ埋まっていない不足を `qty` で割って切り上げ、`limitNum > 0` なら `limitNum` で打ち切り、得る個数を差し引く（同じ素材の品目が複数あるときも元の順。オーナー判断 2026-10-26）
- 「要る」の計画の対象外の品目: `limitNum > 0` なら `limitNum`。`limitNum` が 0（在庫上限なし）なら 0 回にし、回数を手で入れるよう品目の行に示す。上限の無い品目（呼符・種火など）に入れる数は、育成計画から決まらないため
- それ以外: 0 回

採らなかった案: 箱計画の `allocateShop` を使う。`allocateShop` は品目ごとに同じ需要を丸ごと当てるので、同じ素材の品目が複数あると二重に数える。また `limitNum` が 0（在庫上限なし）の品目を `Math.min(..., 0)` で 0 回にしてしまう。直すと箱計画の結果が変わるので、この change では触れない。

### 4. 操作は交換回数を置き換えるだけで、計算は既存の流れに乗せる

「不足素材のみ」は、3 の交換回数で `counts` を置き換える（`setCounts`）。必要量・周回の内訳・合計・AP 予算は、今の `computeShopCurrencyNeeds` → `planShopCurrencies` の流れでそのまま出る。育成計画・所持数・要る・要らないの選択が変わっても `counts` は変えない。操作は「全部交換」の隣に置き、説明の1行（例:「育成計画で足りない分と、要るにした品目」）を添える。

### 5. 交換所で埋まらない不足と要約

3 の関数が返す残りから、在庫上限まで交換しても残る素材の品目に「交換所では N 個足りない」を出す。同じ素材の品目が複数あるときは、その素材の最後の品目の行に出す。要約は、交換所に品目のある素材のうち不足が 1 以上のもの（QP を除く）の数と、残りが 0 になるものの数を、上部の操作の近くに1行で出す。計画の対象外の品目は数えない。要約と「交換所では N 個足りない」は、操作を押す前から、不足の分を全部交換したと仮定して出す。押す前と後で変わらないので、利用者が回数を手で変えても要約は変えない。

### 6. 育成計画が使えないとき

`empty` のときは、`EventCraftSection` と同じ文言の型で「育成対象を設定すると、足りている品目と要る分が分かります」と `/material` へのリンクを出し、操作を `disabled` にする。`loading` は読み込み中の1行、`error` は既存の `event-roster-material-error` の文言を出し、どちらも操作を `disabled` にする。これらのときは、品目のラベルと、計画の対象外の品目の切り替えも出さない。どの状態でも、品目の行・全部交換・交換回数の入力・周回の内訳は今のまま出す。

### 7. 要る・要らないの選択は保存しない

計画の対象外の品目の要る・要らないは、`EventShopList` の `useState`（交換所の配列の添字の集合）に持ち、localStorage にも D1 にも保存しない。画面を開くたびに、すべて「要らない」から始まる。

理由:
- オーナーは、イベントごとに毎回選び直す前提とした
- 交換回数も保存しない（epic #129 の「やらないこと」E2）。回数を保存しないまま選択だけを残すと、開き直したときに「要る」なのに回数が 0 の品目が並び、どちらが今の計画か分かりにくい
- 保存するなら、イベントと品目ごとのキーが要り、終わったイベントのぶんが localStorage に溜まる。クラウド同期（`CLOUD_SYNC_KEYS`）に入れるかも決める必要がある

### 8. 画面

- 品目の行: 品目名の下に小さなラベルで「足りている（交換不要）」「あと N 個」「使わない」「計画の対象外」を出す。「足りている」と「使わない」は行の文字を薄くして、交換不要がひと目で分かるようにする。「交換所では N 個足りない」は「あと N 個」の横に出す
- 計画の対象外の品目: ラベルの横に「要る／要らない」の2択の切り替え（`role="radiogroup"` か2つのボタン、44px 以上の押せる大きさ）を出す。在庫上限の無い品目で「要る」を選んで不足素材のみを押したら、「上限なし: 回数を入れてください」を出す
- 上部: 「全部交換」の隣に「不足素材のみ」と説明の1行。その下に要約の1行、または未設定・読み込み中・失敗の1行、素材カタログを読めないときの1行
- 375px で横スクロールを出さない。ラベルと切り替えは品目名の下に折り返す
- 文言は `locales/ja.json` と `locales/en.json` に足す

## Risks / Trade-offs

- [同じ素材が通貨の違う複数の品目にあるとき、交換所の元の順に割り当てるので、対価の安い品目が後回しになり、周回数が最小にならないことがある] → 交換所で埋まるか・埋まらないかの判定は変わらない。オーナーの判断で元の順に決め、利用者は回数を手で変えられる
- [素材カタログ（最大 5MB）を交換所の画面でも取得する] → 応答は `max-age=300` で、育成計画のページを開いた後ならブラウザのキャッシュが効く。読めなくても、必要数のある品目のラベルと不足素材のみは使える（決定 2）
- [周回で落ちる素材を数えないので、要る分を多めに交換させる] → Non-Goals に書き、別 issue にする。要約の文言は「交換所で埋まる」とし、周回のドロップを含むと読めないようにする
- [育成計画の素材の取得は通信が要る] → `useRosterNeed` の既存の取得をそのまま使う。失敗しても交換所の既存の機能は使える（決定 6）

## Migration Plan

保存先のキーと KV のデータの形は変えない。育成計画・所持数・素材カタログは読むだけ。実装 PR を戻せば、元の表示に戻る。
