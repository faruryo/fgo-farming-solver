# Design

## Context

動機は proposal.md の Why を参照。

今の交換所（`components/events/EventShopList.tsx`、2026-11-07 にコードを読んで確かめた）は次のとおり。

- 品目名は `ItemWantPopover` のボタン（Base UI の `Popover` のトリガー）。ポップアップの中の「欲しい／いらない」（`ItemWantToggle`）を選ぶと、設定を変えてから `setOpen(false)` でポップアップを閉じる
- Base UI の `Popover.Popup` は、閉じるとフォーカスをトリガーへ戻す（`finalFocus` の既定）。行が動くと、戻す先のトリガーが描き直しで消えるので、フォーカスは body に落ちる
- 表（`ShopTable`）は「欲しい」の行を、効率のある行（`ranked`、順位つき）、効率の無い行（`unpriced`）の順に並べる。両方あるときは「効率順」「AP 換算なし」の見出しの行が入る。行の key は交換所の配列の添字の先頭（`row.indices[0]`）
- 畳んだ「いらない品目」（`UnwantedRows`）は、表の後に「いらない」の行が1つ以上あるときだけ描く。開閉の見出しはボタン（`aria-expanded`）で、開閉の状態はこの部品の中に持ち、保存しない
- アイテム一覧（`/items`）の切り替えは行の中に常に出ていて、切り替えても行は動かない。フォーカスはそのまま残るので、この change の対象にしない
- 既存の検査は `components/events/EventHubClient.test.tsx` の「育成計画から見た要る・要らない」にあり、品目名を押してポップアップの radio を押す手順（`chooseWant`）と、見出しの取り方（`unwantedSummary`）がある

## Goals / Non-Goals

**Goals:**

- issue の3つの場合（「いらない」にした、「欲しい」に戻した、最後の1件を戻して畳みが消えた）で、フォーカスを body に落とさない
- 行き先をテストで確かめる

**Non-Goals:**

- スクリーンリーダーへの読み上げ（「聖杯をいらない品目に移しました」のような live region）を足すこと。issue の完了条件はフォーカスの行き先だけなので、要るかは別に決める
- アイテム一覧（`/items`）と、品目がすべてサーヴァント扱いの交換所の一覧（ポップアップの無い一覧）
- タップで操作したときの見た目や並びを変えること

## Decisions

### 判断点

画面のモック（3つの場合ごとに、案ごとのフォーカスの位置）を、仕様 PR の説明の HTML に載せる。

#### 判断点1: 「いらない」にしたあと、フォーカスをどこへ移すか

操作: キーボードで聖杯の品目名を開き、「いらない」を選ぶ。表は呼符・聖杯・伝承結晶の順。

推奨: **A. 表で次にあった行の品目名**（次が無ければ前の行、表に行が残らなければ「いらない品目」の見出し）。

| 案 | 聖杯の後のフォーカス | 続けて何品目も「いらない」にする | 移した先の確認 | 押したところからの距離 |
|---|---|---|---|---|
| **A. 次の行の品目名（推奨）** | 伝承結晶の品目名 | Enter で次をすぐ開ける | 聖杯がどこへ行ったかは見えない（見出しの件数で分かる） | 同じ位置 |
| B. 畳んだ「いらない品目」の見出し | 「▸ いらない品目 1 件」 | 次の品目へ戻るのに表を Shift+Tab でさかのぼる | 件数が増えたことがすぐ分かる | 表の最後まで飛ぶ |
| C. 表（カード）の先頭 | 1行目の品目名か表の見出し | 毎回先頭からたどり直す | 分からない | 先頭まで戻る |

根拠: 「いらない」にする操作は、表を上から読みながら要らない品目を続けて外す使い方が考えられる。A はフォーカスを押した場所に留めるので、Tab や Enter の操作を途切れさせない。B は移した先を確かめられるが、行の多い交換所では、1品目ごとに表の最後まで飛んでからさかのぼる。C は位置を失う点で body に落ちるのと大差がない。A で取りこぼすのは、聖杯がどこへ移ったかをフォーカスで示さないことで、見出しの件数（「いらない品目 N 件」）が増えることで代える。

#### 判断点2: 「いらない品目」から「欲しい」に戻したあと、フォーカスをどこへ移すか

操作: 開いた「いらない品目」に聖杯と呼符がある。聖杯の名前を開き、「欲しい」を選ぶ。

推奨: **A. 表に戻った行の品目名**（画面の外なら見える位置までスクロールする）。

| 案 | 聖杯の後のフォーカス | 戻した品目に回数を入れる | 続けて何品目も戻す | 画面の動き |
|---|---|---|---|---|
| **A. 表に戻った行の品目名（推奨）** | 表の聖杯の品目名 | Tab 1回で聖杯の回数の入力欄 | 「いらない品目」まで Tab でたどり直す | 戻った行までスクロールする |
| B. 「いらない品目」の中の次の名前 | 呼符の名前 | 表の聖杯の行を探しに行く | Enter で次をすぐ開ける | 動かない |
| C. 畳んだ「いらない品目」の見出し | 「▾ いらない品目 1 件」 | 表の聖杯の行を探しに行く | 見出しから Tab で次の名前 | 動かない |

根拠: 「欲しい」に戻すのは、その品目に回数を入れて計算に入れたいからで、次の操作は戻した行の回数の入力になる。A はその入力欄の隣にフォーカスを置き、行が戻った位置も同時に見せる（効率順で表のどこに入ったかが分かる）。B は続けて戻す使い方には向くが、「いらない」を戻すのは押し間違いを直すときか、計画が変わった1〜2品目を戻すときが主で、続けて何品目も戻す場面は少ない。C は戻した品目からも次の候補からも1歩ずれる。A で取りこぼすのは、続けて何品目も戻すときに、毎回表の最後の「いらない品目」までたどり直すことで、「いらない品目」は開いたまま残るので、Shift+Tab ではなく Tab で表の後ろへ進めば着く。

#### 判断点3: 最後の1件を「欲しい」に戻して、「いらない品目」の畳みが消えるときの行き先

操作: 「いらない品目」が聖杯の1件だけ。聖杯を「欲しい」に戻すと、見出しごと消える。

推奨: **A. 判断点2と同じく、表に戻った行の品目名**。

| 案 | 聖杯の後のフォーカス | 判断点2との揃い | 判断点2で B・C を選んだときの意味 |
|---|---|---|---|
| **A. 表に戻った行の品目名（推奨）** | 表の聖杯の品目名 | 同じ規則なので例外が無い | B・C の代わりの行き先として使える |
| B. 表の最後の行の品目名 | 表の最後の行（聖杯とは限らない） | 別の規則になる | 消えた見出しのいちばん近くに留まる |
| C. 表（カード）の先頭 | 1行目の品目名か表の見出し | 別の規則になる | 位置を失う |

根拠: 判断点2で A を採るなら、最後の1件でも戻った行は表にあるので、同じ規則のままで行き先が消えない。B は消えた見出しの近くに留まるが、聖杯でない行にフォーカスが行き、何を戻したかが分からなくなる。C は位置を失う。判断点2で B か C を採るときは、行き先（次の名前や見出し）が消えるこの場合だけ別の行き先が要り、そのときも A が戻した品目に最も近い。A で取りこぼすものは判断点2の A と同じ。

### 決めたこと

- **ポップアップで今と同じ設定を選んだとき、または何も選ばずに閉じたとき**: 行が動かないので、今までどおり Base UI の既定で押した品目名へ戻す。行が動くときだけ既定の戻し先を止める（`finalFocus` を使う）。止めずに後からフォーカスを移すと、既定の戻し先が先に消えたトリガーを探して body に落ちるか、後で移した先を上書きするかが、描き直しとポップアップの閉じる順で変わるため
- **行き先を選んだ時点で決め、描き直したあとに移す**: 「いらない」にしたときの次・前の行は、押した時点の表示の並び（`ranked` の後に `unpriced`、見出しの行は数えない）から決める。描き直したあとの並びで探すと、押した行がもう無いので次の行が分からない。行き先は表の部品（`ShopTable`）に1回だけ使う値として持ち、行が動いた描き直しのあとにその品目名（または見出し）へ `focus()` してから消す。見つからないとき（描き直しの前に交換所が変わったなど）は何もせずに消し、後から別の操作のフォーカスを奪わない
- **品目名と見出しの探し方**: 品目名のボタンに行の key（`row.indices[0]`）を表す `data-` 属性を付け、表のカードの中から探す。行ごとの ref の表を持たない。key は交換所の配列の添字なので、行が表と「いらない品目」の間を動いても変わらない
- **スクロール**: `focus()` は既定で要素が見えるまでスクロールするので、それに任せる。判断点2で戻った行が画面の外にあるときも同じ
- **テスト**: `components/events/EventHubClient.test.tsx` の「育成計画から見た要る・要らない」に、spec の各シナリオの検査を足す。フォーカスの確かめは `document.activeElement` が期待する品目名のボタン（または見出し）であることで行い、`document.body` でないことも確かめる。キーボードでの開閉を再現するために、既存の `fireEvent` の手順に合わせる

## Risks / Trade-offs

- [Base UI の `finalFocus` の扱いが版で変わる] → 行が動くときだけ止める作りにし、テストで「同じ設定を選んだときは品目名に戻る」と「動いたときは行き先に移る」の両方を確かめて、版を上げたときに気付けるようにする
- [設定の保存（端末の保存値）が描き直しを遅らせ、行き先がまだ描かれていない] → 行き先は1回だけ使う値として、行が動いた描き直しを待って移す。描き直しの前に見つからなければ移さずに消すので、フォーカスを奪い続けない
- [jsdom ではスクロールを確かめられない] → 見える位置へのスクロールは、tasks の実画面の確認（dev server）で確かめる
