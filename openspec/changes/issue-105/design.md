# Design

## Context

ストームポッド消費なし期間は、`dashboardMeta.podFreePeriods`（期間ごとの開始・終了と対象の questId）として取り込み済みである。ダッシュボード（`NearGoalSection`・`RecommendedQuest`）とクエスト効率ページ（`QuestEfficiencyList`）は、`useDashboardMeta` と `usePodFreeQuests(podFreePeriods, nowSec)` で現在の期間を求め、`QuestIdentity` に `podFree` を渡して印を出している。

絆トラッカーは、`lib/bond/entry-estimate.ts`（サーヴァント別）と `lib/bond/estimate.ts` の `groupByQuest`（クエスト別）で、`questConsumesPod(area)` なら周回数と同数のポッドを数え、`lib/bond/progress.ts` の `timeToGoal` がその合計で到達日数とボトルネックを決める。期間は見ていない（動機は proposal.md の Why）。

## Goals / Non-Goals

**Goals:**
- 候補にポッド無料の印を出す
- 無料期間中の周回を、必要ポッド数と到達見込みに反映する
- 期間が途中で終わることを、見積もりに入れる

**Non-Goals:**
- 期間のデータの取り込み方を変えること（`podFreePeriods` をそのまま使う）
- 候補の並び順を変えること（基本絆ポイント÷実効APのまま）
- 果実やイベント配布の AP を見積もりに入れること（今の到達見込みと同じく自然回復だけ）
- 将来の（まだ始まっていない）無料期間を見積もりに入れること

## Decisions

### 1. 無料と数える周回は「期間の終わりまでに自然回復の AP で回せる分」まで（推奨。オーナーの判断点）

issue は、期間が途中で終わるときに残り周回をすべて無料と数えてよいかを、仕様の段階で決めるとしている。案は次の3つ。

| 案 | 無料と数える周回 | 長所 | 短所 |
|---|---|---|---|
| A | 期間中なら残り周回をすべて | 実装が最小 | 期間が残り1日でも、数百周のポッドが0個になる。ボトルネックの判定が大きくずれる |
| B（推奨） | 期間の残り時間 × 288AP ÷ 実効AP（切り捨て）まで | 到達見込みと同じ「自然回復だけ」の前提で、期間の長さが見積もりに効く | 果実を使えばもっと回せるが、その分は数えない（到達見込みと同じ割り切り） |
| C | 数えない（印だけ出す） | 見積もりが変わらない | issue の「必要ポッド数」「ボトルネック判定」に反映するという目的を満たさない |

B を推奨する。到達見込みはもともと「AP 自然回復(1日288)だけで回す」近似なので、無料期間の周回も同じ前提で数えると、表示どうしの前提がそろう。期間の残り時間は、現在時刻から `currentPeriod.endedAt`（そのクエストを含む期間の終わり）までの秒数を日に直したものを使う（端数の日も含める）。

### 2. 複数のクエストで期間中の AP を分け合う

クエスト別の集計では、無料期間中のクエストが複数ある（冠位研鑽戦とオーディール・コールなど）と、期間中の自然回復の AP を両方で使うことになる。そのため、期間中の AP をそれらのクエストの必要 AP の割合で分け、クエストごとに無料と数える周回数を決める。期間が複数あってクエストごとに終わりが違うときは、クエストごとに自分の期間の終わりまでの AP を上限にし、分け合いは同じ期間に含まれるクエストどうしで行う（期間ごとに割合で分ける）。

サーヴァント別の表示（`entry-estimate`）は、そのサーヴァントの周回だけで決め、分け合いはしない。サーヴァント別はそのサーヴァント単独で回した場合の見積もりで、合計と到達見込みはクエスト別の集計（分け合いあり）を使う。

### 3. 純粋関数に切り出す

「無料と数える周回数」を、期間の残り秒数・実効AP・周回数（と分け合う相手の必要AP）から求める純粋関数として `lib/bond/` に置く。`groupByQuest` と `estimateEntry` は、questId から「期間の終わり（秒）」を引ける入力（`podFreeEndsAt: Map<questId, endedAt>` と `nowSec`）を受け取り、この関数で `pods` を決める。`use-bond-tracker.ts` で `useDashboardMeta` と `usePodFreeQuests` を呼んでこの入力を作る。期間のデータが無いときは空の入力になり、従来と同じ結果になる。

### 4. 画面

- 候補（`servant-card.tsx`）の `QuestIdentity` に `podFree` を渡す（ダッシュボードと同じ印）
- サーヴァント別とクエスト別のポッド数は、無料と数えた周回を引いた値を出す。無料と数えた周回があるときは、見積もりタブに「ポッド無料期間（M/D HH:mm まで）に自然回復で回せる N 周を0個と数えています」の注記を1行出す

## Risks / Trade-offs

- [果実を使えば期間内にもっと回せる] → 到達見込みと同じ割り切りで、注記に「自然回復で回せる分」と書いて前提を示す
- [ローカルの mock には無料期間が無い（`mocks/dashboard.json` の `podFreePeriods` は空）] → 画面の確認では、確認のときだけ mock に期間を足して見る（commit しない）。ロジックはユニットテストで確かめる

## Open Questions

- 決定 1 の B でよいか（オーナーの判断）。A を選ぶ場合は、決定 2 と注記が要らなくなり、仕様の「無料期間が途中で終わる」と「無料期間の AP を分け合う」のシナリオを外す
