# Design

## Context

ストームポッド消費なし期間は、`dashboardMeta.podFreePeriods`（期間ごとの開始・終了と対象の questId）として取り込み済みである。ダッシュボード（`NearGoalSection`・`RecommendedQuest`）とクエスト効率ページ（`QuestEfficiencyList`）は、`useDashboardMeta` と `usePodFreeQuests(podFreePeriods, nowSec)` で現在の期間を求め、`QuestIdentity` に `podFree` を渡して印を出している。

絆トラッカーは、`lib/bond/entry-estimate.ts`（サーヴァント別）と `lib/bond/estimate.ts` の `groupByQuest`（クエスト別）で、`questConsumesPod(area)` なら周回数と同数のポッドを数え、`lib/bond/progress.ts` の `timeToGoal` がその合計で到達日数とボトルネックを決める。期間は見ていない（動機は proposal.md の Why）。

## Goals / Non-Goals

**Goals:**
- 候補にポッド無料の印を出す
- 無料期間中の周回を、必要ポッド数と到達見込みに反映する
- 期間が途中で終わることを、見積もりに入れる

**Non-Goals:**
- 期間のデータの取り込み方を変えること（`podFreePeriods` をそのまま使う）
- 候補の並び順を変えること（基本絆ポイント÷実効APのまま）
- 果実やイベント配布の AP を見積もりに入れること（今の到達見込みと同じく自然回復だけ）
- 将来の（まだ始まっていない）無料期間を見積もりに入れること

## Decisions

### 1. 無料と数える周回は、既定では「期間の終わりまでに自然回復の AP で回せる分」まで（オーナーの判断で B）

issue は、期間が途中で終わるときに残り周回をすべて無料と数えてよいかを、仕様の段階で決めるとしている。案は次の3つ。

| 案 | 無料と数える周回 | 長所 | 短所 |
|---|---|---|---|
| A | 期間中なら残り周回をすべて | 実装が最小 | 期間が残り1日でも、数百周のポッドが0個になる。ボトルネックの判定が大きくずれる |
| B（推奨） | 期間の残り時間 × 288AP ÷ 実効AP（切り捨て）まで | 到達見込みと同じ「自然回復だけ」の前提で、期間の長さが見積もりに効く | 果実を使えばもっと回せるが、その分は数えない（到達見込みと同じ割り切り） |
| C | 数えない（印だけ出す） | 見積もりが変わらない | issue の「必要ポッド数」「ボトルネック判定」に反映するという目的を満たさない |

オーナーの判断（2026-10-21）で、既定は B にし、A は「りんご・石を使う」切り替えで選べるようにする（決定 5）。C は採らない。B を既定にする理由は、到達見込みはもともと「AP 自然回復(1日288)だけで回す」近似なので、無料期間の周回も同じ前提で数えると、表示どうしの前提がそろう。期間の残り時間は、現在時刻から、そのクエストを含む有効な期間の終わり（複数の期間に含まれるときは遅いほう）までの秒数を日に直したものを使う（端数の日も含める）。`usePodFreeQuests` の `currentPeriod` は一番早く終わる期間だけなので使わず、`podFreePeriods` から questId ごとの終わりを作る。現在時刻は、絆トラッカーがすでに使っている `useActiveCampaigns` の `nowSec`（30分単位で切り捨て）を使い、ダッシュボードと前提をそろえる（切り捨てで最大6AP多く数えることがあるが許容する）。実効APが0のクエストは割り算をせず、期間中なら全周を無料と数える。

### 2. 複数のクエストで期間中の AP を分け合う

クエスト別の集計では、無料期間中のクエストが複数ある（冠位研鑽戦とオーディール・コールなど）と、期間中の自然回復の AP を両方で使うことになる。期間中の自然回復の AP は、ポッドを使わないクエストより無料期間のクエストに優先して使う前提にする（ポッドを節約できるので、実際の回し方としても自然）。クエストを期間の終わりの早い順に並べ、現在からその終わりまでの累計の AP から、それより前に割り当てた AP（周回数に切り捨てる前の値）を引いた分を、終わりが同じクエストどうしで必要 AP の割合で分ける。各クエストに割り当てる AP はその必要 AP を上限にし、余りは終わりの遅い期間のクエストに回す。頭打ちにしないと、先に終わる期間で使われない AP が後のクエストに回らず、B の前提より多くポッドを数えるため。同じ時間帯の AP を2回数えないため、期間ごとに独立に割り当てない。実効APが0のクエストは AP を使わないので分け合いに入れない。ストームポッドを消費しないクエストも、期間の対象に入っていても無料と数える意味がないので分け合いに入れない。

サーヴァント別の表示（`entry-estimate`）は、そのサーヴァントの周回だけで決め、分け合いはしない。サーヴァント別はそのサーヴァント単独で回した場合の見積もりで、合計と到達見込みはクエスト別の集計（分け合いあり）を使う。

### 3. 純粋関数に切り出す

「無料と数える周回数」を、期間の残り秒数・実効AP・周回数（と分け合う相手の必要AP）から求める純粋関数として `lib/bond/` に置く。`groupByQuest` と `estimateEntry` は、questId から「期間の終わり（秒）」を引ける入力（`podFreeEndsAt: Map<questId, endedAt>` と `nowSec`）を受け取り、この関数で `pods` を決める。questId → 期間の終わり（複数あれば遅いほう）の表は、`podFreePeriods` と `nowSec` から作る純粋関数として `lib/bond/` に置く。有効な期間の判定は `computePodFreeQuestsState` と同じ式（`startedAt <= nowSec && endedAt > nowSec`）にする。`use-bond-tracker.ts` はこの関数を呼ぶだけにする。期間のデータが無いときは空の入力になり、従来と同じ結果になる。

### 4. 画面

- 「りんご・石を使う」の切り替えを、ティーポットの切り替え（`components/bond/index.tsx`）の並びに置く

- 候補（`servant-card.tsx`）の `QuestIdentity` に `podFree` を渡す（ダッシュボードと同じ印）
- サーヴァント別とクエスト別のポッド数は、無料と数えた周回を引いた値を出す。ストームポッドを消費するクエストでは、0個になってもカードのストームポッドの欄を出す（今は `result.pods > 0` のときだけ出しているので、ポッドを使わないクエストと区別できない）
- 無料と数えた周回があるときは、見積もりタブに「ポッド無料期間に自然回復で回せる N 周を0個と数えています（M/D HH:mm まで）」の注記を1行出す。N は全クエストの合計、日時は無料と数えたクエストの期間の終わりのうち一番遅いもの。「りんご・石を使う」がオンのときは「ポッド無料期間中の N 周をすべて0個と数えています（M/D HH:mm まで）」にする

### 5. 「りんご・石を使う」で A に切り替える

どれだけ周回したいかは人によって違う（オーナーの判断の理由）。果実や聖晶石で AP を回復して期間内に回し切るつもりの人には、B の数え方は必要ポッドを多く見せすぎる。そこで切り替えを足し、オンなら期間中のクエストの残り周回をすべて0個と数える（A）。オンのときは決定 2 の分け合いをしない（AP の上限を置かないので、分け合う量がない）。

- 初期はオフ（B）。ティーポットと同じく、オンにする人が自分で選ぶ
- 切り替えが変えるのはストームポッドの数え方だけにする。必要AP と到達見込みの AP の所要日数は、自然回復だけの前提のまま変えない。りんご・石の量はユーザーごとに違い、見積もりに入れる値が無いため
- 設定は `bondTracker` の保存値にティーポットと並べて入れる。今の `parseBondTrackerState`（`lib/bond/state.ts`）は形が合わない保存値を丸ごと捨てるので、この設定が無い古い保存値はオフとして読み、登録を失わないようにする
- 純粋関数（決定 3）は、切り替えを引数で受け取り、オンなら期間中の周回数をそのまま無料の周回数として返す

## Risks / Trade-offs

- [果実を使えば期間内にもっと回せる] → 到達見込みと同じ割り切りで、注記に「自然回復で回せる分」と書いて前提を示す
- [`nowSec` は30分単位で切り捨てるので、期間の最後の30分は終わった期間も期間中と扱う] → B では最大6AP分の差で済む。「りんご・石を使う」がオンだと、この30分は期間中の周回がすべて0個のまま表示される。ダッシュボードの印も同じ切り捨てを使うので表示どうしはそろう。許容する
- [ローカルの mock には無料期間が無い（`mocks/dashboard.json` の `podFreePeriods` は空）] → 画面の確認では、確認のときだけ mock に期間を足して見る（commit しない）。ロジックはユニットテストで確かめる
