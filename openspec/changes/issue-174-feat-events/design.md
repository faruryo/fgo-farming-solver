# Design

## Context

#130（PR #187）で、`components/events/EventShopList.tsx` は通貨ごとのボーナス（通貨の品目 ID → +N）を `useState` で持ち、`lib/event-plan.ts` の `applyDropBonus` でドロップごとの1周の獲得量を `perRun + countPerRun × N` にしたイベントを `planShopCurrencies`（1つの LP）に渡している。入力の部品は `components/events/DropBonusInputs.tsx`。#173 で同じ部品を箱計画も使う。

イベントデータは `scripts/refresh-event-data.ts`（GitHub Actions の定期ジョブ）が Atlas から取り込み、KV の `event_data_json` に置く。今の型 `EventPlannerEvent` に、通貨と礼装の ☆ を結ぶ項目は無い。通貨の品目は `nice_item.json` から名前とアイコンと type だけを取っている。

オーナーの判断（issue #174 の issuecomment-6475995655）と、仕様 PR の前に行った Atlas JP の実測（材料コメント issuecomment-6476099151、2026-10-29）を前提にする。

実測（`export/JP/nice_equip.json` 21MB と `export/JP/nice_item.json`）:
- ボーナス礼装のスキルの効果 `funcType: eventDropUp` は、`svals[].EventId` で対象のイベントを、`svals[].Individuality` で対象のアイテムを指す。アイテム側は `individuality[].id` が同じ値を持つ。ポイントを増やす礼装は `eventPointUp`
- 1つの礼装に `condLimitCount` 0（無凸）と 4（凸）の2つのスキルがある
- 80627（パンプキン）・80632（復刻盈月。礼装は初出の 1966〜1968 だが `EventId` は 80632）: ☆5/☆4/☆3 がそれぞれ金/銀/銅の通貨1種だけを対象にする
- 80614（マジムン）: 上と同じ対応に加え、☆5「渓谷の神秘」が銀の背景の3種（うちなー○○盛り）を同時に対象にする

## Goals / Non-Goals

**Goals:**
- 通貨と ☆ の対応をデータから決め、取り込み直す前のデータでは今までどおりに動く
- ☆ ごとの入力から、合計枚数ごとの最良の組み合わせと周回数・AP を出す
- 比較の表を足しても、通貨ごとの +N の欄と今の周回の内訳・合計・AP 予算は変わらない

**Non-Goals:**
- 箱計画への比較の表（オーナーの判断①）。箱計画の「礼装の所持を入れる欄を設けてはならない」は変えない
- 礼装の +N をデータから初期値として入れること（材料の未決事項。手入力のみ）
- 礼装の枚数の比較結果を通貨ごとの +N の欄へ書き写すボタン（issue に無い）
- 値の保存（#130 と同じく画面を開いている間だけ）
- 全組み合わせの一覧（決定 4）

## Decisions

### 1. 通貨と ☆ の対応は取り込みで決めて保存する

`refresh-event-data.ts` が `nice_equip.json` を1回取得し、ロトの無い交換所イベント（`decideEventImport` が `shop`）ごとに、`eventDropUp` で `EventId` がそのイベントの効果から（☆, 対象の individuality の集合）を集める。`nice_item.json` から作る `ItemMap` に `individuality` の id を足し、交換所の通貨（`shop[].costItemId`）の individuality と突き合わせる。規則は spec の「ボーナス礼装の ☆ と通貨の対応の取り込み」のとおりで、純粋関数として `lib/refresh-event-data-compact.ts` に置きテストする。

結果は `EventPlannerEvent` の任意の項目（例: `bonusRarities?: { rarity: 3 | 4 | 5; itemId: number }[]`）に入れる。項目が無いのは取り込み直す前のデータ、空の配列は「対応が1つも無い」を表す。礼装のデータの取得に失敗したときは項目を付けずに取り込む（失敗をイベント全体の取り込みの失敗にしない）。

採らなかった案:
- アイテムの背景色（`background` の gold/silver/bronze）から ☆ を決める: マジムンの盛り3種が銀なので ☆4 に入るが、☆4 の礼装はそれらに効かない
- 画面を開くたびにブラウザから Atlas の礼装のデータを取る: 21MB を毎回読むことになる。イベントごとの対応は取り込みの時に決まる
- 通貨と ☆ を手で割り当てる: オーナーの判断⑤

### 2. 対応は「☆ が1つの通貨だけに効く」ときに限る

比較の表は「☆5 を何枚」という数え方なので、ある ☆ の礼装がどれを選んでも同じ1つの通貨に効くときだけ意味がある。対象が複数の礼装（渓谷の神秘）は数え方が別になるので、それが対象にする通貨は対応させず、通貨ごとの +N の欄で扱う（その ☆ の単一対象の礼装が別の通貨に効くなら、その対応は残す）。1つの ☆ の単一対象の礼装が別々の通貨に効くときは、その ☆ を対応させない。

### 3. 入力と組み合わせの数え方

☆ ごとに「凸の +N」「無凸の +N」「凸の所持枚数」「無凸の所持枚数」、全体に「フレンドの礼装の ☆」を持つ（オーナーの判断③④）。凸と無凸の値を分けた以上、どの枚数が凸かを決めるには所持の入力が要るので、交換所について「礼装の所持を入れる欄を設けてはならない」を改訂する（オーナーの許可）。自分の礼装は凸を先に使う。凸のほうが +N が大きいか等しいので、同じ枚数なら凸を先に数えるのが最良になる（凸の +N を無凸より小さく入れた場合も、spec のとおり凸を先に数える）。

フレンドの1枠は選んだ ☆ の凸の値で必ず含める（判断③）。初期値は対応のある最も高い ☆ にする（フレンドから借りるのは効き目の大きい ☆5 が多い）。

組み合わせから各通貨の +N を作って `applyDropBonus` に渡し、`planShopCurrencies` で解く処理は、`lib/event-plan.ts` に純粋関数（例: `compareBonusCraftEssences`）として置く。対応の無い通貨とイベントポイントの +N は通貨ごとの欄の値を渡す（判断②）。

### 4. 表は合計枚数ごとの最良の1行にする

合計 6 枚までの (☆5, ☆4, ☆3) の組み合わせは最大 84 通りある。issue の問いは「何枚から効き目が減るか」なので、合計枚数ごとに AP が最小の組み合わせを1行ずつ出し、1枚少ない行からの AP の減りを並べる。同じ AP の組み合わせは、周回の少ない、次に ☆5・☆4 の少ない（手持ちの高い ☆ を他に回せる）ものを選ぶ。

計算は所持の範囲の組み合わせをすべて解く（最大 84 回の LP）。交換所の LP は周回クエストの数だけの小さな問題なので、入力のたびに `useMemo` で解いてよいと見込む。実装後に遅ければ、☆ ごとの入力の変更を確定してから解く形にする。

### 5. 画面

- ☆ ごとの欄とフレンドの礼装の欄は、通貨ごとの +N の欄（`DropBonusInputs`）の下に、同じ見た目の枠で出す。見出しは「ボーナス礼装の枚数を比べる」とし、各 ☆ の行に対応する通貨のアイコンと名前を出す
- 比較の表はその枠の中に置く。列は「合計枚数」「☆5」「☆4」「☆3」「周回数」「AP」「AP の減り」。375px で横にはみ出すときは表だけを横スクロールにする
- 周回では集められない通貨があるときは、今の周回の内訳と同じく集められる分だけで解き、表の下にその旨を1行出す
- 新しい文言は `locales` の events の ja と en の両方に足す

## Risks / Trade-offs

- [本番の KV に対応を持たないデータが残る] → 定期ジョブの次の実行で取り込み直される。それまでは「データの更新前」と出し、通貨ごとの欄は今までどおり使える。取り込みは開催終了から30日の窓の中のイベントだけを取り直し、窓の外の過去のイベントは前のデータのまま残る（`refresh-event-data-merge.ts` の蓄積マージ）。過去のイベントにも出したいときは、人が `BACKFILL_SINCE` を付けてジョブを実行する。KV は手で書き換えない
- [`nice_equip.json` の取得で定期ジョブが遅くなる・落ちる] → 1回の取得で 21MB。失敗しても対応を付けずに取り込む（spec）。ジョブは GitHub Actions で動き、Worker の CPU 上限は効かない
- [Atlas のデータの形が変わる・例外的な礼装] → 対応が決まらない通貨は比較に入れないだけで、誤った ☆ を割り当てない規則にしてある（決定 2）
- [84 回の LP が遅い] → 決定 4 のとおり実装後に確かめる。テストで 6 枚・3 ☆ の最大の場合を解き、結果が出ることを見る
- [凸の +N を無凸より小さく入れた] → 凸を先に数える規則のままにし、最良にならないことは受け入れる（入力の誤りなので）

## Migration Plan

KV の形は任意の項目の追加だけで、既存の読み手（箱計画・ダッシュボード）は無視する。デプロイ後、定期ジョブの次の実行（または手動の実行）で取り込み直され、交換所に ☆ ごとの欄が出る。戻すときは画面の変更を戻せばよく、KV に残った項目は害が無い。
