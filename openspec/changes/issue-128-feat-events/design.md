# Design

## Context

#127 の実装で、ロトの無い交換所イベントは KV に `lotteries: []` で入り、イベントページ（`EventHubClient`）は `EventShopList` で交換所を通貨ごとに一覧するだけになっている。周回の計算は箱計画用で、`allocateShop` は対価を1つの合計（`totalCurrencyUsed`）にまとめ、`buildEventDrops` は `event.currency`（1種類）だけを需要にする。ソルバー（`lib/solver.ts` の `solve`）は品目ごとに `min` の制約を持つ LP なので、通貨ごとに制約を置けば、1周で複数の通貨が落ちる場合もそのまま扱える（動機は proposal.md の Why）。

## Goals / Non-Goals

**Goals:**
- ロトの無い交換所イベントで、品目の交換回数と通貨の所持数から、通貨ごとの必要量と AP 最小の周回の内訳を出す
- 複数の通貨を1つの LP で同時に満たす
- 箱計画の結果を変えない

**Non-Goals:**
- ボーナス礼装・サーヴァントによるドロップの増加（#130）。ドロップ統計の値をそのまま使い、前提を画面に書く
- AP 回復アイテム・林檎の数（#134）、会期内にどこまで届くか（#136）
- 選んだ回数や所持数の保存（epic #129 の「やらないこと」E2）。画面を開いている間だけ持つ
- 品目の価値による並べ替えや区切り（#135）
- ミッション・ポイント報酬（#115・#132）

## Decisions

### 1. 通貨ごとの需要を1つの LP に渡す

`buildEventDrops` に、通貨ごとの需要（`Map<costItemId, number>`）を受け取る形を足し、各通貨を `items` の制約にする。ドロップ統計（`farmingNodes[].drops`）には通貨のドロップも入っているので、クエストの変数に各通貨の `perRun` が付き、LP が同時に満たす周回を選ぶ。既存の呼び出し（箱計画の `currencyDemand: number`）は今の形のまま動かし、ボックス計画の結果は変えない（既存テストが変わらず通ることで確かめる）。

採らなかった案: 通貨ごとに別々に LP を解いて足す。1周で3種類が落ちるイベントでは周回を3重に数え、AP を大きく見積もる（#131 の調査でも指摘した点）。

### 2. 交換回数の選択と必要量は純粋関数にする

品目ごとの回数（在庫上限で頭打ち）から通貨ごとの対価の合計を出し、所持数を引いて必要量を出す処理を、`lib/event-shop-summary.ts` に純粋関数として置く。「上限まで選ぶ」は、その通貨のグループで `limitNum > 0` の品目を `limitNum` 回にする。在庫上限の無い（`limitNum` が 0 の）品目は自動では選ばない。

### 3. 画面

ロトの無い交換所イベントの交換所セクションを、一覧から「選べる一覧＋周回の内訳」に広げる。

- 通貨ごとのカード（今の `EventShopList` の構成）に、品目ごとの回数の入力と「上限まで選ぶ」、通貨の所持数の入力、必要量を置く
- その下に周回の内訳（クエストごとの周回数、合計の周回数と AP、通貨ごとの見込み獲得量）と、「ドロップはイベントのボーナスを含まない統計値」の注記を置く
- 375px で横スクロールが出ないよう、回数の入力は数値の入力欄にし、表は今の `EventShopList` と同じ列の幅に収める

## Risks / Trade-offs

- [復刻直後は Atlas のドロップ統計の母数が小さい] → 統計値をそのまま使い、注記で前提を示す。ドロップが1件も無いクエストしか無ければ周回を出さない
- [ボーナスを含まないので、実際より多い周回になる] → #130 でボーナスを入れるまでの割り切りとして注記する
- [mock（`mocks/events.json`）にロトの無いイベントが無い] → ロジックはユニットテスト（3種類の通貨が同時に落ちる fixture を含む）で確かめる。画面の確認は、確認のときだけ mock に既存のイベントのロトを空にした複製を足して見る（commit しない）
