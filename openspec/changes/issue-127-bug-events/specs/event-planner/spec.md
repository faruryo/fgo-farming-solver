## MODIFIED Requirements

### Requirement: イベントデータの取り込み
システムは、ロトか交換所のあるイベントのロトボックス・交換所・イベント通貨の情報を Atlas Academy の `nice_event` から取得・コンパクト化して KV (`event_data_json`) に保存しなければならない (SHALL)。取得・整形は GitHub Actions 定期ワークフローで行い、Cloudflare Workers では KV を読むだけとする。保存は**全置換ではなく蓄積マージ**とし、過去に取り込んだイベントは取り込み窓の外になっても KV から削除してはならない (SHALL NOT)。Atlas のロトが0件で交換所のあるイベントは、ロトを空として取り込まなければならず (SHALL)、ロトも交換所も無いイベントは取り込んではならない (SHALL NOT)。Atlas のロトが1件以上あってすべて検証に通らないイベントは、交換所イベントとして取り込んではならず (SHALL NOT)、今までどおりスキップしなければならない (SHALL)。交換所の各エントリーには、対価の通貨の表示名とアイコンを、取得できるときに保存しなければならない (SHALL)。

#### Scenario: ロトボックスと箱コストの取得
- **WHEN** 取り込みワークフローがロトのある対象イベントを処理するとき
- **THEN** 各ロトの「1箱あたりの確定内容（アイテムと個数）」「1箱あたりのコスト（イベント通貨と個数）」「箱の最大数（`maxNum`）」「レアボックス判定（`isRare`）」が KV に保存される。

#### Scenario: 交換所の取得
- **WHEN** 取り込みワークフローが対象イベントを処理するとき
- **THEN** 交換所アイテムの「獲得物」「コスト（通貨・個数）」「在庫上限（`limitNum`）」が KV に保存される。

#### Scenario: 過去イベントの蓄積保持（マージ）
- **WHEN** 取り込みワークフローが実行され、既存 KV に過去のロト型イベントが存在するとき
- **THEN** 既存イベントは `id` をキーに温存され、今回フェッチしたイベントは同一 `id` を新データで上書き（upsert）、今回フェッチに含まれない過去イベントは削除されずに残る。

#### Scenario: 過去イベントのバックフィル
- **WHEN** 取り込み対象期間の下限を過去に遡って指定して取り込みを実行したとき
- **THEN** 指定期間内の過去ロト型イベントが `nice_event` から取得され、蓄積マージで KV に追加される。

#### Scenario: スキーマ不整合のスキップ
- **WHEN** あるイベントの `nice_event` がバリデーションに失敗したとき
- **THEN** そのイベントはスキップされ、他のイベントの取り込みと既存 KV データは影響を受けない。

#### Scenario: 上流障害時の既存データ保護
- **WHEN** 取り込み元のイベントカタログ (`basic_event.json`) が空、または既存 KV の取得に失敗したとき
- **THEN** KV への書き込みは行われず、既存の `event_data_json` がそのまま温存される（空データで上書きしない）。

#### Scenario: 変化が無いときの非書き込み
- **WHEN** マージ結果が既存 KV と同一（新規追加・更新が無い）のとき
- **THEN** KV への書き込みはスキップされ、既存データが温存される。

#### Scenario: 既存恒常データの不可侵
- **WHEN** イベントデータを取り込むとき
- **THEN** 恒常ドロップデータ (`all_drops_json`) と `getWars` の `eventId == 0` フィルタは変更されない。

#### Scenario: ロトの無い交換所イベントの取り込み
- **WHEN** 取り込みワークフローが、Atlas のロトが0件で交換所のあるイベント（例: `80632`）を処理するとき
- **THEN** そのイベントはロトを空、交換所と周回ノードを箱イベントと同じ形にして KV に保存される。
- **AND** 交換所の各エントリーに、対価の通貨の表示名とアイコンが保存される。

#### Scenario: ロトの検証がすべて失敗したイベントのスキップ
- **WHEN** Atlas のロトが1件以上あり、そのすべてが検証に通らないイベントを処理するとき
- **THEN** そのイベントは交換所イベントとして取り込まれずにスキップされ、既存 KV の同じイベントのデータは影響を受けない。

#### Scenario: ロトも交換所も無いイベントのスキップ
- **WHEN** 取り込みワークフローが、ロトも交換所も空のイベントを処理するとき
- **THEN** そのイベントは KV に保存されない。

### Requirement: ロト計画 UI
システムは、イベントの一覧（`/events`）と、イベントごとのイベントページ（`/events/[id]`）を提供しなければならない (SHALL)。一覧に載るイベントは「KV `event_data_json` に取り込まれたイベント（ロト型イベントと、ロトの無い交換所イベント）」と「イベント機能レジストリに登録されたイベント」の和集合とする。イベントページは、そのイベントで使える機能をセクションとして並べるハブとする。既存の恒常導線 (`/material` → `/farming`) は変更しない。一覧・イベントページは、URL 直打ち以外にアプリ内の常設導線（グローバルナビ等）から到達可能でなければならず (SHALL)、どのページもオーファン（到達不能）であってはならない (SHALL NOT)。画面上の名称は「イベント」「イベント一覧」とし、ロト型に限定した名称（「ボックスイベント」「ロトイベント一覧」）を一覧・ナビの見出しに用いてはならない (SHALL NOT)。

#### Scenario: イベント一覧
- **WHEN** ユーザーが `/events` を開いたとき
- **THEN** KV のイベント（ロトの無い交換所イベントを含む）とレジストリ登録イベントが、同一 ID の重複なく会期情報とともに「開催中・開催予定・終了済み」に分けて一覧表示される。
- **THEN** 各イベントには、そのイベントページで使える機能（「ボックス計画」「交換所」「料理作成」）がバッジで示される。

#### Scenario: KV に無いレジストリ登録イベント
- **WHEN** あるイベントが KV `event_data_json` に存在せず、イベント機能レジストリにのみ登録されているとき
- **THEN** 一覧にはレジストリの表示用メタ（名前・会期）で掲載され、イベントページも開ける。

#### Scenario: 一覧ページへの常設導線（オーファン禁止）
- **WHEN** ユーザーがアプリのどの画面からでもイベント機能を探すとき
- **THEN** グローバルナビゲーション（`components/common/nav.tsx`）に「イベント」の名称で `/events` 一覧への常設エントリが存在し、URL 直打ちなしで一覧ページへ到達できる。
- **AND** ダッシュボードからの個別イベント直行導線（`/events/[id]`）は一覧導線を代替せず、両者が併存する。

#### Scenario: ダッシュボードからのイベントページ導線
- **WHEN** ダッシュボードの開催中イベントカードのイベントが、ハブで機能提供可能な状態（KV `event_data_json` に取り込み済みのイベント ID 集合に含まれる、または静的レジストリに登録されたイベント）であるとき
- **THEN** そのカードに `/events/[id]` への導線が表示される。
- **WHEN** イベントが KV に未取り込みで、静的レジストリにも登録されていないとき（外部メタデータ上で `hasLottery` であっても）
- **THEN** 導線は表示されない（ハブ遷移後の `EventDataMissing` 露出を防止する）。

#### Scenario: 計画ページへの遷移
- **WHEN** ユーザーが一覧からイベントを選ぶ、またはダッシュボードの該当イベントから遷移したとき
- **THEN** そのイベントのイベントページ (`/events/[id]`) が開き、ヘッダー（名前・会期・開催状態）の下に、使える機能のセクションが表示される。

#### Scenario: 取り込みデータ未存在時の表示
- **WHEN** 対象イベントが KV にもイベント機能レジストリにも存在しないとき
- **THEN** イベントページはエラーにならず、データ未取得である旨のプレースホルダを表示する。

#### Scenario: ロトの無い交換所イベントの掲載
- **WHEN** ロトが無く交換所のあるイベント（例: `80632`）が KV に取り込まれているとき
- **THEN** ダッシュボードの開催中イベントのカードに `/events/[id]` への導線が出て、`/events` 一覧にも交換所のバッジ付きで出る。

### Requirement: イベントページのセクション構成
システムは、イベントページにおいて、イベントが持つ機能ごとに独立したセクションを表示しなければならない (SHALL)。ボックス計画セクションは KV のイベントのロトが1件以上あるイベントでのみ、料理作成セクションはレジストリで料理作成が登録されたイベントでのみ表示しなければならない (SHALL)。KV のイベントに交換所があってロトが無いイベントでは、交換所一覧セクションを表示しなければならない (SHALL)。交換所一覧は対価の通貨ごとにまとめ、通貨ごとに全交換に要る合計と、各品目の名前・1回の個数・在庫上限・1回の対価を示さなければならない (SHALL)。在庫上限の無い品目は合計に含めず、上限が無いことを示さなければならない (SHALL)。ロトのあるイベントでは、交換所を今までどおりボックス計画の中で扱い、交換所一覧セクションを重ねて出してはならない (SHALL NOT)。KV に交換所のデータが無いイベントで、交換所一覧セクションを出してはならない (SHALL NOT)。各セクションの計算アルゴリズムは既存のロジック（ボックス計画、料理作成配分ソルバー等）をそのまま用い、同一の入力（素材必要数・所持数・設定値等）に対する算出結果が変わってはならない (SHALL NOT)。ただし、料理作成セクションは永続ロスター由来の need および実所持数（`STORAGE_KEYS.POSSESSION`）を入力とするため、共有 URL 等により `/material/result` とロスター内容が異なる場合は配分結果が異なり得る。ボックス計画セクションはドロップデータ（`/api/drops`）に依存せず独立して動作しなければならない (SHALL)。

#### Scenario: ボックス計画セクション
- **WHEN** KV にロト型データがあるイベントのイベントページを開いたとき
- **THEN** 既存のボックス計画（入力モード・箱数・通貨・周回・AP内訳・育成インパクト・交換所上限警告）がボックス計画セクションとして表示され、所持数キー `STORAGE_KEYS.ITEMS` に基づく既存挙動が維持される。

#### Scenario: 料理作成セクションの need は永続ロスター由来（read-only と旧設定移行維持）
- **WHEN** ロスター設定済みのユーザーが料理作成セクションを表示したとき
- **THEN** 料理作成アドバイザーは、永続ロスター（`ChaldeaState`）から求めた育成必要数と、実所持数（`STORAGE_KEYS.POSSESSION`）を受け取り、周回目的・ストック目標設定に従った実効不足として配分を計算する。
- **THEN** ロスター・所持数・周回目的・ストック目標設定は純粋な読み取り（read-only）として参照され、キー未存在時でも初期値の自動保存等による `ChaldeaState`・所持数・クラウド同期対象データの書き換え・汚染は発生しない (SHALL NOT)。
- **AND** `FARMING_PURPOSE` キーが未保存で旧キー（`QUEST_EFFICIENCY_SHORTAGE_ONLY`, `STOCK_ENABLED`）が残る端末では、自動書き込みを伴わずに旧設定（`all` / `reserve` / `training`）をメモリ上で復元する移行経路が維持される。明示的な切り替え操作時のみ保存が行われる。

#### Scenario: 周回目的が all のときの料理作成セクション
- **WHEN** ユーザーの周回目的が `all`（すべて）のとき
- **THEN** 料理配分計算のための有限目標は `training`（育成）としてフォールバック計算される。
- **AND** UI 上に「配布評価は今の育成を使用」（`common:farming-purpose-advisor-fallback`）の注記が表示される。

#### Scenario: 素材データ取得中・取得失敗・部分欠落時のセーフガード
- **WHEN** ロスター設定済みだが、サーヴァント必要素材（`getMaterialsForServantIds`）が取得中のとき、またはドロップデータが取得中（`drops.isLoading === true`）のとき
- **THEN** 配分計算は開始せず、ローディング状態を表示する。
- **WHEN** サーヴァント必要素材の取得に失敗したとき、一部サーヴァントの素材データが欠落したとき（部分欠落）、またはドロップ取得完了後（`drops.isLoading === false`）に正の need（need > 0）に関与するカタログ・ドロップ率・クエストデータの欠落が検知されたとき
- **THEN** 削減周回/APの過大評価・誤計算を防ぐため配分計算を行わず、データ不整合のエラーメッセージと再試行案内を表示する。

#### Scenario: ロスター未設定時の料理作成セクション
- **WHEN** ロスター未設定のユーザーが料理作成セクションを表示したとき
- **THEN** 配分計算は行わず、育成対象を設定すると料理配分を算出できる旨と、その設定画面への導線を表示する。

#### Scenario: 機能を持たないセクションは出さない
- **WHEN** イベントが KV のロト型データを持たないとき
- **THEN** ボックス計画セクションは表示されない。

#### Scenario: ロトの無い交換所イベントのページ
- **WHEN** ユーザーが、ロトが無く交換所のあるイベント（例: `80632`）のイベントページを開いたとき
- **THEN** ボックス計画セクションは表示されず、交換所一覧セクションが通貨ごとに表示される。
- **AND** 各通貨の見出しに通貨名と全交換に要る合計が出て、その下に品目が並ぶ。

#### Scenario: ロトのあるイベントの表示は変わらない
- **WHEN** ユーザーが、ロトと交換所の両方があるイベントのイベントページを開いたとき
- **THEN** ボックス計画セクションが今までどおり表示され、交換所一覧セクションは表示されない。

#### Scenario: 通貨名を持たない古いデータ
- **WHEN** 交換所のエントリーに通貨の表示名が保存されていないとき
- **THEN** 交換所一覧は通貨の ID を見出しに出し、エラーにならない。
