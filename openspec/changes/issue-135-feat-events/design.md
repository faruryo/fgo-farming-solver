# Design

## Context

この change は #128 の実装 PR #162 がマージされた後の main に乗る。#162 で、ロトの無い交換所イベントの交換所（`components/events/EventShopList.tsx`）は、`groupShopByCurrency` で通貨ごとのカードに分けた品目に交換回数の入力・「上限まで選ぶ」・所持数・必要量・周回の内訳を持つ。品目は交換所の元の順に並ぶ。

イベントページ（`app/events/[id]/page.tsx`）は KV のイベントデータ（交換所の `itemId`・`qty`・`costItemId`・`costAmount`・`limitNum`、周回クエストの `ap` と通貨ごとの `perRun`）だけを読み、フリクエのドロップ表は読まない。素材の AP 換算値は `lib/progress/lap-value.ts` の `resolveUnitPrices(drops, selectedQuestIds)` が atlasId ごとの `apPrice`（min（クエストの AP ÷ ドロップ率））として出せる（#131 の調査）。ドロップ表は `lib/get-drops.ts` の `getDrops()` で読める。

方針は issue #135 の 2026-10-24 のコメントで決まり、同日 17:01 のコメントで「欲しい／要らないの切り替えは作らず、#128 の品目ごとの交換回数（0 なら要らない、1以上なら欲しい）をそのまま使う」に変わった（proposal.md の What Changes）。

## Goals / Non-Goals

**Goals:**
- 通貨ごとのカードの中で、AP 換算値のある品目を効率順に並べて区切りを出し、AP 換算値の無い品目をその後に並べる
- #162 の交換回数・必要量・周回の内訳の動きを変えない

**Non-Goals:**
- 品目ごとの「欲しい／要らない」の切り替え。欲しいかどうかは #162 の交換回数（0 か1以上か）で表す。使ってみて要りそうなら、別の issue で足す（オーナーの 2026-10-24 17:01 のコメント）
- 交換回数の保存（epic #129 の「やらないこと」E2）
- 「区切りまで選ぶ」のように、並びから交換回数を自動で入れる操作
- 利用者の育成計画に合わせた並べ替え（#131 の「自分の計画での限界値」）
- ボーナス礼装・サーヴァントによる通貨の増加（#130）と、キャンペーンによる AP の変化
- 箱のあるイベントの交換所（箱計画の中で扱う）
- 1周で複数の通貨が落ちるときに、周回の AP を通貨ごとに分けること

## Decisions

### 1. AP 換算値はページのサーバー側で品目の分だけ出して渡す

ロトの無い交換所イベント（`EventHubClient` の `shopOnly` になる条件。features に `shop` があり `box` が無く、交換所が1件以上）のときだけ、`page.tsx` で `getDrops()` を読み、`resolveUnitPrices(drops, [])` で全クエストから AP 換算値を出す。そのうち交換所の品目の `itemId` に当たる `apPrice` だけを、atlasId（数値）→ AP 換算値の素のオブジェクトにして `EventHubClient` から `EventShopList` へ渡す。ドロップ表は全素材・全クエストを含み大きいので、クライアントには送らない。この条件は `lib/event-features.ts` の純粋関数に切り出し、`page.tsx` と `EventHubClient` の両方から使う（2か所に書き写すとずれるため）。値は表示のたびに今のドロップ表から求め、定数として持たない（#131 の調査で、効率の良いフリクエが増えると値が大きく動くことが分かったため）。

ドロップ表の読み込みに失敗した、または空のときは、全品目に AP 換算値が無いものとして扱い、ページは出す（全品目が交換所の元の順に並び、順位と区切りは出ない）。

採らなかった案: クライアントで `/api/drops` を取りに行く。表示までに通信が1回増え、ページの他の部分と読み込みの時機がずれる。

### 2. 並べ方は純粋関数にする

`lib/event-shop-summary.ts` に、通貨のグループ（`ShopCurrencyGroup`）・AP 換算値・その通貨の基準を受け取り、効率順の品目（順位と効率付き）、区切りの位置、その後に並ぶ AP 換算値の無い品目を返す純粋関数を置く。画面はその結果を描くだけにする。

- 効率 = `qty × apPrice ÷ costAmount`。`costAmount` が 0 以下の品目は効率を出さず、AP 換算値の無い品目と同じに扱う
- 効率順の並べ替えは安定ソートにし、同じ効率の品目は元の順を保つ
- 並べ替えた後も、各行の交換回数の入力は #162 と同じ「交換所の配列全体の添字」（`ShopExchangeCounts` の鍵、#162 の `shop.indexOf`）で品目に結び付ける。関数は品目そのもの（配列の要素の参照）を返し、画面はその品目から添字を引く。通貨のグループ内の添字は通貨をまたいでぶつかり、同じ `itemId` の品目が対価違いで複数並ぶこともあるため、どちらも鍵にしない
- AP 換算値の無い品目を効率順の後ろに置くのは、効率で比べられない品目を、比べられる品目と区切りの間に混ぜないため。欲しい品目は交換回数を入れれば、並びの位置によらず必要量と周回の内訳に入る
- 効率と基準は丸める前の値で比べる。表示は小数2桁までにし、末尾の0は出さない（「20」「1.2」「1.06」）（基準が 1.04〜1.07 の付近に効率の近い品目があり、小数1桁では区切りの上下で同じ値に見えるため）

### 3. 区切りの基準は通貨ごとに分けない周回の AP

基準 = min over 周回クエスト（`ap ÷ その通貨の perRun`、`ap > 0` かつ `perRun > 0` のものだけ。`resolveUnitPrices` が `ap <= 0` を除くのにそろえる）。オーナーの方針（最高難易度ではどの通貨も必ず落ちるので、AP を通貨ごとに分けず、通貨ごとに効率順に並べる）に従い、1周で3種類が落ちても周回の AP を1つの通貨に全部載せる。そのため基準は実際より高めに出て、区切りは控えめ（区切りの上に入る品目が少なめ）になる。#131 の注意1で挙げた点で、方針として受け入れる。

基準が出ない（どの周回クエストにもその通貨が落ちない）通貨は、区切りを出さず、並びと順位だけを出す。

`mocks/events.json` と `mocks/all.json`（2026-06-12 時点）で、仕様 PR の前にこの式を使い捨てのスクリプトで試した。80549（通貨3種類）では、基準は 1.04〜1.07 AP。区切りの上に入った品目は、AP 換算値のある品目のうちそれぞれ 10/10・10/10・4/7 だった。最後の通貨では輝石（効率 0.75〜0.84）が区切りの下に来た。80429・80455・80506 でも、ピースと輝石が区切りの下に来た。AP 換算値のある品目が1つも無い通貨（各イベントの4種類目の通貨）は、基準も出なかった。

採らなかった案: 周回の AP を通貨ごとのドロップ数の比で分ける。オーナーが採らないと決めた（#135 のコメント）。

### 4. 欲しい／要らないの切り替えは作らない

オーナーの 2026-10-24 17:01 のコメントのとおり、欲しいかどうかは #162 の品目ごとの交換回数（0 なら要らない、1以上なら欲しい）で表し、`EventShopList` に新しい状態を足さない。

採らなかった案: 案B（https://claude.ai/artifact/NmhSfrn6zhSdvKTQ74J8nE ）の「未選択・欲しい・効率順・要らない」の段と切り替えのボタン。交換回数と同じことを2か所で表すことになるため、オーナーが見送った。

### 5. 復刻の判定は名前の先頭の印

復刻の判定は、見出しの「復刻」のバッジにだけ使い、並びには使わない。切り替えをやめた後も残すのは、オーナーの品目ごとの好み（#131 のコメント: サーヴァントコインと礼装は、復刻でなければほぼ必須、復刻ですでに持っていれば好き好き）では、利用者が交換回数を決めるときに復刻かどうかが判断の材料になるため。オーナーの 2026-10-24 の方針のうち「復刻は名前の印で見分ける」は、17:01 の変更でも取り消されていない。

`lib/event-features.ts` に、イベント名が「復刻:」「復刻：」「復刻版:」「復刻版：」のどれかで始まるかを返す純粋関数を置き、`EventHubClient` の見出しで `summary.name` に使う。Atlas の `basic_event.json`（2026-10-25 取得）で名前に「復刻」を含むイベントは48件あった。印の内訳は「復刻:」31件、「復刻版:」7件、「復刻：」6件。残りは「アンケート復刻版」「復刻魔術礼装クエスト」「復刻リチャード1世体験クエスト」のように、名前の途中か印でない形で「復刻」を含むもの。オーナーの方針は「復刻:」で見分けることで、そのプロトタイプでは「復刻版:盈月剣風帖」（80632）を復刻として描いていた。そのため、全角のコロンと「復刻版」も印に含める。

### 6. 画面

プロトタイプ（https://claude.ai/artifact/NmhSfrn6zhSdvKTQ74J8nE の案B）の効率の表示と区切りの行に合わせる。段の帯と切り替えのボタンは使わない（決定 4）。

- 通貨ごとのカードの見出し（#162 の全交換の合計・上限なし）は変えない
- 効率順の行には順位と効率の値を出し、区切りより上の行を目立たせる。区切りは「ここまで交換すれば効率が良い」と基準の値（「1個 1.06 AP」の形、決定 2 の桁）を持つ1行にする
- AP 換算値の無い品目の前に「AP 換算なし」の小さな見出しの行を置き、効率と順位は出さない。見出しは、そのカードに AP 換算値のある品目が1つ以上あるときだけ出す（全品目が AP 換算値の無いカードは、#162 と同じく元の順に並ぶだけにする。ドロップ表の読み込みに失敗したときと、各イベントの4種類目の通貨がこれに当たる）
- 行の交換回数の入力は #162 のまま置く
- 375px で横スクロールが出ないよう、順位・効率・交換回数の入力は #162 の行の幅に収める

## Risks / Trade-offs

- [ドロップ表と交換所の品目の atlasId が合わない（ドロップ表の `atlasId` が無い素材）] → その品目は AP 換算値の無い品目として後ろに並ぶ。誤った効率は出さない
- [ドロップ表の読み込みでページの表示が遅くなる] → ロトの無い交換所イベントのときだけ読む。`getDrops()` は既存のページでも使っている
- [伝承結晶など、欲しい人が多い品目が後ろに並ぶ] → 交換回数を入れれば並びの位置によらず計画に入る。使ってみて不便なら、切り替えを別の issue で足す（Non-Goals）
- [基準は周回の AP を分けないので高めに出る] → 決定 3 のとおり方針として受け入れる。区切りには基準の値を添え、何と比べた区切りかを画面で分かるようにする
- [#162 がマージされる前に実装に入ると、乗る画面が無い] → 実装（ops-graph）は #162 のマージ後に main から始める

## Migration Plan

KV とデータの形は変えない。実装 PR を戻せば元の並びに戻る。
