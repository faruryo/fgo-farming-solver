# Design

## Context

動機は proposal.md の Why を参照。

交換所のデータは、取り込みの `lib/refresh-event-data-compact.ts` の `compactShop` が Atlas の `nice/JP/event/<id>` の `shop[]` を `EventShopItem[]` に変えて KV `event_data_json` に保存する。Atlas の各交換所データには `priority` があるが、`compactShop` は取り込まず、配列は Atlas の順（交換所の ID の順）のままになる。

2026-11-03 に Atlas から 80632 を取得して確かめた `priority` の並び（抜粋）:

| priority | 品目 | 通貨 | 対価 | 在庫上限 |
|---|---|---|---|---|
| 10・20・30 | サーヴァントコイン ×10 | 武蔵うどん・江戸むすび・東干し柿 | 10 | 16・16・16 |
| 40・50・60 | 月より団子 | 同上 | 100 | 2・1・1 |
| 70・80・90 | 伝承結晶 | 同上 | 200 | 2・2・1 |
| 100・110 | 英霊結晶・流星のフォウくん | 武蔵うどん・東干し柿 | 150 | 1・1 |
| 120・130 | 英霊結晶・日輪のフォウくん | 武蔵うどん・江戸むすび | 150 | 1・1 |
| 140・150・160 | 巡霊の葉 ×10 | 3通貨 | 10 | 25・25・25 |
| 170・180・190 | コード・リムーバー | 3通貨 | 20 | 1・1・1 |
| 200〜 | 英霊結晶・星のフォウくん、叡智の業火… | 1通貨ずつ | | |

今の KV のデータ（ID の順）では、80632 は月より団子（ID 80632001〜003）が先頭で、サーヴァントコインは 4〜6 番目になる。

画面は `components/events/EventShopList.tsx` の `EventShopList` が、`groupShopByCurrency` で通貨ごとのカード（`CurrencyGroupCard`: 見出し・品目の表・所持数と必要量のフッター）に分け、カードの中を `orderShopByEfficiency` で AP 換算なし → 効率順に並べて順位を付ける。交換回数は交換所の配列の添字をキーにした `Map` で持ち、保存は `shopItemKeys` の品目キー（種類・獲得物・個数・通貨・対価・同じ組での出現順）に変えて `events/shopInputs/<id>` の `counts` に入れる。周回の計算（`planShopCurrencies`）は通貨ごとの必要量を受け取るだけで、品目の並びも回数の持ち方も知らない。

手元のイベントデータ（46件、2026-11-03 の dev KV の写し）で、複数の通貨で交換できる品目（種類・獲得物・個数が同じで、通貨が2つ以上）を数えた: 交換所のある 45件のうち 14件・101組。うち在庫上限ありが 95組、在庫上限なしが 6組（QP 3件、80614 の「うちなー」3品目）、上限ありとなしの混在は 0組、同じ通貨だけで重なる組は 0組。在庫上限ありで対価が通貨で違うのは 80611 の伝承結晶（200 と 400）の1組。

同じ 14件を 2026-11-03 に Atlas から取得し直し、`priority` で並べた交換所で確かめた（`purchaseType` が item か servant で `payType` が eventItem、`targetIds` のある交換所データを対象にした）: 在庫上限のある複数通貨の 95組は、どれも `priority` の並びで続けて並ぶ（間に別の品目が入る組は 0組）。`priority` の無い交換所データと、同じ `priority` の交換所データはどのイベントにも無い。交換所データの区分（`slot`）は 13件で1つだけで、80603（アフタータイム・バレンタイン2026、516行）だけが3つ持つ。80603 は、区分 3（54行、`priority` 30〜930、親愛のミトンなど複数の通貨）と、区分 1（290行）・区分 2（172行）（どちらもロックオンチョコ、`priority` 1001 以降で 1001・1002・1003… と区分 2・1 が交互）に分かれる。80603 を区分ごと（下の「決めたこと」）で並べても、まとめる 6組はどれも1つの区分の中で続けて並ぶ（区分をまたぐ組は 0組）。

`event-planner` の spec には、未 archive の change `issue-127-bug-events` の delta がある。この change では `event-planner` の要件を書き換えない（下の「決めたこと」）。

## Goals / Non-Goals

**Goals:**
- 交換所の周回計算と、品目がすべてサーヴァント扱いの一覧を、通貨ごとのカードに分けない1つの一覧にする
- 複数の通貨で交換できる品目を1行にし、入力の数をゲームの画面の品目の数に近づける
- 周回計算の一覧は効率の高い順を保ち、AP 換算できない品目はその下にゲーム内の順で並べる
- 計算・保存の形・既存の保存値の結果を変えない

**Non-Goals:**
- まとめた行を一部だけ交換するときに、どの通貨の品目に回数を入れるかを決めること。2026-11-04 のオーナーの判断で考慮不要とし、要件にしない（入れた回数の合計と在庫上限だけを要件にする）
- 周回の計算で通貨の割り振りを最適化すること
- 箱のあるイベントの箱計画、ロトのあるイベントの交換所の扱い
- 交換所の品目の行の見た目の作り直し（列は、対価に通貨を出すことのほかは今のまま）

## Decisions

### 判断点

なし。仕様 PR #238 で挙げた判断点は、2026-11-04 にオーナーが答え、下の「決めたこと」に移した（まとめた行を一部だけ交換するときの通貨は、考慮不要として判断点から外し、Non-Goals に書いた）。

### 決めたこと

#### 通貨ごとの所持数と必要量の置き場所（2026-11-04 オーナーの判断）

3通貨の所持数の入力は、品目の一覧の上に横1列で並べる。通貨ごとの選んだ交換の合計・必要量・全交換の合計（例: 武蔵うどん 360・江戸むすび 140・東干し柿 0 のような通貨ごとの必要量）は、品目の一覧の下に並べる。所持数はゲームの通貨の画面から先に写す値なので一覧の前に置き、必要量は品目を入れた結果なので一覧の後ろで3通貨を並べて見比べる。

オーナーの答えは所持数と必要量の置き場所だけを決めている。選んだ交換の合計と全交換の合計は、品目の選び方から出る値なので、必要量と同じ一覧の下に置いた。

#### 一覧の並び（2026-11-04 オーナーの判断）

一覧は1つのまま、効率順を残す。行の値は、その行の品目を交換できる通貨のうち一番いい AP/個 とし（まとめた行で対価が通貨で違うときは、その中の最大）、値の高い順に並べる（例: 鬼炎鬼灯 7.72 → 蛮神の心臓 7.63。通貨が違っても値で並べる）。値の同じ行は、行の最初の品目の交換所の順を保つ。AP 換算できない品目（サーヴァントコイン・団子・結晶など）は、効率順の品目の下に、交換所の順（ゲーム内の順）でまとめる。プロトタイプでは上に置いていたが、オーナーの決定は下。

今の画面の見出し（「効率順」「AP 換算なし」）と順位の列は、この並びに合わせて残す。順位は通貨ごとではなく、一覧の効率順の行に 1 から付ける。見出しの順は「効率順」→「AP 換算なし」に入れ替わる。品目がすべてサーヴァント扱いの一覧は効率を出さないので、交換所の順で並べる。

#### 保存した交換回数の引き継ぎ

保存の形を変えず、通貨ごとの品目の回数として保存し、まとめた行はその合計として表示する。例（80632）: 前に江戸むすびの月より団子だけに 1 を保存していた人は、行が「1（江戸むすび 1）」で表示され、必要量も前と同じ。行の回数を変えた時点で、通貨ごとの品目に分け直す。

計算は通貨ごとの品目の回数から出すので、保存もその単位にすれば、まとめた行は表示と入力の単位にとどまり、前の保存値の必要量が開いた時点で変わらない（`event-shop-saved-inputs` の「保存した値から出す必要量は手で入れたときと同じ」を保つ）。まとめた行ごとのキーで保存する案は保存値の形が2種類になり、前の値を捨てる案は #222 で保存を入れた意味を消すので採らない。

#### ゲーム内の順をどこで持つか

取り込みで `priority` の順に並べて保存し、`priority` の値は保存しない。「元の順」を使う要件は `event-shop-roster-need`・`event-shop-servant-exchange`・`event-shop-efficiency` に散っていて、保存した順そのものをゲームの順にすれば、それらを書き換えずに揃う（AP 換算できない品目の並び、「不足素材のみ」の品目を見る順、埋まらない不足を出す最後の品目、一覧だけの交換所）。`priority` を品目に保存して画面で並べ替える案は、並べ替えの漏れが一覧と「不足素材のみ」の食い違いとして現れるので採らない。保存したデータから `priority` の値は読めなくなる。

#### まとめる品目の条件

種類・獲得物・個数が同じで、どれも在庫上限があり、2つ以上の異なる通貨にまたがる品目をまとめる。対価が違ってもまとめる。80632 の7品目（月より団子・サーヴァントコイン・伝承結晶・流星／日輪のフォウくん・巡霊の葉・コード・リムーバー）はすべてまとまる。80606 の QP（上限なし、対価 2・50・50・50）はまとめない。80611 の伝承結晶（対価 200・200・400・400・400）はまとめる。

上限なしの品目（QP など）は「その通貨の余りを使い切る」ために交換するので、通貨ごとに回数を入れられないと用をなさない。対価が違う組は手元の 101組のうち 1組だけで、ゲームの画面でも1品目に見えるので、別の行にするとゲームの画面と行が合わなくなる。

#### 区分（`slot`）が複数ある交換所の並び

区分ごとにまとめ、区分どうしはその区分の最小の `priority` の順、区分の中は `priority` の順に並べる。例（80603）: 区分 3（親愛のミトンなどの 54行）→ 区分 2（172行）→ 区分 1（290行）。`priority` だけで並べると、区分 1 と区分 2 のロックオンチョコの品目が 1行ずつ交互に並び、ゲームのどの画面とも合わない。区分の番号とタブの並びの対応は確かめられていないので、番号の順ではなく `priority` の小ささで区分を並べる。80603 のタブの並びをゲームの画面と見比べる確認は、実装 PR の「人がやること」に入れる。

#### そのほか

- AP 換算できない品目のまとめた行の位置は、まとめた品目のうち交換所の順で最初の品目の位置にする。手元の 14件の 95組は、どれも `priority` の並びで続けて並ぶ（Context）ので、ゲームの並びと合う
- まとめた行には、通貨ごとの回数（例:「武蔵うどん 2・江戸むすび 1」）を出す。利用者に通貨を選ばせない（issue の方針）代わりに、どの通貨の必要量に効いたかを見せる
- 品目ごとに出す育成計画の表示（必要／不要・計画の状態）は、まとめた行に1つ出す。まとめた品目は獲得物が同じなので、状態は1つに決まる。「交換所で埋まらない不足」は今の spec では交換所の元の順で最後の品目に出すので、その品目がまとめた行の中にあるときは、まとめた行に出す
- まとめる条件の境目（組に在庫上限なしの品目が混ざる、組の中で同じ通貨が重なる）は、組ごとまとめない。手元のデータではどちらも 0組で、一部だけまとめると、ゲームの画面で1品目に見えるものが2行に分かれた理由を利用者が読み取れないため
- 品目がすべてサーヴァント扱いの一覧も、通貨ごとのカードをやめた1つの一覧にし、同じ条件で行をまとめる。周回計算の一覧とまとめ方が食い違わないようにするため
- `event-planner` の「ロトの無い交換所イベントの周回計画」にある「通貨ごとのカードには上限まで選ぶ操作が無い」の文は、カードが無くなると読み方が古くなるが、この change では書き換えない。未 archive の change `issue-127-bug-events` が同じ capability の delta を持ち、ここで MODIFIED を書くと archive の順で要件が消えるため。`issue-127-bug-events` の archive の後に直す
- 取り込みの並べ替えは安定な並べ替えにする。交換所データのどれかに数の `priority` が無いとき（Atlas の形が変わったとき）は、並べ替えずに今の順で保存する。一部だけを並べると、無い品目の置き場所が決まらないため。`slot` が無い交換所データは、同じ1つの区分として扱う
- 新しい capability の名前は `event-shop-single-list` にする。並びは効率順が主で、ゲーム内の順は AP 換算できない品目にだけ効くので、`game-order` の名前は中身と合わない

## Risks / Trade-offs

- [`priority` の小さい順がゲームの順だというのは、Atlas の値と issue の観察による。ゲームの画面とは並べて確かめていない] → 実装 PR の「人がやること」に、80632 の交換所の AP 換算できない品目の並びをゲームの画面と見比べることを入れる
- [取り込みの定期ジョブは、開催中と終了後 30 日以内のイベントしか取り込み直さない] → それより前のイベントの AP 換算できない品目は、今の順（ID の順）で並ぶ。揃えるには `refresh-event-data` を `backfill_since` 付きで手動実行する（実装 PR の「人がやること」）
- [PR の preview は KV の今のデータを読むので、新しい順を preview で確かめられない] → 並べ替えは `compactShop` のテストで確かめ、画面は、80632 を取り込み直したデータを dev server に読ませて確かめる
- [同じ組（種類・獲得物・個数・通貨・対価）の品目が2つ以上あるとき、並べ替えでその出現順が変わると、保存した回数が入れ替わる] → 手元の 46件では同じ通貨で重なる組は 0組。起きても回数が別の品目に移るだけで、画面は落ちない
- [まとめた行の一部だけの交換で、どの通貨に回数が入るかを要件にしない] → 後ろの通貨のほうが周回で集めやすいイベントでは、最少より多く周回することがある。行に通貨ごとの回数を出すので、利用者はどの通貨に効いているかを見られる

## Migration Plan

1. マージ後、取り込みの定期ジョブ（毎日 02:17 UTC）で、開催中と終了後 30 日以内のイベントが新しい順で保存される
2. 必要なら `refresh-event-data` を `backfill_since` 付きで手動実行し、それより前のイベントも並べ替える
3. 戻すときは PR を revert する。KV に保存した並べ替え済みのデータは、前の画面でもそのまま読める（項目は増やしていない）
