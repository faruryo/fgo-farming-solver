## Context

- 今は `material/result` に「育成ぶん + その時点のクラススコアぶん」を混ぜて保存しており、書くのは `/material` の Calculate だけ（`components/material/index.tsx`・`material-calc-button.tsx` が `calculateTotalRequiredMaterials` の結果を保存）
- 読む側は `components/material/result.tsx`（全体は保存値、内訳の CS はライブ計算）、`hooks/use-quest-efficiency-options.ts`、`components/dashboard/NearGoalSection.tsx`・`RecommendedQuest.tsx`、`hooks/use-progress-report.ts`、サーバー側の `lib/progress/*`（スナップショットの `material/result` を比べる）
- クラスのステータスは `lib/class-score/route-actions.ts` の `deriveClassStatusFromBoard` が「全マスが目標か解放済」のときだけ `target` を返す。クラスカードは盤面によらず全マス合計を表示する
- 方針はオーナーの決定（2026-11-28、issue #266 のコメント）で、論点1は案A2（分けて持つ）、論点2は案C（目標にしたマスぶん）に決まっている

## Goals / Non-Goals

**Goals:**

- 必要数を読むすべての画面が、同じ1つの合算の手順で「育成ぶん + クラススコアぶん」を得る
- 育成ぶんがサーヴァントの状態の変更に追従する
- 部分目標のクラスが一覧の集計とカードに正しく出る

**Non-Goals:**

- 一覧画面の見た目の作り直し（#321）
- クラススコア以外の必要数（イベント交換など）の合算

## Decisions

### 決めたこと

- 育成ぶんの保存先は新しいキー `material/servant-result` とする。オーナーの決定のとおり、旧キーと同じ名前で育成ぶんを読むと、混ぜ込み済みの値にクラススコアぶんをもう一度足すため
- 合算の手順は純関数1つ（例: `resolveRequiredMaterials(servantResult, legacyResult, classScoreState)`）にまとめ、クライアントの読み手とサーバー側の進捗比較の両方から呼ぶ。クラススコアぶんは既存の `sumClassScoreMaterials` を使う。盤面データは静的に読み込めるのでサーバーでも同じ値が出る
- 旧 `material/result` は書かなくなる。クラウド同期の対象には、移行前のデータを読み替えるために残す。両方の画面から合算値を書き続ける案は、書き手が2つになりオーナーの決定（それぞれ自分のぶんだけ書く）と食い違うので採らない
- 育成ぶんの自動更新は `/material` の画面で、サーヴァント素材のデータを読み込んだあと、サーヴァントの状態が変わるたびに書き直し、`ls-sync` を出す。サーヴァントの状態を変えられるのは `/material` の画面（スクショ取り込みを含む）だけなので、ほかの画面には書き手を置かない。素材データを読む前に書くと空の必要数で上書きするので、読み込み前は書かない
- `deriveClassStatusFromBoard` は「全マス解放済 → `completed`、未解放の目標マスが1つ以上 → `target`、それ以外 → `none`」に変える。全マスが目標か解放済のときの結果は変わらない

### 判断点

#### 1. 育成ぶんがまだ無い端末・スナップショットの必要数

推奨: 案A（旧値を合算済みの必要数として読み、クラススコアぶんを足さない）

| 案 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|
| A 旧値をそのまま合算済みとして読む（推奨） | 二重計上も、育成ぶんの欠落も起きない。移行後の最初の状態変更か Calculate で正しい値に切り替わる | 移行前にクラススコアを変えていた場合、その差分は切り替わるまで反映されない（今と同じ） |
| B 旧値からいまのクラススコアぶんを引いて育成ぶんとみなす | 移行直後からクラススコアの変更が反映される | 旧値を保存したときと今でクラススコアが違うと、育成ぶんが増減して誤る。0 未満を切り捨てると値が消える |
| C 育成ぶんを空とみなす | 実装が最も単純 | 移行直後の端末で育成の必要数がすべて消え、周回・ダッシュボードが「目標なし」になる |

#### 2. ルート一括で「解放済」を「目標」に戻す操作の形

推奨: 案A（詳細ダイアログに経路を目標に戻す操作を別に足す）

| 案 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|
| A 別の操作を足す（推奨） | ふだんの「ルート目標」で、奥のマスを目標にしたときに経路上の解放済が目標に戻ってしまう誤操作を避ける | ダイアログの選択肢が1つ増える |
| B 「ルート目標」の既定を、経路上の解放済も目標にする動きに変える | 操作の数が増えない | 解放済の記録が気づかないうちに消え、必要数が増える |
| C 単体操作だけで戻せるようにする | 一括で戻す誤操作が起きない | 経路が長いと1マスずつ戻す手間が残り、オーナーの「ルート一括で戻せる」に届かない |

#### 3. 未設定のカードの見せ方（team-lead の提案。オーナー未回答）

推奨: 案A（見出しを「全マス解放に必要」にして、目標のカードの「目標ぶん」と分ける）

| 案 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|
| A 見出しを変えて全マス解放ぶんを出す（推奨） | 未設定の数を目標ぶんと取り違えて、カードの合計がサマリーと合わないと誤解するのを避ける。目標にする前に総量が分かる | 見出しの文言が2種類になる |
| B 未設定のカードは数を出さない | 取り違えが起きない | 目標にする前に、そのクラスにどれだけ要るかが分からなくなる |
| C 今の見出しのまま数を薄く出す | 変更が小さい | 見出しが同じなので、意味の違いが色の濃さでしか伝わらない |

#### 4. 一部だけ目標のクラスの、未設定 / 目標 / 解放済 の切り替えの表示（team-lead の提案。オーナー未回答）

推奨: 案A（「目標」が選ばれた表示にする）

| 案 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|
| A 「目標」が選ばれた表示（推奨） | 集計で目標に数えているのに「未設定」と表示される食い違いを避ける。ステータスの導出と表示が一致する | 「目標」を押し直すと全マス目標になる（今の挙動）ことが、表示からは分からない |
| B どれも選ばれていない表示にして、バッジで「n マス目標」を出す | 全マス目標と一部目標を見分けられる | 3つのどれでもない状態ができ、押したときの結果が読みにくい |
| C 「未設定」のまま | 変更がない | 今の不具合（目標なのに未設定に見える）が残る |

## Risks / Trade-offs

- [新しいキーが同期対象に増える] → 縮小保存の抑止の対象に入るので、空の育成ぶんでクラウドを上書きしないよう、素材データ読み込み前は書かない（上の「決めたこと」）
- [サーバー側の進捗比較がクラススコアの盤面データに依存する] → 盤面データは静的に同梱されている。読み込めないクラスはクラススコアぶんを 0 とし、今のスナップショット比較より悪くはならない
- [自動更新の書き込み回数が増える] → 状態変更ごとに1回。既存の `material` キーの保存と同じ頻度で、同期は既存のデバウンスに乗る
