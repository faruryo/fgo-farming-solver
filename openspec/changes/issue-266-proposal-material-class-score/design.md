## Context

- 今は `material/result` に「育成ぶん + その時点のクラススコアぶん」を混ぜて保存しており、書くのは `/material` の Calculate だけ（`components/material/index.tsx`・`material-calc-button.tsx` が `calculateTotalRequiredMaterials` の結果を保存）
- 読む側は `components/material/result.tsx`（全体は保存値、内訳の CS はライブ計算）、`hooks/use-quest-efficiency-options.ts`、`components/dashboard/NearGoalSection.tsx`・`RecommendedQuest.tsx`、`hooks/use-progress-report.ts`（現在の必要数を目標として使う。サーバー `lib/progress/summary.ts` は過去の所持数を返すだけで、必要数は比べない）
- クラスのステータスは `lib/class-score/route-actions.ts` の `deriveClassStatusFromBoard` が「全マスが目標か解放済」のときだけ `target` を返す。クラスカードは盤面によらず全マス合計を表示する
- 方針はオーナーの決定（2026-11-28、issue #266 のコメント）で、論点1は案A2（分けて持つ）、論点2は案C（目標にしたマスぶん）に決まっている
- 育成ぶんがまだ無い端末の扱いは、オーナーの方針の追加（2026-11-28、PR #322 のコメント）で「旧値のまま読む」でなく移行すると決まった
- 方針の追加 2（2026-11-28、PR #322 のコメント）で、育成ぶんのクラウド同期、クエリ値と移行値の優先順位、判断点4 の推奨（案E）が決まった
- `hooks/use-roster-need.ts` は、有効なサーヴァントの素材データをクライアントで取得し、保存せずに必要数を求めている

## Goals / Non-Goals

**Goals:**

- 必要数を読むすべての画面が、同じ1つの合算の手順で「育成ぶん + クラススコアぶん」を得る
- 育成ぶんがサーヴァントの状態の変更に追従する
- 部分目標のクラスが一覧の集計とカードに正しく出る

**Non-Goals:**

- 一覧画面の見た目の作り直し（#321）
- クラススコア以外の必要数（イベント交換など）の合算

## Decisions

### 決めたこと

- 育成ぶんの保存先は新しいキー `material/servant-result` とする。オーナーの決定のとおり、旧キーと同じ名前で育成ぶんを読むと、混ぜ込み済みの値にクラススコアぶんをもう一度足すため
- 合算の手順は純関数1つ（例: `resolveRequiredMaterials(servantResult, legacyResult, classScoreState)`）にまとめ、クライアントの読み手から呼ぶ（サーバーは必要数を扱わないので呼ばない）。クラススコアぶんは既存の `sumClassScoreMaterials` を使う
- `material/servant-result` はクラウド同期の対象に入れない。育成ぶんは、同期されるサーヴァントの状態（`material`）から各端末で求め直せる導出値で、必要数のフックがどの読む画面でも求め直すので、クラウドに置く必要が無い。これで、導出値の書き込みが自動保存されない問題、同期のキーが増えること、復元の前に `{}` を作ると復元した値が無視される問題が、まとめて起きなくなる
- 旧 `material/result` は書かなくなる。クラウド同期の対象には、移行前のデータを読み替えるために残す。両方の画面から合算値を書き続ける案は、書き手が2つになりオーナーの決定（それぞれ自分のぶんだけ書く）と食い違うので採らない
- 育成ぶんの自動更新は、サーヴァントの状態を変えられる `/material` と `/material/[className]`（`components/material/index.tsx`・`material.tsx`。スクショ取り込みを含む）が共通で使う1つの hook に置く。サーヴァント素材のデータを読み込んだ直後に1回と、サーヴァントの状態が変わるたびに（ユーザーの操作でも、クラウド復元などの読み込みでも）書き直す。値が変わったときだけ書き、同じ画面の読み手のために `ls-sync` を出す。`material/servant-result` は同期の対象外なので、この書き込みで同期は dirty にならず、新しい端末で `/material` を開いただけで最初のクラウド復元が競合として止まることもない。Calculate も同じキーに書くので同じ扱いになる。素材データを読む前に書くと空の必要数で上書きするので、読み込み前は書かない
- 育成ぶんがまだ無い端末は移行する。旧 `material/result` は育成ぶんとクラススコアぶんが混ざっていて分けられないので、分けない（旧値からクラススコアぶんを引かない）。育成ぶんはサーヴァントの状態（`material`）から求め直せるので、`material/servant-result` が無い端末では、サーヴァントの状態から育成ぶんを求めて新しいキーに保存する。これを移行とする
- 移行は `/material` を開いたときだけでなく、必要数を読む画面（素材結果、周回、ダッシュボード、進捗レポート）を開いたときにも走らせる。素材データの取得は `hooks/use-roster-need.ts` と同じ仕方（有効なサーヴァントの素材データをクライアントで取得する）を使い、1つの必要数のフックにまとめる。このフックはキーが無いときだけでなく、サーヴァントの状態（`material`）が変わるたび（クラウド復元の `ls-sync` を含む）に育成ぶんを求め直し、値が変われば書く。つまり移行と自動更新を同じフックで行い、`/material` 系の画面もこのフックを使う。書くのは、書く直前の最新の `material` から求めた結果だけにする（取得中に状態が変われば、古い状態で求めた結果は捨てる）。`material` の保存値を読み込む前は、目標の有無を判定せず書かない（`useLocalStorage` はマウント直後に初期値の `{}` を返すため）。同じ画面で複数の部品がフックを使っても、素材データの取得は既存の `loadMaterialCatalog` の共有で1回にまとめる。有効なサーヴァントが無い、または目標が無ければ、育成ぶんは素材データを取得せずに `{}` で確定して保存する
- 旧値を読むのは、移行がまだ終わっていない間（素材データの取得中）と、取得に失敗したときだけにする。どちらの間も旧値は合算済みとして読み、クラススコアぶんを足さない。旧値も無ければクラススコアぶんだけを出す
- クラウド復元との順序: 育成ぶんはクラウドから戻らず、移行は旧値に頼らずサーヴァントの状態から求めるので、復元の前に新しいキーを作っても、復元でサーヴァントの状態が入ったあとに求め直せば正しい値になる。復元でサーヴァントの状態が変わると、どの画面でも必要数のフックが求め直して書き直す（`/material` を開いていなくてもよい）。サーヴァントの状態が変わらない復元では、手元の育成ぶんは同じ状態から求めた値なので食い違わない。素材データの取得に失敗し続ける端末だけは移行が終わらず旧値を読み続ける（下の Risks）。状態スナップショットから戻す経路があれば、戻したサーヴァントの状態の `ls-sync` で同じく求め直す（その経路の有無は実装時に確かめる）
- 状態スナップショット（進捗レポート）への影響は無い。サーバー（`lib/progress/summary.ts`）はスナップショットの必要数を読まず、`lib/progress/diff.ts` の型に `material/result` の欄があるだけで、どこからも読まれていない。進捗レポートの現在の必要数は端末の値から読むので、`hooks/use-progress-report.ts` を必要数のフックに変えれば合算の手順で求まる
- 必要数のフックは、保存された育成ぶんが今の `material` から求めた値かどうかを持つ。キーがあっても、そのあと `material` が変わって（クラウド復元を含む）求め直しが取得中か取得失敗のときは、保存値を今の状態の育成ぶんとみなさない。その間は、旧値があれば旧値を合算済みとして読み、無ければ保存値を使い、取得に失敗したら必要数が古い可能性を画面に出す。目標なしで `{}` を作ったあとに復元が来て取得に失敗した端末で、育成ぶんが黙って 0 になるのを防ぐため
- 素材データに無いサーヴァントは、Calculate（`sumMaterials`）と同じく飛ばして求める。`use-roster-need.ts` の「1体でも無ければ error」には揃えない。カタログに無い ID を持つ端末で移行が終わらず、Calculate とだけ値が食い違うのを防ぐため
- 育成ぶんが「ある」かどうかはキーがあるかで決める。値が `{}`（育成目標をすべて消した、または目標の無い端末を移行した）でも「ある」として扱い、旧値に戻らない
- `material/servant-result` を書くのは Calculate、育成ぶんの自動更新、移行の3つだけとする。読む側（素材結果、クエスト効率、ダッシュボード、進捗レポート）は `useLocalStorage` の初期値を保存せず（`lazyWrite`）、書くのは素材データからサーヴァントの状態の育成ぶんを求め終えた移行と、`material` の保存値を読み込んだあとの目標なしの `{}` の確定だけにする。取得前に初期値の `{}` を保存すると、まだ求めていない育成ぶんを空として確定してしまうため
- `/material/result` を URL のクエリ付きで開いたときは、サーヴァントの状態から求めた育成ぶんが空（目標なし）ならクエリの値を育成ぶんとして表示に使い、空でなければ求めた育成ぶんを使う。クエリの値は保存しない。素材データの取得中と取得失敗の間は、空かどうかが決まらないのでクエリの値を使う。今の「保存値が無いときだけクエリを使う」に最も近い形にするため。移行で新しいキーができても、求めた育成ぶんが空ならクエリが使われ続ける
- `calculateTotalRequiredMaterials` を呼ぶ `hooks/use-roster-need.ts` も、合算の関数に揃える
- `deriveClassStatusFromBoard` は「全マス解放済 → `completed`、未解放の目標マスが1つ以上 → `target`、それ以外 → `none`」に変える。全マスが目標か解放済のときの結果は変わらない
- クラスのステータスは、盤面（boards）があるクラスでは保存済みの値を使わず、読むたびに盤面から導出する（一覧の目標クラス数、カードの切り替え、サマリー）。書き込み時の導出だけを変えると、変更前に部分目標を作って `none` が保存された利用者やクラウドから同期した状態が、盤面を触るまで直らないため。読み込み時に一度だけ書き直す移行は、同期で古い値が戻ると再発するので採らない

### 判断点

#### 2. ルート一括で「解放済」を「目標」に戻す操作の形

推奨: 案A（詳細ダイアログに経路を目標に戻す操作を別に足す）

| 案 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|
| A 別の操作を足す（推奨） | ふだんの「ルート目標」で、奥のマスを目標にしたときに経路上の解放済が目標に戻ってしまう誤操作を避ける | ダイアログの選択肢が1つ増える |
| B 「ルート目標」の既定を、経路上の解放済も目標にする動きに変える | 操作の数が増えない | 解放済の記録が気づかないうちに消え、必要数が増える |
| C 単体操作だけで戻せるようにする | 一括で戻す誤操作が起きない | 経路が長いと1マスずつ戻す手間が残り、オーナーの「ルート一括で戻せる」に届かない |

#### 3. 未設定のカードの見せ方（team-lead の提案。オーナー未回答）

推奨: 案A（見出しを「全マス解放に必要」にして、目標のカードの「目標ぶん」と分ける）

| 案 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|
| A 見出しを変えて全マス解放ぶんを出す（推奨） | 未設定の数を目標ぶんと取り違えて、カードの合計がサマリーと合わないと誤解するのを避ける。目標にする前に総量が分かる | 見出しの文言が2種類になる |
| B 未設定のカードは数を出さない | 取り違えが起きない | 目標にする前に、そのクラスにどれだけ要るかが分からなくなる |
| C 今の見出しのまま数を薄く出す | 変更が小さい | 見出しが同じなので、意味の違いが色の濃さでしか伝わらない |

#### 4. 一部だけ目標のクラスの、未設定 / 目標 / 解放済 の切り替えの表示（オーナーの指摘から案E を推奨。最終の ok は未取得）

推奨: 案E（カードに状態を大きく出し、クラス全体への操作は状態の表示を押したときだけ出す）

未設定 / 目標 / 解放済 の3つは、もともと「クラス全体を目標にするか」を選ぶ操作で、状態を見せるものではなく、何度も押すものでもない（オーナーの指摘）。案E は、いまどうなっているかを大きく見せ、操作は表示を押したときだけ出す。ボタンの大きさ・並び・アイコン・文言、状態の帯などの見た目の作り込みは #321 の範囲とし、この仕様では決めない。「盤面マップで個別指定」を操作の中に入れるかもこの仕様では決めず、今のとおり常に出す。

| 案 | 避けられる失敗 | 取りこぼすもの |
|---|---|---|
| E 状態を大きく出し、操作は押したときだけ出す（推奨） | 部分目標を「未設定」と見せる食い違いも、「目標」を押し直すと全マス目標になることが表示から分からない問題も、3つの切り替えを常に出さないので起きない。状態（未設定 / n マス目標 / 全マス目標 / 解放済 と、解放済・目標・残りのマス数）が一目で分かる | クラス全体への操作（全マスを目標に、全マスを解放済に、すべて外す）が1回押した先になる |
| A 「目標」が選ばれた表示 | 集計で目標に数えているのに「未設定」と表示される食い違いを避ける。ステータスの導出と表示が一致する | 「目標」を押し直すと全マス目標になる（今の挙動）ことが、表示からは分からない |
| B どれも選ばれていない表示にして、バッジで「n マス目標」を出す | 全マス目標と一部目標を見分けられる | 3つのどれでもない状態ができ、押したときの結果が読みにくい |
| C 「未設定」のまま | 変更がない | 今の不具合（目標なのに未設定に見える）が残る |

## Risks / Trade-offs

- [育成ぶんは端末ごとに求め直す] → 別の端末に移ると、素材データを取得し終えるまでは育成ぶんが無く、旧値があれば旧値、無ければクラススコアぶんだけを表示する。取得後はその端末のサーヴァントの状態から求めた値になる
- [素材データの取得に失敗し続ける端末は移行が終わらない] → その間は旧値を合算済みとして読み（二重計上はしない）、旧値が無ければ保存値を使って古い可能性を画面に出す。移行前にクラススコアを変えていた差分は、取得に成功して移行するまで反映されない
- [判断点3・4はオーナーの最終の ok が未取得] → 推奨（判断点3は案A、判断点4は案E）を仕様と tasks に既定として入れている。違う案になったら spec の該当場面とタスク 4.2・4.3 を差し替える
- [自動更新の書き込み回数が増える] → 状態変更ごとに1回。既存の `material` キーの保存と同じ頻度で、同期は既存のデバウンスに乗る
