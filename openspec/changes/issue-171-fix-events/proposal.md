# Proposal

## Why

交換所の「ここまで交換すれば効率が良い」区切りの基準（通貨1個を周回で集める AP）は、周回クエストの「1周の AP ÷ その通貨の1周のドロップ数」の最小で出している。1周で複数の通貨が同時に落ちても、1周の AP をまるごと1つの通貨の値段として数えるので、通貨1個の値段が高く見積もられ、区切りが実際より控えめ（上に来る品目が少なめ）になる（#171）。オーナーは 2026-10-26 に、正しい値に直すと判断した。

## What Changes

- 区切りの基準を、「全部交換」したときの必要量を前提に、その通貨の必要量を1個増やしたときに周回の合計 AP（ソルバーの連続の最適値）がいくつ増えるか（通貨ごとの限界の値段）に変える。同時に落ちる他の通貨の分は自然に割り引かれる
- 前提の必要量は、品目ごとの交換回数の入力に関係なく「全部交換」の必要量に固定する。品目の交換回数を変えるたびに区切りが動かないようにするため
- 他の通貨を集める周回のついでに足りる通貨は、基準が 0 になる。そのときはすべての品目を区切りの上に置き、基準の近くに「他の通貨を集める周回のついでに足りる」と示す
- 基準の表示（通貨1個あたりの AP）はそのまま残し、「全部交換を前提に、同時に落ちる他の通貨の分を差し引いた値」と注記する

## Capabilities

### New Capabilities

なし

### Modified Capabilities

- `event-shop-efficiency`: 「効率が良い区切り」の要件の基準の求め方を、通貨ごとの限界の値段に変える

## Impact

- `lib/event-shop-summary.ts` の区切りの基準の計算（`currencyApThresholds`）と、その入力（全部交換の必要量）
- `lib/event-shop-summary.ts` から `javascript-lp-solver` を直接呼び、連続の最適値を使う（今の `solve` は周回数を切り上げた合計 AP だけを返すため。`lib/solver.ts` と `lib/event-plan.ts` は変えない）
- `components/events/EventShopList.tsx` の基準の表示と注記、`locales/`
- #168（#134 の実装）と同じ `lib/event-shop-summary.ts` に触れるので、実装は #168 のマージ後に main から始める
