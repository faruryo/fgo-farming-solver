# Design

## Context

区切りの基準は `lib/event-shop-summary.ts` の `currencyApThresholds(farmingNodes)` が出し、`components/events/EventShopList.tsx` が `useMemo` でイベントの `farmingNodes` だけから求めて、通貨のカードの `orderShopByEfficiency` に渡している。基準は交換回数にも所持数にも依存しない。

周回の内訳は `lib/event-plan.ts` の `planShopCurrencies` が出す。中では `lib/solver.ts` の `solve` が `javascript-lp-solver` で連続の LP（周回数の変数に整数の制約なし、合計 AP の最小化）を解き、その後でクエストごとの周回数を切り上げた合計 AP を返す。連続の最適値そのものは返さない。

### ソルバーが双対変数を返せるか（確認済み）

`javascript-lp-solver` 1.0.3（`package.json` は `^1.0.3`）の `Solve` の結果（`SolveResult`）は、`feasible`・`result`（目的関数の値）・`bounded`・`isIntegral` と、変数ごとの値だけを持つ。`SolveOptions` にも、制約ごとの双対変数（shadow price）を出す設定は無い。型定義の `dualSimplex()` は内部の warm start 用で、双対変数の値は外に出ない。issue の推奨 A の「既存ソルバーから双対変数を出す」は、そのままではできない。

### 実データでの測定

`mocks/events.json` のイベントのうち、周回クエストで複数の通貨が同時に落ちる4件で測った。前提は全部交換の必要量（所持数 0）。周回クエストの `ap` と `perRun` から LP を組み、`javascript-lp-solver` で解いた。比べたのは次の3つ。

- 今の基準（`currencyApThresholds`）
- 必要量を1個増やしたときの連続の最適値の増分
- 双対の LP を別に解いた値

| 80429 | 94083602 | 1.204 | 0 | 0 |
| 80429 | 94083601 | 1.200 | 0 | 0 |

| 80549 | 94145802 | 1.044 | 0.134 | 0.134 |

4件とも、双対の LP の最適値は元の LP の最適値と一致した（80429 は 5820.9、80455 は 4530.7、80506 は 6014.8、80549 は 6868.1）。周回で落ちない通貨（80429 の 94083604 など）は LP から外した。分かったことは次の2つ。

- 全部交換を前提にすると、多くの通貨の基準が 0 になる。他の通貨のついでに必要量より多く集まるため
- 0 にならない通貨でも、今の基準より下がるものがある（80455 の 94090902 は 1.201 から 1.130 に下がる）

## Goals / Non-Goals

**Goals:**
- 区切りの基準を、全部交換を前提にした通貨ごとの限界の値段に変える
- 基準が 0 の通貨の区切りの見せ方を決める

**Non-Goals:**
- 品目ごとの交換回数（今の選択）を前提にした基準。線を見て選び直すたびに線が動くため、採らない
- 効率（品目の側の値）の求め方。素材の AP 換算値の求め方は変えない
- イベントのボーナス（#130）。#130 は、ボーナス込みの `farmingNodes` を基準の計算に渡す形で載る（下の決定 2）
- ソルバーの差し替え

## Decisions

### 1. 限界の値段は「必要量を1個増やして解き直した増分」で出す

ソルバーは双対変数を返さないので、次の手順で基準を出す。

1. 全部交換の必要量で連続の LP を1回解く
2. 周回で集められる通貨ごとに、その通貨の必要量だけを +1 した LP を解き直す
3. 連続の最適値の増分を基準にする

通貨の数は多くても4程度なので、解くのは5回程度で済む。浮動小数の誤差で出る小さな値（絶対値 1e-9 未満）は 0 に丸め、負の値は 0 にする。

採らなかった案は次の3つ。

- 双対の LP を別に組んで解く: 測定では同じ値になった。ただ、退化した（双対の最適解が1つに決まらない）ときにどの値が返るかがソルバーの内部で決まり、spec の定義「1個増やしたときの増分」と一致する保証が無い
- 周回数を切り上げた合計 AP（`solve` の `total_ap`）の差を使う: 切り上げで値が段になり、1個の増分が 0 か 1周分の AP のどちらかになる
- B（1周の AP をドロップ数の比で通貨に割り振る）: issue のとおり恣意的なので採らない

### 2. 基準の計算は `lib/event-shop-summary.ts` に閉じ、`farmingNodes` と必要量を受け取る

`currencyApThresholds` を、`farmingNodes` と、通貨ごとの前提の必要量（atlasId → 個数）を受け取る純粋関数に変える。中で `javascript-lp-solver` を直接呼び、連続の最適値（`Solve` の `result`）を使う。LP の組み方は、今の `currencyApThresholds` と同じく、周回クエストの `ap` と `perRun` から組む。`ap` も `perRun` も正のものだけを使い、キャンペーンの AP は含めない。効率の要件（キャンペーンとボーナスを含めない）と同じ前提にそろえるため。周回で集められない通貨と、LP が解けない（`feasible` が偽）ときは、その通貨の基準を出さない。カードには区切りを出さない。

`lib/solver.ts` の `solve` と `lib/event-plan.ts` は変えない。`solve` は周回の内訳の表示用の結果を返す共通の関数で、連続の最適値を返すように変えると、ほかの呼び出し側（周回ソルバー全般）の型に波及するため。#130 の design は「`currencyApThresholds` の呼び出し側でボーナス込みの `farmingNodes` を渡し、中は変えない」としており、引数に `farmingNodes` を残せばその形のまま載る。

### 3. 前提の必要量は全部交換の必要量にする

通貨ごとの前提の必要量は、交換所の品目のうち在庫上限のある品目をすべて上限まで交換したときの対価の合計から、その通貨の所持数を引いた量（0 未満は 0）にする。在庫上限の無い品目は数えない。上限が無いので全部交換の量が決まらないためで、利用者が入れた回数も使わない。今の `groupShopByCurrency` の `totalCost` と、`EventShopList` が持つ所持数から求められる。所持数を変えると前提が変わり、基準が動くことがある。所持数は「選び直し」ではなく持っている事実なので、動いてよいとする。

### 4. 基準が 0 の通貨は、すべての品目を区切りの上に置いて理由を添える

全部交換を前提にすると、他の通貨を集める周回のついでに必要量より多く集まる通貨は、追加の1個に AP がかからない。基準 0 で比べると、AP 換算値のある品目はすべて基準以上になる。区切りは効率順の最後の品目の下に出る（既存の「全品目が基準以上」と同じ位置）。区切りの文言の近くに「他の通貨を集める周回のついでに足りる」ことを添える。

採らなかった案は次の2つ。

- 今の基準（`ap ÷ perRun` の最小）に戻す: 0 の通貨では、追加の1個は実際に AP がかからない。今の基準に戻すと、直したい誤り（高く見積もる）がいちばん大きく出る
- 区切りを出さない: 「全部交換が得」という情報が消える

### 5. 画面

- 基準の表示（通貨1個あたりの AP）は残す。区切りの文言に「同時に落ちる他の通貨の分を差し引いた値」の短い注記を添える
- 基準が 0 のときは、決定 4 の文言を添える
- 文言は `locales/ja.json` と `locales/en.json` に足す。375px で横スクロールを出さない

## Risks / Trade-offs

- [全部交換を前提にすると、利用者が一部の品目しか交換しないときには基準が低すぎる（区切りが甘い）] → 全部交換の前提であることを注記で示す。前提を今の選択にすると線が動くので、issue の判断どおり固定する
- [多くの通貨の基準が 0 になり、区切りが最後の品目の下に出て、並びの情報が減る] → 順位と効率の並びは残る。0 の理由を添える
- [#168 と同じ `lib/event-shop-summary.ts` と `EventShopList.tsx` に触れる] → 実装（ops-graph）は #168 のマージ後に main から始める
- [LP を通貨の数 +1 回解くので、表示のたびに計算が増える] → 前提の必要量（所持数）と `farmingNodes` が変わったときだけ `useMemo` で解き直す。交換回数の入力では解き直さない
