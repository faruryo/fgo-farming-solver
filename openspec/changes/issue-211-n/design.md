# Design

## Context

動機は proposal.md の Why を参照。オーナーの判断は #211 の 2026-11-10 のコメント（判断点A=A1、判断点B=B1）と、それを起こした材料のコメント（`<!-- ops-issue:materials -->`）にある。

今の交換所（`components/events/EventShopList.tsx`、2026-11-10 にコードを読んで確かめた）は次のとおり。

- 画面の縦の並びは、周回の合計（`PlanSummary`）→ 所持数の段（`OwnedInputs`。通貨ごとの所持数の入力を横1列）→ 全部交換・優先素材（`SelectControls`）→ 品目の一覧（`ShopTable`）→ 通貨ごとのカード（`CurrencyNeeds`。通貨の名前とアイコンの見出し、「選んだ交換 N・必要量 N」の行、「全交換 N ＋上限なし N 品目」の行）→ ボーナス以降。保存値を読み終えるまでは、全体を読み込み中の表示（`ShopLoadingSkeleton`）にしている
- 一覧は「欲しい」の行を `orderShopByEfficiency`（`lib/event-shop-summary.ts`）で、効率のある行（`ranked`、効率の高い順に 1 からの順位）と効率の無い行（`unpriced`、交換所の順）に分け、両方あるときだけ「効率順」「AP 換算なし」の見出しの行（`GroupLabelRow`）を入れる
- 行の育成計画の表示は `planOf(row)` が返す `RowPlan`（`status` と `remainder` と `promptUnlimited`）。育成計画が使えないとき（未設定・読み込み中・失敗）は `undefined`。まとめた行（複数の通貨で交換できる品目）は、まとめた品目の最初の品目の `status` を使う。`status.kind` は `short`（不足あり）・`enough`・`unused`・`outside` のどれかで、QP と見分けられない品目は `status` が無い
- `RowPlanLabel` が `short` に「あと N 個」と、`remainder` があれば赤の「交換所では N 個足りない」を出す。`remainder` は `allocateShortfallOnly` の `remainders`（在庫上限まで交換しても残る不足を、素材の「欲しい」の品目のうち交換所の元の順で最後の品目に付けたもの）
- `ShopRow` は `status.kind` が `enough` か `unused` の行をいつも薄い文字色（`var(--text3)`）にする。交換回数は同じ部品の中の `rowCountOf(row, counts).count`
- フォーカスの移し先（`useFocusAfterWantedMove`、#246）は、押した時点の並び `[...ranked, ...unpriced]` から次・前の行を決める
- 既存の検査は `components/events/EventHubClient.test.tsx`（「あと N 個」「交換所では N 個足りない」、見出しと順位、フォーカス）と `components/events/EventShopList.test.tsx`（所持数の段 `shop-owned-inputs` と通貨ごとのカード `shop-currency-needs`、「交換所では 50 個足りない」）にある

## Goals / Non-Goals

**Goals:**

- 一覧の並び・行のラベル・行の文字色・所持数の入力の場所を、proposal の What Changes のとおりに変え、各 spec のシナリオを検査で確かめる

**Non-Goals:**

- 判定（足りている・使わない・計画の対象外）、不足の求め方、優先素材の回数の入れ方、一番上の要約の数え方を変えること
- 品目がすべてサーヴァント扱いの交換所の一覧（周回計算をしない一覧）。所持数も必要量も出さないので変わらない
- 箱のあるイベントの箱計画の画面

## Decisions

### 判断点

#### 判断点1: 上下のグループに、グループの見出しを出すか

B1 で、「欲しい」の行を「育成にあと N 個」の行（上）とそれ以外（下）に分け、「効率順」「AP 換算なし」の見出しの決まりを上下それぞれに当てると決まった。グループそのものを示す見出しは issue でもオーナーのコメントでも決まっていない。例として、80632 で上に効率のある行2つ（順位 1・4）と効率の無い行1つ、下に効率のある行と効率の無い行があるとき、上から見える並びは次のようになる。

推奨: **A. 両方のグループに行があるときだけ、上に「育成に足りない品目」、下に「そのほかの品目」の見出しを出し、その下に今の「効率順」「AP 換算なし」の見出しを1段下げて出す**。

| 案 | 見える並び（例） | 順位が 1・4 と飛ぶ理由 | 「効率順」が2回出る理由 | 375px での縦の長さ |
|---|---|---|---|---|
| **A. グループの見出しを出す（推奨）** | 育成に足りない品目 / 効率順 / 1 / 4 / AP 換算なし / … / そのほかの品目 / 効率順 / 2 / 3 / … | 見出しで2つに分けたと分かる | 上下で別のグループと分かる | 見出しの行が最大2行増える |
| B. 見出しは出さず、グループの境に太い区切り線だけ引く | 効率順 / 1 / 4 / AP 換算なし / … / ━━ / 効率順 / 2 / 3 / … | 線の意味を行のラベルから読み取る | 線の意味を行のラベルから読み取る | 増えない |
| C. 見出しも線も出さない | 効率順 / 1 / 4 / AP 換算なし / … / 効率順 / 2 / 3 / … | 説明が無い | 説明が無い | 増えない |

根拠: B1 で順位の番号を変えないと決めたので、上のグループの順位は 1・4・7 のように飛び、「効率順」「AP 換算なし」の見出しも上下で2回ずつ出る。A はなぜ分かれたかを見出しの言葉で示すので、飛んだ番号と2回目の「効率順」を不具合と読み違えない。B は縦の長さを増やさないが、分けた理由を「育成にあと N 個」のラベルから読み取ってもらうことになり、下のグループの先頭の行のラベル（「足りている」「計画の対象外」など）が揃っていないので読み取りにくい。C は issue の「上にまとめる」を並びだけで満たすが、2回目の「効率順」の見出しが説明なしに出る。A で取りこぼすのは、375px で見出しの行が最大2行増えることで、品目の行（2〜3行の高さ）より低い見出しの行なので、スクロールの量は1品目分に満たない。グループのどちらかが空のときは、今の「両方あるときだけ見出しを出す」と同じ考えで、グループの見出しも出さない。

### 決めたこと

- **上のグループに入る行**: `planOf(row)` の `status.kind` が `short` の行（まとめた行は今と同じく最初の品目の判定）。それ以外（`enough`・`unused`・`outside`、`status` の無い行）は下のグループ。育成計画が使えず `planOf` が `undefined` のときは、すべての行を今の並び（グループに分けない）で出す。並べ方は `orderShopByEfficiency` の結果（`ranked` と `unpriced`）を、上のグループに入るかで2つに分ける（`ranked` の順と順位の番号、`unpriced` の交換所の順はそのまま保つ）。`lib/event-shop-summary.ts` の `orderShopByEfficiency` と効率の計算は変えない
- **見出しの出し方**: 判断点1の A を採るとき、グループの見出しは今の `GroupLabelRow` と同じ行の形で出し、「効率順」「AP 換算なし」はグループの中の小見出しとして字下げか文字の大きさで1段下げる。グループのどちらかが空ならグループの見出しは出さず、残ったグループの中で今の決まり（効率のある行と無い行の両方があるときだけ「効率順」「AP 換算なし」）を当てる。見出しの行は `scope="colgroup"` の `th` のまま、表の列数をまたぐ
- **「交換所では N 個足りない」の削除**: `RowPlanLabel` で出すのをやめ、`RowPlan` から `remainder` を外す。`lib/event-shop-summary.ts` の `allocateShortfallOnly` が返す `remainders` は、関数とその検査に手を入れずに残す（一番上の要約と優先素材の回数の計算は同じ関数の別の値を使っていて、変えない範囲を広げないため）。`locales/ja.json`・`locales/en.json` の `event-shop-status-remainder` は使う場所が無くなるので消す
- **「育成にあと N 個」**: `event-shop-status-short` のキーはそのままにし、`ja.json` を「育成にあと {{n}} 個」、`en.json` を「{{n}} more for your plan」にする。コードの第2引数のフォールバックも同じ日本語にする
- **薄い文字色**: `ShopRow` の薄くする条件を、`status.kind` が `enough` か `unused` で、かつ行の交換回数（`rowCountOf(row, counts).count`）が 0 のときにする。回数を入れた途端に行の色が戻る
- **所持数の入力の場所（A1）**: `OwnedInputs` の段をなくし、所持数の入力を `CurrencyNeeds` の通貨ごとのカードの中に移す。カードの中は、見出し（通貨のアイコンと名前）→「所持数 [入力]・選んだ交換 N・必要量 N」の行 → 「全交換 N ＋上限なし N 品目」の行の順。入力欄は今の大きさと縮め方（16px のまま 3/4 に縮めて 12px に見せる。iOS Safari の拡大を避ける）と、`aria-label`（「{{name}} の所持数」）をそのまま使う。カードの `data-testid`（`shop-currency-needs`）は残し、`shop-owned-inputs` は消す。保存（`useShopSavedInputs` の `owned` と `setOwned`）と必要量の計算（`computeShopCurrencyNeeds`）には手を入れない。読み込み中は今と同じく全体が `ShopLoadingSkeleton` になるので、カードの中の入力欄に別の読み込み中の扱いは要らない
- **フォーカスの移し先**: `useFocusAfterWantedMove` の並びを、表に出ている順（上のグループの `ranked`・`unpriced`、下のグループの `ranked`・`unpriced`、見出しの行は数えない）にする。並びは表と同じ関数から作り、表とフォーカスで並びの決め方が食い違わないようにする
- **テスト**: `components/events/EventHubClient.test.tsx` と `components/events/EventShopList.test.tsx` の「あと N 個」「交換所では N 個足りない」「所持数の段」を前提にした検査を新しい仕様に合わせて直し、各 spec の追加・変更したシナリオごとの検査を足す。並びは、品目名の出る順（表の行の順）と見出しの行の位置で確かめる

## Risks / Trade-offs

- [上のグループの順位が 1・4・7 と飛び、不具合に見える] → 判断点1の A でグループの見出しを出して、分けた理由を示す。順位の番号を変えないのはオーナーの判断（B1）
- [優先素材の操作のあとも、在庫上限で埋まらない不足がどの品目に残るかが行からは見えなくなる] → 一番上の要約（「…のうち、交換所で埋まるのは M 素材」）で埋まらない素材があることは分かる。行の「育成にあと N 個」は不足そのものを示す。issue の項目1でオーナーが消すと決めている
- [所持数の入力が一覧の下に移り、一覧の上で所持数を入れてから回数を入れる今の手順が変わる] → 必要量は交換回数と所持数の両方から出るので、どちらを先に入れても結果は同じ。A1 はオーナーの判断
- [行の交換回数が 0 から 1 に変わると、その行の文字色が変わる] → 色が戻るのは回数を入れた行だけで、並び（上下のグループ）は回数では変わらない（グループは育成計画の判定だけで決まる）
