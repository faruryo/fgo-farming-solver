# Design: クラウド保存の縮小ガード

## 1. 指標の選定

判定は保存直前の `dataObj`(実際に送信するバイト列)と、`cloudData.storage` の間で行う。指標は3つ。

| 指標 | 算出 |
|---|---|
| `servants` | `material` の各エントリのうち `id !== 'all' && !disabled` の件数 |
| `possessions` | `posession` の値が数値かつ `> 0` のエントリ件数 |
| `missingKeys` | `KEYS ∩ cloud.storage` のうち、保存内容に存在しないキーの件数 |

### `getStats` を使わない理由

`components/cloud/parts/stats-logic.ts` の素材個数は `posession` を `items` カタログに join して算出している(`items.find(...)`)。`items` が未ロードだと両側とも 0 になり、ガードが差分なしと誤認して黙って素通りする。逆にローカル側とクラウド側の算出の間に `items` がロードされると偽陽性になる。カタログに依存しない生の件数で測る。

### 素材の「個数」を指標にしない理由

総個数は在庫の少ないプレイヤーほど誤警告を受ける逆進性がある。在庫 5,000 個の人が 300 個使っても 6% だが、在庫 400 個の人が同じ 300 個を使うと 75% 減で発火する。素材を貯め込まず使い切るプレイヤーが罰される形になるため採らない。所持数スクリーンショット取り込みが低い数値を OCR したときにも鳴りうる。

## 2. 発火条件

`servants` / `possessions` は、それぞれ独立に次を満たしたとき発火する(C = クラウド, N = 保存しようとする値)。

```
C - N >= 10  かつ  N <= C * 0.5
```

`missingKeys` は **2 件以上**で発火する。3 指標のいずれかが成立すれば発火。

### 閾値の根拠

| クラウド C | 発火する N |
|---|---|
| 461 | 230 以下 |
| 104 | 52 以下 |
| 20 | 10 以下 |
| 10 | 0 |
| 9 以下 | 発火しない |

事故ケース(461→0 / 104→0)は `servants` と `possessions` が独立に発火するため、片方の指標定義を誤っても捕まる。日常操作(461→458、104→95)は絶対件数10件の下限で除外される。素材を複数種類あわせて 300 個消費しても、種類数がゼロになるのは使い切った種類だけなので、104 種類の人が発火するには 1 回の保存で 52 種類以上を同時にゼロにする必要がある。

クラウド側が 9 件以下のユーザーは `servants` / `possessions` では保護されない。失うデータも小さいため許容する。

### `missingKeys` の判定対象を `KEYS ∩ cloud.storage` に限る理由

将来 `KEYS` からキーを削除したとき、旧データにそのキーが残っている全ユーザーで一度ダイアログが出てしまう。現行の `KEYS` に含まれるキーだけを対象にする。

### `missingKeys` を 2 件以上にする理由

キーを1件だけ消す正規の経路が実在する。`components/farming/index.tsx:71` の `migrateLocalInput` は旧 `input` キーを個別キーへ展開したうえで `localStorage.removeItem('input')` する。クラウドに `input` が残っているユーザーがこの移行を通ると、次の保存で欠落1件が立つ。`missingKeys` には件数の緩衝帯が無いため、1件で発火させるとこの移行が確実に誤発火する。

一方、事故側で単一キーが消えるケースのうち重大なもの(`material` / `posession`)は `servants` / `possessions` が独立に捕まえる。`missingKeys` が本来受け持つのは指標を持たないキー(`todoState`、`quests`、`farming/results` など)であり、それらが失われる事故 — サイトデータ削除や一括初期化 — は複数キーが同時に消える。2件で必要な検知力は残る。

なお、ローカルバックアップの取り込み(`components/cloud/parts/local-section.tsx`)は `setItem` のみでキーを削除しないため、この経路では欠落は発生しない。`useLocalStorage` もキー未作成時に既定値を書き込むので、値が空になることはあってもキー自体は残る。`removeItem` を `KEYS` のキーに対して呼ぶ箇所は現状 `migrateLocalInput` のみである。

## 3. 基準値が取れない場合

`cloudData` が `null` のときは保存を**中止**する(通さない)。

- クラウドが本当に空の場合、GET は `{}` を返し `fetchCloudData` は `{ storage: {}, metadata: epoch }` を組み立てるので `cloudData` は非 null になる。したがって `null` は「クラウドが空」ではなく「クラウドの状態が不明」を意味する。
- `handleSave` は `cloudData` が `null` のとき `fetchCloudData()` を1回待ってから再判定し、それでも `null` なら `saveStatus: 'failed'` で中止する。
- ここを「比較できないから通す」にすると、通信が不安定な端末という**事故が起きたのとほぼ同じ条件でだけガードが無効**になる。

`material` / `posession` の JSON パースに失敗した場合も測定不能として中止する。純関数は 0 ではなく `null` を返して両者を区別する。

### 未ログイン(開発時モック)は対象外

`fetchCloudData` は `session == null` のとき早期 return し、`MOCK_CLOUD_KEY` が存在するときしか `cloudData` を設定しない。したがって開発用プロファイルの初回は `cloudData` が `null` のままである。ここで中止すると、`handleSave` のモック保存分岐(`hooks/use-cloud-sync.ts:287`)に到達できず、最初のモックデータを作れない ＝ 縮小を起こす前提条件そのものが作れなくなる。ガードは `session != null` のときだけ適用する。

## 4. `force` と `allowShrink` を分ける

`handleSave(force = false)` の `force` は現状「コンフリクト中でも保存する」というバイパスで、`/cloud` の「強制上書き」ボタンが `true` を渡している。縮小ガードが同じフラグを読むと、**クラウドを潰す実行犯であるそのボタンだけがガードを素通りする**。別のオプションにする。

```ts
handleSave(force = false, options?: { allowShrink?: boolean })
```

`/cloud` の強制上書きは件数比較を画面に出しているが、それでもガードは効かせる。二重確認になるコストより、潰れるコストが大きい。

## 5. ダイアログと再発防止

`divergence-dialog.tsx` と同じ構成を採る。判定が「保存を止める」だけでは終わらないためである。事故時、スマホのローカルは空同然のままで、中止しても画面は直らず、次の編集で同じダイアログが出る。ユーザーが取るべき行動はクラウドの内容を引き下ろすことであり、その材料(`cloudData`)はダイアログを出す時点で手元に揃っている。

- **クラウドから復元**(既定) → `applyData(cloudData.storage, cloudData.metadata)`。ローカルが clean になりガードが自然に解ける
- **見比べる** → `/cloud` へ遷移
- **このまま保存する**(destructive) → `handleSave(false, { allowShrink: true })`

pending 状態はモジュールスコープに置く。フックは nav / `/cloud` など複数コンポーネントからマウントされており、インスタンスごとの state では他インスタンスのオートセーブを止められない(`isApplyingCloudData` / `lastCloudFetchAt` と同じ理由)。

pending が残っている間は変更リスナーがオートセーブの debounce を再武装しない。ダイアログを閉じても pending は残り、次の編集で再提示される。リロードで消える。

**pending の解除は明示的に行う。**「クラウドから復元」と「このまま保存する」の両方で `pendingShrink` を `null` に戻し、変更を全インスタンスへ通知する。復元によってローカルが clean になれば以後の判定は自然に通るが、pending 変数そのものは誰も触らないため、解除を書き忘れるとリロードするまでオートセーブが止まったままになる。POST の有無だけを見る単体テストでは検出できないので、pending の解除を明示的にテストする。

## 6. PR #18 との守備範囲

`checkConflict` は divergent でも `hasConflict = true` を立てるため、未同期端末のオートセーブは #18 の時点で既に止まっている。本ガードが実際に効くのは次の 2 つ。

1. **同期済み端末で `material` などのキーだけが初期化される** — メタデータは正常なので divergent にならない。7/10 の 1.2KB 保存はこの型の可能性が高い
2. 分岐モーダルで「あとで」を選んだ端末が `/cloud` から手動で強制上書きする

1 は「キー単位で壊れる」事故なので、`missingKeys` 指標が本命の受け皿になる。

## 7. 検知しないもの(意図的)

- **段階的な減少**。保存のたびに基準値も下がるため、10 回に分ければいくらでも減らせる。ユーザーの意図した操作と区別できない
- **46% の減少**(461→250 など)。半分の閾値を割らない
- **素材の個数**(各30個→各1個)。種類数しか見ない
- **コンソールからの直 POST**。クライアントガードの射程外

このガードは「一発でごっそり消える」型に限定した防御であり、汎用の削除防止ではない。

## 8. テスト

`lib/cloud-sync/shrink-guard.test.ts` に事故そのものを再現するフィクスチャを置く。

| ケース | 期待 |
|---|---|
| ローカル `material` 462件すべて `disabled: true` / `posession` `{}` vs クラウド 465件中461有効・所持104 | 発火 |
| 461 → 458 / 104 → 95 | 発火しない |
| 461 → 200 | 発火 |
| 新規アカウント(クラウド 0 → ローカル 300) | 発火しない |
| 両側とも空 | 発火しない |
| `todoState` と `quests` が保存内容から消える | 発火(`missingKeys`) |
| `input` だけが保存内容から消える(`migrateLocalInput` 相当) | 発火しない |
| `KEYS` に無いキーがクラウドにだけ存在する | 発火しない |
| `material` が不正 JSON | `null`(測定不能) |

フック側は次を確認する。

- 縮小時に POST を発行しないこと
- `allowShrink` で POST を発行すること
- `cloudData` が `null` のとき、再フェッチ後も `null` なら POST しないこと
- 未ログイン(モック)では判定が走らないこと
- 復元・強制保存のいずれでも `pendingShrink` が解除され、以後のオートセーブが再開すること
