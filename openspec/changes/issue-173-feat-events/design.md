# Design

## Context

#130（PR #187）で、ロトの無い交換所イベントの交換所の周回計算に、ドロップ増加礼装のボーナスの入力を足した。`components/events/EventShopList.tsx` は、ボーナス（通貨の品目 ID → +N）を `useState` で持ち、`lib/event-plan.ts` の `applyDropBonus` でドロップごとの1周の獲得量を `perRun + countPerRun × N` にしたイベントを `planShopCurrencies` に渡す。入力の部品 `DropBonusInputs`（見出し・説明の1行・欄・反映できない品目の表示）は `EventShopList.tsx` の中にある。#130 の design は、箱計画への反映をオーナーの判断に無いとして Non-Goals にし、`buildEventDrops` の形を変えない案を採った。

箱計画（`components/events/EventPlannerClient.tsx`）は、入力（箱数・所持通貨・開封済みの箱数・手入力のドロップ・欲しいアイテム）をすべて `useState` で持つ。ドロップの統計が無いときだけ、手で入れた1周の獲得数を最初の周回クエストのドロップに差し替えた `effectiveEvent` を作り、`reverseCalcBoxes`・`calcBoxLayer`・`allocateShop`・`runEventSolver` に渡す。周回数と合計 AP は `runEventSolver` の結果から出て、AP 予算（#167、PR #196）は合計 AP から出る。ドロップの統計を使うのは `runEventSolver`（`buildEventDrops`）だけで、箱数の逆算・箱の確定報酬・交換所の配分はドロップ率を使わない。

`/events/[id]` は、箱のあるイベントでは箱計画を、ロトの無い交換所イベントでは交換所の周回計算を出し、同じページに両方は出ない（`EventHubClient` の `isShopOnlyEvent`）。モックの 80506 は、箱を開ける通貨1種と交換所の対価の通貨4種を持ち、ドロップは1周あたりのドロップ回数を持たない。

## Goals / Non-Goals

**Goals:**
- 箱計画で通貨ごとのボーナスを入れ、箱を開けるのに要る周回数と AP をボーナス込みにする
- 入力を交換所と同じ持ち方（同じ形の値・画面を開いている間だけ・同じ部品）にする
- ボーナスがすべて0のときは、今の箱計画と完全に同じ結果にする

**Non-Goals:**
- ボーナスの値の保存（下の決定 1）
- 箱計画でのクエストごとのボーナス込みの1周の獲得量の表（交換所にはある）。issue は周回数と AP への反映を求めていて、表は求めていない
- イベントポイントの欄。箱計画はポイントの品目を受け取っておらず、ポイントは箱計画の計算に効かない
- `buildEventDrops`・`runEventSolver`・`applyDropBonus` の中の変更
- Atlas の礼装からの自動取り込みと、礼装の所持の入力（#130 と同じくオーナーの判断で後回し）

## Decisions

### 1. 「交換所と同じ保存先を共有する」は、交換所と同じ持ち方にすることとして読む

issue の「入力は交換所と同じ保存先を共有する」は、交換所の今の持ち方（`useState` で画面を開いている間だけ持ち、保存しない。`event-drop-bonus` の「ボーナスの入力」の要件）に合わせることとして読む。値の形（通貨の品目 ID → +N）と入力の部品も交換所と同じにする。箱のあるイベントのページには交換所の周回計算が出ないので、同じページの中で2つの入力が値を受け渡すことはない。

採らなかった案: 端末（localStorage）に保存し、交換所と箱計画が同じキーを読み書きする。交換所の既存の要件「保存してはならない」を書き換えることになり、#130 の design はボーナスの保存を「要望が出たら別の issue で扱う」としている。issue の本文は保存を明示していないので、この change では採らない。オーナーが保存を望むなら、交換所の要件の変更と合わせて別の issue で扱う（仕様 PR で判断を仰ぐ）。

### 2. ボーナスはソルバーに渡す前のイベントに足す

`EventPlannerClient` で、`effectiveEvent` を `applyDropBonus` に通したイベントを周回の計算に渡す。`runEventSolver` だけがドロップ率を使うので、`reverseCalcBoxes`・`calcBoxLayer`・`allocateShop` に渡しても結果は変わらないが、1つのイベントを使い回して、入力モードによらず同じ値で解く。ボーナスが空か全部0なら `applyDropBonus` は入ったイベントをそのまま返すので、今の結果と同じになる（`useMemo` の依存が変わるだけ）。

手入力のドロップ（ドロップの統計が無いとき）は、利用者が自分の1周の獲得数を入れる欄で、1周あたりのドロップ回数を持たない。この場合はボーナスの欄を出さず、`applyDropBonus` にも通さない（手入力の値に礼装の分を含めて入れてもらう）。

採らなかった案: 手入力のときもボーナスの欄を出し、反映できない旨を出す。足せないと分かっている欄を出すことになる。

### 3. 対象の通貨

箱を開ける通貨（`event.currency`）と、交換所の対価の通貨（`groupShopByCurrency(event.shop)` の各グループ）を、箱の通貨を先頭にして重複を除いて並べる。名前とアイコンは交換所と同じく、ドロップか交換所の品目の表記から取り、無ければ ID の表記にする（`useBonusTargets` と同じ規則）。

### 4. 入力の部品を共用する

`DropBonusInputs` と `BonusTarget`、対象の通貨を組み立てる処理を `EventShopList.tsx` から共用できるファイル（例: `components/events/DropBonusInputs.tsx`）へ出し、交換所と箱計画の両方から使う。交換所の表示と振る舞いは変えない（既存のテストをそのまま通す）。値を 0 以上の整数に直す処理も同じものを使う。

### 5. 画面

- ボーナスの欄: 箱計画の入力の列の、AP 予算の入力（`ApBudgetInputs`）の上に置く。ドロップの統計が無いときは出さない
- 注記: ボーナスを1つでも入れたら、計算結果のカード（`EventPlanResultCard`）の中か直下に、交換所と同じ文言「入れたドロップ増加礼装のボーナス（1ドロップにつき +N）を足して計算しています。」を出す。交換所の既存の文言キー（`event-shop-plan-bonus-applied`）を使い回すか、同じ文言の新しいキーを足す（キー名は実装で決める。足すなら ja と en の両方）
- 反映できない通貨: 交換所と同じく、ボーナスの欄の下にその通貨名を挙げて出す
- 375px では交換所と同じく2列で折り返す

## Risks / Trade-offs

- [本番の KV でドロップ回数を持たない箱のイベントが残る] → #130 と同じ。取り込み直すまで、反映できないことを表示して素の値で計算する。KV は手で書き換えない
- [オーナーが「保存先を共有」を保存の意味で書いていた] → 決定 1 のとおり仕様 PR で判断を仰ぐ。保存にするなら、交換所の要件も合わせて変える別の issue にするか、この仕様 PR を直す
- [部品を別ファイルへ出すことで交換所の表示が変わる] → 交換所の既存のテスト（`EventHubClient.test.tsx`）をそのまま通すことで確かめる
